Node.js — המדריך המלא למפתח Backend

הפער שדילגנו עליו: כיסינו את TypeScript (השפה) ואת NestJS (ה-framework), אבל לא את ה-runtime עצמו. המדריך הזה מסביר איך Node עובד מתחת למכסה — ה-event loop, async internals, streams, modules — כדי שתבין למה הקוד שלך מתנהג כמו שהוא מתנהג, לא רק שהוא עובד.

הכתר של המדריך הוא ה-event loop (פרק 2). אם תבין אותו לעומק — הפכת ממישהו שמשתמש ב-Node למישהו שמבין אותו. עברית להסבר, אנגלית לקוד.

1. מבוא: מה זה Node.js — V8 ו-libuv

Node.js הוא runtime שמריץ JavaScript מחוץ לדפדפן — בשרת. לפני Node, JS רץ רק בדפדפן; Node לקח את מנוע ה-JS של Chrome (V8) ואיפשר לו לגשת לקבצים, לרשת, ולמערכת ההפעלה. זה מה שהפך את JavaScript לשפת Backend.

משני רכיבים

  • V8 — מנוע ה-JavaScript של Google (מ-Chrome). מקמפל ומריץ את קוד ה-JS. מהיר מאוד.
  • libuv — ספריית C שנותנת ל-Node את היכולות שאין ל-JS לבד: גישה לקבצים, רשת, וה-event loop (פרק 2). זה החלק שהופך את Node ל-non-blocking.

הרעיון המרכזי: Single-threaded, Non-blocking I/O

זו הנקודה שהכי חשוב להבין, ומה שמבדיל את Node מ-frameworks אחרים. Node רץ את הקוד שלך על thread אחד. נשמע מגביל — אבל זה בדיוק החוזק שלו:

במקום ליצור thread לכל בקשה (המודל הקלאסי, יקר בזיכרון), Node משתמש ב-thread אחד עם event loop: כשמגיעה פעולה איטית (קריאת DB, קריאת קובץ, בקשת רשת), Node לא מחכה — הוא שולח אותה הצידה (ל-libuv) וממשיך לטפל בבקשות אחרות. כשהפעולה מסתיימת, callback שלה נכנס לתור וממתין לתורו. כך thread אחד מטפל באלפי בקשות בו-זמנית — כל עוד רובן הן I/O (המתנה), לא CPU.

למה זה מתאים ל-Backend

רוב עבודת ה-Backend היא I/O-bound — מחכים ל-DB, ל-APIs, לקבצים — לא CPU-bound. במשימות כאלה, המודל של Node מבריק: בזמן שבקשה אחת מחכה ל-DB, ה-thread מטפל בעשר אחרות. זו הסיבה ש-Node מעולה ל-APIs, microservices, ו-real-time. אבל — משימה CPU כבדה (חישוב ארוך) חוסמת את ה-thread היחיד ומקפיאה את הכל (נחזור לזה בפרק 13).

2. ה-Event Loop — הכתר

זה הנושא היחיד שאם תבין אותו לעומק, תבין את Node. ה-event loop הוא המנגנון שמאפשר ל-thread אחד לטפל בהמון פעולות אסינכרוניות. נעשה את זה לאט וברור.

הרעיון הבסיסי

ה-event loop הוא לולאה אינסופית שכל הזמן שואלת: "יש callback מוכן להרצה? אם כן — הרץ אותו". כשאתה קורא ל-fs.readFile עם callback, Node שולח את הקריאה ל-libuv וממשיך. כשהקובץ מוכן, ה-callback נכנס לתור, וה-event loop יריץ אותו כשה-thread פנוי.

הפאזות של ה-Event Loop

ה-event loop לא תור אחד — הוא עובר במחזור בין כמה פאזות, כל אחת עם סוג callbacks משלה:

┌───────────────────────────┐
┌─>│ timers (setTimeout/Interval)│
│ ├───────────────────────────┤
│ │ pending callbacks │
│ ├───────────────────────────┤
│ │ poll (I/O — קריאת קבצים/רשת)│ ← כאן מבלים רוב הזמן
│ ├───────────────────────────┤
│ │ check (setImmediate) │
│ ├───────────────────────────┤
└──│ close callbacks │
└───────────────────────────┘

הפאזות החשובות למפתח: timers (מריץ callbacks של setTimeout), poll (מטפל ב-I/O — כאן רוב הפעולות), ו-check (מריץ setImmediate).

Microtasks מול Macrotasks — ההבחנה הקריטית

זו הנקודה שהכי מבלבלת ומופיעה בכל ראיון. בין כל פאזה (ולמעשה אחרי כל callback), Node מריץ את ה-microtask queue עד שהיא ריקה. ל-microtasks יש עדיפות על הכל:

Microtasks (עדיפות גבוהה)Macrotasks
process.nextTick()setTimeout / setInterval
Promise callbacks (.then/await)setImmediate
רצים מיד אחרי ה-callback הנוכחיI/O callbacks

הכלל: אחרי כל פעולה, Node מרוקן את כל ה-microtasks לפני שהוא עובר ל-macrotask הבא. ו-process.nextTick קודם אפילו ל-Promises.

הדוגמה שמבהירה הכל

console.log("1: start");

setTimeout(() => console.log("2: setTimeout"), 0);   // macrotask

Promise.resolve().then(() => console.log("3: promise"));  // microtask

process.nextTick(() => console.log("4: nextTick"));   // microtask (עדיפות עליונה)

console.log("5: end");

// הפלט:
// 1: start        ← קוד סינכרוני רץ קודם
// 5: end          ← עדיין סינכרוני
// 4: nextTick     ← microtask, עדיפות עליונה
// 3: promise      ← microtask
// 2: setTimeout   ← macrotask, אחרון (למרות ה-0!)

למה זה חשוב מעשית: ההבנה הזו מסבירה באגים אמיתיים — למה setTimeout(fn, 0) לא רץ "מיד", למה סדר הפעולות לפעמים מפתיע, ולמה process.nextTick בלולאה יכול "להרעיב" את ה-event loop (למנוע ממנו להתקדם לפאזות אחרות). מפתח שמבין את זה כותב קוד אסינכרוני צפוי; מפתח שלא — מדבג "כישופים" לנצח.

הכלל הזהב: אל תחסום את ה-Event Loop

מכיוון שהכל רץ על thread אחד, קוד סינכרוני כבד חוסם את הכל. לולאה של מיליון איטרציות, JSON.parse על מגה-בייטים, hashing כבד — כל אלה "מקפיאים" את השרת, וכל הבקשות האחרות ממתינות. זה החטא הגדול ב-Node. פתרונות: לפרק לחתיכות, או להעביר ל-worker thread (פרק 13).

3. Async — Callbacks, Promises, async/await

כל עבודת ה-I/O ב-Node אסינכרונית. השפה עברה שלושה דורות של תחביר לטיפול בזה — חשוב להכיר את כולם כי תיתקל בכל השלושה בקוד אמיתי.

דור 1: Callbacks (וה-"callback hell")

הדפוס המקורי של Node: פונקציה מקבלת callback שירוץ כשהפעולה נגמרת. המוסכמה היא error-first callback — הפרמטר הראשון הוא השגיאה:

fs.readFile("a.txt", (err, data) => {
  if (err) return handle(err);     // error-first: תמיד בודקים err קודם
  fs.readFile("b.txt", (err, data2) => {
    if (err) return handle(err);
    // ...מקונן ומקונן — "callback hell" / "pyramid of doom"
  });
});

הבעיה: קינון עמוק, קשה לקריאה, error handling חוזר. זה הוביל לדור הבא.

דור 2: Promises

Promise הוא אובייקט שמייצג ערך עתידי — pending, ואז fulfilled או rejected. משטח את הקינון:

readFilePromise("a.txt")
  .then(data => readFilePromise("b.txt"))
  .then(data2 => { /* ... */ })
  .catch(err => handle(err));      // catch אחד לכל השרשרת

דור 3: async/await (המודרני)

סוכר תחבירי על Promises שנותן קוד אסינכרוני שנראה סינכרוני. זה מה שתכתוב היום:

async function readBoth() {
  try {
    const data = await readFilePromise("a.txt");
    const data2 = await readFilePromise("b.txt");
    return { data, data2 };
  } catch (err) {
    handle(err);                   // try/catch רגיל!
  }
}

(כיסינו את הטיפוסים של זה במדריך TypeScript — כאן ההקשר הוא ה-runtime). await "משהה" את הפונקציה עד שה-Promise נפתר, בלי לחסום את ה-event loop — מאחורי הקלעים זה רושם microtask שימשיך כשהתוצאה מוכנה.

עבודה במקביל — הטעות הנפוצה

מלכודת ביצועים: await ברצף מריץ דברים בזה אחר זה — גם כשהם עצמאיים. אם שתי הקריאות לא תלויות זו בזו, הרצה סדרתית מבזבזת זמן:

// ❌ סדרתי — 200ms (100+100):
const a = await fetchA();   // מחכה 100ms
const b = await fetchB();   // ואז עוד 100ms

// ✅ מקבילי — 100ms (שניהם יחד):
const [a, b] = await Promise.all([fetchA(), fetchB()]);

Promise.all מריץ במקביל וממתין לכולם. שווה זהב ב-Backend שעושה כמה קריאות עצמאיות. (זוכר מ-TypeScript? כאן זה למה זה חשוב לביצועים).

4. Modules — CommonJS מול ESM

נגענו בזה קצר במדריך TypeScript; כאן נעמיק כי ב-Node זה מקור אמיתי לכאב. ל-Node יש שתי מערכות modules שחיות זו לצד זו, והבלבול ביניהן מפיל מפתחים.

CommonJS (CJS) — הוותיק

מערכת ה-modules המקורית של Node. סינכרונית, עם require ו-module.exports:

// math.js
function add(a, b) { return a + b; }
module.exports = { add };

// app.js
const { add } = require("./math");

ES Modules (ESM) — הסטנדרט המודרני

התחביר הסטנדרטי של JavaScript (גם בדפדפן). אסינכרוני, עם import/export:

// math.js
export function add(a, b) { return a + b; }

// app.js
import { add } from "./math.js";

איך Node מחליט איזו מערכת

מפעיל ESMמפעיל CJS
"type": "module" ב-package.jsonברירת מחדל (בלי type)
סיומת .mjsסיומת .cjs

ההבדלים המעשיים שחשוב לדעת

  • ESM דורש סיומות מלאות ב-import ("./math.js", לא "./math"). CJS סלחני.
  • אין __dirname/__filename ב-ESM — צריך לגזור מ-import.meta.url.
  • ESM אסינכרוני — תומך ב-top-level await. CJS סינכרוני.
  • ערבוב מסובך — לייבא CJS מ-ESM עובד לרוב; ההפך בעייתי.

מעשי: הכיוון הוא ESM (הסטנדרט), אבל הרבה פרויקטי Node ו-NestJS עדיין ב-CJS מטעמי תאימות. אם אתה מתחיל פרויקט חדש — ESM. אם אתה מצטרף לקיים — בדוק את ה-"type" ב-package.json והישאר עקבי. השגיאה Cannot use import statement outside a module או require is not defined = ערבבת בין השתיים. עם TypeScript, ה-tsconfig (module/moduleResolution) מתרגם, אז לרוב אתה כותב import וה-compiler מטפל.

5. npm ו-ניהול תלויות

npm (Node Package Manager) הוא איך אתה מתקין ומנהל ספריות. הוא גם הרישום (registry) הכי גדול בעולם — מיליוני חבילות.

package.json — תעודת הזהות של הפרויקט

{
  "name": "my-app",
  "version": "1.0.0",
  "type": "module",
  "scripts": {
    "start": "node dist/main.js",
    "dev": "tsx watch src/main.ts",
    "test": "vitest"
  },
  "dependencies": {          // נחוצות ל-runtime
    "express": "^4.18.0"
  },
  "devDependencies": {       // רק לפיתוח (build, test)
    "typescript": "^5.4.0"
  }
}

dependencies מול devDependencies — הבחנה חשובה

  • dependencies — נחוצות כשהאפליקציה רצה (express, pg, zod). מותקנות ב-production.
  • devDependencies — רק לפיתוח (typescript, טסטים, linters). לא מותקנות ב-production (npm ci --omit=dev). זה מקטין את ה-image (זוכר multi-stage build ממדריך DevOps?).

Semantic Versioning (semver)

גרסאות בפורמט MAJOR.MINOR.PATCH (למשל 4.18.2):

  • MAJOR — שינוי שובר תאימות (breaking).
  • MINOR — feature חדש, תואם אחורה.
  • PATCH — תיקון באג.

הסימנים ב-package.json קובעים כמה "חופש" לעדכן: ^4.18.0 = עדכוני minor+patch (עד 5.0), ~4.18.0 = רק patch, 4.18.0 = מדויק בדיוק.

Lockfile — למה הוא קריטי

package-lock.json נועל את הגרסאות המדויקות של כל התלויות (כולל תלויות-של-תלויות). זה מבטיח שכולם מתקינים בדיוק אותו דבר — reproducibility (זוכר ממדריך DevOps?). בלעדיו, שני מפתחים או ה-CI עלולים לקבל גרסאות שונות, ו"עובד אצלי" חוזר. תמיד commit את ה-lockfile ל-git, והשתמש ב-npm ci (לא npm install) ב-CI/production — הוא מתקין בדיוק לפי ה-lockfile, מהיר ודטרמיניסטי.

npm מול yarn מול pnpm

שלושה package managers, אותו רעיון. pnpm חוסך מקום (משתף חבילות בין פרויקטים) ומהיר; yarn ותיק; npm ברירת המחדל. כולם עובדים — הצוות בוחר אחד ונדבק בו (lockfile שונה לכל אחד).

Node מגיע עם ספריות מובנות (built-in), בלי צורך בהתקנה. אלה שתשתמש בהם. מייבאים עם prefix node: (מומלץ, מבהיר שזה core):

fs — קבצים, עם דגש חשוב

import { readFile } from "node:fs/promises";   // גרסת ה-Promise — מומלצת

const data = await readFile("config.json", "utf-8");   // async, לא חוסם

// לעומת הגרסה הסינכרונית:
import { readFileSync } from "node:fs";
const data2 = readFileSync("config.json", "utf-8");    // ⚠️ חוסם את ה-event loop!

כלל: העדף תמיד את הגרסאות ה-async (fs/promises) על ה-*Sync. גרסאות Sync חוסמות את ה-event loop (זוכר את הכלל הזהב?) ומקפיאות את השרת. גרסאות Sync בסדר רק ב-startup (טעינת config פעם אחת לפני שהשרת מקבל בקשות) — אף פעם לא בתוך request handler.

7. EventEmitter — הדפוס ש-Node בנוי עליו

הרבה מ-Node בנוי על דפוס ה-event-driven: אובייקטים פולטים אירועים, ואחרים מאזינים ומגיבים. EventEmitter הוא המחלקה שמממשת את זה, והרבה ממחלקות ה-core (streams, HTTP servers) יורשות ממנה.

import { EventEmitter } from "node:events";

const emitter = new EventEmitter();

// מאזינים לאירוע:
emitter.on("order", (data) => {
  console.log("New order:", data.id);
});

// פולטים אירוע:
emitter.emit("order", { id: 42 });   // מפעיל את כל המאזינים

זה דפוס ה-pub/sub ברמת התהליך (זוכר ממדריך System Design?). היתרון: decoupling — מי שפולט את האירוע לא צריך לדעת מי מאזין. אפשר להוסיף מאזינים בלי לשנות את הפולט.

איפה תיתקל בזה: server.on("request", ...), stream.on("data", ...), process.on("exit", ...) — כולם EventEmitters. הבנת הדפוס עוזרת לך להבין את כל ה-API של Node.

מלכודת: אם המאזין זורק שגיאה על אירוע "error" ואין לו handler — Node קורס. תמיד הוסף emitter.on("error", ...). וזהירות מ-memory leaks: הוספת מאזינים בלי להסיר (off/removeListener) מצטברת. Node מזהיר אחרי 10 מאזינים לאותו אירוע — זה בדרך כלל סימן לדליפה.

8. Streams ו-Backpressure

Streams הם אחד הנושאים החזקים והפחות-מובנים ב-Node. הם הדרך לעבד נתונים בחתיכות (chunks) במקום לטעון הכל לזיכרון בבת אחת. קריטי לקבצים גדולים ולתעבורת רשת.

הבעיה שהם פותרים

// ❌ טוען קובץ 2GB כולו לזיכרון — קורס / זולל RAM:
const data = await readFile("huge.mp4");
response.write(data);

// ✅ stream — מעביר chunk-chunk, זיכרון קבוע וקטן:
createReadStream("huge.mp4").pipe(response);

עם stream, אתה אף פעם לא מחזיק את כל הקובץ בזיכרון — רק chunk קטן בכל רגע. זה מה שמאפשר ל-Node לשרת קבצים ענקיים עם זיכרון מזערי.

ארבעת סוגי ה-Streams

  • Readable — קוראים ממנו (קובץ נקרא, request נכנס).
  • Writable — כותבים אליו (קובץ נכתב, response יוצא).
  • Duplex — גם וגם (socket רשת).
  • Transform — duplex שמעבד תוך כדי (דחיסה, הצפנה).

pipe — חיבור streams

import { createReadStream, createWriteStream } from "node:fs";
import { createGzip } from "node:zlib";

// קרא קובץ → דחוס → כתוב, הכל ב-streaming:
createReadStream("input.txt")
  .pipe(createGzip())            // transform stream
  .pipe(createWriteStream("input.txt.gz"));

Backpressure — הרעיון הכי חשוב ב-streams

מה קורה כשקוראים מהר יותר ממה שכותבים? (למשל, קוראים מ-SSD מהיר וכותבים לרשת איטית). בלי בקרה, ה-chunks היו מצטברים בזיכרון עד קריסה. Backpressure הוא המנגנון שבו ה-writable stream "אומר" ל-readable "האט, אני עמוס" — וה-readable מפסיק זמנית. pipe() מטפל בזה אוטומטית — זו הסיבה המרכזית להשתמש ב-pipe (או pipeline) במקום לחבר ידנית עם on("data") + write(), שם אתה אחראי ל-backpressure בעצמך וקל לטעות. זה הרעיון שמבדיל בין מי ש"מכיר streams" למי שמבין אותם.

import { pipeline } from "node:stream/promises";

// pipeline = pipe עם error handling ו-cleanup נכונים (מומלץ על pipe):
await pipeline(
  createReadStream("input.txt"),
  createGzip(),
  createWriteStream("output.gz")
);

9. Buffers ונתונים בינאריים

JavaScript נועד לטקסט, אבל Backend מתעסק גם בנתונים בינאריים — קבצים, תמונות, פרוטוקולי רשת. Buffer הוא הטיפוס של Node לרצף bytes גולמי (בזיכרון מחוץ ל-V8 heap).

// Buffer מטקסט:
const buf = Buffer.from("hello", "utf-8");
console.log(buf);              // <Buffer 68 65 6c 6c 6f>  (ה-bytes)
console.log(buf.length);       // 5
console.log(buf.toString("hex"));     // "68656c6c6f"
console.log(buf.toString("base64"));  // קידוד base64

איפה תיתקל ב-Buffers: chunks של streams הם Buffers, crypto עובד עם Buffers, קריאת קובץ בינארי, וקידוד/פענוח (base64 — זוכר מ-JWT ב-Auth? ה-payload מקודד base64). encoding נכון (utf-8 לטקסט, hex/base64 לייצוג) הוא מקור נפוץ לבאגים — טקסט עברי ב-encoding שגוי = ג'יבריש.

10. מודול ה-HTTP — שרת בלי framework

לפני Express ו-NestJS יש את מודול ה-http של Node. חשוב לראות אותו פעם אחת — כי זה מה שכל ה-frameworks עוטפים. כשתבין את זה, NestJS יפסיק להיות "קסם".

import { createServer } from "node:http";

const server = createServer((req, res) => {
  // req = IncomingMessage (readable stream), res = ServerResponse (writable stream)
  if (req.url === "/users" && req.method === "GET") {
    res.writeHead(200, { "Content-Type": "application/json" });
    res.end(JSON.stringify([{ id: 1, name: "Eliya" }]));
  } else {
    res.writeHead(404);
    res.end("Not Found");
  }
});

server.listen(3000, () => console.log("Listening on :3000"));

מה זה מלמד

שים לב לכמה דברים שמתחברים לכל הסדרה:

  • createServer מקבל callback שרץ לכל בקשה — וה-event loop הוא זה שמזמן אותו. thread אחד, אלפי בקשות.
  • req ו-res הם streams (פרק 8) — request נקרא chunk-chunk, response נכתב chunk-chunk. זו הסיבה ש-res.end() ולא "return".
  • אין routing, אין parsing של body, אין validation — הכל ידני. זה בדיוק מה ש-Express/NestJS מוסיפים: הם עוטפים את ה-http הגולמי בשכבות נוחות (routing, middleware, DI).
  • הכל כאן זה HTTP ממדריך Networking — methods, status codes, headers — עכשיו בקוד.

למה שווה לראות את זה: ברגע שאתה מבין ש-NestJS הוא בסופו של דבר http.createServer עם המון שכבות נוחות מעליו, אתה מפסיק לפחד מה-framework ומתחיל להבין מה קורה מתחת. וכשמשהו נשבר ברמה נמוכה — אתה יודע לאן להסתכל.

11. Process ו-Environment

האובייקט הגלובלי process מייצג את התהליך הרץ ונותן גישה לסביבה, לארגומנטים, ולמחזור החיים.

Environment variables

const port = process.env.PORT || 3000;
const dbUrl = process.env.DATABASE_URL;
// ⚠️ אלה תמיד strings! process.env.PORT הוא "3000", לא 3000.
const portNum = Number(process.env.PORT) || 3000;   // המרה נכונה

זה איך קונפיגורציה מגיעה פנימה (זוכר 12-factor וsecrets ממדריך DevOps?). בפיתוח משתמשים ב-.env (עם dotenv או תמיכה מובנית ב-Node חדש).

Arguments וקלט/פלט

process.argv          // ארגומנטים משורת הפקודה: ["node", "script.js", "arg1"]
process.stdout.write("...")   // כתיבה ל-stdout (מה ש-console.log עושה)
process.exit(1)       // יציאה עם קוד (0 = הצלחה, אחר = שגיאה)

Signals ו-Graceful Shutdown

נקודה חשובה ל-production (וזוכר "disposability" מ-12-factor?). כשמערכת ההפעלה/Docker רוצה לכבות את התהליך, היא שולחת signal (SIGTERM). אתה צריך לתפוס אותו ולסגור בחן — לסיים בקשות פעילות, לסגור חיבורי DB — לפני היציאה:

process.on("SIGTERM", async () => {
  console.log("Shutting down gracefully...");
  await server.close();        // הפסק לקבל בקשות חדשות, סיים קיימות
  await db.disconnect();        // סגור משאבים
  process.exit(0);
});

בלי זה, deploy (שמכבה container ומעלה חדש — זוכר rolling deploy?) יקטע בקשות באמצע. graceful shutdown הוא מה שהופך deploys לחלקים באמת.

12. Error Handling ב-Async

טיפול בשגיאות ב-Node קשה יותר מבשפות סינכרוניות, כי שגיאה יכולה לקרות "מאוחר" (ב-callback/promise) כשה-stack כבר לא שם. חובה לעשות את זה נכון — שגיאה לא-מטופלת יכולה להפיל את כל התהליך.

הכללים לפי סוג

// async/await — try/catch רגיל:
try {
  await riskyOperation();
} catch (err) {
  handle(err);
}

// Promise — .catch:
riskyOperation().catch(handle);

// error-first callback — בדוק את err תמיד:
fs.readFile("f", (err, data) => {
  if (err) return handle(err);
  // ...
});

המלכודת הכי מסוכנת: unhandled rejection

אם Promise נדחה ואין לו .catch (או try/catch סביב ה-await), זה unhandled rejection. ב-Node מודרני זה מפיל את התהליך. הדוגמה הקלאסית — לשכוח await:

async function bad() {
  riskyOperation();   // ❌ בלי await — אם זה נכשל, unhandled rejection!
}
async function good() {
  await riskyOperation();   // ✅ עכשיו try/catch תופס
}

רשתות ביטחון גלובליות

process.on("unhandledRejection", (reason) => {
  console.error("Unhandled rejection:", reason);
  // log, ואז יציאה מבוקרת — לא להמשיך במצב לא-ידוע
});

process.on("uncaughtException", (err) => {
  console.error("Uncaught exception:", err);
  process.exit(1);   // המצב לא בטוח — צא ותן ל-orchestrator להרים מחדש
});

עיקרון חשוב: אלה רשתות ביטחון ל-logging ויציאה מבוקרת — לא תחליף לטיפול נכון בשגיאות. אחרי uncaughtException, התהליך במצב לא-ידוע ומסוכן להמשיך — עדיף לצאת ולתת ל-Docker/K8s להרים instance נקי (זוכר self-healing ו-restart ממדריך DevOps?). "crash fast, restart clean" עדיף על "המשך במצב שבור".

13. Worker Threads, Child Processes ו-Cluster

Node הוא single-threaded — אז מה עושים עם משימה CPU כבדה שחוסמת את ה-event loop, או עם מכונה מרובת-cores? שלושה כלים, לשלושה צרכים שונים.

Worker Threads — למשימות CPU

הבעיה: חישוב כבד (עיבוד תמונה, hashing, פענוח גדול) חוסם את ה-thread היחיד ומקפיא את השרת (הכלל הזהב מפרק 2). הפתרון: worker thread — thread נפרד שמריץ את החישוב הכבד במקביל, בלי לחסום את ה-main thread:

import { Worker } from "node:worker_threads";

// מעביר חישוב כבד ל-thread נפרד:
const worker = new Worker("./heavy-computation.js");
worker.on("message", (result) => console.log("Done:", result));
// ה-event loop הראשי נשאר חופשי לטפל בבקשות

Child Processes — להריץ תוכניות אחרות

להריץ תהליך נפרד לגמרי — פקודת shell, סקריפט Python, כלי CLI:

import { spawn } from "node:child_process";
const ls = spawn("ls", ["-la"]);
ls.stdout.on("data", (data) => console.log(data.toString()));

Cluster — לנצל את כל ה-Cores

מכונה עם 8 cores, אבל Node רץ על core אחד. cluster מריץ כמה עותקים (workers) של האפליקציה — אחד לכל core — עם load balancing ביניהם. זה מנצל את כל המכונה:

import cluster from "node:cluster";
import { cpus } from "node:os";

if (cluster.isPrimary) {
  for (let i = 0; i < cpus().length; i++) cluster.fork();   // worker לכל core
} else {
  // כל worker מריץ את השרת
  startServer();
}

מעשי ל-production: בפועל, לרוב לא תשתמש ב-cluster ידנית — כלים כמו PM2, או פשוט להריץ כמה containers מאחורי load balancer (זוכר horizontal scaling ממדריך System Design?), עושים את אותו דבר בצורה נקייה יותר. worker threads כן שימושיים ישירות למשימות CPU נקודתיות. הכלל: Node מבריק ל-I/O; למשימות CPU כבדות — worker threads או, עדיף, הוצא את זה לשירות נפרד. אם רוב העבודה שלך CPU-bound, ייתכן ש-Node הוא הכלי הלא-נכון מלכתחילה.

זרקור: Advanced Node — AsyncLocalStorage, Atomics, perf_hooks, N-API

הנושאים המתקדמים-נישתיים שלא תיגע בהם כל יום, אבל כשתצטרך אותם — טוב לדעת שהם קיימים. אלה מפרידים בין מי שמכיר Node למי ששולט בו.

1. AsyncLocalStorage — "context" שעובר לאורך async

הבעיה: ב-Node single-threaded עם המון בקשות אסינכרוניות מעורבבות, איך מצמידים context (למשל request ID, user, trace) לכל ה-logs של בקשה מסוימת — בלי להעביר אותו ידנית דרך כל פונקציה? ב-thread-per-request פשוט היו משתמשים ב-thread-local, אבל אין כזה ב-Node.

AsyncLocalStorage (מ-node:async_hooks) פותר בדיוק את זה — הוא שומר ערך ש"נוסע" לאורך שרשרת ה-async של בקשה, וזמין בכל מקום בתוכה:

import { AsyncLocalStorage } from "node:async_hooks";
const als = new AsyncLocalStorage();

// middleware: מריץ את הבקשה עם context
app.use((req, res, next) => {
  als.run({ requestId: crypto.randomUUID() }, () => next());
});

// בכל מקום עמוק בקוד — בלי להעביר את זה כפרמטר:
function log(msg) {
  const { requestId } = als.getStore();   // זמין אוטומטית!
  console.log(`[${requestId}] ${msg}`);
}

זה הבסיס ל-request-scoped logging ו-distributed tracing ב-Node (זוכר observability ממדריך System Design?). NestJS ו-ספריות logging משתמשות בזה מתחת. יש לו overhead קטן, אז לא לשים בו הכל — רק context אמיתי.

2. SharedArrayBuffer + Atomics — זיכרון משותף אמיתי בין threads

זוכר שworker threads מתקשרים דרך העברת הודעות (מעתיק נתונים)? לעבודה מרובת-threads על נתונים גדולים זה יקר. SharedArrayBuffer הוא בלוק זיכרון שכמה worker threads חולקים ישירות — בלי העתקה. אבל עכשיו יש לך את כל בעיות ה-concurrency (זוכר את מדריך ה-systems? race conditions!), אז משתמשים ב-Atomics לפעולות אטומיות בטוחות על הזיכרון המשותף:

const shared = new SharedArrayBuffer(1024);
const view = new Int32Array(shared);
// מעבירים את shared ל-worker (בלי העתקה — משותף)
Atomics.add(view, 0, 1);      // increment אטומי — בטוח בין threads
Atomics.load(view, 0);        // קריאה אטומית
Atomics.wait(view, 0, 0);     // המתנה עד שערך משתנה (כמו condition variable!)

זה בדיוק ה-atomics ו-CAS ממדריך ה-systems, ברמת JavaScript. שימושי לחישוב מקבילי כבד (עיבוד תמונה/וידאו, סימולציות). נדיר בקוד Backend רגיל, אבל זו הדרך היחידה ל-shared state אמיתי בין workers.

3. perf_hooks — מדידת ביצועים מדויקת

ל-profiling מדויק בקוד (לא רק כלים חיצוניים), node:perf_hooks נותן מדידות ברמת דיוק גבוהה — כולל מדידת event loop lag ישירות (זוכר את האויב מספר אחת מפרק 14?):

import { performance, monitorEventLoopDelay } from "node:perf_hooks";

const start = performance.now();
doWork();
console.log(`Took ${performance.now() - start}ms`);   // דיוק תת-מילישנייה

// ניטור event loop lag — קריטי ל-production:
const h = monitorEventLoopDelay();
h.enable();
// אחרי זמן: h.mean, h.max — כמה ה-event loop "נתקע"

זה מה ש-APM tools (Datadog וכו') משתמשים בו מתחת כדי להתריע על event loop lag. שימושי לבנות מדדים משלך.

4. Native Addons (N-API) — לקרוא C++ מ-Node

כשצריך ביצועים שמעבר ל-JS (חישוב כבד, גישה לחומרה, ספריית C קיימת), אפשר לכתוב native addon ב-C++ ולקרוא לו מ-Node דרך N-API (ממשק יציב). ספריות כמו bcrypt (זוכר מ-Auth?), sharp (עיבוד תמונות), ו-drivers של DB הן native addons מתחת — זו הסיבה שהן מהירות. אתה כמעט אף פעם לא תכתוב אחד, אבל טוב להבין למה חלק מ-npm install "מקמפל" דברים (native code שצריך build לפלטפורמה שלך).

5. Diagnostics מתקדם — Heap Snapshots ו-Flame Graphs

לדיבוג memory leaks ובעיות ביצועים עמוקות:

  • Heap snapshots — צילום של כל ה-heap ברגע נתון. משווים שני snapshots לאורך זמן כדי לראות מה גדל ולא משתחרר (מוצא memory leaks — זוכר מפרק 14?). דרך node --inspect + Chrome DevTools.
  • Flame graphs — ויזואליזציה של איפה ה-CPU מבלה זמן (איזו פונקציה "רחבה" = אוכלת CPU). הכלי הכי טוב למצוא bottlenecks. דרך --prof או כלים כמו 0x.
  • node --inspect — מחבר את Node ל-Chrome DevTools לדיבוג עם breakpoints, profiling, ו-memory analysis מלא.

מתי להגיע לאלה: אל תלמד אותם עכשיו בעל-פה — הם למקרים ספציפיים. AsyncLocalStorage תפגוש כשתבנה logging/tracing רציני. perf_hooks ו-diagnostics כשתדבג בעיית ביצועים אמיתית ב-production. Atomics/SharedArrayBuffer רק אם תיגע בחישוב מקבילי כבד. N-API — כמעט לעולם לא ישירות. הנקודה: לדעת שהם קיימים ומה הם פותרים, כדי שכשתיתקל בבעיה — תדע לאן לפנות. זה ההבדל בין "לא ידעתי שאפשר" ל"אני יודע בדיוק איזה כלי צריך".

14. Performance ו-Profiling

מכיוון ש-Node הוא single-threaded, בעיות ביצועים שונות מבשפות מרובות-threads. שני האויבים העיקריים: חסימת ה-event loop ו-memory leaks.

Event Loop Lag — האויב מספר אחת

אם קוד סינכרוני חוסם את ה-event loop, כל הבקשות מתעכבות. זה נמדד כ-"event loop lag" — כמה זמן ה-loop מתעכב מלהגיע לפאזה הבאה. סימנים: latency שקופץ תחת עומס, בקשות שנתקעות. הגורמים הנפוצים:

  • לולאות ארוכות / עיבוד מערכים ענקיים סינכרונית.
  • JSON.parse/stringify על נתונים גדולים.
  • פעולות *Sync (readFileSync וכו').
  • Regex מסובך על טקסט גדול (ReDoS).

הפתרון: לפרק עבודה לחתיכות (עם setImmediate בין חתיכות), או worker threads.

Memory Leaks

הזיכרון גדל ולא משתחרר עד קריסה (out of memory). גורמים נפוצים ב-Node:

  • מאזיני events שלא הוסרו (פרק 7) — מצטברים.
  • closures שמחזיקים אובייקטים גדולים בטעות.
  • caches שגדלים בלי גבול — בלי eviction (זוכר LRU ממדריך System Design?).
  • global arrays/maps שרק דוחפים אליהם.

כלים

node --inspect app.js        # מאפשר debugging + profiling ב-Chrome DevTools
node --prof app.js           # CPU profiling
process.memoryUsage()        # מדידת זיכרון נוכחי בקוד

ב-production, APM (Datadog, New Relic — זוכר observability?) מנטר event loop lag וזיכרון, ומתריע לפני קריסה.

הכלל: אל תאופטמז מראש (זוכר את העיקרון מכל הסדרה?). קוד ברור קודם, ואם יש בעיית ביצועים — מדוד (profile) לפני שאתה מנחש. רוב "האטות ה-Node" הן event loop שנחסם או N+1 queries (זוכר ממדריך SQL?) — לא ה-CPU. profiler מראה לך בדיוק איפה, במקום לנחש.

15. אבטחה ו-Tooling

אבטחה ספציפית ל-Node

  • תלויות — הסיכון הגדול. פרויקט Node טיפוסי גורר מאות חבילות. הרץ npm audit לזיהוי חולשות ידועות, ועדכן. חבילה זדונית/פרוצה = פרצה ישירה.
  • אל תריץ eval על קלט — הרצת קוד שרירותי.
  • Injection — SQL injection (מדריך SQL — השתמש ב-parameterized queries), command injection ב-child_process (אל תשרשר קלט לפקודות shell).
  • ReDoS — regex מסובך על קלט משתמש יכול לתקוע את ה-event loop.
  • Secrets — ב-env, לא בקוד (מדריכי DevOps/Auth/Git).
  • validate כל קלט — zod/class-validator (מדריכי TypeScript/NestJS).

Tooling מודרני

  • Testing — ל-Node יש node:test מובנה; פופולריים: Vitest, Jest.
  • Linting/Formatting — ESLint + Prettier. תופסים באגים וסגנון.
  • tsx / ts-node — הרצת TypeScript ישירות בפיתוח (מדריך TypeScript).
  • Debugging — node --inspect + Chrome DevTools, או ה-debugger של VS Code (breakpoints, לא console.log).
  • nodemon / --watch — restart אוטומטי בשינוי קוד בפיתוח.

16. Best Practices וטעויות נפוצות

  1. אל תחסום את ה-event loop — הכלל הזהב. async תמיד, בלי *Sync ב-request handlers, בלי CPU כבד על ה-main thread.
  2. async/await + try/catch — לא callback hell. ותמיד await (או .catch) כל Promise.
  3. Promise.all לעבודה מקבילה — לא await סדרתי לדברים עצמאיים.
  4. streams לנתונים גדולים — לא לטעון הכל לזיכרון. pipeline ל-backpressure.
  5. graceful shutdown — תפוס SIGTERM, סגור משאבים.
  6. טפל בשגיאות async נכון — unhandled rejection מפיל את התהליך.
  7. commit את ה-lockfile, npm ci ב-CI — reproducibility.
  8. env vars הם strings — המר טיפוסים.
  9. worker threads ל-CPU, לא על ה-main thread.
  10. מדוד לפני אופטימיזציה — profile, אל תנחש.

טעויות נפוצות

  • קוד סינכרוני כבד שחוסם את ה-event loop ומקפיא את השרת.
  • לשכוח await — unhandled rejection / התנהגות לא-צפויה.
  • await סדרתי לדברים שיכלו לרוץ במקביל — איטי.
  • טעינת קובץ ענק לזיכרון במקום stream.
  • מאזיני events שלא מוסרים — memory leak.
  • לא לתפוס SIGTERM — deploys קוטעים בקשות.
  • לבלבל בין CJS ל-ESM — require/import errors.
  • להתעלם מ-npm audit — תלויות פרוצות.

17. תרגילים

1 — Event Loop. נבא את סדר הפלט של קוד עם console.log, setTimeout(0), Promise.resolve().then, ו-process.nextTick. הרץ ובדוק אם צדקת. (זה מבחן ההבנה של פרק 2).

2 — HTTP גולמי. בנה שרת REST פשוט עם מודול http בלבד (בלי Express) — שני endpoints, JSON, status codes נכונים. תעריך כמה NestJS חוסך לך.

3 — Streams. כתוב סקריפט שקורא קובץ CSV גדול, מסנן שורות, וכותב לקובץ חדש — הכל ב-streaming עם pipeline, בלי לטעון את הכל לזיכרון.

4 — Async מקבילי. כתוב פונקציה שמביאה נתונים מ-3 APIs עצמאיים. ממש אותה קודם סדרתית ואז עם Promise.all, ומדוד את ההפרש בזמן.

5 — Worker Thread. כתוב חישוב כבד (למשל, מספרים ראשוניים עד מיליון) שחוסם את השרת, ואז העבר אותו ל-worker thread כדי שהשרת יישאר responsive. בדוק את ההבדל.

6 — Graceful Shutdown. הוסף לשרת טיפול ב-SIGTERM שסוגר חיבורים בחן. בדוק עם Ctrl+C.

סיכום — מה הלאה

הדבר האחד לקחת: הכל ב-Node חוזר ל-event loop. thread אחד, non-blocking I/O, ו"אל תחסום את ה-loop" — מזה נגזרים async/await, streams, worker threads, וכל דפוסי הביצועים. ברגע שהמודל הזה מתיישב בראש, Node מפסיק להפתיע אותך.

שים לב כמה מהמדריך חיבר את הסדרה מלמטה: NestJS הוא http.createServer עם שכבות; async/await הם הטיפוסים מ-TypeScript בפעולה; streams וזיכרון קשורים ל-System Design; env ו-graceful shutdown ל-DevOps. עכשיו אתה מבין את הרצפה שכל השאר עומד עליה.
