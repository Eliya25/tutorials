Django הוא framework ל-Backend ב-Python, בפילוסופיה הפוכה מ-NestJS: "batteries-included" — ORM, admin, auth, forms, הכל מובנה מהקופסה. המדריך מנצל את מה שאתה כבר יודע (NestJS, SQL, HTTP, auth) ומבליט את הניגודים, כדי שתלמד מהר.

1. מבוא: Django, MVT, ו-Batteries-Included

Django הוא framework ותיק, בוגר ומאוד פרודוקטיבי לבניית אפליקציות web ב-Python. הסלוגן שלו: "The web framework for perfectionists with deadlines" — כלומר, לבנות מהר בלי להתפשר על איכות.

הפילוסופיה: Batteries-Included

זה ההבדל המהותי מ-NestJS, וחשוב להפנים אותו. NestJS הוא מינימלי — אתה בוחר ORM, ספריית auth, וכו', ומרכיב. Django הוא ההפך: הכל כבר בפנים — ORM משלו, מערכת auth מלאה, admin panel אוטומטי, forms, migrations, caching. אתה מקבל אפליקציה עובדת מהר מאוד, אבל עם "הדרך של Django" (opinionated). ה-tradeoff: פחות החלטות והרכבה (מהיר), אבל פחות גמישות לבחור רכיבים משלך. שני הגישות לגיטימיות — Django מנצח על מהירות פיתוח וקוהרנטיות; NestJS על גמישות ומודולריות.

MVT — המודל של Django

Django משתמש בדפוס MVT (Model-View-Template), וריאציה על MVC המוכר:

  • Model — הנתונים והלוגיקה העסקית (טבלאות ה-DB דרך ה-ORM).
  • View — מקבל request, מדבר עם ה-models, ומחזיר response. (שים לב: ב-Django "View" הוא מה ש-NestJS קורא לו controller — לא ה-UI!).
  • Template — ה-HTML (עבורך כמפתח API, פחות רלוונטי — תחזיר JSON דרך DRF).

2. התקנה ומבנה — Project מול Apps

התקנה

python -m venv venv           # virtual environment (מבודד תלויות — כמו node_modules)
source venv/bin/activate      # (Windows: venv\Scripts\activate)
pip install django
django-admin startproject myproject
cd myproject
python manage.py runserver    # השרת עולה על :8000

ההבחנה הקריטית: Project מול App

זו הנקודה שהכי מבלבלת מתחילים ב-Django. Project = כל האפליקציה שלך (ההגדרות, ה-config). App = מודול/רכיב עצמאי בתוך ה-project (users, orders, blog). project אחד מכיל כמה apps. חשוב על app כמו על module ב-NestJS — יחידה עצמאית עם models, views, ו-URLs משלה, שאפשר לעשות בה שימוש חוזר. הרעיון: apps קטנים וממוקדים, לא app ענק אחד.

python manage.py startapp users    # יוצר app בשם users

המבנה

myproject/
├── manage.py              # ה-CLI — כל הפקודות (runserver, migrate, ...)
├── myproject/             # ה-project (config)
│   ├── settings.py        # כל ההגדרות (DB, apps, middleware)
│   ├── urls.py            # ה-routing הראשי
│   └── wsgi.py / asgi.py  # נקודות כניסה ל-production
└── users/                 # app
    ├── models.py          # טבלאות ה-DB
    ├── views.py           # הלוגיקה (controllers)
    ├── urls.py            # routing של ה-app
    ├── admin.py           # רישום ל-admin panel
    └── migrations/        # שינויי סכמה

manage.py — ה-CLI שלך

כל פעולה ב-Django עוברת דרך manage.py (מקביל ל-nest CLI):

python manage.py runserver          # מריץ שרת פיתוח
python manage.py startapp <name>     # יוצר app
python manage.py makemigrations     # יוצר migrations מ-models
python manage.py migrate            # מחיל migrations על ה-DB
python manage.py createsuperuser    # יוצר admin user
python manage.py shell              # Python shell עם Django טעון

רישום App

אחרי יצירת app, חובה לרשום אותו ב-settings.py תחת INSTALLED_APPS — אחרת Django מתעלם ממנו (כמו imports ב-NestJS module):

# settings.py
INSTALLED_APPS = [
    "django.contrib.admin",     # ה-apps המובנים של Django
    "django.contrib.auth",
    # ...
    "users",                    # ה-app שלך
]

3. מחזור הבקשה — URLs, Views, Response

לפני שנצלול לרכיבים, חשוב להבין את הזרימה — איך בקשה הופכת לתשובה ב-Django. זה מקביל ל-request lifecycle שראית ב-NestJS.

1. בקשה מגיעה →
2. Middleware (סדרה של עיבודים — auth, sessions, ...)
3. URL Resolver — מתאים את ה-URL ל-view הנכון (urls.py)
4. View — הלוגיקה: מדבר עם Models, מכין נתונים
5. (Template או Serializer → JSON)
6. Middleware (בכיוון החזרה)
7. Response חוזר ללקוח

שים לב כמה זה דומה ל-NestJS: middleware → routing → handler → response, עם middleware שעוטף בשני הכיוונים. הרעיונות זהים; רק השמות והתחביר שונים. זה למה הבסיס שלמדת מעביר אותך מ-framework ל-framework.

4. URLs ו-Routing

ב-Django, ה-routing מפורש ומרוכז בקבצי urls.py (בניגוד ל-decorators על methods ב-NestJS). ה-project מפנה ל-apps, וכל app מגדיר את ה-URLs שלו.

# myproject/urls.py — הראשי
from django.urls import path, include

urlpatterns = [
    path("admin/", admin.site.urls),
    path("api/users/", include("users.urls")),   # מאציל ל-app
]

# users/urls.py
from django.urls import path
from . import views

urlpatterns = [
    path("", views.user_list),              # /api/users/
    path("<int:user_id>/", views.user_detail),  # /api/users/42/
]

<int:user_id> הוא path parameter עם המרת טיפוס — Django ממיר ל-int ומעביר ל-view (מקביל ל-ParseIntPipe ב-NestJS). ה-include מאפשר לכל app לנהל את ה-URLs שלו — מודולריות.

5. Views — Function-Based מול Class-Based

View ב-Django הוא מה שמטפל בבקשה (= controller ב-NestJS). יש שתי גישות, ושתיהן נפוצות.

Function-Based Views (FBV)

פונקציה פשוטה שמקבלת request ומחזירה response:

from django.http import JsonResponse

def user_list(request):
    if request.method == "GET":
        users = User.objects.all()          # ORM query
        data = [{"id": u.id, "name": u.name} for u in users]
        return JsonResponse(data, safe=False)

Class-Based Views (CBV)

מחלקה שמארגנת לוגיקה לפי HTTP method, ומאפשרת שימוש חוזר דרך ירושה:

from django.views import View

class UserListView(View):
    def get(self, request):
        # ...טיפול ב-GET
    def post(self, request):
        # ...טיפול ב-POST

מעשי: FBV פשוט וברור לדברים קטנים; CBV נותן שימוש חוזר וארגון לדברים מורכבים. אבל האמת — כמפתח API, ברוב הזמן לא תכתוב אף אחד מאלה ידנית. תשתמש ב-Django REST Framework (פרק 10) שנותן ViewSets ברמה גבוהה יותר שמייצרים את כל ה-CRUD אוטומטית. ה-views הגולמיים חשובים להבנה, אבל DRF הוא מה שתעבוד איתו בפועל.

6. Models ו-ORM — הכתר

ה-ORM של Django הוא אחד החזקים והנוחים שקיימים, וזה כנראה הסיבה המרכזית לבחור ב-Django. אתה מגדיר את הטבלאות כמחלקות Python, ו-Django מתרגם לכל ה-SQL — כולל migrations.

הגדרת Model

# users/models.py
from django.db import models

class User(models.Model):
    name = models.CharField(max_length=100)
    email = models.EmailField(unique=True)
    age = models.IntegerField(null=True, blank=True)
    is_active = models.BooleanField(default=True)
    created_at = models.DateTimeField(auto_now_add=True)

    def __str__(self):
        return self.name        # תצוגה קריאה (חשוב ל-admin)

שים לב: אין צורך להגדיר id — Django מוסיף primary key אוטומטי. כל Field מתרגם לעמודה עם טיפוס וה-constraints (זוכר DDL ממדריך SQL? זה בדיוק אותו דבר, מוגדר ב-Python).

סוגי Fields עיקריים

Fieldעמודה

IntegerField / BigIntegerFieldINT / BIGINT
DecimalFieldNUMERIC (לכסף! זוכר מ-SQL?)
BooleanFieldBOOLEAN
DateTimeFieldTIMESTAMP

JSONFieldJSONB (זוכר ממדריך Databases?)

קשרים (Relationships) — בדיוק המודל הרלציוני

class Order(models.Model):
    # One-to-Many: user אחד → הרבה orders
    user = models.ForeignKey(User, on_delete=models.CASCADE, related_name="orders")
    total = models.DecimalField(max_digits=10, decimal_places=2)

class Profile(models.Model):
    # One-to-One
    user = models.OneToOneField(User, on_delete=models.CASCADE)

class Course(models.Model):
    # Many-to-Many — Django יוצר את ה-junction table אוטומטית!
    students = models.ManyToManyField(User, related_name="courses")

נקודה יפה: זוכר שבמדריך Databases היינו צריכים ליצור junction table ידנית ל-M:N? Django עושה את זה אוטומטית עם ManyToManyField. וה-on_delete=CASCADE הוא בדיוק ה-referential action מ-SQL. ה-ORM לא מסתיר ממך את המודל הרלציוני — הוא נותן לך אותו בתחביר Python נקי. כל מה שלמדת ב-SQL ו-Databases חל כאן, רק בממשק אחר.

7. ORM Queries — QuerySets ו-N+1

ה-QuerySet הוא איך אתה שולף נתונים. הוא חזק, קריא, ויש לו כמה מאפיינים חשובים להבין — במיוחד לביצועים.

Queries בסיסיים

User.objects.all()                          # SELECT * FROM users
User.objects.filter(age__gte=18)            # WHERE age >= 18
User.objects.filter(is_active=True).exclude(age__lt=18)  # WHERE + NOT
User.objects.get(id=42)                      # שורה אחת (זורק אם 0 או >1)
User.objects.filter(name__icontains="eli")  # WHERE name ILIKE '%eli%'
User.objects.order_by("-created_at")[:10]   # ORDER BY DESC LIMIT 10
User.objects.count()                         # COUNT(*)

ה-__ (double underscore) הוא ה-syntax של lookups: age__gte = "age >= ", name__icontains = case-insensitive contains. זה כל ה-WHERE מ-SQL, בתחביר Python.

Lazy Evaluation — מאפיין חשוב

QuerySets הם עצלים (lazy) — הם לא פונים ל-DB עד שאתה באמת צריך את הנתונים (iteration, list(), len()). זה מאפשר לשרשר סינונים בלי לפגוע ב-DB בכל שלב:

qs = User.objects.filter(is_active=True)   # עדיין אין query!
qs = qs.filter(age__gte=18)                # עדיין אין query — רק בונה
users = list(qs)                           # ← עכשיו ה-SQL רץ, פעם אחת

יתרון: יעילות. סכנה: קל לגרום בטעות לכמה queries אם לא מבינים מתי הם "מתממשים".

הבעיה הכי חשובה: N+1 Queries

זו הטעות מספר אחת עם כל ORM (כיסינו אותה ב-SQL וב-Databases — כאן ספציפית ל-Django). גישה ל-relation בתוך לולאה מפעילה query נפרד לכל שורה:

# ❌ N+1: query אחד ל-orders, ואז query לכל order.user!
for order in Order.objects.all():
    print(order.user.name)      # ← query נפרד לכל order

# ✅ select_related — JOIN אחד (ל-ForeignKey / OneToOne):
for order in Order.objects.select_related("user"):
    print(order.user.name)      # ← query אחד עם JOIN

# ✅ prefetch_related — ל-ManyToMany / reverse FK:
for user in User.objects.prefetch_related("orders"):
    print(user.orders.all())    # ← 2 queries סה"כ, לא N+1

הכלל שיחסוך לך ביצועים: select_related ל-ForeignKey/OneToOne (עושה JOIN), prefetch_related ל-ManyToMany/reverse (עושה query שני ומחבר בזיכרון). כמעט כל בעיית ביצועים ב-Django היא N+1 שלא טופל. הכלי לזיהוי: django-debug-toolbar מראה לך כמה queries כל דף מריץ — אם אתה רואה 50 queries לרשימה, יש לך N+1. (זוכר את EXPLAIN ממדריך SQL? כאן ה-debug toolbar הוא הכלי המקביל).

Aggregations ו-annotations

from django.db.models import Count, Sum, Avg

User.objects.aggregate(Avg("age"))                    # ממוצע כללי
User.objects.annotate(order_count=Count("orders"))    # מוסיף שדה מחושב לכל שורה

annotate הוא כמו window/aggregate שמצורף לכל שורה — חזק מאוד לדוחות, בלי לכתוב SQL גולמי.

8. Migrations

אחד היתרונות הגדולים של Django: migrations אוטומטיים. אתה משנה model, Django מייצר את ה-migration, ומחיל אותו. (זוכר migrations ממדריך Databases? כאן זה חלק ומובנה).

# 1. שינית/הוספת model ב-models.py
# 2. Django מזהה את השינוי ומייצר migration:
python manage.py makemigrations
#    → יוצר קובץ migrations/0002_add_phone.py

# 3. מחיל על ה-DB:
python manage.py migrate

איך זה עובד

Django שומר את היסטוריית ה-migrations (בקבצים ובטבלה ב-DB), ומחיל רק את החדשים. כל migration הוא Python עם operations (הוסף עמודה, צור טבלה). אפשר גם לכתוב migrations ידניים (data migrations — למשל למלא נתונים).

אזהרות מ-production (חוזר ממדריך Databases): migrations הרסניים (מחיקת עמודה) על טבלה חיה עלולים לשבור קוד שעדיין רץ, ולנעול טבלאות גדולות. הכלל expand-contract חל גם כאן: הוסף, פרוס קוד, ואז מחק. וחשוב: commit את קבצי ה-migrations ל-git — הם חלק מהקוד, וכל הצוות והשרתים צריכים אותם. אל תמחק migrations שכבר רצו בשרת.

9. Django Admin — ה-Feature המנצח

זה ה-feature ש-Django מפורסם בזכותו, ושאין לו מקביל ב-NestJS. עם כמה שורות, אתה מקבל ממשק ניהול web מלא לכל ה-models — CRUD, חיפוש, סינון, הרשאות — בחינם.

# users/admin.py
from django.contrib import admin
from .models import User

@admin.register(User)
class UserAdmin(admin.ModelAdmin):
    list_display = ["name", "email", "is_active", "created_at"]   # עמודות בטבלה
    list_filter = ["is_active"]                                    # מסננים בצד
    search_fields = ["name", "email"]                              # חיפוש

אחרי createsuperuser, נכנסים ל-/admin ומקבלים ממשק מלא לנהל את הנתונים — בלי לכתוב שום frontend.

למה זה כל כך שימושי: ה-admin חוסך שבועות של עבודה על "ממשק ניהול פנימי". לצוותים, ל-CMS, ל-back-office — זה זהב. הרבה חברות בונות MVP שלם רק על ה-admin. זה הביטוי הכי חזק של "batteries-included". אבל — הוא לא נועד להיות ה-UI של המשתמשים שלך (הוא ממשק פנימי/אדמין); לזה תבנה frontend נפרד שמדבר עם ה-API (DRF).

10. Django REST Framework — בניית APIs

זה הפרק הכי חשוב עבורך כמפתח API. Django "טהור" בנוי לאתרים עם templates; לבניית REST APIs משתמשים ב-Django REST Framework (DRF) — ספרייה שהיא כמעט סטנדרט. היא נותנת serializers, viewsets, auth, ו-pagination מובנים.

pip install djangorestframework
# ואז מוסיפים "rest_framework" ל-INSTALLED_APPS

Serializers — הלב של DRF

Serializer ממיר בין objects של Django (models) ל-JSON וחזרה, וגם מבצע validation. זה בדיוק ה-DTO + validation שהכרת ב-NestJS (class-validator), מאוחד לרכיב אחד:

# users/serializers.py
from rest_framework import serializers
from .models import User

class UserSerializer(serializers.ModelSerializer):
    class Meta:
        model = User
        fields = ["id", "name", "email", "age"]   # אילו שדות לחשוף
        # אפשר read_only_fields, validation מותאם, וכו'

ה-ModelSerializer גוזר אוטומטית את השדות מה-model — כולל טיפוסים ו-validation בסיסי. שים לב איך זה מקביל ל-DTOs עם Pick/Omit מ-NestJS: בוחרים בדיוק מה נכנס/יוצא ב-API.

ViewSets — CRUD מלא כמעט בחינם

ViewSet נותן את כל פעולות ה-CRUD (list, create, retrieve, update, delete) ממחלקה אחת:

# users/views.py
from rest_framework import viewsets
from .models import User
from .serializers import UserSerializer

class UserViewSet(viewsets.ModelViewSet):
    queryset = User.objects.all()
    serializer_class = UserSerializer
    # וזהו! GET/POST/PUT/PATCH/DELETE — הכל עובד.
# users/urls.py — router מחבר את ה-viewset ל-URLs אוטומטית:
from rest_framework.routers import DefaultRouter
router = DefaultRouter()
router.register("users", UserViewSet)
urlpatterns = router.urls
# → GET /users/, POST /users/, GET /users/42/, PUT, DELETE — הכל!

הכוח של DRF: שלושת הקטעים למעלה נותנים לך API CRUD מלא, עם validation, pagination, ו-browsable API (ממשק web לבדיקה) — בפחות מ-15 שורות. זה ה-"batteries-included" בפעולה. השווה לכמה קוד זה היה ב-NestJS (controller + service + DTOs + module). DRF מבריק ל-CRUD-heavy APIs. ה-tradeoff: כשצריך לוגיקה לא-סטנדרטית, ה-magic יכול להפריע — ואז מוסיפים custom methods או יורדים ל-views ידניים.

11. Authentication ו-Permissions

Django מגיע עם מערכת auth מלאה מובנית (זוכר כמה עבדנו על זה ב-NestJS? כאן הרבה מזה בחינם) — user model, sessions, password hashing, permissions.

מה מובנה

  • User model — מובנה (django.contrib.auth), עם username, email, password.
  • Password hashing — אוטומטי (PBKDF2 חזק — זוכר bcrypt מ-Auth? Django עושה את זה בשבילך).
  • Sessions — מובנה (session-based auth, זוכר ממדריך Auth?).
  • Permissions & groups — מערכת הרשאות מובנית.

Auth ב-DRF — לבחירתך

ל-APIs, DRF תומך בכמה שיטות (כולן מהמדריך על Authentication):

  • Session auth — טוב ל-frontend באותו domain.
  • Token auth — token פשוט לכל user (מובנה ב-DRF).
  • JWT — דרך djangorestframework-simplejwt (access + refresh — בדיוק הדפוס ממדריך Auth).

Permissions

from rest_framework.permissions import IsAuthenticated

class UserViewSet(viewsets.ModelViewSet):
    permission_classes = [IsAuthenticated]   # רק מחוברים
    # אפשר permissions מותאמים: IsOwner, IsAdmin, וכו'

הקשר למדריך Auth: כל מה שלמדת שם חל — sessions מול JWT, hashing, permissions. ההבדל: Django נותן לך את רוב זה מובנה ובדוק, במקום להרכיב עם Passport כמו ב-NestJS. זה בדיוק היתרון של batteries-included לאבטחה — פחות קוד שאתה כותב (ופחות קוד שאתה יכול לטעות בו). וזה מחזק את העצה ממדריך Auth: אל תבנה auth מאפס — Django נותן לך מימוש בדוק.

12. Middleware

Middleware ב-Django הוא סדרה של "שכבות" שכל בקשה עוברת דרכן בכניסה, וכל תשובה ביציאה (בדיוק המושג ממדריכי Networking ו-NestJS). זה המקום ל-cross-cutting concerns: auth, sessions, CORS, security headers.

    "django.middleware.common.CommonMiddleware",
    "django.middleware.csrf.CsrfViewMiddleware",
    "django.contrib.auth.middleware.AuthenticationMiddleware",
    # middleware מותאם שלך

Django מגיע עם middleware מובנה חשוב: security headers, sessions, CSRF protection (זוכר CSRF ממדריך Auth/Networking? Django מגן מזה כברירת מחדל). middleware מותאם הוא פונקציה/מחלקה שעוטפת את ה-view.

13. Settings ו-Environments

settings.py הוא ה-control panel של הפרויקט — DB, apps, middleware, secrets. ניהול נכון שלו בין סביבות (dev/prod) הוא קריטי.

הגדרות מרכזיות

# settings.py
DEBUG = False                    # ⚠️ תמיד False ב-production!
SECRET_KEY = os.environ["SECRET_KEY"]    # מ-env, לא בקוד!
ALLOWED_HOSTS = ["myapp.com"]
DATABASES = {
    "default": {
        "ENGINE": "django.db.backends.postgresql",
        "NAME": os.environ["DB_NAME"],
        # ...מ-env
    }
}

כללי ברזל (חוזרים ממדריכי DevOps/Auth/Git): (1) SECRET_KEY וסיסמאות מ-environment variables, אף פעם לא בקוד/git. (2) DEBUG = False ב-production תמיד — DEBUG=True חושף stack traces ומידע רגיש לתוקפים, וזו פרצת אבטחה קלאסית. (3) הפרד settings לסביבות (למשל settings/base.py, settings/prod.py) או השתמש ב-django-environ. זה בדיוק ה-12-factor config שראית ב-DevOps.

14. Async, Celery, Caching ו-Signals

Async Django

Django נבנה במקור סביב WSGI סינכרוני, אך כיום תומך גם ב-ASGI, ב-async def views ובחלק משמעותי מפעולות ה-ORM בצורה אסינכרונית. תחת ASGI אפשר לטפל ב-I/O מקביל בלי להחזיק thread לכל המתנה, בתנאי שכל ה-call chain תומך async. קוד סינכרוני, middleware ישן או library חוסמת עדיין דורשים התאמה ועלולים לבטל את היתרון. פירוט מדויק נמצא בפרק 23.

Celery — עבודה ברקע

ל-Django אין event loop לעבודה אסינכרונית, אז משימות כבדות/איטיות (שליחת מייל, עיבוד, דוחות) מועברות ל-Celery — task queue שרץ ב-workers נפרדים, בדרך כלל עם Redis/RabbitMQ כ-broker (זוכר message queues ממדריך System Design?):

from celery import shared_task

@shared_task
def send_welcome_email(user_id):
    # רץ ב-worker נפרד, לא חוסם את הבקשה
    ...

# ב-view:
send_welcome_email.delay(user.id)   # מכניס לתור, מחזיר מיד

Celery אינה תחליף ל-async I/O. היא פותרת בעיה אחרת: עבודה שצריכה להמשיך מעבר לחיי בקשת HTTP, לשרוד retries, לרוץ בתזמון או להתבצע ב-workers נפרדים. בקשת async קצרה ועבודת background durable הן שני כלים שונים.

Caching

Django מגיע עם framework caching מובנה — cache-per-view, cache-per-query, או low-level. בד"כ עם Redis (זוכר caching ממדריכי System Design/Databases?):

from django.core.cache import cache
cache.set("key", value, timeout=300)
value = cache.get("key")

Signals

מנגנון event-driven מובנה: קוד שרץ אוטומטית באירועים של models (נשמר, נמחק). למשל, ליצור Profile אוטומטית כשנוצר User:

from django.db.models.signals import post_save

@receiver(post_save, sender=User)
def create_profile(sender, instance, created, **kwargs):
    if created:
        Profile.objects.create(user=instance)

אזהרה (כמו triggers ב-SQL): signals נוחים אבל מסתירים לוגיקה — קשה לעקוב אחרי מה קורה מתי. השתמש בהם ל-cross-cutting נקי (audit, יצירת objects נלווים), אבל לוגיקה עסקית עדיף במקום מפורש. אותה עצה כמו על triggers ממדריך SQL.

15. Testing

Django מגיע עם framework testing מובנה (מבוסס על unittest של Python), עם DB בדיקה שנוצר ונמחק אוטומטית לכל ריצה:

from django.test import TestCase

class UserModelTest(TestCase):
    def setUp(self):
        User.objects.create(name="Eliya", email="e@x.com")

    def test_user_str(self):
        user = User.objects.get(email="e@x.com")

from rest_framework.test import APITestCase

class UserAPITest(APITestCase):
    def test_list_users(self):

python manage.py test מריץ הכל. Django מקים DB בדיקה נפרד, אז הטסטים לא נוגעים בנתונים אמיתיים. (הרבה צוותים מעדיפים pytest-django — נוח יותר). זוכר את חשיבות הטסטים בעידן ה-AI ממדריך DevOps? חל גם כאן.

16. Deployment

שרת הפיתוח (runserver) הוא לא ל-production. בפרודקשן מריצים דרך application server:

  • WSGI (סינכרוני) — Gunicorn או uWSGI. הסטנדרט ל-Django רגיל.
  • ASGI (אסינכרוני) — Uvicorn/Daphne, אם אתה משתמש ב-async Django/WebSockets.
Client → Nginx (reverse proxy) → Gunicorn (כמה workers) → Django
            (static files, TLS)      (worker per request)

הכל מ-DevOps חל: Docker (containerize את Django + Gunicorn), reverse proxy (Nginx — TLS termination, static files), env vars, ו-migrations כחלק מה-deploy. collectstatic אוסף קבצים סטטיים. מספר ה-workers של Gunicorn = איך Django מנצל כמה cores (זוכר שהוא סינכרוני? זה ה-cluster המקביל).

checklist ל-production: DEBUG=False, SECRET_KEY מ-env, ALLOWED_HOSTS מוגדר, Postgres (לא SQLite), Gunicorn+Nginx, static files מוגשים נכון, HTTPS, ו-python manage.py check --deploy (Django בודק לך הגדרות אבטחה!). זה בדיוק ה-deploy checklist ממדריך DevOps, מותאם ל-Django.

17. Best Practices וטעויות נפוצות

  1. apps קטנים וממוקדים — לא app ענק אחד. כמו modules ב-NestJS.
  2. select_related / prefetch_related — הכלי מספר אחד נגד N+1. השתמש ב-debug-toolbar לזהות.
  3. DRF ל-APIs — serializers + viewsets, לא views ידניים לכל CRUD.
  4. נצל את ה-admin — ל-back-office, חוסך שבועות.
  5. DEBUG=False + secrets ב-env ב-production — קריטי לאבטחה.
  6. commit migrations ל-git, expand-contract לשינויים הרסניים.
  7. Celery לעבודה כבדה — Django סינכרוני, אל תחסום בקשות.
  8. נצל את ה-auth המובנה — אל תבנה מאפס.
  9. fat models, thin views — לוגיקה ב-models/services, views דקים (מקביל ל-thin controllers).
  10. Postgres, לא SQLite ב-production.

טעויות נפוצות

  • N+1 queries — הכי נפוצה. select_related/prefetch_related.
  • DEBUG=True ב-production — פרצת אבטחה חמורה.
  • secrets ב-settings.py שב-git — זוכר את הכלל מ-Git?
  • לוגיקה כבדה ב-view סינכרוני — חוסם worker. Celery.
  • לבלבל project ו-app — או app ענק מונוליטי.
  • signals מוגזמים — לוגיקה נסתרת קשה לדיבוג.
  • get() בלי טיפול בחריגה — DoesNotExist מפיל אם אין תוצאה (השתמש ב-get_object_or_404).

18. Custom User ו-Authentication נכון

אם יש סיכוי שתצטרך login באמצעות email, שדות profile נוספים או שינוי identity, הגדר custom user בתחילת הפרויקט ולפני migration ראשון. החלפת user model אחרי שהטבלאות והקשרים קיימים אפשרית, אבל יקרה ומסוכנת.

# users/models.py
from django.contrib.auth.models import AbstractUser
from django.db import models

class User(AbstractUser):
    email = models.EmailField(unique=True)

# settings.py
AUTH_USER_MODEL = "users.User"

# בכל model אחר — לא לייבא User הקונקרטי
class Workout(models.Model):
    owner = models.ForeignKey(
        settings.AUTH_USER_MODEL,
        on_delete=models.CASCADE,
        related_name="workouts",
    )

AbstractUser שומר את רוב המערכת המובנית; AbstractBaseUser נותן שליטה מלאה אך דורש manager, admin ושדות נוספים. אל תבחר בו רק כי הוא “מתקדם”. סיסמאות נשמרות באמצעות hash איטי ומומלח דרך set_password; לעולם אין לבצע assignment ישיר לשדה password.

ב־API בחר authentication לפי סוג הלקוח: session + CSRF מתאים לאתר browser באותו domain; access token קצר ו־refresh rotation מתאים ללקוחות נפרדים. Permission היא החלטה עסקית: “האם המשתמש המחובר רשאי לבצע פעולה על האובייקט הזה?”. Authentication לבדו אינו מונע IDOR.

19. Models מתקדמים ו-Constraints

Model הוא לא רק תיאור טבלה. הוא המקום להגדיר invariants שה־database יכול לאכוף גם אם הנתונים נכתבים מ־admin, task או script. Validation ב־serializer משפר הודעה למשתמש; constraint ב־DB שומר correctness מול races וכניסות אחרות.

class Enrollment(models.Model):
    user = models.ForeignKey(settings.AUTH_USER_MODEL, on_delete=models.CASCADE)
    course = models.ForeignKey("courses.Course", on_delete=models.CASCADE)
    progress = models.PositiveSmallIntegerField(default=0)

    class Meta:
        constraints = [
            models.UniqueConstraint(fields=["user", "course"], name="uniq_user_course"),
            models.CheckConstraint(
                condition=models.Q(progress__gte=0, progress__lte=100),
                name="progress_between_0_and_100",
            ),
        ]
        indexes = [models.Index(fields=["user", "-id"])]

הוסף index לפי query pattern, לא לכל field. Composite index תלוי בסדר העמודות. ‏db_index=True יכול להאיץ קריאה אבל מוסיף מקום ועלות לכל INSERT/UPDATE.

Managers ו-QuerySets

class WorkoutQuerySet(models.QuerySet):
    def visible_to(self, user):
        return self.filter(owner=user, deleted_at__isnull=True)

class Workout(models.Model):
    objects = WorkoutQuerySet.as_manager()

QuerySet מותאם מרכז query logic חוזר ושומר composability. אל תכניס ל־manager side effects או HTTP concerns.

20. Transactions ו-Concurrency

Transaction היא יחידת עבודה אטומית: או שכל השינויים מתבצעים, או שאף אחד מהם. היא אינה “נעילה של כל ה־DB”. ברירת המחדל של Django היא autocommit—כל query מתחייבת בנפרד אלא אם עטפת scope ב־transaction.atomic.

from django.db import transaction

@transaction.atomic
def transfer(source_id: int, target_id: int, amount: int) -> None:
    accounts = Account.objects.select_for_update().filter(
        id__in=[source_id, target_id]
    ).in_bulk()
    source, target = accounts[source_id], accounts[target_id]
    if source.balance < amount:
        raise InsufficientBalance()
    source.balance -= amount
    target.balance += amount
    Account.objects.bulk_update([source, target], ["balance"])

select_for_update נועל rows עד סוף transaction ומונע lost update, אבל רק בתוך transaction. כדי לצמצם deadlock, נעל resources בסדר עקבי ושמור transactions קצרות—בלי API חיצוני או שליחת email בתוכן.

Optimistic update

updated = Account.objects.filter(id=account_id, version=expected_version).update(
    balance=new_balance,
    version=models.F("version") + 1,
)
if updated == 0:
    raise ConcurrentModification()

זו Compare-And-Swap ברמת DB. ‏F() מבקש מה־database לחשב על הערך הנוכחי ומונע read-modify-write פשוט. בחר pessimistic locking כשעימות סביר והפעולה קצרה; optimistic כשהעימות נדיר וניתן retry.

Side effects אחרי commit: אם task נשלח לפני commit ו־worker מהיר קורא את הנתון, הוא עלול לא למצוא אותו. השתמש ב־transaction.on_commit(lambda: task.delay(id)). לדרישה אמינה יותר בין DB ל־broker השתמש ב־Transactional Outbox.

21. DRF לעומק — API Design

Serializer אחראי על boundary: parsing, validation וייצוג. הוא אינו חייב להכיל את כל ה־business workflow. ViewSet מתאם HTTP; service/use-case מבצע פעולה עסקית; model/DB אוכפים invariants.

class WorkoutCreateSerializer(serializers.ModelSerializer):
    class Meta:
        model = Workout
        fields = ["name", "performed_at", "duration_minutes"]

    def validate_duration_minutes(self, value):
        if not 1 <= value <= 600:
            raise serializers.ValidationError("Duration must be between 1 and 600")
        return value

class WorkoutViewSet(ModelViewSet):
    permission_classes = [IsAuthenticated, IsOwner]
    filter_backends = [DjangoFilterBackend, OrderingFilter]
    filterset_fields = ["performed_at"]
    ordering_fields = ["performed_at", "duration_minutes"]

    def get_queryset(self):
        return Workout.objects.visible_to(self.request.user).select_related("owner")

    def perform_create(self, serializer):
        serializer.save(owner=self.request.user)
  • Pagination: offset פשוט אך נהיה יקר ולא יציב בשינויים; cursor מתאים ל־feeds גדולים ודורש ordering יציב וייחודי.
  • Versioning: שינוי additive לרוב backward compatible; rename/removal דורש deprecation וגרסה.
  • Idempotency: ל־POST של payment/order שמור idempotency key ותוצאה תחת unique constraint.
  • Errors: envelope עקבי עם code יציב, message בטוח ו־request ID; אל תחשוף traceback.
  • Schema: הפק OpenAPI ובדוק אותו ב־CI כדי לזהות breaking changes.

22. Performance ו-Query Planning

אופטימיזציה מתחילה במספר queries, זמן query, rows שנסרקו וגודל response—not בתחושת בטן.

queryset = (
    Workout.objects
    .filter(owner=request.user)
    .select_related("owner")                 # FK / OneToOne באותו JOIN
    .prefetch_related("sets__exercise")      # many relation בשאילתה נוספת
    .only("id", "name", "performed_at", "owner__id")
)

print(queryset.explain(analyze=False))

select_related מתאים ליחס יחיד; prefetch_related מבצע שאילתה נפרדת ומחבר ב־Python. Serializer שמבצע query לכל row יוצר N+1 גם אם ה־view נראה נקי. בדוק query count ב־tests.

השתמש ב־bulk_create/bulk_update כשמתאים, אך זכור שהם יכולים לעקוף save() ו־signals. ‏iterator() מתאים לעיבוד dataset גדול. Cache הוא optimization עם invalidation policy; הוא אינו תיקון ל־query שגויה.

23. Async Django — המודל המדויק

Django תומך ב־ASGI וב־async views, וחלק הולך וגדל מה־ORM מספק פעולות async. אבל async מועיל רק כאשר כל מסלול ה־I/O אינו חוסם. Middleware סינכרוני או library חוסמת יכולים לגרום למעברים בין sync ל־async ולהקטין את התועלת.

async def status_view(request):
    async with httpx.AsyncClient(timeout=3) as client:
        response = await client.get("https://service.internal/health")
    return JsonResponse({"upstream": response.status_code})

Async אינו תחליף ל־Celery: view async עדיין שייכת לחיי request ועלולה להיחתך כשהלקוח/שרת מבטל. השתמש בה ל־concurrent I/O קצר. עבודה ארוכה, durable או retryable עוברת ל־queue. עבודה CPU-bound צריכה process/worker, לא coroutine.

24. Celery ו-Background Jobs אמינים

ברוב ה־brokers המסירה היא לפחות פעם אחת, ולכן task חייבת להיות idempotent. Worker עלול להשלים פעולה ולקרוס לפני acknowledgement—ואז אותה הודעה תגיע שוב.

    retry_jitter=True,
    max_retries=5,

def generate_report(report_id: int):
    report = Report.objects.get(id=report_id)
    if report.status == Report.Status.COMPLETED:
        return
    # ביצוע עם idempotency key מול ספק חיצוני
    ...
  • העבר IDs, לא model objects serialized.
  • קבע time limit ו־retry רק לשגיאות זמניות.
  • הגדר Dead Letter/failed-task workflow וניטור queue depth.
  • הפרד queues של משימות קצרות וכבדות כדי למנוע starvation.
  • אל תניח “exactly once”; אכוף uniqueness/state transition ב־DB.

25. Security ו-Hardening

  • CSRF: נדרש כשדפדפן שולח credential אוטומטית, במיוחד session cookie.
  • CORS: מדיניות browser, לא מנגנון authentication ולא הגנה על server-to-server.
  • IDOR: סנן queryset לפי המשתמש ובדוק object permission; אל תעשה get גלובלי ואז “תקווה”.
  • Mass assignment: קבע fields מפורשות; owner/role נקבעים מה־server.
  • Uploads: הגבל גודל וסוג, שנה שם, אחסן מחוץ לנתיב executable וסרוק לפי הסיכון.
  • SQL injection: ORM parameterizes values; ‏RawSQL/extra דורשים parameters ולעולם לא string interpolation.
  • Rate limit: throttling של DRF אינו בהכרח הגנת abuse קשיחה; שכבה חיצונית/Redis atomic נדרשת בסקייל.
  • Headers/cookies: HTTPS, Secure, HttpOnly, SameSite, HSTS והגדרות proxy נכונות.

26. Testing Strategy

אל תסתפק ב־status code. בדוק behavior, הרשאות, DB state, query count ו־side effects.

@pytest.mark.django_db
def test_user_cannot_read_another_users_workout(api_client, user_factory, workout_factory):
    owner = user_factory()
    attacker = user_factory()
    workout = workout_factory(owner=owner)
    api_client.force_authenticate(attacker)

    response = api_client.get(f"/api/workouts/{workout.id}/")

    assert response.status_code == 404

@pytest.mark.django_db
def test_list_has_bounded_query_count(api_client, django_assert_num_queries, workout_factory):
    workout_factory.create_batch(20)
    with django_assert_num_queries(3):
        api_client.get("/api/workouts/")

Factories עדיפות ל־fixtures ענקיים כשצריך data ממוקד. Mock בגבול חיצוני—email/provider/time—לא ב־ORM בכל unit. השתמש ב־TransactionTestCase או pytest מתאים כאשר באמת בודקים commit/locking; TestCase עוטף test ב־transaction ועלול להסתיר behavior.

27. Production Architecture

Client → CDN/WAF/Load Balancer → Gunicorn/Uvicorn → Django/DRF
↘ PostgreSQL   ↘ Redis   ↘ Object Storage
Broker → Celery Workers → providers
  • Readiness בודקת אם instance יכול לקבל traffic; liveness אם התהליך תקוע. אל תהפוך כל provider חיצוני לתנאי liveness.
  • Structured logs עם request ID, metrics ל־latency/error rate ו־tracing ל־DB/HTTP/tasks.
  • Graceful shutdown ו־worker timeouts תואמים ל־load balancer.
  • Migrations בשיטת expand/migrate/contract כדי שקוד ישן וחדש יעבדו יחד בזמן rolling deployment.
  • גיבויים אינם מספיקים עד שבודקים restore.
  • Static/media הם דברים שונים: static שייך לגרסת הקוד; user media לא נשמר בדיסק ephemeral של container.

28. פרויקט ותרגול מסכם

פרויקט: בנה Workout Tracking API שמתאים לשימוש האישי שלך. הוא יכלול custom user, workouts, exercises, sets, templates ומדדי התקדמות.

  1. כתוב ERD ו־invariants לפני models.
  2. הגדר constraints, indexes ו־custom QuerySets.
  3. בנה DRF API עם permissions ברמת object, filtering ו־cursor pagination.
  4. כתוב use case של “סיום אימון” בתוך transaction.
  5. שלח summary task עם on_commit וודא idempotency.
  6. מנע N+1 והוסף query-count test.
  7. הוסף OpenAPI, tests, Docker, PostgreSQL, Redis ו־CI.
  8. תעד threat model, failure modes ו־trade-offs.
Definition of Done: משתמש אינו יכול לקרוא או לשנות נתונים של אחר; כתיבה מקבילית אינה שוברת invariant; retries אינם יוצרים כפילויות; migrations תואמות deployment הדרגתי; tests מכסים domain, DB ו־API; ואתה מסוגל להסביר את זרימת הבקשה מה־socket ועד commit.

סיכום

Django אינו רק CRUD מהיר. שימוש מקצועי דורש להבין היכן נמצא כל invariant, איך ORM הופך ל־SQL, איך transactions מתנהגות תחת concurrency, כיצד DRF מגן על גבולות המערכת ואיך web workers, task workers, PostgreSQL ו־Redis משתפים פעולה. חזור לפרק הרלוונטי בזמן בניית הפרויקט—המטרה היא לא לשנן אלא לדעת לנתח.
