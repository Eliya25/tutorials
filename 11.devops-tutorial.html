DevOps ותשתית — המדריך המלא למפתח Backend

המשך לסדרה. עד עכשיו בנינו וכתבנו קוד; כאן לומדים איך לארוז אותו, לפרוס אותו, ולהריץ אותו בפרודקשן בצורה אמינה וחוזרת על עצמה.

הרעיון המרכזי: DevOps אינו אוסף פקודות לשנן — הוא שתי מטרות: reproducibility (שזה ירוץ אותו דבר בכל מקום) ו-automation (שבני אדם לא יעשו ידנית מה שמכונה יכולה). אתה לא צריך להיות DevOps engineer — צריך אוריינות עבודה. עברית להסבר, אנגלית למונחים ולפקודות.

1. מבוא: מה זה DevOps ובעיית "עובד אצלי במחשב"

DevOps הוא תרבות ופרקטיקות שמקרבות בין Dev (פיתוח) ל-Ops (תפעול) — כדי שקוד יעבור מ"נכתב" ל"רץ בפרודקשן" מהר, בבטחה, ובאופן חוזר. בשביל מפתח Backend זה אומר: לדעת לארוז את הקוד שלך, לאוטמט את הבנייה והבדיקות, ולפרוס בלי דרמה.

הבעיה שהכל מתחיל ממנה

"אבל זה עובד אצלי במחשב!" — המשפט הכי מתסכל בהיסטוריית התוכנה. הקוד רץ אצל המפתח ונכשל בשרת. למה? כי הסביבות שונות: גרסת Node אחרת, ספרייה חסרה, משתנה סביבה אחר, מערכת הפעלה שונה. כל ההבדלים הקטנים האלה מצטברים לכשלים.

כל DevOps בעצם מתקף סביב פתרון הבעיה הזו: איך גורמים לקוד לרוץ בדיוק אותו דבר בכל מקום — במחשב שלך, ב-CI, ובפרודקשן. התשובה המרכזית היא containers (Docker), שאורזים את הקוד יחד עם כל הסביבה שלו. זה הרעיון שיחזור לאורך כל המדריך.

שתי המטרות שמנחות הכל

  • Reproducibility — אותו input מייצר אותו output בכל מקום. אין הפתעות בין סביבות.
  • Automation — כל דבר חוזר (build, test, deploy) נעשה על ידי מכונה, לא ידנית. בני אדם עושים טעויות; אוטומציה עקבית.

המסגור הנכון: אל תלמד DevOps כרשימת כלים ("Docker, Kubernetes, Terraform"). למד אותו כפתרונות לבעיות: containers פותרים את "עובד אצלי", CI/CD פותר "שכחנו להריץ טסטים / פרסנו ידנית וטעינו", IaC פותר "אף אחד לא זוכר איך הוקמה התשתית". כשאתה מבין איזו בעיה כל כלי פותר — הכל מתחבר.

2. Linux ו-Shell — הבסיס

כמעט כל שרת בעולם רץ Linux. אתה לא צריך להיות sysadmin, אבל בלי היכרות בסיסית עם shell — אתה תקוע. זה הבסיס שהכל יושב עליו.

הפקודות שחייבים לדעת

# ניווט וקבצים
ls -la          # רשימת קבצים (כולל מוסתרים והרשאות)
cd /path        # מעבר תיקייה
pwd             # איפה אני
cat / less      # הצגת תוכן קובץ
grep "text" f   # חיפוש בתוך קבצים (זוכר מ-ripgrep?)
find . -name    # חיפוש קבצים

# תהליכים ומשאבים
ps aux          # תהליכים רצים
top / htop      # ניטור CPU/RAM חי
kill -9 PID     # הריגת תהליך
df -h           # מקום בדיסק
free -h         # זיכרון פנוי

# רשת (זוכר ממדריך Networking?)
curl / ping / netstat / lsof -i :3000

# הרשאות
chmod +x file   # הפיכה לניתן-להרצה
chown user file # שינוי בעלים
sudo command    # הרצה כ-root

מושגים חשובים

  • Pipes ו-redirection — | מעביר פלט של פקודה אחת לקלט של הבאה; > כותב לקובץ. למשל ps aux | grep node.
  • Environment variables — export KEY=value, נקראים ב-$KEY. קריטי לקונפיגורציה (פרק 13).
  • Permissions — read/write/execute למשתמש/קבוצה/כולם. מקור נפוץ ל-"permission denied".
  • SSH — ssh user@server להתחברות מאובטחת לשרת מרוחק. הדרך הסטנדרטית לגשת לשרתים.

מעשי: אתה לא צריך לשלוט ב-Linux ברמת מומחה — צריך לנוע בנוחות ב-shell, לקרוא logs, לבדוק תהליכים ומשאבים, ולהתחבר ב-SSH. ברגע שתעבוד עם Docker וענן, ה-shell יהיה הכלי היומיומי שלך. השקעה קטנה כאן משתלמת בכל שאר המדריך.

3. Docker — Images מול Containers

Docker הוא הכלי שפותר את "עובד אצלי". הוא אורז את האפליקציה יחד עם כל הסביבה שלה (runtime, ספריות, קונפיגורציה) ליחידה אחת שרצה אותו דבר בכל מקום. זה הכלי הכי חשוב במדריך הזה.

Container מול Virtual Machine

נקודה שחשוב להבין. VM מדמה מחשב שלם כולל מערכת הפעלה — כבד (גיגה-בייטים, דקות לעלייה). Container חולק את ה-kernel של המארח ומבודד רק את האפליקציה — קל (מגה-בייטים, שניות לעלייה):

Virtual MachineContainer
מכילOS מלארק האפליקציה + תלויות
גודלגיגה-בייטיםמגה-בייטים
זמן עלייהדקותשניות
בידודמלא (OS נפרד)ברמת התהליך (kernel משותף)

הקלילות הזו היא מה שהפך containers לסטנדרט — אפשר להריץ עשרות על מכונה אחת, לעלות ולרדת מיידית.

שלושת המושגים המרכזיים

  • Dockerfile — "מתכון": קובץ טקסט עם ההוראות איך לבנות את ה-image.
  • Image — התבנית הבנויה, לקריאה בלבד (immutable). כמו "class" בקוד.
  • Container — instance רץ של image. כמו "object" — instance של class.
Dockerfile → (docker build) → Image → (docker run) → Container
מתכון בנייה תבנית הרצה instance רץ

אנלוגיה שתעזור לך: Dockerfile הוא המתכון, Image הוא העוגה האפויה (אפשר לשכפל), Container הוא הפרוסה שאתה אוכל (instance רץ). מ-image אחד אפשר להריץ הרבה containers זהים — בדיוק מה שצריך ל-horizontal scaling מ-System Design.

4. Dockerfile ו-Multi-stage Builds

Dockerfile בסיסי ל-NestJS

FROM node:20-alpine          # image בסיס (Node 20, גרסת alpine קטנה)
WORKDIR /app                 # תיקיית העבודה בתוך ה-container

COPY package*.json ./        # מעתיקים קודם רק את package.json
RUN npm ci                   # מתקינים תלויות

COPY . .                     # מעתיקים את שאר הקוד
RUN npm run build            # בונים

EXPOSE 3000                  # מתעדים שה-app מאזין על 3000
CMD ["node", "dist/main.js"] # הפקודה שרצה כשה-container עולה

Layers ו-Caching — למה סדר השורות חשוב

נקודה שמשפרת דרמטית את זמני הבנייה. כל הוראה ב-Dockerfile יוצרת layer, ו-Docker מטמן layers — אם שורה לא השתנתה, הוא משתמש ב-cache במקום להריץ שוב. לכן מעתיקים קודם package.json ומריצים npm ci, ורק אז מעתיקים את הקוד:

אם היינו עושים COPY . . לפני npm ci, כל שינוי קוד קטן היה מבטל את ה-cache של התקנת התלויות — ו-npm ci היה רץ מחדש בכל build (איטי). בסדר הנכון, ה-layer של התלויות נשמר ב-cache כל עוד package.json לא השתנה. סדר השורות = מהירות ה-build.

Multi-stage Build — image רזה ל-production

טכניקה חשובה: שלב אחד בונה (עם כל כלי הבנייה), שלב שני מעתיק רק את התוצר הסופי ל-image נקי וקטן. זה מקטין את ה-image פי כמה ומשפר אבטחה (פחות כלים = פחות משטח תקיפה):

# שלב 1 — build (עם devDependencies וכלי build)
FROM node:20-alpine AS builder
WORKDIR /app
COPY package*.json ./
RUN npm ci
COPY . .
RUN npm run build

# שלב 2 — production (רק מה שצריך להרצה)
FROM node:20-alpine
WORKDIR /app
COPY package*.json ./
RUN npm ci --omit=dev              # רק production dependencies
COPY --from=builder /app/dist ./dist   # מעתיקים רק את התוצר מהשלב הקודם
EXPOSE 3000
CMD ["node", "dist/main.js"]

נקודה חשובה: הוסף .dockerignore (כמו .gitignore) שמחריג node_modules, .git, .env — כדי לא להעתיק אותם ל-image (מאט את ה-build ומסכן דליפת secrets). image רזה = deploy מהיר, פחות מקום, פחות פרצות.

5. Docker בפועל — Ports, Volumes, Env

הפקודות היומיומיות

docker build -t myapp .            # בונה image בשם myapp מה-Dockerfile
docker run -p 3000:3000 myapp      # מריץ, ממפה port
docker ps                          # containers רצים
docker logs <container>            # צפייה ב-logs
docker exec -it <container> sh      # כניסה לתוך container רץ (debug)
docker stop <container>             # עצירה
docker images                      # רשימת images

Port mapping

-p 3000:3000 ממפה port של המארח (משמאל) ל-port בתוך ה-container (מימין). בלי זה, ה-app מאזין בתוך ה-container אבל אף אחד מבחוץ לא יכול להגיע אליו. (זוכר ports ממדריך Networking?)

Volumes — נתונים ששורדים

Container הוא ephemeral — כשהוא נמחק, כל מה שבתוכו נעלם. זו בעיה ל-DB. Volume מחבר תיקייה מהמארח ל-container, כך שהנתונים שורדים:

docker run -v pgdata:/var/lib/postgresql/data postgres
#            └─ הנתונים של Postgres נשמרים ב-volume, שורדים מחיקת container

Environment variables

docker run -e DATABASE_URL=postgres://... -e NODE_ENV=production myapp
#           └─ מזריקים קונפיגורציה בזמן ריצה (פרק 13)

העיקרון: ה-image זהה בכל הסביבות; ה-env vars משנים את ההתנהגות. אותו image רץ ב-dev וב-production, רק עם משתני סביבה שונים. זה החלק של reproducibility — לא בונים image שונה לכל סביבה.

6. Docker Compose — סביבה מרובת-שירותים

אפליקציה אמיתית היא לא רק ה-app — היא app + Postgres + Redis. להריץ כל אחד ב-docker run נפרד זה כאב. Docker Compose מגדיר את כל השירותים בקובץ YAML אחד ומריץ את כולם בפקודה אחת. זה הכלי שישנה לך את הפיתוח המקומי.

# docker-compose.yml
version: "3.8"
services:
  app:
    build: .
    ports:
      - "3000:3000"
    environment:
      DATABASE_URL: postgres://user:pass@db:5432/mydb
      REDIS_URL: redis://cache:6379
    depends_on:
      - db
      - cache

  db:
    image: postgres:16
    environment:
      POSTGRES_USER: user
      POSTGRES_PASSWORD: pass
      POSTGRES_DB: mydb
    volumes:
      - pgdata:/var/lib/postgresql/data

  cache:
    image: redis:7

volumes:
  pgdata:
docker compose up      # מרים את הכל: app + db + cache
docker compose down    # מוריד הכל

שים לב ל-DATABASE_URL: ה-host הוא db — שם השירות. Compose יוצר רשת פנימית שבה השירותים מוצאים זה את זה לפי שם (service discovery מובנה). זה מחבר ישירות ל-DNS ממדריך Networking.

למה זה משנה לך יומיומית: Docker Compose הופך את הקמת סביבת הפיתוח מ"התקן Postgres, התקן Redis, הגדר, קווה שיעבוד" ל-docker compose up אחד. מפתח חדש בצוות מקים סביבה מלאה בדקה. וזו בדיוק אותה reproducibility — כולם רצים את אותה סביבה בדיוק. זה כנראה הדבר הראשון שכדאי לך ליישם בפרויקט NestJS שלך.

7. Container Registries

בנית image במחשב שלך. איך הוא מגיע לשרת? דרך container registry — "GitHub ל-images". דוחפים (push) לשם, והשרת/CI מושכים (pull).

docker tag myapp registry.example.com/myapp:1.0    # מתייגים עם כתובת וגרסה
docker push registry.example.com/myapp:1.0          # דוחפים לregistry
docker pull registry.example.com/myapp:1.0          # מושכים (בשרת)

Registries נפוצים: Docker Hub (הציבורי), GitHub Container Registry, ו-registries של הענן (AWS ECR, Google Artifact Registry).

Tags — נקודה חשובה

ה-tag (למשל :1.0) מזהה גרסה. אל תסתמך על :latest ב-production — הוא "זז" (מצביע כל פעם למשהו אחר), ואז אתה לא יודע איזו גרסה באמת רצה, ו-rollback הופך לניחוש. השתמש בגרסאות מפורשות (semantic version או git commit hash). זה חלק מ-reproducibility — לדעת בדיוק מה רץ.

8. CI/CD — אוטומציה של Build, Test, Deploy

זה הלב של ה-automation. CI/CD הוא pipeline אוטומטי שרץ בכל שינוי קוד: בונה, בודק, ומפרס — בלי מגע יד אדם.

הפירוק

  • CI (Continuous Integration) — בכל push, אוטומטית: build + הרצת טסטים + linting. תופס בעיות מוקדם, לפני merge. "אל תיתן לקוד שבור להיכנס".
  • CD (Continuous Delivery/Deployment) — אחרי ש-CI עבר, אוטומטית פורס ל-staging/production. "מה שעבר את הבדיקות — יוצא לאוויר".

שלבי pipeline טיפוסי

Push → [ Lint ] → [ Build ] → [ Test ] → [ Build Docker image ] → [ Push to registry ] → [ Deploy ]
        כל שלב חייב לעבור כדי להמשיך לבא. נכשל? עוצר ומודיע.

דוגמה — GitHub Actions

# .github/workflows/ci.yml
name: CI
on: [push]

jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: 20
      - run: npm ci
      - run: npm run lint
      - run: npm test
      - run: npm run build

בכל push ל-repo, GitHub מריץ את השלבים האלה אוטומטית. אם טסט נכשל — אתה (וכל הצוות) מקבלים התראה, וה-PR מסומן אדום. זה תופס באגים לפני שהם מגיעים ל-main.

למה זה קריטי בעידן ה-AI: כשחלק מהקוד נכתב בעזרת AI, CI/CD הופך לחשוב עוד יותר — הוא רשת הביטחון שמוודאת שקוד שנוצר (ואולי לא נבדק מספיק) עובר טסטים ו-linting לפני שהוא מגיע לפרודקשן. pipeline טוב הוא ה-code reviewer האוטומטי שלך. גם פרויקט אישי קטן ראוי ל-CI בסיסי — זה הרגל שמבדיל מפתח מקצועי.

9. Cloud — יסודות

כמעט אף אחד לא מריץ שרתים פיזיים בעצמו יותר. הענן (AWS, GCP, Azure) נותן תשתית on-demand. אתה לא צריך מומחיות בענן, אבל צריך להבין את המושגים ואת המפה.

ארבע קטגוריות המשאבים

קטגוריהמה זהדוגמאות (AWS)
Computeכוח עיבוד — שרתים, containers, functionsEC2, ECS, Lambda
Storageאחסון — קבצים, blocksS3, EBS
DatabaseDBs מנוהליםRDS (Postgres), DynamoDB, ElastiCache (Redis)
Networkרשת, LB, DNSVPC, ELB, Route 53

מודלי שירות — IaaS / PaaS / SaaS

כמה מהתשתית אתה מנהל מול כמה הספק:

  • IaaS (Infrastructure) — הספק נותן שרת גולמי (VM), אתה מנהל הכל מעליו. גמישות מלאה, אחריות מלאה. (EC2).
  • PaaS (Platform) — הספק מנהל את התשתית, אתה רק דוחף קוד. פחות שליטה, פחות כאב. (Heroku, Render, Railway, App Engine).
  • SaaS (Software) — מוצר מוכן (Gmail). לא רלוונטי לפריסה שלך.

Serverless (Lambda/Cloud Functions) — קצה ה-PaaS: אתה כותב פונקציה, הספק מריץ אותה on-demand ומחייב רק על זמן ריצה. אין שרת לנהל, scaling אוטומטי — אבל cold starts ומגבלות.

Regions ו-Availability Zones

ספקי הענן פרוסים ב-regions (אזורים גאוגרפיים — us-east, eu-central) שכל אחד מחולק ל-availability zones (datacenters נפרדים באותו אזור). פורסים על כמה AZs ל-high availability (זוכר redundancy מ-System Design?) — אם datacenter אחד נופל, האחרים ממשיכים. ובוחרים region קרוב למשתמשים ל-latency נמוך (זוכר ממדריך Networking?).

עצה למתחיל: אל תתחיל מ-Kubernetes על AWS גולמי — זה over-engineering. לפרויקט/סטארטאפ, PaaS כמו Render/Railway/Fly.io נותן לך deploy בדקות בלי לנהל תשתית. עבור ל-IaaS/K8s רק כשאתה באמת צריך את השליטה. אותו עיקרון מ-System Design: תתחיל פשוט, הוסף מורכבות כשהצורך מוכח.

10. אסטרטגיות Deployment

איך מוציאים גרסה חדשה בלי להפיל את השירות? (זוכר את ה-load balancer ו-health checks מ-System Design?) יש כמה אסטרטגיות, בסדר בטיחות עולה.

אסטרטגיהאיךtradeoff
Recreateמכבים ישן, מעלים חדשפשוט, אבל downtime
Rollingמחליפים instances בהדרגה, אחד-אחדללא downtime, אבל שתי גרסאות רצות במקביל זמנית
Blue-Greenסביבה חדשה מלאה (green) לצד הישנה (blue), מחליפים תעבורה במכהrollback מיידי, אבל דורש כפל משאבים
Canaryמפנים אחוז קטן מהתעבורה לגרסה החדשה, מגדילים בהדרגההכי בטוח, אבל מורכב

Rolling — ברירת המחדל

הנפוץ ביותר (וברירת המחדל של Kubernetes). מחליפים instance אחד בכל פעם: מורידים ישן, מעלים חדש, מוודאים שהוא בריא (health check), ורק אז ממשיכים לבא. בכל רגע יש instances בריאים שמשרתים — אין downtime.

Canary — הכי בטוח

מוציאים את הגרסה החדשה ל-5% מהמשתמשים, מנטרים (זוכר observability מ-System Design?). נראה טוב? מגדילים ל-25%, 50%, 100%. בעיה? מחזירים את ה-5% לגרסה הישנה — רק חלק קטן מהמשתמשים נפגע. זו הדרך להוציא שינויים מסוכנים בביטחון.

הקשר: כל האסטרטגיות האלה מסתמכות על health checks ו-stateless app servers (מ-System Design). זו הסיבה שדיברנו על stateless — בלי זה, אי אפשר להחליף שרתים חלק. וזו עוד סיבה ש-JWT מנצח session בהקשר הזה. הכל מתחבר.

11. Kubernetes — מתי ולמה

Kubernetes (מקוצר K8s) הוא ה-buzzword הכי גדול ב-DevOps — ומקור לכי הרבה over-engineering. נבין מה זה, ובעיקר מתי אתה באמת צריך אותו (רמז: פחות ממה שאתה חושב).

איזו בעיה K8s פותר

יש לך 50 containers רצים על 10 שרתים. מה קורה כשאחד קורס? מי מפזר עומס? איך עושים rolling deploy? איך מגדילים אוטומטית תחת עומס? לעשות את זה ידנית — בלתי אפשרי. Kubernetes הוא orchestrator — הוא מנהל containers בקנה מידה: פריסה, scaling, self-healing (מרים מחדש container שנפל), load balancing, ו-rolling updates. אתה מצהיר "אני רוצה 5 עותקים של האפליקציה", ו-K8s דואג שזה תמיד יתקיים.

המושגים המרכזיים (ברמת הבנה)

  • Pod — היחידה הקטנה ביותר, עוטף container אחד (או כמה קשורים). זה מה ש-K8s מריץ.
  • Deployment — מגדיר כמה pods לרוץ ואיזה image, ומנהל rolling updates ו-self-healing.
  • Service — נקודת גישה יציבה ל-pods (load balancing פנימי, כי pods עולים ויורדים).
  • Ingress — חושף שירותים החוצה (routing, TLS termination).
  • ConfigMap / Secret — קונפיגורציה וסודות (פרק 13).

K8s הוא declarative (בדיוק כמו SQL!): אתה כותב YAML שמתאר את המצב הרצוי, ו-K8s דואג להגיע אליו ולשמר אותו. לא "עשה X", אלא "אני רוצה שהמצב יהיה Y".

העצה הכי חשובה בפרק, ואולי במדריך: רוב הפרויקטים לא צריכים Kubernetes. הוא מורכב מאוד — עקומת למידה תלולה, overhead תפעולי כבד, וקל לפצוע את עצמך. הוא נועד לבעיה של קנה מידה גדול: הרבה שירותים, הרבה צוותים, הרבה תעבורה. לסטארטאפ או פרויקט בינוני — PaaS (Render/Railway/Fly), או ECS/Cloud Run פשוטים יותר, יתנו לך 90% מהערך ב-10% מהמורכבות. הכר את K8s ברמת מושגים (כדי לדבר עליו ולהבין ארכיטקטורות), אבל אל תמהר לאמץ אותו. זה בדיוק ה-over-engineering ש-System Design הזהיר מפניו.

12. Infrastructure as Code

איך מקימים תשתית בענן? אפשר ללחוץ בממשק הweb של AWS — אבל אז אף אחד לא זוכר מה נעשה, אי אפשר לשחזר, ואי אפשר לגרסן. Infrastructure as Code (IaC) פותר את זה: מגדירים את התשתית בקוד, מגורסן ב-git.

# Terraform — מתאר תשתית declaratively
resource "aws_instance" "web" {
  ami           = "ami-12345"
  instance_type = "t3.micro"
  tags = { Name = "web-server" }
}

terraform apply יוצר/מעדכן את התשתית כך שתתאים לקוד. היתרונות: reproducibility (מקימים סביבה זהה בפקודה אחת), version control (רואים בדיוק מי שינה מה ומתי), ו-code review לשינויי תשתית. Terraform הוא הכלי המוביל; יש גם Pulumi, CloudFormation.

שים לב שזה בדיוק אותו רעיון declarative של K8s ו-SQL — מתארים מצב רצוי, הכלי מגיע אליו. זה חוט מחשבה שחוזר בכל DevOps מודרני.

13. Secrets ו-Configuration

נושא קטן אבל קריטי לאבטחה. סיסמאות, API keys, DB credentials — איך מנהלים אותם?

הכללים

  • לעולם לא סודות בקוד / ב-git. secret שנכנס ל-git נשאר בהיסטוריה לנצח (גם אם מחקת). זו דליפה קלאסית.
  • Configuration ב-environment variables — לא בקוד. אותו image, קונפיג שונה לכל סביבה (זוכר מפרק 5? זה גם עיקרון 12-factor, פרק הבא).
  • Secrets ב-secret manager — כלים ייעודיים מצפינים ומנהלים גישה: AWS Secrets Manager, HashiCorp Vault, Doppler. הם גם מאפשרים rotation (החלפה תקופתית).
  • .env מקומי בלבד, ותמיד ב-.gitignore. בפרודקשן — לא .env אלא secret manager.

קשר למדריך Authentication: ה-JWT secret, ה-DB password, מפתחות ה-OAuth — כל אלה חייבים לחיות ב-secret manager או env vars, אף פעם בקוד. secret שדלף ל-repo ציבורי מנוצל תוך דקות על ידי בוטים שסורקים את GitHub. אם קרה — צריך לבטל (rotate) את הסוד מיד, לא רק למחוק את ה-commit.

14. The Twelve-Factor App

מתודולוגיה בת 12 עקרונות לבניית אפליקציות שקל לפרוס ולסקיילר בענן. היא מסכמת הרבה ממה שלמדנו כאן לעקרונות מנחים. אלה החשובים ביותר למפתח Backend:

  • Codebase — codebase אחד ב-version control, הרבה deploys ממנו.
  • Dependencies — הצהר על כל התלויות מפורשות (package.json), אל תסמוך על מה שמותקן במערכת.
  • Config — קונפיגורציה ב-environment, לא בקוד. (בדיוק פרק 13).
  • Backing services — DB, cache, queue הם משאבים מחוברים דרך URL — ניתנים להחלפה בלי שינוי קוד.
  • Build, release, run — הפרד בין בנייה, שחרור, והרצה (בדיוק ה-CI/CD).
  • Processes — האפליקציה היא תהליכים stateless. state חי ב-backing services (DB/Redis), לא בזיכרון התהליך. (זוכר כמה פעמים זה חזר?)
  • Port binding — האפליקציה חושפת את עצמה דרך port.
  • Concurrency — סקיילינג על ידי הרצת עוד תהליכים (horizontal).
  • Disposability — עלייה מהירה, כיבוי חלק (graceful shutdown). containers חייבים את זה.
  • Dev/prod parity — שמור סביבות דומות ככל האפשר. (בדיוק מה ש-Docker נותן).
  • Logs — התייחס ל-logs כזרם אירועים ל-stdout, לא כקבצים. (מרכזים מבחוץ — observability).

למה זה שווה לקרוא: 12-factor הוא הזיקוק של הרבה שנות ניסיון להרצת אפליקציות בענן. שים לב כמה מהעקרונות כבר פגשת בסדרה — stateless (Auth, System Design), config ב-env (כאן), backing services (Databases). זה החוט שקושר את הכל: אפליקציה שבנויה לפי 12-factor היא אפליקציה שקל לארוז ב-Docker, לפרוס ב-CI/CD, ולסקיילר. שווה לקרוא את המקור המלא (12factor.net).

15. Best Practices וטעויות נפוצות

  1. הבן את ה"why", לא רק פקודות. containers = reproducibility, CI/CD = automation, IaC = תשתית מגורסנת.
  2. Dockerize מוקדם. Docker Compose לפיתוח מקומי — הדבר הראשון ליישם. מבטל "עובד אצלי".
  3. Multi-stage builds + .dockerignore — images רזים, מהירים, בטוחים.
  4. גרסאות מפורשות ל-images, לא :latest בפרודקשן.
  5. CI מהיום הראשון — lint + test + build אוטומטי בכל push.
  6. סודות ב-secret manager / env, אף פעם ב-git.
  7. Config ב-environment, אותו image לכל הסביבות.
  8. אל תמהר ל-Kubernetes. תתחיל PaaS, עבור למורכבות רק כשצריך.
  9. אוטמט הכל שחוזר — deploy ידני = טעות אנוש מחכה לקרות.
  10. Health checks + graceful shutdown — הבסיס ל-deploys ללא downtime.

טעויות נפוצות

  • :latest בפרודקשן — אין לך מושג מה רץ, rollback הוא ניחוש.
  • secret ב-git — בהיסטוריה לנצח, דולף לבוטים תוך דקות.
  • Kubernetes לפרויקט קטן — over-engineering שהורג מהירות.
  • image ענק (בלי multi-stage / .dockerignore) — deploy איטי, פרצות.
  • deploy ידני — לא חוזר, מועד לטעויות, לא מגורסן.
  • state בזיכרון התהליך — שובר horizontal scaling ו-deploys.

16. תרגילים

1 — Dockerize. קח את פרויקט ה-NestJS שלך וכתוב לו Dockerfile עם multi-stage build ו-.dockerignore. בנה והרץ אותו מקומית.

2 — Docker Compose. כתוב docker-compose.yml שמרים את ה-app + Postgres + Redis יחד, עם volume ל-DB ו-env vars לחיבור. הרם עם docker compose up.

3 — CI Pipeline. הוסף .github/workflows/ci.yml שרץ בכל push: lint, test, build. גרום לו להיכשל בכוונה (טסט שבור) וראה את ההתראה.

4 — Deploy אמיתי. פרוס את האפליקציה ל-PaaS (Render/Railway/Fly.io) — חבר את ה-repo, הגדר env vars, וראה אותה חיה באוויר. (בלי Kubernetes!)

5 — אסטרטגיית Deploy. תאר איך היית מוציא שינוי מסוכן (שינוי סכמת DB) בבטחה — איזו אסטרטגיה, ואיך זה מתחבר ל-expand-contract migrations ממדריך Databases.

6 — Secrets. קח פרויקט עם secret ב-.env, ודא שהוא ב-.gitignore, ותאר איך היית מנהל אותו בפרודקשן.

סיכום — מה הלאה

שני דברים לקחת: DevOps הוא reproducibility + automation, לא כלים לשנן — כל כלי פותר בעיה ספציפית (Docker = "עובד אצלי", CI/CD = טעות אנוש, IaC = תשתית לא-מגורסנת). והשני, שחוזר מ-System Design: תתחיל פשוט. Docker Compose לפיתוח, CI בסיסי, PaaS ל-deploy — לפני Kubernetes ו-Terraform. over-engineering בתשתית הורג מהירות בדיוק כמו בארכיטקטורה.

שים לב איך הכל התחבר: stateless מ-Auth ו-System Design הוא הבסיס ל-deploys; ports ו-DNS מ-Networking הם איך containers מתקשרים; migrations מ-Databases נפגשות עם deployment strategies. DevOps הוא השכבה שמפעילה את כל מה שבנינו.

הצעד הבא: קח את פרויקט ה-NestJS שלך ועבור את תרגילים 1–4 — Dockerize, Compose, CI, deploy אמיתי. פרויקט אחד שעובר את כל המסלול מלמד יותר מכל תיאוריה.
