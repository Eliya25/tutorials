1 מפת הדרכים — מה זה מה

לפני שצוללים, חשוב להבין שיש כמה "דלתות" שונות לאותו מוח:

מוצרמה זהמתי להשתמש
Claude.ai (אתר / אפליקציה)צ'אט רגיל עם Claude, כולל Projects, Artifacts וחיבור Connectorsשאלות, כתיבה, ניתוח קבצים, מחקר
Claude Codeכלי CLI (טרמינל) שנותן ל-Claude גישה לקבצים, לטרמינל ול-Git שלך. הוא קורא, כותב, מריץ טסטים ועושה קומיטיםפיתוח: פיצ'רים, באגים, רפקטורינג, אוטומציות
Coworkמצב באפליקציית הדסקטופ — כמו Claude Code אבל למי שלא רוצה טרמינל. עובד על תיקיות, יוצר קבצים, מריץ Skillsעבודה עם מסמכים, אקסלים, מצגות, אוטומציות אישיות
Claude APIגישה תכנותית למודלים (claude-sonnet-5, claude-opus-5 וכו')כשבונים מוצר משלך על Claude

ארבעת מנגנוני ההרחבה — בשורה אחת כל אחד

  • CLAUDE.md — קובץ הוראות קבוע שנטען בתחילת כל שיחה. "החוקים של הבית".
  • MCP — פרוטוקול שמחבר את Claude לכלים חיצוניים (DB, Slack, GitHub, Notion...). "הידיים".
  • Skills — תיקיות עם הוראות למשימה ספציפית, שנטענות רק כשצריך. "ספר המתכונים".
  • Plugins — חבילה שאורזת Skills + Agents + Hooks + MCP ביחד, להתקנה ולשיתוף. "האריזה".
העיקרון החשוב ביותר במדריך CLAUDE.md נטען תמיד ושורף קונטקסט בכל שיחה. Skill נטען רק כשרלוונטי. לכן: מה שצריך תמיד → CLAUDE.md (וקצר!). מה שצריך לפעמים → Skill. מה שחייב לקרות בכל מקרה (למשל lint לפני קומיט) → Hook, כי הוראות טקסט הן המלצה ולא אכיפה.

2 Claude Code — התקנה ועבודה יומיומית

התקנה והרצה ראשונה

# התקנה (Windows PowerShell / macOS / Linux)
npm install -g @anthropic-ai/claude-code

# נכנסים לתיקיית הפרויקט ומריצים
cd my-project
claude

# בהרצה ראשונה: התחברות עם חשבון Claude (Pro/Max) או API key

צורות הרצה שימושיות

claude                          # סשן אינטראקטיבי רגיל
claude "תקן את הבאג בלוגין"      # מתחיל סשן עם משימה
claude -p "מה עושה הקובץ הזה?"   # מצב headless: תשובה ויציאה (טוב לסקריפטים)
claude -c                       # ממשיך את השיחה האחרונה
claude --resume                 # בוחר שיחה קודמת מרשימה
claude --add-dir ../shared-lib  # נותן גישה לתיקייה נוספת

מצב תכנון (Plan Mode)

לוחצים Shift+Tab כדי לעבור בין מצבים. במצב Plan, קלוד רק קורא ומתכנן — לא נוגע בקבצים — עד שמאשרים את התוכנית. כלל אצבע: כל משימה שנוגעת ביותר מ-2–3 קבצים מתחילים ב-Plan Mode.

שגרת עבודה מומלצת למשימה 1. /clear (מתחילים נקי) → 2. Plan Mode + תיאור המשימה → 3. מאשרים תוכנית → 4. קלוד מבצע ומריץ טסטים → 5. סוקרים diff → 6. מבקשים קומיט. אם קלוד טעה פעמיים באותו דבר — זה סימן שחסרה שורה ב-CLAUDE.md.

3 איך לדבר עם קלוד — הפרק שהכי משפיע על התוצאות

רוב ההבדל בין מי שמקבל תוצאות מעולות למי שמתוסכל הוא לא הכלים — זה ניסוח המשימה וניהול הסשן. ארבעה עקרונות:

עיקרון 1: משימה קטנה, ספציפית, עם קריטריון הצלחה

❌ פרומפט חלש✅ פרומפט חזק
"תשפר את הקוד""תעשה רפקטור ל-userService.ts: תוציא את הלוגיקה של הוולידציה לפונקציות נפרדות. אל תשנה התנהגות — כל הטסטים הקיימים צריכים לעבור"
"יש באג בלוגין, תתקן""כשמזינים אימייל עם אות גדולה, הלוגין נכשל עם 401. השגיאה מגיעה מ-auth/login.ts. תמצא את הסיבה, תציע תיקון, ותוסיף טסט שמכסה את המקרה"
"תבנה מערכת הרשאות"לפרק ל-3–4 משימות: "שלב 1: תוסיף שדה role למודל User עם מיגרציה. בלי לגעת ב-API עדיין"

נוסחה לפרומפט טוב: מה לעשות + איפה (קבצים) + מה אסור לשבור + איך נדע שהצליח.

עיקרון 2: תן הקשר, אל תסמוך על ניחוש

  • הדבק שגיאות מלאות כלשונן — stack trace שלם, לא "יש שגיאה".
  • הפנה לקבצים ספציפיים: @src/api/handlers/auth.ts (תיוג @ מצרף את הקובץ לשיחה).
  • ציין אילוצים מראש: "בלי ספריות חדשות", "חייב לתמוך ב-Node 18".

עיקרון 3: דע מתי לעצור סשן

זו הטעות הנפוצה ביותר: להתווכח עם קלוד חמישה סיבובים כשהסשן כבר "התלכלך" מניסיונות כושלים. הקונטקסט מלא בקוד שגוי ובכיוונים מתים, וכל תשובה נבנית על הזבל הזה.

כלל שני התיקונים אם אחרי שני ניסיונות תיקון קלוד עדיין לא שם — עצור. /clear, ונסח מחדש את המשימה עם מה שלמדת: "ניסיתי X, זה נכשל בגלל Y. הבעיה האמיתית היא כנראה Z. תתחיל מ...". סשן נקי עם פרומפט חכם יותר מנצח סשן ארוך ומבולגן כמעט תמיד. באמצע ריצה אפשר ללחוץ Esc כדי לעצור את קלוד ולתקן כיוון.

עיקרון 4: סגור את הלולאה — אמת ולמד

  • בסוף כל משימה: "תריץ את הטסטים ותראה לי שהכל עובר". אל תסמוך על "סיימתי".
  • סקור את ה-diff לפני קומיט. אם משהו לא ברור — "למה שינית את X?"
  • כל תיקון שנתת פעמיים → "תוסיף ל-CLAUDE.md: ..." או "תזכור ש..." (נשמר ב-Auto Memory). ככה הסשן הבא מתחיל חכם יותר.

תבנית מוכנה להעתקה

המשימה: [מה לעשות, במשפט אחד]
קבצים רלוונטיים: @path/to/file1 @path/to/file2
הקשר: [למה, מה כבר ניסיתי, שגיאות מלאות]
אילוצים: [מה אסור לשבור / לשנות]
הצלחה = [טסטים עוברים / התנהגות X קורית]
תתחיל בתוכנית קצרה לפני שאתה נוגע בקוד.

4 פרויקט חדש מאפס — ומה להכניס לקלוד

פרויקט קיים מתחילים עם /init. פרויקט מאפס זה סיפור אחר: אין קוד לסרוק, ולכן ההצלחה נקבעת לפני שנכתבת שורת קוד. הטעות הקלאסית: "תבנה לי אפליקציה ל-X" בפרומפט אחד — מקבלים 40 קבצים שאי אפשר לתחזק ולא מבינים.

שלב 0: מסמך אפיון (SPEC) — קודם מדברים, אחר כך בונים

את האפיון הכי טוב לעשות בצ'אט רגיל (Claude.ai) לפני שפותחים את הטרמינל: מתארים את הרעיון, מבקשים מקלוד לאתגר אותו ולשאול שאלות, ומגבשים ביחד מסמך. את התוצאה שומרים כ-SPEC.md — הוא יהיה מקור האמת של הפרויקט.

מה חייב להיות ב-SPEC:

  • מה המוצר עושה — 3–5 משפטים, ומה הוא לא עושה בגרסה ראשונה.
  • Stack — שפה, פריימוורק, DB, ספריות עיקריות. אם אתה לא בטוח — תבקש מקלוד להשוות 2–3 אפשרויות לפני שמתחילים, לא באמצע.
  • מודל הנתונים — הישויות המרכזיות והקשרים ביניהן.
  • אבני דרך — פירוק ל-4–8 שלבים שכל אחד מסתיים במשהו שרץ ואפשר לבדוק.

שלב 1: שלד + תשתית (סשן ראשון)

mkdir my-app && cd my-app && git init
claude

# הפרומפט הראשון:
"קרא את @SPEC.md. הקם שלד פרויקט לפי ה-stack שמוגדר שם:
מבנה תיקיות, קונפיגורציה, linter, framework לטסטים, README קצר,
ו-CLAUDE.md עם פקודות ה-build/test והקונבנציות שקבענו.
בלי לוגיקה עסקית עדיין. בסוף — ודא ש'npm test' רץ (גם אם ריק) ועשה קומיט ראשון."
  • CLAUDE.md נוצר מהיום הראשון — לא מחכים ל-/init. כל החלטה מהאפיון (סטאק, קונבנציות) נכנסת אליו מיד, כדי שכל סשן עתידי יתחיל איתה.
  • git מהקומיט הראשון — רשת הביטחון שלך. קלוד הרס משהו? git checkout וממשיכים.
  • טסטים מהשלד — תשתית טסטים ריקה ביום 1 עולה 5 דקות. להוסיף טסטים לפרויקט קיים בלעדיה — ימים.

שלב 2: לולאת אבני דרך

כל אבן דרך = סשן (או כמה): /clear → "קרא את @SPEC.md ו-@CLAUDE.md. אנחנו באבן דרך 3: [תיאור]. תציג תוכנית" → אישור → ביצוע → טסטים → diff → קומיט → עדכון סטטוס ב-SPEC. חתיכות אנכיות (פיצ'ר שלם מקצה לקצה, גם אם מינימלי) עדיפות על שכבות רוחביות ("כל המודלים, אחר כך כל ה-API").

דוגמה ל-CLAUDE.md טוב

# MyApp

## Commands
- Build: `npm run build`
- Test: `npm test` (run before every commit)
- Single test: `npm test -- --grep "name"`

## Architecture
- API handlers live in `src/api/handlers/`
- DB access ONLY through `src/db/repo.ts` — never raw SQL in handlers

## Rules
- TypeScript strict mode, no `any`
- 2-space indentation
- Commit messages in English, conventional commits format

כללי כתיבה שמשפיעים באמת

  • קצר: יעד — מתחת ל-200 שורות. קובץ ארוך = פחות ציות ויותר טוקנים בכל שיחה.
  • ספציפי וניתן לבדיקה: "הרץ npm test לפני קומיט" ולא "תבדוק את הקוד".
  • בלי סתירות: שתי הוראות סותרות = קלוד יבחר אחת אקראית.
  • זה לא אכיפה: CLAUDE.md הוא הקשר, לא חוק. מה שחייב לקרות תמיד — עושים כ-Hook.

- Use the standard error response format

Auto Memory — הזיכרון שקלוד כותב לעצמו

מופעל כברירת מחדל. קלוד שומר לעצמו תובנות (פקודות build שעבדו, דפוסי דיבוג) ב-~/.claude/projects/<project>/memory/. ה-200 שורות הראשונות של MEMORY.md נטענות בכל שיחה. הכל markdown רגיל — /memory מאפשר לעיין, לערוך ולמחוק. כשאומרים לקלוד "תזכור ש..." — זה נשמר לשם.

ההוראות לא נשמרות אחרי /compact? רק CLAUDE.md של שורש הפרויקט נטען מחדש אוטומטית אחרי compact. הוראות שנאמרו רק בשיחה — נעלמות. מה שחשוב לך לאורך זמן, תכניס לקובץ.

6 MCP — חיבור Claude לכלים חיצוניים

Model Context Protocol הוא תקן פתוח שנותן לקלוד כלים (tools) מול מערכות חיצוניות: לשאול DB, לקרוא טיקטים ב-Jira, לשלוח הודעות Slack, לקרוא דפי Notion ועוד. שרת MCP = תוכנה קטנה שחושפת כלים כאלה.

שלושה סוגי חיבור (Transports)

סוגמה זהמתי
httpשרת מרוחק בענן, לרוב עם OAuthשירותי SaaS: Notion, Sentry, GitHub, Stripe
sseשרת מרוחק בפרוטוקול ישן יותררק אם השירות תומך רק בזה (Asana)
stdioתהליך שרץ מקומית אצלךDB מקומי, קבצים, כלים בהתקנת npx

הפקודות המרכזיות

# הוספת שרת HTTP מרוחק (הכי נפוץ)
claude mcp add --transport http notion https://mcp.notion.com/mcp

# הוספה עם header של אימות
claude mcp add --transport http github https://api.githubcopilot.com/mcp/ \
  --header "Authorization: Bearer YOUR_GITHUB_PAT"

# שרת מקומי (stdio) עם משתנה סביבה
claude mcp add --env AIRTABLE_API_KEY=YOUR_KEY --transport stdio airtable \
  -- npx -y airtable-mcp-server

# ניהול
claude mcp list        # רשימה + סטטוס חיבור (Connected / Needs auth / Failed)
claude mcp get notion  # פרטים על שרת
claude mcp remove notion

אחרי ההוספה, בתוך הסשן מריצים /mcp כדי לבדוק סטטוס ולהשלים אימות OAuth אם צריך.

Scopes — איפה הקונפיגורציה נשמרת

Scopeפקודהמי רואה
local (ברירת מחדל)--scope localרק אתה, רק בפרויקט הזה
project--scope projectכל הצוות — נשמר ב-.mcp.json בשורש הפרויקט (נכנס לגיט)
user--scope userאתה, בכל הפרויקטים במחשב

דוגמת .mcp.json לצוות

{
  "mcpServers": {
    "sentry": {
      "type": "http",
      "url": "https://mcp.sentry.dev/mcp"
    },
    "db": {
      "type": "stdio",
      "command": "npx",
      "args": ["-y", "@bytebase/dbhub", "--dsn", "${DB_DSN}"]
    }
  }
}

אפשר להשתמש ב-${VAR} ובברירת מחדל ${VAR:-default} כדי לא לשמור סודות בגיט.

אבטחה — שלושה כללים 1. מתקינים רק שרתי MCP ממקורות מהימנים (התחילו מה-Anthropic Directory). 2. שרת MCP יכול להחזיר טקסט זדוני שמנסה לתמרן את קלוד (prompt injection) — היזהרו במיוחד משרתים שמושכים תוכן חיצוני. 3. טוקנים שמים במשתני סביבה, לא בקבצים שנכנסים לגיט.

MCP ב-Claude.ai (בלי טרמינל)

באתר ובאפליקציה זה נקרא Connectors: Settings ← Connectors ← Browse. אותם שרתים, ממשק גרפי. ב-Cowork הם זמינים אוטומטית אחרי חיבור.

7 Skills — הוראות עבודה שנטענות לפי הצורך

Skill = תיקייה עם קובץ SKILL.md (ואופציונלית סקריפטים וקבצי עזר). בניגוד ל-CLAUDE.md, ה-Skill נטען לקונטקסט רק כשמפעילים אותו — ידנית עם /skill-name או אוטומטית כשקלוד מזהה שהוא רלוונטי (לפי ה-description).

איפה Skills חיים

היקףמיקוםזמין ב...
אישי~/.claude/skills/<name>/SKILL.mdכל הפרויקטים שלך
פרויקט.claude/skills/<name>/SKILL.mdהפרויקט (משותף בגיט)
פלאגיןplugin/skills/<name>/SKILL.mdאיפה שהפלאגין מותקן, בשם /plugin:name

שם התיקייה = שם הפקודה: .claude/skills/deploy-staging/ יוצר /deploy-staging. שינויים נקלטים תוך כדי סשן, בלי restart.

דוגמה מלאה — Skill לקומיטים

---
description: Create a git commit following team conventions.
  Use when the user asks to commit changes.
disable-model-invocation: true
allowed-tools: Bash(git add *) Bash(git commit *) Bash(git status *) Bash(git diff *)
---

# Commit Skill

1. Run `git status` and `git diff --staged` to review changes
2. Write a conventional commit message: `type(scope): summary`
3. Types: feat / fix / refactor / docs / test / chore
4. Subject under 70 chars, in English
5. Never use `git add -A` — stage only relevant files

שדות ה-Frontmatter החשובים

שדהמה עושה
descriptionהכי חשוב! לפי זה קלוד מחליט מתי להפעיל אוטומטית. לכתוב מה הכלי עושה + מתי להשתמש בו
disable-model-invocation: trueרק אתה יכול להפעיל (עם /name). חובה לפעולות עם תופעות לוואי: deploy, commit, שליחת הודעות
allowed-toolsמאשר מראש כלים ספציפיים — בלי חלונות אישור באמצע
context: forkמריץ את ה-Skill ב-subagent נפרד, בלי לזהם את השיחה הראשית

ארגומנטים

---
description: Fix a GitHub issue by number
disable-model-invocation: true
---
Fix GitHub issue #$ARGUMENTS.
First read the issue with `gh issue view $ARGUMENTS`, then plan the fix.

הפעלה: /fix-issue 123. יש גם $1, $2 לארגומנטים נפרדים.

מתי Skill ומתי CLAUDE.md?

  • הוראה שרלוונטית לכל אינטראקציה (סגנון קוד, פקודת build) → CLAUDE.md.
  • תהליך רב-שלבי שרלוונטי לפעמים (דוח שבועי, יצירת migration, code review לפי צ'קליסט) → Skill.
  • ב-Claude.ai ו-Cowork אפשר להעלות Skills דרך Settings ← Capabilities — אותו פורמט SKILL.md בדיוק.

8 Plugins — אריזה ושיתוף

Plugin אורז בחבילה אחת: Skills, Agents (סוכני משנה), Hooks, שרתי MCP ואפילו שרתי LSP. מתקינים פעם אחת — מקבלים הכל. זה הפתרון כשרוצים לשתף סטאפ עם צוות או קהילה.

התקנת פלאגינים קיימים

# בתוך סשן — פותח את מנהל הפלאגינים (מרקטפלייס רשמי מובנה)
/plugin

# הוספת מרקטפלייס הקהילה והתקנה ממנו
/plugin marketplace add anthropics/claude-plugins-community
/plugin install some-plugin@claude-community

מבנה פלאגין

my-plugin/
├── .claude-plugin/
│   └── plugin.json        # המניפסט — רק הוא יושב בתיקייה הזאת!
├── skills/
│   └── code-review/
│       └── SKILL.md       # יהפוך ל-/my-plugin:code-review
├── agents/                # הגדרות סוכנים
├── hooks/
│   └── hooks.json         # אוטומציות על אירועים
└── .mcp.json              # שרתי MCP שמגיעים עם הפלאגין

plugin.json מינימלי

{
  "name": "my-plugin",
  "description": "Team workflow toolkit",
  "version": "1.0.0",
  "author": { "name": "Eliya" }
}

פיתוח ובדיקה מקומית

claude plugin init my-tool        # מייצר שלד מוכן ב-~/.claude/skills/my-tool
claude --plugin-dir ./my-plugin   # טוען פלאגין מקומי לבדיקה
/reload-plugins                   # קולט שינויים בלי לצאת
claude plugin validate ./my-plugin # ולידציה לפני שיתוף
הטעות הנפוצה ביותר לשים את skills/ או hooks/ בתוך .claude-plugin/. לא! רק plugin.json יושב שם. כל שאר התיקיות — בשורש הפלאגין.

דוגמת Hook בתוך פלאגין

Hook רץ תמיד כשהאירוע קורה — לא תלוי בשיקול דעת של קלוד. למשל, lint אוטומטי אחרי כל עריכה:

{
  "hooks": {
    "PostToolUse": [
      {
        "matcher": "Write|Edit",
        "hooks": [{ "type": "command",
          "command": "jq -r '.tool_input.file_path' | xargs npm run lint:fix" }]
      }
    ]
  }
}

סדר פעולות מומלץ לפרויקט חדש

  1. claude בתיקיית הפרויקט ← /init ליצירת CLAUDE.md.
  2. עוברים על ה-CLAUDE.md שנוצר, מקצרים ומוסיפים את מה שקלוד לא יכול לגלות לבד (החלטות, מלכודות).
  3. מחברים MCP רק למה שבאמת צריך (כל שרת = עוד כלים בקונטקסט).
  4. אחרי שבוע עבודה: כל תיקון שחזרת עליו פעמיים → שורה ב-CLAUDE.md. כל תהליך שחזרת עליו פעמיים → Skill.
  5. כשהסטאפ מתייצב ורוצים לשתף → אורזים כ-Plugin.

10 תרגיל: השעה הראשונה שלך

קריאת המדריך לא יוצרת מיומנות — ביצוע כן. פתח פרויקט אמיתי (לא דוגמה) והרץ את המסלול הזה פעם אחת מהתחלה לסוף. סמן לעצמך כל שלב.

זמןמה עושיםמה לומדים
0–10 דק'התקנה, cd לפרויקט, claude, ואז /init. פתח את ה-CLAUDE.md שנוצר, מחק מה שמיותר, הוסף שורה אחת שקלוד לא יכול לדעת לבד (למשל החלטה ארכיטקטונית)Setup + זיכרון פרויקט
10–20 דק'שאל שאלה על הקוד שלך: "תסביר איך עובד הפלואו של [פיצ'ר], אילו קבצים מעורבים ובאיזה סדר". בדוק אם הוא צדקלתת לקלוד לחקור לבד — ולכייל כמה לסמוך עליו
20–35 דק'בחר באג קטן או שיפור אמיתי. Shift+Tab ל-Plan Mode, נסח לפי התבנית מפרק 3 (כולל "הצלחה ="), אשר את התוכנית, תן לו לבצע, בקש שיריץ טסטים, סקור diff, בקש קומיטמחזור העבודה המלא — לב העניין
35–45 דק'צור Skill אישי ראשון: mkdir -p ~/.claude/skills/explain, כתוב SKILL.md שמסביר קוד בעברית פשוטה עם דיאגרמה. הפעל: /explain @somefileSkills זה 5 דקות עבודה, לא פרויקט
45–55 דק'חבר שרת MCP אחד שרלוונטי לך (למשל claude mcp add --transport http github ... מפרק 6), הרץ /mcp לאימות, ובקש משהו שדורש אותו: "מה ה-issues הפתוחים שלי?"חיבור לעולם החיצוני
55–60 דק'סיכום: הרץ /context וראה מה טעון. תקן משהו שקלוד עשה לא לטעמך ואמור לו "תזכור ש-...". סגור עם /clearניהול קונטקסט + למידה מתמשכת
אחרי השעה הזאת יש לך: CLAUDE.md אמיתי, קומיט ראשון שקלוד כתב, Skill אחד, שרת MCP אחד, והרגל לסקור diff. זה 80% ממה שמשתמש מיומן עושה ביום-יום. השאר (Plugins, Hooks, Subagents) מוסיפים כשמרגישים צורך — לא לפני.

11 תקלות נפוצות וטיפים מתקדמים

תקלות נפוצות

סימפטוםאבחון וטיפול
קלוד מתעלם מ-CLAUDE.md/context — לבדוק שהקובץ בכלל נטען. אם כן: ההוראה כנראה מעורפלת או סותרת אחרת. לנסח ספציפי. אם זה קריטי — להפוך ל-Hook
שרת MCP לא עובדclaude mcp list — לראות סטטוס. Needs authentication ← להריץ /mcp ולהשלים OAuth. Failed ← לבדוק URL וטוקן
Skill לא מופעל אוטומטיתה-description חלש. לכתוב בו גם מה הכלי עושה וגם מתי להשתמש ("Use when...")
פלאגין לא נטען/plugin ← טאב Errors. לרוב: תיקיות בתוך .claude-plugin/ בטעות
הקונטקסט מתמלא מהר/context לזהות מה שורף. CLAUDE.md ארוך מדי? לפצל ל-rules עם paths או ל-Skills. ו-/clear בין משימות

טיפים מתקדמים

  • Headless לאוטומציה: claude -p "..." בתוך סקריפטים ו-CI. עם --output-format json מקבלים פלט מובנה.
  • Subagents: מגדירים סוכנים ייעודיים ב-.claude/agents/ (למשל code-reviewer עם כלי קריאה בלבד) — הם רצים בקונטקסט נפרד ומחזירים רק מסקנה.
  • שאלות על Claude Code לקלוד עצמו: פשוט לשאול בתוך הסשן — "איך אני מגדיר hook שרץ לפני קומיט?" — הוא מכיר את התיעוד של עצמו.
  • עלויות: /cost מראה צריכת טוקנים בסשן (למשתמשי API). למנויי Pro/Max זה כלול במנוי.
  • תיעוד רשמי: code.claude.com/docs — המקור המלא והעדכני.
