1. מבוא: למה Data Modeling הוא ההחלטה הכי חשובה

אפשר לתקן קוד גרוע ב-refactor. אפשר להחליף שרת. אבל schema גרועה עם מיליוני שורות עליה — כמעט בלתי אפשרית לתקן בלי migration מסוכן וכואב. זו ההחלטה הכי יקרה לשנות בדיעבד, וזו הסיבה ש-data modeling הוא המיומנות הכי חשובה בעבודה עם DBs — יותר מכתיבת queries חכמות.

מה זה data modeling

Data modeling הוא התהליך של להחליט איך לייצג את הנתונים של הבעיה שלך בטבלאות/מסמכים: אילו entities יש, אילו תכונות, ואיך הם קשורים. זה הגשר בין "העולם האמיתי" (משתמשים, הזמנות, מוצרים) ל"סכמה ב-DB".

הכלל המנחה

נקודה קריטית שמפרידה בין SQL ל-NoSQL: ב-SQL אתה מודל לפי מבנה הנתונים (מה ה-entities והקשרים ביניהם), ומאמין שה-DB יטפל בכל query עתידי דרך JOINs. ב-NoSQL אתה מודל לפי דפוסי הגישה (אילו queries תריץ), ומעצב את הנתונים כדי לשרת אותם ישירות. זה הבדל תפיסתי מהותי — נחזור אליו בפרק 8. הבנתו היא מחצית מהקרב.

2. Data Modeling ו-ER — Entities, Attributes, Relationships

המודל הרלציוני מתחיל בשלושה מושגים. חשוב עליהם לפני שאתה כותב CREATE TABLE.

  • Entity — "דבר" בעולם שאתה עוקב אחריו: User, Order, Product. הופך לרוב לטבלה.
  • Attribute — תכונה של entity: ל-User יש name, email, age. הופך לעמודה.
  • Relationship — קשר בין entities: User מבצע Orders. הופך ל-foreign key או לטבלת קישור.

שלושת סוגי הקשרים — הליבה של המודל

One-to-One (1:1)

שורה אחת קשורה לכל היותר לשורה אחת. למשל User ↔ UserProfile. לרוב אפשר לאחד לטבלה אחת; מפרידים כשחלק מהשדות נדירים/כבדים או מסיבות אבטחה.

One-to-Many (1:N) — הנפוץ ביותר

שורה אחת קשורה להרבה. User אחד → הרבה Orders. המימוש: FK בצד ה"רבים":

-- ה-FK תמיד יושב בצד ה"many":
CREATE TABLE orders (
  id       BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  user_id  INT NOT NULL REFERENCES users(id),   -- FK כאן, בצד ה-many
  total    NUMERIC(10,2)
);

Many-to-Many (M:N)

הרבה להרבה. Students ↔ Courses (סטודנט בכמה קורסים, קורס עם כמה סטודנטים). אי אפשר לייצג עם FK יחיד — חייבים junction table (טבלת קישור) באמצע:

CREATE TABLE students ( id INT PRIMARY KEY, name TEXT );
CREATE TABLE courses  ( id INT PRIMARY KEY, title TEXT );

-- טבלת הקישור — כל שורה היא "סטודנט X רשום לקורס Y":
CREATE TABLE enrollments (
  student_id INT REFERENCES students(id),
  course_id  INT REFERENCES courses(id),
  enrolled_at TIMESTAMPTZ DEFAULT now(),
  PRIMARY KEY (student_id, course_id)   -- composite PK מונע כפילויות
);

שים לב: ל-junction table אפשר להוסיף תכונות משלה (כמו enrolled_at) — כי הקשר עצמו הוא ישות עם מידע.

ER Diagram

לפני כתיבת סכמה, מציירים Entity-Relationship diagram — תרשים של הטבלאות והקשרים. גם סקיצה על נייר עוזרת לתפוס בעיות מוקדם. הסימון הנפוץ הוא "crow's foot" (רגל עורב) שמראה 1:1 / 1:N / M:N ויזואלית. השקעה של 20 דקות בתרשים חוסכת migration כואב בעתיד.

3. Normalization — 1NF עד 3NF

Normalization הוא תהליך ארגון הטבלאות כדי למנוע כפילות ואי-עקביות. הרעיון המרכזי: כל עובדה נשמרת במקום אחד בדיוק. אם אותו מידע חוזר בכמה מקומות — עדכון עלול לפספס חלק, ונוצרת אי-עקביות.

הבעיה — טבלה לא מנורמלת

-- ❌ הכל בטבלה אחת — כפילות ובעיות:
orders:
  id | customer_name | customer_email    | product | price
  1  | Eliya         | eliya@x.com       | Laptop  | 5000
  2  | Eliya         | eliya@x.com       | Mouse   | 100
-- שם ומייל של Eliya חוזרים. אם המייל משתנה — צריך לעדכן כל שורה.
-- ואם מפספסים אחת — יש שני מיילים סותרים לאותו לקוח.

שלוש הצורות הראשונות

  • 1NF (First Normal Form) — כל תא מכיל ערך אטומי אחד (לא רשימות/מבנים בתוך תא), ולכל שורה מזהה ייחודי. אין עמודה tags = "a,b,c".
  • 2NF — עומד ב-1NF, וכל עמודה לא-מפתח תלויה בכל ה-PK (רלוונטי כשיש composite PK). אין תלות בחלק מהמפתח.
  • 3NF — עומד ב-2NF, ואין תלות בין עמודות לא-מפתח (transitive dependency). אם zip קובע city, ה-city לא צריך לשבת בטבלת ההזמנות.

הפתרון המנורמל

-- ✅ מפרידים ל-entities נפרדים:
customers: id | name  | email
           1  | Eliya | eliya@x.com     -- העובדה נשמרת פעם אחת

orders:    id | customer_id | product | price
           1  | 1           | Laptop  | 5000
           2  | 1           | Mouse   | 100
-- עכשיו שינוי מייל = עדכון שורה אחת. אין אפשרות לאי-עקביות.

כלל אצבע מעשי: 3NF הוא היעד לרוב הסכמות ה-transactional (OLTP). אם אתה מוצא את עצמך משכפל אותו מידע בכמה שורות — כנראה חסרה נורמליזציה, וזה מוביל לבאגי עקביות.

4. Denormalization — מתי לשבור את הכללים בכוונה

נורמליזציה מונעת כפילות — אבל היא מחייבת JOINs כדי לאחד את המידע בחזרה, ו-JOINs עולים בביצועים. Denormalization הוא ההיפוך המכוון: לשכפל נתונים בכוונה כדי להאיץ קריאות.

-- מנורמל: כדי להציג הזמנה עם שם הלקוח צריך JOIN בכל קריאה.
-- denormalized: שומרים גם customer_name בטבלת orders (משוכפל).
orders: id | customer_id | customer_name | product | price
-- קריאה מהירה (בלי JOIN), אבל שינוי שם לקוח = עדכון בכמה מקומות.

ה-tradeoff הבסיסי

NormalizedDenormalized
כפילותמינימליתמכוונת
עקביותקלה לשמורקשה (עדכון בכמה מקומות)
קריאהאיטית יותר (JOINs)מהירה
כתיבהפשוטהמורכבת

העצה שלי: נרמל כברירת מחדל, denormalize רק כשמדדת בעיית ביצועים אמיתית. denormalization מוקדם הוא מקור לבאגי עקביות ("למה השם שונה בשני מקומות?"). זה כלי אופטימיזציה מודע, לא נקודת פתיחה. וכשאתה כן עושה denormalize — תעד למה, ותבנה מנגנון שמסנכרן את העותקים (trigger, או עדכון באפליקציה). זה מקביל בדיוק ל-caching מ-System Design: אותו tradeoff של מהירות מול טריות/עקביות.

5. Keys — Surrogate מול Natural, Auto-increment מול UUID

בחירת ה-primary key נראית טריוויאלית אבל יש לה השלכות אמיתיות.

Natural מול Surrogate key

  • Natural key — מזהה מהעולם האמיתי (email, ת"ז, ISBN). חיסרון: יכול להשתנות (אנשים מחליפים מייל), ואז כל ה-FKs שבורים. לרוב נמנעים מזה כ-PK.
  • Surrogate key — מזהה מלאכותי חסר משמעות (id אוטומטי או UUID). לא משתנה לעולם, יציב. זו הבחירה המומלצת ברוב המקרים.

Auto-increment מול UUID — ה-tradeoff המעשי

Auto-increment (BIGINT)UUID
גודלקטן (8 bytes)גדול (16 bytes)
ביצועי indexמעולים (רציף)פחות טובים (אקראי)*
ניחוש/אבטחהניתן לניחוש (1,2,3...)לא ניתן לניחוש
יצירה מבוזרתקשה (צריך תיאום)קל (כל שרת מייצר לבד)
מיזוג/shardingהתנגשויותייחודי גלובלית

*הערה: UUIDv7 (מבוסס-זמן, חדש יחסית) פותר את בעיית האקראיות ב-index ומשלב את היתרונות של שניהם — שווה להכיר.

מתי מה: BIGINT auto-increment למערכת פנימית פשוטה (מהיר, קטן). UUID כשצריך: יצירת IDs מבוזרת (כמה שרתים/מכשירים), הסתרת מספר הרשומות מהחוץ (אבטחה — ID רץ חושף כמה משתמשים יש), או מיזוג נתונים ממקורות שונים. ב-Postgres יש טיפוס UUID ייעודי — אל תשמור UUID כ-VARCHAR, זה מבזבז מקום.

6. ACID מול BASE — שתי פילוסופיות

כיסינו ACID במדריך SQL. כאן נעמיד אותו מול הפילוסופיה הנגדית — BASE — כי ההבנה הזו היא מה שמסביר את ההבדל בין עולם ה-SQL לעולם ה-NoSQL.

ACID (עולם ה-SQL)

Atomicity, Consistency, Isolation, Durability (ראה מדריך SQL פרק 14). הפילוסופיה: עקביות מעל הכל. עדיף לדחות פעולה מאשר להשאיר נתונים במצב לא-עקבי. מתאים לכסף, מלאי, כל דבר שחייב להיות מדויק.

BASE (עולם ה-NoSQL)

ראשי תיבות (קצת מאולצים): Basically Available, Soft state, Eventual consistency. הפילוסופיה ההפוכה: זמינות וסקייל מעל עקביות מיידית. המערכת תמיד עונה, גם אם הנתון מעט ישן, ומתעדכן "בסופו של דבר" (זוכר eventual consistency מ-System Design פרק 7?).

ACIDBASE
עדיפותעקביותזמינות + סקייל
עולםSQL רלציוניהרבה NoSQL
מתאים ל-כסף, מלאי, הזמנותfeeds, לוגים, analytics, סשנים

זה לא "טוב מול רע" — זה בחירת כלי לפי הצורך. אותה מערכת יכולה להשתמש בשניהם: Postgres (ACID) לתשלומים, ו-Cassandra (BASE) ללוגים. חלק מהבשלות ההנדסית היא לזהות איזה נתון דורש איזו פילוסופיה.

7. SQL מול NoSQL — ההחלטה לפי צורת הנתונים

סקרנו את משפחות ה-NoSQL ב-System Design (פרק 8). כאן ההחלטה המעשית: מתי לבחור מה, לפי צורת הנתונים ודפוסי הגישה — לא לפי אופנה.

בחר SQL כאשר

  • הנתונים מובנים ועם קשרים ברורים (users, orders, products).
  • אתה צריך transactions ו-ACID (כסף, מלאי).
  • אתה צריך queries גמישים ולא-צפויים (JOINs, aggregations, דוחות אד-הוק).
  • עקביות חשובה יותר מסקייל אינסופי.

בחר NoSQL כאשר

  • נפח/throughput עצום שקשה ל-DB רלציוני יחיד (אבל — זכור, Postgres מגיע רחוק מאוד).
  • הנתונים לא-מובנים או משתנים (schema גמיש).
  • דפוסי הגישה ידועים ופשוטים מראש (lookup לפי מפתח, ללא JOINs מורכבים).
  • מוכן לוותר על עקביות מיידית תמורת זמינות/סקייל.

העמדה שאני ממליץ (וגם רוב המנוסים): ברירת המחדל היא SQL (Postgres), וזה נכון ל-90% מהפרויקטים. Postgres מטפל ב-JSON, full-text, ואפילו vectors — לפני שאתה "צריך NoSQL", בדוק אם Postgres לא פותר את זה. ה-NoSQL הכי שימושי למפתח Backend הוא דווקא לא כתחליף אלא כמשלים: Redis ל-caching/sessions לצד Postgres. אל תבחר MongoDB "כי מודרני" ואז תתגעגע ל-transactions ו-JOINs.

8. NoSQL Data Modeling — לחשוב הפוך

זה הפרק שהכי שווה את זמנך, כי כאן טועים הכי הרבה: אנשים לוקחים NoSQL וממדלים אותו כמו SQL — וזה נכשל. NoSQL דורש היפוך תפיסתי.

ההבדל המהותי

  • SQL: ממדלים לפי הנתונים (נרמול, entities נפרדים), וה-JOINs מרכיבים בזמן ה-query. "אחסן נקי, שאל בגמישות".
  • NoSQL: ממדלים לפי דפוסי הגישה (queries). קודם שואלים "אילו queries ארוץ?", ואז מעצבים את הנתונים כדי לשרת אותם ישירות — לרוב עם denormalization ו-embedding, כי אין JOINs יעילים.

דוגמה: בלוג עם posts ו-comments

// גישת SQL — נרמול, שתי טבלאות, JOIN:
posts(id, title, body)
comments(id, post_id, text)     // JOIN כדי להציג פוסט + תגובות

// גישת NoSQL (document, כמו MongoDB) — embedding:
{
  "_id": "post1",
  "title": "...",
  "body": "...",
  "comments": [                  // התגובות מוטמעות בתוך הפוסט
    { "text": "Great!", "author": "Eliya" },
    { "text": "Thanks", "author": "Dan" }
  ]
}
// קריאת פוסט אחד = מסמך אחד, בלי JOIN. מהיר מאוד לדפוס "הצג פוסט".

Embedding מול Referencing

ההחלטה המרכזית ב-document DBs:

  • Embedding (הטמעה) — נתונים קשורים בתוך אותו מסמך. מהיר לקריאה, אטומי לכתיבה. טוב כשהנתונים "נקראים ביחד" ולא גדלים בלי גבול.
  • Referencing (הפניה) — מסמך מצביע לאחר (כמו FK). טוב לקשרים M:N, או כשהנתון המוטמע גדול/משותף/גדל ללא הגבלה (למשל, פוסט עם מיליון תגובות — לא מטמיעים).

הכלל: ב-NoSQL, denormalization היא ברירת המחדל, לא חריגה. משכפלים נתונים כדי לשרת query במסמך אחד. המחיר: עדכון נתון משוכפל דורש עדכון בכמה מקומות (בדיוק ה-tradeoff מפרק 4, רק שכאן הוא הנורמה). לכן NoSQL מבריק כשדפוסי הגישה יציבים וידועים — ובעייתי כשהם משתנים, כי שינוי דפוס עלול לדרוש מידול מחדש של הנתונים.

9. Redis לעומק — מבני נתונים ושימושים

Redis הוא ה-NoSQL שכל מפתח Backend חייב להכיר — לא כתחליף ל-DB אלא כשכבה מהירה לצד ה-DB. הוא in-memory (הכל ב-RAM), ולכן מהיר בצורה קיצונית. הטעות הנפוצה: לחשוב עליו רק כ"cache". הוא הרבה יותר — key-value store עם מבני נתונים עשירים.

מבני הנתונים והשימושים שלהם

מבנהמה זהשימוש קלאסי
Stringערך פשוט (טקסט/מספר)cache, מונים (INCR)
Hashשדות→ערכים (כמו object)אובייקטים (session, user profile)
Listרשימה מסודרתתורים, feeds אחרונים
Setאוסף ייחודי לא-מסודרtags, "מי אונליין", ייחודיות
Sorted Setset עם score לכל איברleaderboards, priority queues

שימושים נפוצים ב-Backend

  • Cache — cache-aside (מדריך System Design פרק 5). השימוש הכי נפוץ.
  • Sessions — אחסון session data מהיר ומשותף בין שרתים (מדריך Authentication).
  • Rate limiting — מונה מבוזר עם INCR + TTL (System Design פרק 12).
  • Leaderboards — Sorted Set נותן דירוג בזמן אמת ב-O(log n): ZADD, ZRANGE.
  • Distributed locks — SET key value NX EX 30 ליצירת lock מבוזר (למניעת עיבוד כפול).
  • Pub/Sub — הודעות בזמן אמת בין שירותים.
# מונה עם תפוגה — rate limiting בשתי פקודות:
INCR  user:42:requests        # מגדיל ומחזיר
EXPIRE user:42:requests 60    # פג אחרי דקה

# Leaderboard:
ZADD leaderboard 500 "player1"
ZADD leaderboard 800 "player2"

Persistence — Redis לא רק בזיכרון

נקודה שמפתיעה: Redis יכול לשמור לדיסק (persistence) כדי לשרוד restart. שתי אפשרויות: RDB (snapshots תקופתיים — מהיר, אבל עלול לאבד את הרגעים האחרונים) ו-AOF (append-only log של כל פעולה — עמיד יותר, איטי יותר). ל-cache טהור אפשר בלי persistence; ל-data שחשוב לשרוד — הפעל AOF.

אזהרה: Redis הוא in-memory — ה-RAM מוגבל ויקר. אל תשמור בו הכל. הוא לנתונים "חמים" (נגישים הרבה, זמניים, או שאפשר לשחזר). ה-source of truth נשאר ה-DB הקבוע (Postgres). Redis הוא שכבת מהירות, לא מסד הנתונים הראשי.

10. Connection Pooling

נושא מעשי שמפילים עליו הרבה מפתחים, ולא מדברים עליו מספיק. פתיחת חיבור ל-DB היא יקרה — היא כוללת TCP handshake, אימות, והקצאת משאבים בשרת ה-DB (זוכר מ-Networking כמה handshake עולה?). לפתוח חיבור חדש לכל query זה בזבזני ואיטי.

הפתרון: pool של חיבורים

Connection pool מחזיק מספר קבוע של חיבורים פתוחים ומוכנים. במקום לפתוח חיבור חדש, האפליקציה "שואלת" חיבור מה-pool, משתמשת בו, ומחזירה אותו — בלי handshake בכל פעם:

Without pool: request → open connection → query → close (יקר, כל פעם)
With pool: request → borrow from pool → query → return to pool (מהיר)

למה זה קריטי במיוחד

ל-DB יש גבול קשיח על מספר החיבורים (ב-Postgres, ברירת מחדל ~100). בלי pool, אפליקציה עם תעבורה גבוהה תפתח מאות חיבורים ותמצה את הגבול — ואז "too many connections", וכל האפליקציה נופלת. עם pool, אתה שולט במספר החיבורים המקסימלי.

מעשי ל-NestJS: TypeORM/Prisma כוללים connection pooling מובנה — הגדר את max connections לפי מה שה-DB תומך ומחולק במספר ה-instances של האפליקציה (אם יש 5 instances וה-DB תומך ב-100, כל אחד לא יותר מ-~20). בסקייל גבוה או serverless, מוסיפים pooler חיצוני כמו PgBouncer שמנהל את החיבורים מול Postgres. זו אחת הסיבות הנפוצות ל-"ה-DB נופל תחת עומס" — לא ה-queries, אלא מיצוי החיבורים.

11. ORMs מול Raw SQL

ORM (Object-Relational Mapping) ממפה טבלאות למחלקות/אובייקטים בקוד, כך שאתה עובד עם objects במקום לכתוב SQL. ב-NestJS אלה TypeORM ו-Prisma.

ה-tradeoff

פרודוקטיביותגבוהה (פחות boilerplate)נמוכה יותר

מלכודת ה-N+1 (שוב) — עכשיו בהקשר ORM

זו הטעות מספר אחת עם ORMs, וכיסינו אותה במדריך SQL. ORM מקל כל כך לגשת לנתונים קשורים שקל לא לשים לב שכל גישה היא query נפרד:

// ❌ N+1 עם ORM — נראה תמים, הורג ביצועים:
const users = await userRepo.find();        // query 1
for (const user of users) {
  console.log(user.orders);                 // query נוסף לכל user!  (N queries)
}

// ✅ eager loading / join בבת אחת:
const users = await userRepo.find({ relations: ["orders"] });  // query אחד

העמדה המאוזנת: השתמש ב-ORM לרוב העבודה (CRUD, queries פשוטים) — הוא חוסך זמן ונותן type safety. אבל למד SQL היטב (יש לך כבר מדריך שלם) כי: (1) תצטרך raw SQL ל-queries מורכבים/מאופטמים, (2) תזהה מתי ה-ORM מייצר SQL גרוע (הפעל query logging!), ו-(3) לא תיפול ל-N+1. מפתח שנשען על ORM בלי להבין SQL — כותב קוד איטי בלי לדעת למה. ה-ORM הוא נוחות, לא תחליף להבנה.

12. Migrations — שינוי סכמה ב-Production בבטחה

הסכמה משתנה כל הזמן — עמודה חדשה, טבלה חדשה, שינוי טיפוס. Migration הוא קובץ מגורסן שמתאר שינוי סכמה, כך שאפשר להחיל אותו בעקביות בכל הסביבות (dev, staging, production) ולעקוב אחרי ההיסטוריה ב-git.

איך זה עובד

// migration עם up (החלה) ו-down (ביטול):
export class AddPhoneToUsers {
  async up(q) {
    await q.query(`ALTER TABLE users ADD COLUMN phone VARCHAR(20)`);
  }
  async down(q) {
    await q.query(`ALTER TABLE users DROP COLUMN phone`);
  }
}

ה-ORM עוקב אילו migrations כבר רצו (בטבלה מיוחדת), ומריץ רק את החדשים. זה נותן היסטוריה מסודרת ויכולת rollback.

הכללים לשינויים בטוחים ב-Production

זה קריטי — migration רשלני יכול להפיל את ה-production או לנעול טבלה לדקות:

  • עמודה חדשה — תמיד nullable או עם DEFAULT. ADD COLUMN ... NOT NULL בלי default על טבלה קיימת נכשל/נועל.
  • שינויים הרסניים בשלבים. למחוק עמודה? קודם הפסק להשתמש בה בקוד (deploy), ורק ב-deploy הבא מחק אותה. אחרת קוד ישן שעדיין רץ יקרוס.
  • היזהר מ-locks. על טבלאות גדולות, שינויים מסוימים נועלים את הטבלה וחוסמים תעבורה. ב-Postgres יש דרכים לא-חוסמות (למשל CREATE INDEX CONCURRENTLY).
  • backward compatibility. בזמן deploy, הקוד הישן והחדש רצים במקביל לרגע — הסכמה צריכה לעבוד עם שניהם.
  • גבה לפני migration הרסני, ותרגל את ה-down.

הכלל שמציל: חשוב על migrations כexpand-then-contract: קודם מרחיבים (מוסיפים את החדש בלי לשבור את הישן), פורסים קוד שמשתמש בחדש, ורק אז מכווצים (מוחקים את הישן). לעולם לא לשנות סכמה וקוד ב"מכה" אחת על טבלה חיה — זה מתכון ל-downtime.

13. Best Practices וטעויות נפוצות

  1. Data modeling לפני קוד. צייר ER, נרמל ל-3NF, ורק אז CREATE TABLE. זה הכי יקר לתקן.
  2. נרמל כברירת מחדל, denormalize רק אחרי מדידה.
  3. אנדקס FKs ועמודות WHERE/JOIN (מדריך SQL) — FK לא-מאונדקס הוא בעיה נפוצה.
  4. Surrogate keys כברירת מחדל (id/UUID), לא natural keys משתנים.
  5. אכוף constraints ב-DB, לא רק באפליקציה — קו ההגנה האחרון.
  6. Connection pool תמיד, עם max מותאם ל-DB ולמספר ה-instances.
  7. הפעל query logging בפיתוח — לתפוס N+1 ו-SQL גרוע של ה-ORM.
  8. Migrations בשלבים (expand-contract), לעולם לא שינוי הרסני חד-פעמי על טבלה חיה.
  9. גבה, ותרגל שחזור. (חוזר מ-SQL — כי זה הכי חשוב והכי מוזנח).
  10. SQL כברירת מחדל, NoSQL כמשלים. Redis לצד Postgres, לא במקומו.

טעויות נפוצות

  • לשמור רשימה כ-CSV בעמודה (tags = "a,b,c") — שובר 1NF, בלתי-שאיל. השתמש בטבלת קישור או array/JSONB.
  • FLOAT לכסף — שגיאות עיגול (מדריך SQL). תמיד NUMERIC.
  • N+1 queries — הכי נפוצה עם ORMs.
  • אין connection pool / pool קטן מדי — "too many connections" תחת עומס.
  • denormalization מוקדם — באגי עקביות בלי צורך אמיתי.
  • NoSQL בגלל אופנה — ואז מתגעגעים ל-transactions ו-JOINs.

14. תרגילים

1 — Data Modeling. עצב סכמה למערכת בלוג: users, posts, comments, tags (פוסט יכול לכמה tags, tag על כמה פוסטים). זהה את סוגי הקשרים והוסף junction table איפה שצריך.

2 — Normalization. נתונה טבלה שטוחה של הזמנות עם שם לקוח, מייל ומוצר משוכפלים בכל שורה. נרמל אותה ל-3NF וצייר את הטבלאות המתקבלות.

3 — SQL מול NoSQL. לכל אחד מאלה, בחר SQL או NoSQL ונמק: (א) מערכת בנקאית, (ב) לוגים של אפליקציה, (ג) קטלוג מוצרים עם attributes משתנים, (ד) leaderboard בזמן אמת.

4 — NoSQL Modeling. עצב מודל document (כמו MongoDB) לפוסט בבלוג עם תגובות. החלט embedding מול referencing לתגובות, ונמק — מה קורה אם לפוסט יכולות להיות מיליון תגובות?

5 — Redis. באיזה מבנה נתונים של Redis תשתמש ל: (א) cache של פרופיל משתמש, (ב) rate limiter, (ג) leaderboard, (ד) "מי מחובר עכשיו"? נמק כל בחירה.

6 — Migration. אתה צריך להוסיף עמודה NOT NULL לטבלת users עם 10M שורות ב-production, בלי downtime. תאר את השלבים (רמז: expand-contract).

סיכום — מה הלאה

שני דברים לקחת: data modeling הוא ההחלטה הכי יקרה לתיקון — השקע בו זמן מראש (ER, נרמול, בחירת keys), כי migration על מיליוני שורות הוא כאב אמיתי. והשני: SQL הוא הבסיס, NoSQL הוא משלים — Postgres מגיע רחוק מאוד, ו-Redis לצידו מכסה את רוב מה שצריך; NoSQL "אמיתי" נכנס רק בסקייל/צורת-נתונים ספציפיים, ואז ממדלים לפי דפוסי הגישה, לא לפי הנתונים.

המדריך הזה חיבר בין SQL (השכבה הנמוכה — queries) ל-System Design (הגבוהה — סקייל): data modeling ובחירת DB הם השכבה שמחברת ביניהן.
