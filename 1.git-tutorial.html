1. מבוא: מה זה Git והמודל המנטלי

Git הוא version control system מבוזר — כלי שעוקב אחרי כל שינוי בקוד, מאפשר לחזור אחורה, לעבוד על כמה דברים במקביל, ולשלב עבודה של כמה אנשים. הוא הסטנדרט המוחלט; כל פרויקט תוכנה משתמש בו.

"מבוזר" — למה זה חשוב

ב-Git, לכל מפתח יש עותק מלא של כל ההיסטוריה על המחשב שלו — לא רק הגרסה הנוכחית. אתה יכול לעשות commit, לעיין בהיסטוריה, ולעבוד על branches בלי חיבור לאינטרנט. GitHub הוא רק "עותק מרכזי משותף" לסנכרון — לא ה-git עצמו. (זוכר את ההבחנה מ-System Design בין מבוזר למרכזי? אותו רעיון).

המודל המנטלי החשוב: snapshots, לא diffs

הרבה אנשים חושבים ש-Git שומר "שינויים" (diffs). זה לא המודל הנכון. Git שומר snapshots — צילום מצב של כל הפרויקט בכל commit. כל commit הוא "תמונה" מלאה של הקבצים באותו רגע (בפועל, קבצים שלא השתנו מקושרים ולא משוכפלים, אבל תפיסתית — snapshot). כשאתה מבין את זה, branches ו-merges מפסיקים להיות קסם: branch הוא פשוט מצביע ל-snapshot מסוים, ו-Git עובר ביניהם.

Commit — יחידת השמירה

Commit הוא נקודת שמירה בהיסטוריה: snapshot + הודעה + מי ומתי. לכל commit יש hash ייחודי (למשל a1b2c3d) שמזהה אותו. ההיסטוריה היא שרשרת של commits, כל אחד מצביע לקודם שלו.

הגדרה ראשונית (פעם אחת)

git config --global user.name "Eliya"
git config --global user.email "eliya@x.com"
# זה מה שיופיע בכל commit שלך

2. שלושת האזורים — Working, Staging, Repo

זו התפיסה שהכי מבלבלת מתחילים, ואם תבין אותה — 80% מ-Git יתבהר. ב-Git יש שלושה "אזורים" שקובץ עובר ביניהם:

Working Directory → Staging Area (Index) → Repository
  (הקבצים שלך)       (מה שיכנס ל-commit)   (ההיסטוריה הקבועה)

       git add →           git commit →
  • Working Directory — הקבצים שאתה עורך בפועל. כאן אתה עובד.
  • Staging Area (Index) — "חדר המתנה". אתה בוחר אילו שינויים ייכנסו ל-commit הבא. זה מה ש-git add עושה.
  • Repository — ההיסטוריה הקבועה. git commit לוקח את מה שב-staging ושומר אותו כ-snapshot.

למה שני שלבים (add ואז commit)?

ה-staging area נראה מיותר בהתחלה, אבל הוא נותן לך שליטה עדינה — לבחור בדיוק אילו שינויים ייכנסו ל-commit. ערכת 3 קבצים אבל רוצה לחלק לשני commits לוגיים? מוסיפים ל-staging רק את הקבצים של ה-commit הראשון, עושים commit, ואז את השאר. זה מאפשר commits אטומיים ונקיים (פרק 10).

HEAD

HEAD הוא מצביע ל-commit ה"נוכחי" שאתה עומד עליו (בדרך כלל הראש של ה-branch הפעיל). כשאתה עושה commit, HEAD זז קדימה. הרבה פקודות מתייחסות אליו — HEAD~1 זה "commit אחד אחורה", HEAD~2 שניים, וכו'.

3. הלולאה הבסיסית — add, commit, log

התחלה — init או clone

git init                              # מתחיל repo חדש בתיקייה הנוכחית
git clone https://github.com/user/repo.git   # מעתיק repo קיים

הלולאה היומיומית

git status                    # מה השתנה? מה ב-staging? — הפקודה שתריץ הכי הרבה
git add file.ts               # מוסיף קובץ ל-staging
git add .                     # מוסיף את כל השינויים
git commit -m "Add user auth" # שומר snapshot עם הודעה
git log                       # מציג את היסטוריית ה-commits
git log --oneline             # גרסה קומפקטית (שורה per commit)

לראות מה השתנה

git diff                # שינויים ב-working dir שעדיין לא ב-staging
git diff --staged       # שינויים שב-staging (מה שייכנס ל-commit)
git show <hash>          # מה השתנה ב-commit מסוים

ההרגל שיציל אותך: הרץ git status כל הזמן — לפני commit, אחרי, כשאתה מבולבל. הוא אומר לך בדיוק באיזה מצב אתה ומה הצעד הבא. מפתחים מנוסים מריצים אותו עשרות פעמים ביום. זה ה-console.log של Git.

4. Branches — ענפים

Branch (ענף) הוא אחד הרעיונות החזקים ב-Git, ובזכות המודל של snapshots — הוא זול וקל. branch מאפשר לך לעבוד על feature בלי לגעת בקוד הראשי, ולשלב חזרה כשמוכן.

מה זה branch באמת

זוכר ש-Git שומר snapshots ו-branch הוא מצביע? branch הוא בסך הכול מצביע קליל ל-commit. יצירת branch = יצירת מצביע חדש. זו הסיבה ש-branching ב-Git מהיר ומיידי (בניגוד למערכות ישנות שהעתיקו קבצים). ה-branch הראשי נקרא בדרך כלל main (בעבר master).

הפקודות

git branch                    # רשימת branches (הנוכחי מסומן ב-*)
git branch feature-auth       # יוצר branch חדש
git switch feature-auth       # עובר אליו (או: git checkout feature-auth)
git switch -c feature-auth    # יוצר ועובר בבת אחת (קיצור נפוץ)

git switch main               # חוזר ל-main
git branch -d feature-auth    # מוחק branch (אחרי merge)

הרעיון המרכזי: בידוד

כל feature/bugfix מקבל branch משלו. אתה עובד עליו, עושה commits, וה-main נשאר יציב ונקי. כשה-feature מוכן ובדוק — משלבים אותו חזרה ל-main (פרק 5). זה מאפשר לעבוד על כמה דברים במקביל, ולשמור על main תמיד במצב שאפשר לפרוס ממנו.

main: A —— B —————————— (merge) —— F
              \            /
feature:       C —— D —— E
      עובדים על ה-feature בבידוד, ואז ממזגים חזרה

5. Merge מול Rebase

שתי דרכים לשלב עבודה מ-branch אחד לאחר. זה אחד הנושאים הכי מבלבלים ב-Git — והכי נשאלים. נבין את שניהם ואת ה-tradeoff.

Merge — שילוב שמשמר היסטוריה

git switch main
git merge feature-auth        # מביא את ה-feature לתוך main

merge יוצר merge commit חדש שמאחד את שתי ההיסטוריות. ה-history משמר את הצורה האמיתית — רואים שהיה branch שהתפצל והתאחד. יתרון: לא משכתב היסטוריה, בטוח. חיסרון: ההיסטוריה יכולה להיראות "מסועפת" ועמוסה ב-merge commits.

Fast-forward

אם ל-main לא היו commits חדשים מאז שיצרת את ה-branch, Git פשוט "מזיז את המצביע קדימה" בלי merge commit — זה נקרא fast-forward. נקי, אבל מאבד את המידע שהיה branch.

Rebase — שכתוב היסטוריה לקו ישר

git switch feature-auth
git rebase main               # "מעביר" את ה-commits של ה-feature לראש main

rebase לוקח את ה-commits שלך ו"מדביק" אותם מחדש על ראש ה-main, כאילו כתבת אותם עכשיו. התוצאה: היסטוריה ישרה ונקייה, בלי merge commits. חיסרון: זה משכתב את ההיסטוריה (ה-commits מקבלים hashes חדשים).

Merge:   main ——A——B————M   (M = merge commit, היסטוריה מסועפת)
              \——C——D——/

Rebase:  main ——A——B——C'——D'  (קו ישר, נקי, אבל C/D נכתבו מחדש)

הכלל הזהב של rebase

לעולם אל תעשה rebase ל-branch שכבר דחפת ומישהו אחר עובד עליו (במיוחד main/master). כי rebase משכתב היסטוריה — ה-hashes משתנים — ואם מישהו אחר בנה על ה-commits הישנים, אתה שובר לו את העבודה ויוצר בלגן קשה. הכלל הפשוט: rebase רק על branch מקומי פרטי שלך, merge לשילוב לתוך branch משותף. הפרה של הכלל הזה היא אחד המקורות הגדולים ל"Git הרס לי הכל".

מתי מה — בפועל

  • rebase את ה-feature branch המקומי שלך על main לפני שאתה פותח PR — כדי לקבל היסטוריה נקייה ולפתור conflicts מוקדם.
  • merge את ה-PR לתוך main (דרך GitHub) — לשילוב הרשמי.
  • אם לא בטוח — merge. הוא בטוח יותר; אף פעם לא משכתב היסטוריה.

6. Remotes ו-GitHub — push, pull, fetch

עד כה הכל היה מקומי. Remote הוא עותק של ה-repo בשרת (GitHub/GitLab), שמאפשר לשתף ולסנכרן. ה-remote ברירת המחדל נקרא origin.

הפקודות

git remote -v                        # אילו remotes מוגדרים
git remote add origin <url>           # מקשר ל-remote (אם עשית init מקומי)

git push origin main                  # דוחף commits מקומיים ל-remote
git push -u origin feature-auth       # דוחף branch חדש ומקשר אותו (-u פעם ראשונה)

git fetch                             # מוריד שינויים מה-remote בלי לשלב
git pull                              # fetch + merge (מוריד ומשלב מיד)

ההבחנה החשובה: fetch מול pull

  • fetch — מוריד את השינויים מה-remote אבל לא משלב אותם לקוד שלך. אתה יכול לבדוק מה השתנה קודם. בטוח.
  • pull — fetch + merge בבת אחת. נוח, אבל משלב מיד (ולפעמים יוצר merge commit או conflict לא צפוי).

הרגל טוב: git pull לפני שאתה מתחיל לעבוד ולפני push — כדי שתהיה מסונכרן ותמנע conflicts.

Tracking branches

branch מקומי יכול "לעקוב" אחרי branch מרוחק — אז git push/git pull יודעים לאן. ה--u (או --set-upstream) בפעם הראשונה מגדיר את הקישור הזה.

7. ה-Workflow הצוותי — Feature Branch + PR

עכשיו נחבר הכל ל-workflow שכל צוות תוכנה עובד לפיו. זה כנראה החלק הכי חשוב מעשית — כי ככה עבודה אמיתית נראית.

מחזור העבודה המלא

1. git switch main && git pull     # מתעדכן לאחרון
2. git switch -c feature-x        # branch חדש ל-feature
3. ...עובד, git add, git commit...  # commits קטנים ולוגיים
4. git push -u origin feature-x    # דוחף את ה-branch
5. פותח Pull Request ב-GitHub     # מבקש לשלב ל-main
6. Code Review — חברי צוות בודקים ומעירים
7. מתקן לפי הערות, דוחף עוד commits
8. אושר → Merge ל-main ב-GitHub
9. git switch main && git pull     # מתעדכן, מוחק את ה-branch

Pull Request (PR) — הלב של העבודה הצוותית

PR הוא בקשה לשלב את ה-branch שלך ל-main. הוא לא רק "merge" — הוא נקודת ביקורת: מקום שבו חברי הצוות רואים את השינוי, מריצים עליו CI (זוכר ממדריך DevOps?), מעירים, ומאשרים. שום דבר לא נכנס ל-main בלי לעבור דרך PR ו-review. זה מה ששומר על איכות הקוד ומפיץ ידע בצוות.

Code Review — למה זה קריטי

  • תופס באגים לפני production — עוד זוג עיניים.
  • מפיץ ידע — הצוות מכיר את הקוד, לא רק הכותב.
  • שומר עקביות — סטנדרטים אחידים.
  • בעידן ה-AI — [Likely] חשוב במיוחד: review של קוד שנוצר עם AI תופס hallucinations ובעיות אבטחה שה-AI פספס.

עצה ל-PRs טובים: שמור אותם קטנים וממוקדים — PR של 50 שורות מקבל review איכותי; PR של 2,000 שורות מקבל "LGTM 👍" בלי שאף אחד באמת קרא. PR = feature/fix אחד, לא "כל מה שעשיתי השבוע". זה גם מקביל ל-commits אטומיים (פרק 10) — יחידות קטנות וברורות מנצחות.

8. Merge Conflicts — פתרון התנגשויות

ה-conflict הוא מה שהכי מפחיד מתחילים, אבל הוא פשוט ולא מסוכן ברגע שמבינים אותו. conflict קורה כששני branches שינו את אותה שורה — Git לא יודע איזו גרסה נכונה, אז הוא מבקש ממך להחליט.

איך זה נראה

<<<<<<< HEAD
const timeout = 3000;        // הגרסה שלך (ב-branch הנוכחי)
=======
const timeout = 5000;        // הגרסה מה-branch שאתה ממזג
>>>>>>> feature-x

Git מסמן את שני הצדדים. התפקיד שלך: למחוק את הסימונים ולהשאיר את הקוד הנכון (אחד מהם, שילוב, או משהו חדש לגמרי).

התהליך

git merge feature-x           # → CONFLICT!
# 1. git status מראה אילו קבצים בקונפליקט
# 2. פותחים כל קובץ, מוצאים את <<</===/>>>, בוחרים את הגרסה הנכונה, מוחקים הסימונים
# 3. אחרי שפתרת:
git add <resolved-file>       # מסמן שפתרת
git commit                    # משלים את ה-merge
# (אם נבהלת ורוצה לבטל: git merge --abort)

הנקודה שמרגיעה: conflict הוא לא שגיאה ולא נזק — הוא Git ששואל אותך שאלה. שום דבר לא אבד; שתי הגרסאות שם. אתה פשוט בוחר. git merge --abort תמיד מחזיר אותך למצב שלפני ה-merge. וכדי למנוע conflicts גדולים: pull תכוף, branches קצרי-חיים, ו-PRs קטנים. ככל שה-branch חי יותר זמן, כך הוא מתרחק מ-main ויותר conflicts מצטברים.

9. ביטול שינויים — reset, revert, restore, stash

"עשיתי טעות, איך מבטלים?" — השאלה הכי נפוצה ב-Git, וגם הכי מלחיצה כי הפקודות דומות ומבלבלות. נעשה סדר. הכלל: לכל מצב יש פקודה שונה.

הטבלה שמסדרת הכל

מה אתה רוצהפקודה
לבטל שינוי בקובץ שעדיין לא ב-staginggit restore file
להוציא קובץ מ-staging (בלי לבטל שינוי)git restore --staged file
לתקן את הודעת ה-commit האחרוןgit commit --amend
לבטל commit אחרון, לשמור שינוייםgit reset --soft HEAD~1
לבטל commit אחרון, למחוק שינוייםgit reset --hard HEAD~1 ⚠️
לבטל commit שכבר דחפת (בטוח)git revert <hash>
לשמור שינויים זמנית בצדgit stash

ההבחנה הכי חשובה: reset מול revert

  • reset — מוחק commits מההיסטוריה (מזיז את המצביע אחורה). משכתב היסטוריה. רק ל-commits מקומיים שלא דחפת.
  • revert — יוצר commit חדש שמבטל את השינוי, בלי למחוק היסטוריה. זו הדרך הבטוחה לבטל משהו שכבר דחפת — כי היא לא משכתבת היסטוריה משותפת (זוכר את הכלל מ-rebase?).

⚠️ --hard — הזהירות

git reset --hard מוחק שינויים ללא שאלה. זו הפקודה היח­ידה ב-Git שבאמת יכולה למחוק עבודה. השתמש בה רק כשאתה בטוח. (אבל גם ממנה יש דרך חזרה — reflog, למטה).

stash — "שמור בצד רגע"

git stash              # שומר את השינויים בצד ומנקה את ה-working dir
# ...עכשיו אתה נקי, יכול לעבור branch לתקן משהו דחוף...
git stash pop          # מחזיר את השינויים ששמרת

שימושי כשאתה באמצע עבודה וצריך לקפוץ למשהו אחר בלי לעשות commit חצי-גמור.

reflog — רשת הביטחון הסודית

הפקודה שתציל אותך ביום שתחשוב ש"הרסת הכל": git reflog. Git שומר לוג של כל מקום ש-HEAD היה בו — כולל commits ש"מחקת" עם reset. אז גם אחרי reset --hard שגוי, אתה יכול למצוא את ה-hash ב-reflog ולחזור אליו: git reset --hard <hash-מה-reflog>. ב-Git כמעט בלתי אפשרי לאבד commit שכבר נעשה — הוא נשמר גם אם "נמחק", לזמן מה. זה מה שהופך את Git לבטוח להתנסות: כמעט הכל הפיך.

10. Commits טובים והודעות

Commits הם לא רק "שמירה" — הם תיעוד של למה הקוד השתנה. commit history טוב הוא נכס; רע הוא חסר ערך. שני עקרונות:

Atomic commits — commit אחד = שינוי לוגי אחד

כל commit צריך לעשות דבר אחד שלם. לא "תיקנתי באג + הוספתי feature + שיניתי עיצוב" בcommit אחד. commits אטומיים מאפשרים: להבין את ההיסטוריה, לבטל שינוי ספציפי (revert), ולעשות review קל. זה בדיוק למה ה-staging area קיים (פרק 2) — לבחור מה נכנס לכל commit.

הודעות טובות

# ❌ הודעות חסרות ערך:
git commit -m "fix"
git commit -m "changes"
git commit -m "asdf"

# ✅ הודעה טובה — מה ולמה, בציווי:
git commit -m "Add rate limiting to login endpoint"
git commit -m "Fix null pointer when user has no orders"

Conventional Commits — קונבנציה נפוצה

פורמט מקובל שמוסיף מבנה: type: description. עוזר לקריאוּת ולאוטומציה (changelogs):

feat: add JWT refresh token support
fix: prevent duplicate orders on double-click
docs: update API authentication guide
refactor: extract validation logic to service
test: add integration tests for user creation
chore: bump dependencies

מבחן פשוט להודעה טובה: ההודעה צריכה להשלים את המשפט "This commit will..." — "This commit will add rate limiting". אם ההודעה שלך לא משתלבת (כמו "changes" או "fix stuff") — היא לא טובה מספיק. ה-history שלך הוא מכתב לעצמך-של-העתיד ולצוות; כתוב אותו כך.

11. .gitignore ומה לא לcommit

לא כל קובץ צריך להיכנס ל-Git. .gitignore הוא קובץ שמפרט מה להתעלם ממנו — Git פשוט לא יראה אותם.

# .gitignore טיפוסי לפרויקט Node/NestJS:
node_modules/        # תלויות — משוחזרות מ-package.json, ענקיות
dist/                # תוצרי build
.env                 # ⚠️ סודות! (זוכר ממדריך DevOps?)
*.log                # לוגים
.DS_Store            # קבצי מערכת
coverage/            # תוצרי טסטים

הכלל הקריטי ביותר — סודות

לעולם אל תעשה commit ל-secrets (.env, API keys, passwords). וזו לא רק "לא יפה" — זו סכנה אמיתית: ברגע ש-secret נכנס ל-git history, הוא שם לנצח — גם אם תמחק את הקובץ ב-commit הבא, הוא נשאר בהיסטוריה ונגיש לכל מי שיש לו את ה-repo. בוטים סורקים את GitHub ומנצלים secrets דלופים תוך דקות. אם קרה — לא מספיק למחוק; חייבים לבטל (rotate) את הסוד מיד (זוכר ממדריך DevOps ו-Auth?). הוסף .env ל-.gitignore לפני ה-commit הראשון, לא אחרי.

12. כלים מתקדמים — cherry-pick, rebase -i, bisect, tags

כלים שלא תצטרך כל יום, אבל כשתצטרך — הם מצילים. שווה לדעת שהם קיימים.

cherry-pick — commit בודד ל-branch אחר

git cherry-pick <hash>    # מעתיק commit ספציפי ל-branch הנוכחי

שימושי כשצריך רק commit אחד מ-branch אחר (למשל hotfix דחוף), בלי למזג את הכל.

Interactive Rebase — לנקות היסטוריה

git rebase -i HEAD~3      # עורך את 3 ה-commits האחרונים

מאפשר לך לאחד commits (squash), לשנות הודעות (reword), למחוק, או לשנות סדר — לפני שאתה דוחף. נפוץ מאוד: לנקות סדרה של "wip", "fix typo", "oops" ל-commit אחד נקי לפני PR. (זהירות: משכתב היסטוריה — רק על מקומי!)

bisect — לצוד באג בהיסטוריה

git bisect start
git bisect bad           # ה-commit הנוכחי שבור
git bisect good <hash>   # commit ישן שעבד
# Git עושה binary search בין השניים, קופץ ל-commit באמצע כל פעם
# אתה בודק ואומר good/bad, עד שהוא מוצא את ה-commit ששבר

גאוני לבאגים "מתי זה נשבר?". במקום לחפש ידנית, binary search מוצא את ה-commit האשם ב-log(n) בדיקות. (זוכר binary search ממדריך SQL/indexes? אותו רעיון).

Tags — סימון גרסאות

git tag v1.0.0                    # מסמן commit כגרסה
git tag -a v1.0.0 -m "Release"    # tag עם הודעה
git push origin v1.0.0            # דוחף את ה-tag

Tags מסמנים נקודות חשובות (releases). זה מה שמאפשר לחזור בדיוק ל"גרסה שרצה בפרודקשן" (זוכר image tags ממדריך DevOps? רעיון קרוב).

13. אסטרטגיות Branching

איך צוות מארגן את ה-branches שלו. שתי גישות עיקריות:

Trunk-Based Development

הגישה המודרנית והפשוטה. כולם עובדים על branches קצרי-חיים (יום-יומיים) שנמזגים מהר ל-main. main תמיד ניתן לפריסה. מסתמך על CI חזק ו-feature flags. מומלץ לרוב הצוותים — פשוט, מהיר, פחות merge hell.

Git Flow

גישה ותיקה ומורכבת יותר: branches נפרדים ל-main, develop, feature/*, release/*, hotfix/*. מתאים למוצרים עם releases מתוזמנים וגרסאות נתמכות מרובות, אבל overhead כבד לרוב הפרויקטים המודרניים (שמפרסים כל יום).

ההמלצה (ושוב, אותו עיקרון מכל הסדרה): התחל עם trunk-based — branches קצרים, merge מהיר ל-main, CI שמגן. Git Flow הוא over-engineering לרוב הצוותים היום, בדיוק כמו microservices ו-Kubernetes מוקדם מדי. אמץ מורכבות רק כשמודל השחרור שלך באמת מצריך אותה.

14. Best Practices וטעויות נפוצות

  1. Commit לעתים קרובות, קטן ואטומי — שינוי לוגי אחד per commit.
  2. הודעות commit משמעותיות — מה ולמה, בציווי. "This commit will...".
  3. branch לכל feature/fix — main תמיד יציב וניתן לפריסה.
  4. Pull לפני שמתחילים ולפני push — הישאר מסונכרן, מנע conflicts.
  5. PRs קטנים וממוקדים — מקבלים review אמיתי.
  6. revert למשהו שדחפת, reset רק למקומי — אל תשכתב היסטוריה משותפת.
  7. אף פעם לא secrets ב-git — .gitignore לפני ה-commit הראשון.
  8. branches קצרי-חיים — ככל שחי יותר, יותר conflicts.
  9. נקה היסטוריה עם rebase -i לפני PR (רק על מקומי).
  10. זכור את git reflog — רשת הביטחון כשנדמה שהרסת.

טעויות נפוצות

  • commit ל-.env/secrets — הטעות המסוכנת ביותר.
  • rebase על branch משותף — שובר לאחרים. הכלל הזהב.
  • reset --hard בלי מחשבה — הפקודה היחידה שמוחקת עבודה.
  • commits ענקיים ("כל השבוע") — אי אפשר לעשות review או revert.
  • הודעות "fix"/"changes" — history חסר ערך.
  • branch שחי שבועיים — merge hell מובטח.
  • לפחד מ-conflicts — הם שאלה, לא נזק. --abort תמיד מציל.

15. Cheat Sheet

# --- הלולאה היומיומית ---
git status                      # מה קורה עכשיו (הרץ הרבה!)
git add .                       # הכל ל-staging
git commit -m "message"         # שמור snapshot
git push                        # דחוף ל-remote
git pull                        # משוך ושלב מ-remote

# --- Branches ---
git switch -c feature-x         # צור ועבור ל-branch חדש
git switch main                 # חזור ל-main
git merge feature-x             # שלב branch ל-נוכחי
git branch -d feature-x         # מחק branch

# --- מידע ---
git log --oneline --graph       # היסטוריה ויזואלית
git diff                        # מה השתנה
git show <hash>                  # פרטי commit

# --- ביטול ---
git restore file                # בטל שינוי לא-staged
git restore --staged file       # הוצא מ-staging
git commit --amend              # תקן commit אחרון
git reset --soft HEAD~1         # בטל commit, שמור שינויים
git revert <hash>               # בטל commit שדחפת (בטוח)
git stash / git stash pop       # שמור בצד / החזר
git reflog                      # רשת ביטחון — מצא commits "אבודים"

# --- Remote ---
git clone <url>                  # העתק repo
git fetch                       # הורד בלי לשלב
git push -u origin feature-x    # דחוף branch חדש

# --- מתקדם ---
git rebase main                 # יישר branch על main (מקומי!)
git rebase -i HEAD~3            # נקה 3 commits אחרונים
git cherry-pick <hash>          # העתק commit בודד
git bisect start                # צוד באג ב-binary search
git tag v1.0.0                  # סמן גרסה

סיכום — מה הלאה

שני דברים לקחת: המודל המנטלי — Git שומר snapshots, branch הוא מצביע, ושלושת האזורים (working/staging/repo) הם המפתח — ברגע שזה מתיישב, הכל הגיוני. והשני: Git כמעט תמיד הפיך (reflog), אז אל תפחד להתנסות. הפחד מ-Git נובע מחוסר הבנה של המודל, לא ממורכבות אמיתית.

שים לב איך זה מתחבר לסדרה: PRs ו-code review נפגשים עם CI/CD (DevOps), secrets ב-gitignore חוזרים מ-Auth ו-DevOps, ו-branches קצרי-חיים הם אותו עיקרון "פשוט לפני מורכב" שחזר בכל מדריך.

הצעד הבא הוא מושלם עבורך עכשיו: אתה הולך לבנות את פרויקט ה-RAG — עשה אותו עם Git מהרגע הראשון. git init, commits קטנים ואטומיים לאורך הדרך, branch לכל feature, ודחוף ל-GitHub. ככה תתרגל את כל מה שכאן על קוד אמיתי — וגם יהיה לך את הפרויקט ב-portfolio.

וכשתחזור עם הקוד ביד — Clean Code + Design Patterns מחכה, ואז תוכל לראות את העקרונות על משהו שאתה כתבת. בהצלחה בבנייה! 🚀
