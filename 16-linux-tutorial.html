1. מבוא: מה זה Linux והפילוסופיה

Linux היא מערכת הפעלה חופשית ובקוד פתוח, ששולטת בשרתים — כמעט כל שרת web, cloud instance, ו-container רץ עליה. אם אתה מפתח Backend, אתה עובד עם Linux בין אם אתה יודע ובין אם לא (זוכר את הסביבה של Docker ממדריך DevOps? זה Linux).

Kernel מול Distribution

נקודה שמבלבלת: Linux הוא בעצם רק ה-kernel (זוכר ממדריך systems? הליבה שמנהלת חומרה, processes, זיכרון). Distribution (distro) = ה-kernel + כלים + package manager + הגדרות, ארוזים יחד. הנפוצים: Ubuntu/Debian (apt, הכי נפוץ לשרתים), RHEL/CentOS/Fedora (dnf/yum, בארגונים), Alpine (זעיר, נפוץ ב-containers — זוכר node:20-alpine?). ברמת ה-shell הם כמעט זהים; ההבדל העיקרי הוא ב-package manager.

שתי הפילוסופיות שמסבירות הכל

  • "Everything is a file" — ב-Linux, כמעט הכל מיוצג כקובץ: קבצים רגילים, תיקיות, התקנים (/dev/sda = הדיסק), ואפילו מידע על תהליכים (/proc). זה מאחד את הממשק — אותן פקודות (read/write) עובדות על הכל.
  • "Small tools that do one thing well" — במקום כלי ענק אחד, Linux נותן הרבה כלים קטנים (grep, sort, wc), ומחברים אותם עם pipes (פרק 8). זה הכוח האמיתי של ה-shell — הרכבת כלים פשוטים לפתרונות חזקים.

שתי הפילוסופיות האלה הן למה ה-shell של Linux כל כך חזק, ולמה שווה להשקיע בו.

2. ה-Shell — bash והטרמינל

ה-shell הוא התוכנית שמפרשת את הפקודות שאתה מקליד. הנפוץ ביותר הוא bash (ויש גם zsh, fish). ה-terminal הוא החלון שבו ה-shell רץ. זה הממשק העיקרי שלך לשרת.

מבנה של פקודה

command  -flags  arguments
ls       -la     /home/user
│         │        │
פקודה    דגלים   ארגומנט (על מה לפעול)

ה-Prompt וקיצורים שחוסכים זמן

ה-prompt (user@host:~$) מראה מי אתה, איזה שרת, ואיפה אתה. הקיצורים שכל משתמש shell חייב:

  • Tab — השלמה אוטומטית של שמות קבצים/פקודות. תשתמש בזה כל הזמן — חוסך הקלדות ומונע שגיאות.
  • ↑ / ↓ — מעבר בהיסטוריית הפקודות.
  • Ctrl+R — חיפוש בהיסטוריה (הקלד חלק מפקודה קודמת). קיצור מציל-חיים.
  • Ctrl+C — עצירת הפקודה הרצה. Ctrl+D — סוף קלט/יציאה.
  • Ctrl+A/Ctrl+E — תחילת/סוף השורה. Ctrl+L — ניקוי מסך.
  • !! — הפקודה הקודמת (למשל sudo !! = הרץ שוב עם sudo).

עזרה — כשלא זוכרים

man ls          # המדריך המלא של פקודה (q ליציאה)
ls --help       # עזרה מהירה
which node      # איפה הפקודה ממוקמת
type cd         # מה זה (built-in / alias / קובץ)

עצה למתחיל: אל תנסה לזכור את כל הפקודות בעל-פה. תזכור את השמות ואת --help/man. השאיפה היא שטף — לנוע בנוחות, לא לדעת הכל. Tab-completion ו-Ctrl+R יעשו אותך מהיר יותר מלשנן פקודות.

3. Filesystem Hierarchy — מפת התיקיות

ב-Linux הכל תחת שורש אחד — / (root). אין "C:" ו-"D:" כמו Windows. הבנת מה כל תיקייה עושה חוסכת בלבול ומכוונת אותך כשמחפשים קבצים בשרת.

תיקייהמה יש שם
/השורש — הכל מתחתיו
/home/userקבצי המשתמש (~ = הבית שלך)
/etcקבצי הגדרות של המערכת והשירותים — פה תערוך config
/varנתונים משתנים — /var/log = לוגים! (חשוב לדיבוג)
/usrתוכניות וספריות מותקנות (/usr/bin)
/bin, /sbinפקודות בסיס (ls, cp) / פקודות מערכת (root)
/tmpקבצים זמניים (נמחקים ב-reboot)
/procמידע על תהליכים ומערכת (וירטואלי — זוכר "everything is a file"?)
/devהתקנים (דיסקים, etc)
/optתוכנות צד-שלישי

השתיים שתשתמש בהן הכי הרבה בדיבוג: /etc (הגדרות — "איפה ה-config של nginx?" → /etc/nginx/) ו-/var/log (לוגים — "למה השירות נפל?" → /var/log/). כשמשהו לא עובד בשרת, הלוגים ב-/var/log הם המקום הראשון להסתכל.

נתיבים מוחלטים מול יחסיים

/home/user/app/config.js   # מוחלט — מהשורש, תמיד אותו מקום
./config.js                # יחסי — מהתיקייה הנוכחית
../                        # תיקייה אחת למעלה
~                         # הבית שלך (/home/user)
~/app                     # app בתוך הבית

4. ניווט ופעולות על קבצים

ניווט וצפייה

pwd                 # איפה אני עכשיו (print working directory)
ls                  # רשימת קבצים
ls -la              # מפורט (permissions, גודל) + מוסתרים (מתחילים ב-.)
ls -lh              # גדלים קריאים (KB/MB)
cd /path            # מעבר תיקייה
cd ..               # תיקייה למעלה
cd ~  /  cd         # הביתה
cd -                # חזרה לתיקייה הקודמת

צפייה בקבצים

cat file.txt        # הצג הכל (לקבצים קטנים)
less file.txt       # דפדוף (חצים, /חיפוש, q ליציאה) — לקבצים גדולים
head -20 file       # 20 שורות ראשונות
tail -20 file       # 20 שורות אחרונות
tail -f app.log     # ⭐ "עוקב" — מציג שורות חדשות בזמן אמת (לדיבוג לוגים!)

פעולות על קבצים ותיקיות

touch file.txt          # יוצר קובץ ריק
mkdir mydir             # יוצר תיקייה
mkdir -p a/b/c          # יוצר שרשרת תיקיות
cp file.txt backup.txt  # העתקה
cp -r dir1 dir2         # העתקת תיקייה (recursive)
mv old.txt new.txt      # העברה / שינוי שם
rm file.txt             # מחיקה
rm -r mydir             # מחיקת תיקייה
rm -rf mydir            # ⚠️ מחיקה בכוח, בלי שאלות — זהירות!

חיפוש קבצים

find /path -name "*.log"        # לפי שם
find . -type f -mtime -7        # קבצים ששונו בשבוע האחרון
find . -size +100M              # גדולים מ-100MB (למצוא מה תופס מקום)
locate filename                 # מהיר (מ-index, אם מותקן)

⚠️ הפקודה המסוכנת ביותר ב-Linux: rm -rf מוחקת הכל, מיד, בלי סל מיחזור ובלי אישור. rm -rf / (עם רווח או משתנה ריק בטעות) יכולה למחוק את כל השרת. תמיד תבדוק פעמיים את הנתיב לפני rm -rf, ואף פעם אל תריץ אותה על משתנה בלי לוודא שהוא לא ריק (rm -rf "$DIR/" כש-$DIR ריק = אסון). זה שקול ל-DROP TABLE בלי WHERE ממדריך SQL.

חלק ב' — הרשאות וטקסט

5. Permissions ו-Ownership

אחד הנושאים הכי חשובים ב-Linux, ומקור נפוץ ל-"permission denied". כל קובץ שייך למשתמש וקבוצה, ויש לו הרשאות לשלושה סוגי גישה.

קריאת הפלט של ls -l

$ ls -l
-rwxr-xr--  1  eliya  developers  4096  Jan 1  app.sh
│└┬┘└┬┘└┬┘      │       │
│ │  │  │       │       └─ group (הקבוצה שהקובץ שייך לה)
│ │  │  │       └─ owner (המשתמש שהקובץ שייך לו)
│ │  │  └─ other (כל השאר):  r--  (קריאה בלבד)
│ │  └─ group:               r-x  (קריאה + הרצה)
│ └─ owner:                  rwx  (קריאה + כתיבה + הרצה)
└─ סוג:  -=קובץ  d=תיקייה  l=link

שלוש ההרשאות

  • r (read) = 4 — קריאת קובץ / רשימת תיקייה.
  • w (write) = 2 — עריכת קובץ / הוספה-מחיקה בתיקייה.
  • x (execute) = 1 — הרצת קובץ / כניסה לתיקייה.

chmod — שינוי הרשאות (ה-octal)

מחברים את הערכים לכל קבוצה: rwx = 4+2+1 = 7, r-x = 4+1 = 5, r-- = 4. אז chmod 755 = owner מלא (7), group ו-other קריאה+הרצה (5):

chmod 755 script.sh    # rwxr-xr-x — נפוץ לסקריפטים/תוכניות
chmod 644 file.txt     # rw-r--r-- — נפוץ לקבצים רגילים
chmod 600 secret.key   # rw------- — רק owner (secrets! זוכר מ-SSH keys)
chmod +x script.sh     # מוסיף הרצה (דרך קלה — בלי octal)

המספרים לזכור: 755 (הרצה — סקריפטים, תיקיות), 644 (קבצים רגילים), 600 (פרטי — מפתחות וסודות).

chown — שינוי בעלות

chown eliya file.txt          # שנה owner
chown eliya:developers file   # owner:group
chown -R eliya /app           # recursive על תיקייה שלמה

מעשי: "Permission denied" בשרת = כמעט תמיד בעיית permissions/ownership. הרץ ls -l על הקובץ, בדוק מי ה-owner ומה ההרשאות, ותקן עם chmod/chown. וזוכר chmod 600 לסודות? זו בדיוק הסיבה ש-SSH דורש הרשאות מחמירות על מפתחות (פרק 14) — קובץ מפתח קריא-לכולם נדחה.

6. Users, Groups ו-sudo

Linux היא multi-user מהיסוד — כמה משתמשים חולקים מכונה, כל אחד עם הרשאות משלו (זוכר user/kernel mode ובידוד ממדריך systems?).

root — המשתמש העל

root (UID 0) הוא המנהל — הרשאות מלאות לכל דבר. עוצמתי ומסוכן: טעות כ-root יכולה להרוס את המערכת. לכן לא עובדים כ-root ביומיום — משתמשים ב-sudo לפעולות ספציפיות.

sudo — "הרץ את זה כ-root, פעם אחת"

sudo apt update          # מריץ פקודה אחת עם הרשאות root
sudo systemctl restart nginx
sudo !!                  # הרץ שוב את הפקודה הקודמת עם sudo
sudo su                  # הפוך ל-root (זהירות!)

העיקרון (חוזר ממדריכי Auth ו-systems): least privilege — הרשאות מינימליות. השתמש ב-sudo רק כשצריך, לא תעבוד כ-root כברירת מחדל. כל sudo נרשם ב-log — יש accountability.

Users ו-groups

whoami                   # מי אני
id                       # ה-UID, GID והקבוצות שלי
groups                   # לאילו קבוצות אני שייך
sudo useradd -m newuser  # יצירת משתמש
sudo usermod -aG docker eliya   # הוסף את eliya לקבוצת docker
cat /etc/passwd          # רשימת המשתמשים (everything is a file!)

Groups מאפשרים לתת הרשאות לכמה משתמשים יחד (למשל, כל מי שבקבוצת docker יכול להריץ containers). זה מקביל ל-roles/permissions ממדריך Auth, ברמת ה-OS.

7. כלי עיבוד טקסט — grep, sed, awk

כאן הכוח האמיתי של ה-shell. Linux מלא בכלים קטנים לעיבוד טקסט, ובשילוב עם pipes (פרק 8) הם הופכים לכלי דיבוג וניתוח עוצמתיים — במיוחד על לוגים.

grep — חיפוש בטקסט

הכלי שתשתמש בו הכי הרבה. מחפש שורות שמכילות תבנית:

grep "error" app.log              # שורות עם "error"
grep -i "error" app.log           # case-insensitive
grep -r "TODO" ./src              # חיפוש רקורסיבי בתיקייה
grep -n "error" app.log           # עם מספרי שורות
grep -v "debug" app.log           # שורות שה-NOT מכילות (invert)
grep -c "error" app.log           # ספירת התאמות
grep -A 3 -B 3 "error" app.log    # 3 שורות אחרי (After) ולפני (Before)

שימוש קלאסי לדיבוג: grep -i error /var/log/app.log — מצא את כל השגיאות בלוג.

sed — עריכה והחלפה בזרם

sed 's/old/new/g' file.txt        # החלף old ב-new (בכל מופע)
sed -i 's/old/new/g' file.txt     # -i = ערוך את הקובץ במקום
sed -n '10,20p' file.txt          # הדפס שורות 10-20
sed '/pattern/d' file.txt         # מחק שורות שמתאימות

awk — עיבוד לפי עמודות

awk '{print $1}' file             # העמודה הראשונה של כל שורה
awk '{print $1, $3}' file         # עמודות 1 ו-3
awk -F',' '{print $2}' file.csv   # מפריד לפי פסיק (CSV!)
awk '{sum += $1} END {print sum}' # סכום העמודה הראשונה
ps aux | awk '{print $2, $11}'    # PID ושם התהליך

כלי עזר נוספים

sort file.txt          # מיון שורות
sort -u file.txt       # מיון + הסרת כפילויות
uniq -c file.txt       # ספירת שורות ייחודיות
wc -l file.txt         # ספירת שורות (l=lines)
cut -d',' -f2 file.csv # חיתוך עמודה
tr 'a-z' 'A-Z'         # החלפת תווים

למה זה כלי-על: כל אלה נראים פשוטים, אבל בשילוב (פרק 8) הם עוצמתיים. "כמה שגיאות מכל סוג היו בלוג?" זו שורה אחת: grep error app.log | awk '{print $5}' | sort | uniq -c | sort -rn. זה הכוח של "small tools + pipes" — במקום לכתוב סקריפט, מרכיבים כלים. שווה להשקיע ב-grep וב-pipes; הם משנים איך אתה עובד עם שרתים ולוגים.

8. Redirection ו-Pipes

המנגנון שמחבר את הכלים יחד, והלב של פילוסופיית Unix. הכל מבוסס על שלושה "זרמים" סטנדרטיים (זוכר process.stdout ממדריך Node?).

שלושת הזרמים

  • stdin (0) — קלט (בד"כ מהמקלדת).
  • stdout (1) — פלט רגיל.
  • stderr (2) — פלט שגיאות (נפרד מ-stdout!).

Redirection — הפניית זרמים

command > file.txt      # שלח stdout לקובץ (דורס)
command >> file.txt     # הוסף לסוף הקובץ (append)
command < input.txt     # קרא stdin מקובץ
command 2> errors.txt   # שלח stderr לקובץ
command > out.txt 2>&1  # שלח גם stdout וגם stderr לאותו קובץ
command > /dev/null 2>&1 # "זרוק" את כל הפלט (שקט מוחלט)

Pipes — חיבור פקודות

ה-pipe (|) לוקח את ה-stdout של פקודה אחת ומכניס אותו כ-stdin של הבאה. זה מה שמחבר את הכלים הקטנים לשרשראות עוצמתיות (זוכר pipes ממדריך systems? זה IPC):

# מצא את 10 ה-IP שהכי פנו לשרת (ניתוח access log):
cat access.log | awk '{print $1}' | sort | uniq -c | sort -rn | head -10

# כמה processes של node רצים:
ps aux | grep node | grep -v grep | wc -l

# התהליכים שהכי אוכלים זיכרון:
ps aux | sort -k4 -rn | head -5

כל pipe מעביר את הפלט הלאה. אתה בונה פתרון על ידי הרכבת כלים — לא כותב תוכנית. זה הכוח שהופך את ה-shell למכונת ניתוח.

חלק ג' — תהליכים ומערכת

9. Processes — ניהול תהליכים

כל תוכנית רצה היא process (זוכר ממדריך systems? עם PID, זיכרון, ו-address space משלו). ניהול processes הוא ליבת העבודה בשרת — לראות מה רץ, מה תקוע, ומה אוכל משאבים.

לראות מה רץ

ps aux                  # כל התהליכים (user, PID, CPU%, MEM%, command)
ps aux | grep node      # רק תהליכי node
top                     # ניטור חי — מתעדכן, ממוין לפי CPU (q ליציאה)
htop                    # גרסה יפה ואינטראקטיבית (אם מותקן) — מומלץ

הריגת תהליכים ו-Signals

זוכר signals ממדריך systems/Node (SIGTERM, graceful shutdown)? כאן משתמשים בהם:

kill 1234            # שולח SIGTERM (בקשה מנומסת לסיים — graceful)
kill -9 1234         # SIGKILL (הריגה בכוח — מוצא אחרון, לא graceful!)
kill -15 1234        # SIGTERM מפורש
pkill node           # הרוג לפי שם
killall node         # הרוג את כל תהליכי node

נקודה חשובה: העדף kill (SIGTERM) על kill -9 (SIGKILL). SIGTERM נותן לתהליך לסגור בחן — לסיים בקשות, לסגור חיבורי DB (זוכר graceful shutdown ממדריך Node?). SIGKILL קוטע מיד ויכול להשאיר נתונים במצב לא-עקבי. השתמש ב--9 רק כשהתהליך לא מגיב ל-SIGTERM.

Jobs — רקע וקדמה

command &             # הרץ ברקע
Ctrl+Z                # השהה את התהליך הנוכחי
bg                    # המשך אותו ברקע
fg                    # החזר לקדמה
jobs                  # רשימת jobs ברקע
nohup command &       # הרץ ברקע שישרוד גם אחרי סגירת ה-terminal

nohup חשוב: בלעדיו, סגירת חיבור ה-SSH הורגת את התהליכים שהרצת. בפועל ל-production משתמשים ב-systemd (הפרק הבא) או pm2, לא nohup.

10. systemd ו-Services

איך שירות (השרת שלך, nginx, postgres) רץ ברקע, עולה אוטומטית ב-boot, ומופעל מחדש אם קרס? התשובה ברוב ה-distros המודרניים היא systemd — מנהל השירותים של המערכת.

systemctl — שליטה בשירותים

sudo systemctl start nginx      # הפעל שירות
sudo systemctl stop nginx       # עצור
sudo systemctl restart nginx    # הפעל מחדש
sudo systemctl reload nginx     # טען config מחדש בלי restart מלא
systemctl status nginx          # ⭐ מצב השירות — רץ? נפל? למה?
sudo systemctl enable nginx     # יעלה אוטומטית ב-boot
sudo systemctl disable nginx    # לא יעלה ב-boot
systemctl list-units --type=service   # כל השירותים

journalctl — הלוגים של systemd

כששירות נופל, כאן מסתכלים. journalctl נותן את הלוגים של systemd:

journalctl -u nginx             # לוגים של שירות ספציפי
journalctl -u nginx -f          # עוקב בזמן אמת (כמו tail -f)
journalctl -u nginx --since "10 min ago"
journalctl -u nginx -n 50       # 50 השורות האחרונות
journalctl -p err               # רק שגיאות

הצירוף systemctl status <service> + journalctl -u <service> -f הוא ה-workflow לדיבוג שירות שלא עובד.

יצירת service משלך

כדי שהאפליקציה שלך (Node/Python) תרוץ כשירות מנוהל — יוצרים unit file ב-/etc/systemd/system/myapp.service:

[Unit]
Description=My Node App
After=network.target

[Service]
ExecStart=/usr/bin/node /app/main.js
Restart=always              # הפעל מחדש אוטומטית אם קרס!
User=eliya
Environment=NODE_ENV=production

[Install]
WantedBy=multi-user.target

Restart=always הוא הקסם — self-healing ברמת ה-OS (זוכר reliability ממדריך System Design?). זו דרך אחת להריץ אפליקציה ב-production; החלופות: Docker (מדריך DevOps), pm2, או PaaS.

11. Package Management

איך מתקינים תוכנות ב-Linux. לכל distro יש package manager, אבל הרעיון זהה: מאגר מרכזי של חבילות עם ניהול תלויות אוטומטי.

Debian/Ubuntu — apt

sudo apt update              # רענן את רשימת החבילות (תמיד קודם!)
sudo apt upgrade             # שדרג חבילות מותקנות
sudo apt install nginx       # התקן
sudo apt remove nginx        # הסר
sudo apt search postgres     # חפש חבילה
apt list --installed         # מה מותקן

RHEL/Fedora/CentOS — dnf/yum

sudo dnf install nginx       # (או yum בגרסאות ישנות)
sudo dnf update
sudo dnf remove nginx

הבדל דיאלקט (זוכר SQL dialects?): Ubuntu/Debian = apt, RHEL/Fedora = dnf/yum, Alpine = apk (ה-image הזעיר ב-Docker). הפקודות שונות אבל הרעיון זהה. ב-Dockerfile (מדריך DevOps) תראה apt-get install — זה בדיוק זה, בתוך ה-container. תמיד apt update לפני install, אחרת תתקין גרסאות ישנות.

12. ניטור משאבים

כשהשרת איטי או נתקע — כאן בודקים למה. ארבעה משאבים לבדוק: CPU, זיכרון, דיסק, ורשת.

זיכרון

free -h              # RAM פנוי/בשימוש (h = קריא)
# שים לב ל-"available" — כמה באמת פנוי לאפליקציות
# אם swap גבוה בשימוש = חוסר RAM, swapping (זוכר ממדריך systems? איטי!)

דיסק

df -h                # מקום פנוי בכל הדיסקים/partitions
du -sh /var/log      # כמה תופסת תיקייה מסוימת
du -sh * | sort -rh  # מה תופס הכי הרבה בתיקייה הנוכחית
# "disk full" (100% ב-df) = סיבה נפוצה לשירות שנופל!

CPU ועומס

top / htop           # CPU% לכל תהליך, load average
uptime               # load average (1/5/15 דקות)
# load average ~= מספר ה-cores = עומס מלא. גבוה בהרבה = עומס יתר.

מבט כללי מהיר

vmstat 1             # סטטיסטיקות מערכת כל שנייה
iostat               # I/O של דיסק (אם מותקן)
cat /proc/loadavg    # load (everything is a file!)

ה-workflow לדיבוג "השרת איטי": (1) top/htop — CPU גבוה? מי? (2) free -h — נגמר RAM? swapping? (3) df -h — דיסק מלא? (4) journalctl//var/log — מה הלוגים אומרים? רוב הבעיות בשרת הן אחד מ: CPU עמוס (זוכר "אל תחסום את ה-event loop" ממדריך Node?), חוסר RAM (memory leak — מדריך Node/systems), או דיסק מלא. הרחבנו על זה ב-playbook בפרק 18.

חלק ד' — רשת, SSH, סקריפטים

13. Networking על השרת

מדריך Networking כיסה את התיאוריה (TCP/IP, ports, DNS). כאן — הפקודות המעשיות לבדוק רשת על שרת. חיוני לדיבוג "למה השירות לא נגיש".

מי מאזין על אילו ports

הפקודה הכי חשובה לדיבוג רשת בשרת:

ss -tlnp             # כל ה-ports שמאזינים (TCP), עם התהליך
# t=TCP, l=listening, n=numeric, p=process
sudo ss -tlnp | grep 3000    # מי מאזין על port 3000?
netstat -tlnp        # הגרסה הישנה (ss מהיר יותר)
lsof -i :3000        # מי תופס את port 3000 (זוכר "port in use" ממדריך Node?)

שימוש קלאסי: "השרת שלי אמור לרוץ על 3000 אבל לא נגיש" → ss -tlnp | grep 3000 → אם ריק, האפליקציה לא עלתה או מאזינה על port אחר.

בדיקת קישוריות

curl http://localhost:3000/health   # בדוק endpoint (זוכר מ-Networking?)
curl -I https://example.com         # רק headers
ping google.com                     # האם יש קישוריות בכלל
dig example.com                     # שאילתת DNS (זוכר מ-Networking?)
traceroute example.com              # המסלול לשרת

Firewall — מה חסום

# ufw (Ubuntu — פשוט):
sudo ufw status              # מה מותר/חסום
sudo ufw allow 443           # פתח port
sudo ufw allow 22            # SSH (זהירות לא לחסום את עצמך!)

# iptables (הבסיסי, מורכב יותר):
sudo iptables -L             # רשימת כללים

מלכודת נפוצה: "האפליקציה רצה אבל לא נגישה מבחוץ" — לרוב זה firewall (ה-port חסום) או שהאפליקציה מאזינה על 127.0.0.1 (localhost בלבד) במקום 0.0.0.0 (כל הכתובות). בדוק עם ss -tlnp: אם רשום 127.0.0.1:3000 — זה נגיש רק מהשרת עצמו. זה מחבר לכל מה שלמדת ב-Networking על IP binding ו-firewall.

14. SSH לעומק

SSH (Secure Shell) הוא איך אתה מתחבר לשרת מרוחק (זוכר מ-Networking? port 22, מוצפן). זה הכלי שדרכו תעבוד עם כל שרת production.

התחברות בסיסית

ssh user@server.com           # התחבר
ssh user@1.2.3.4 -p 2222      # port לא-סטנדרטי
exit                          # התנתק

SSH Keys — אימות בלי סיסמה (ובטוח יותר)

במקום סיסמה, SSH keys נותנים אימות מבוסס public/private key (זוכר הצפנה א-סימטרית ממדריך Networking/Auth?). בטוח יותר ונוח יותר:

# צור זוג מפתחות (פעם אחת):
ssh-keygen -t ed25519 -C "eliya@x.com"
# נוצרים: ~/.ssh/id_ed25519 (private — סודי!) + .pub (public)

# העתק את ה-public key לשרת:
ssh-copy-id user@server.com

# עכשיו מתחברים בלי סיסמה:
ssh user@server.com

ה-private key נשאר אצלך (אף פעם לא משתפים!), ה-public key יושב בשרת ב-~/.ssh/authorized_keys. השרת "מאתגר" אותך, ורק ה-private key שלך יכול לענות. זה בדיוק המנגנון של TLS certificates ממדריך Networking.

הרשאות — מלכודת נפוצה

זוכר chmod 600 מפרק 5? SSH דורש הרשאות מחמירות על המפתחות, אחרת הוא מסרב לעבוד (מטעמי אבטחה):

chmod 700 ~/.ssh
chmod 600 ~/.ssh/id_ed25519        # private key — רק אתה
chmod 644 ~/.ssh/id_ed25519.pub

SSH config — לחסוך הקלדות

# ~/.ssh/config
Host myserver
    HostName 1.2.3.4
    User eliya
    Port 2222
    IdentityFile ~/.ssh/id_ed25519
# עכשיו פשוט:  ssh myserver

העברת קבצים ו-tunneling

scp file.txt user@server:/path/     # העתק קובץ לשרת
scp -r dir user@server:/path/       # תיקייה
scp user@server:/path/file.txt .    # הורד מהשרת

# Tunneling — גישה ל-port מרוחק דרך SSH (למשל DB פנימי):
ssh -L 5432:localhost:5432 user@server
# עכשיו localhost:5432 שלך = ה-Postgres בשרת המרוחק

15. Environment ו-Config

Environment Variables

זוכר env vars ממדריכי Node/DevOps (config, secrets)? הנה איך הם עובדים ב-shell:

echo $PATH               # הצג משתנה
export API_KEY="secret"  # הגדר משתנה (לסשן הנוכחי)
env                      # כל המשתנים
printenv PATH            # משתנה ספציפי
NODE_ENV=production node app.js   # משתנה לפקודה בודדת

PATH — איך ה-shell מוצא פקודות

PATH הוא רשימת התיקיות שבהן ה-shell מחפש פקודות. כשאתה מקליד node, ה-shell עובר על תיקיות ה-PATH עד שמוצא. זו הסיבה ל-"command not found" — התוכנית לא ב-PATH. which node מראה איפה נמצאה. מוסיפים ל-PATH: export PATH="$PATH:/new/dir".

קבצי config של ה-shell

# ~/.bashrc — רץ בכל פתיחת terminal. פה שמים:
export PATH="$PATH:$HOME/bin"     # הוספות ל-PATH
export NODE_ENV=development        # env vars קבועים
alias ll="ls -la"                  # קיצורים
alias gs="git status"

source ~/.bashrc                   # טען מחדש בלי לפתוח terminal חדש

Aliases חוסכים הקלדות על פקודות חוזרות. ~/.bashrc (או ~/.zshrc ל-zsh) הוא איפה שמתאימים אישית את הסביבה שלך.

16. Bash Scripting

bash הוא לא רק פקודות — הוא שפת תכנות. סקריפטים מאפשרים לאוטמט משימות חוזרות (deploy, backup, setup). לא צריך להיות מומחה, אבל לדעת לקרוא ולכתוב סקריפט בסיסי חיוני.

סקריפט בסיסי

#!/bin/bash               # "shebang" — איזה interpreter (חובה בשורה 1)

NAME="Eliya"              # משתנה (בלי רווחים סביב =!)
echo "Hello $NAME"        # שימוש עם $
echo "Files: $(ls | wc -l)"   # $(...) = תוצאת פקודה
chmod +x script.sh        # הפוך לניתן-הרצה (זוכר chmod?)
./script.sh               # הרץ

תנאים

if [ -f "config.json" ]; then       # -f = הקובץ קיים?
  echo "Config found"
elif [ "$NODE_ENV" == "production" ]; then
  echo "Prod mode"
else
  echo "No config"
fi

# בדיקות נפוצות: -f (קובץ), -d (תיקייה), -z (string ריק), == , -eq (מספרים)

לולאות

for file in *.log; do               # על כל קובץ log
  echo "Processing $file"
  gzip "$file"
done

for i in {1..5}; do echo $i; done   # טווח

while read line; do                 # קריאת קובץ שורה-שורה
  echo "$line"
done < input.txt

ארגומנטים, exit codes, ו-functions

#!/bin/bash
# ארגומנטים: $1, $2 ... $@ (כולם), $# (כמות)
echo "First arg: $1"

deploy() {                          # function
  local env=$1
  echo "Deploying to $env"
}
deploy production

# Exit codes (זוכר ממדריך Node? 0=הצלחה):
if [ $? -ne 0 ]; then               # $? = exit code של הפקודה הקודמת
  echo "Previous command failed"
  exit 1
fi

סקריפט אמיתי — deploy פשוט

#!/bin/bash
set -e                              # ⭐ עצור בכל שגיאה (חשוב!)

echo "Pulling latest code..."
git pull origin main

echo "Installing dependencies..."
npm ci

echo "Building..."
npm run build

echo "Restarting service..."
sudo systemctl restart myapp

echo "✅ Deploy complete"

שתי הרגלים שמצילים: (1) set -e בראש כל סקריפט — עוצר בשגיאה ראשונה במקום להמשיך "עיוור" (בלעדיו, סקריפט deploy יכול להמשיך אחרי כישלון ולגרום נזק). (2) set -u — שגיאה על משתנה לא-מוגדר (מונע את אסון ה-rm -rf "$DIR" כש-DIR ריק). ביחד set -eu בראש הסקריפט = הרבה פחות באגים. ל-scripts רציניים באמת — עדיף Python על bash כשזה נהיה מורכב.

חלק ה' — מעשי

17. Cron — משימות מתוזמנות

cron מריץ פקודות אוטומטית לפי לוח זמנים — backups, ניקוי לוגים, דוחות תקופתיים. הכלי הסטנדרטי לתזמון ב-Linux.

crontab -e           # ערוך את ה-crontab שלך
crontab -l           # הצג את המשימות

פורמט ה-cron

# ┌─ דקה (0-59)
# │ ┌─ שעה (0-23)
# │ │ ┌─ יום בחודש (1-31)
# │ │ │ ┌─ חודש (1-12)
# │ │ │ │ ┌─ יום בשבוע (0-6, 0=ראשון)
# │ │ │ │ │
# * * * * *  command

0 2 * * *    /app/backup.sh              # כל יום ב-2:00 לפנות בוקר
*/15 * * * * /app/check.sh               # כל 15 דקות
0 0 * * 0    /app/weekly-report.sh       # כל יום ראשון בחצות
0 9 * * 1-5  /app/workday.sh             # 9:00, ימי חול (א-ה)

מלכודות cron: (1) cron רץ עם סביבה מינימלית — ה-PATH וה-env vars שלך לא קיימים! השתמש בנתיבים מלאים (/usr/bin/node לא node). (2) הפנה פלט לקובץ כדי לראות מה קרה: 0 2 * * * /app/backup.sh >> /var/log/backup.log 2>&1 (זוכר redirection?). (3) בדוק את הביטוי ב-crontab.guru לפני שסומכים עליו. הרבה "ה-cron לא רץ" זה בעצם PATH חסר או שגיאה שלא ראית כי לא הפנית את הפלט.

18. Production Debugging Playbook

זה החלק שמחבר הכל — ה-workflow המנטלי כשמשהו נשבר ב-production ואתה מתחבר ב-SSH. שמור את זה; זה מה שתשלוף באמת.

תרחיש א': "השרת לא מגיב / איטי"

1. htop / top     → CPU גבוה? איזה תהליך? (מדריך Node: event loop חסום?)
2. free -h      → נגמר RAM? swap בשימוש? (memory leak?)
3. df -h        → דיסק מלא? (סיבה נפוצה מאוד לקריסה!)
4. ss -tlnp    → האפליקציה מאזינה על ה-port הנכון?
5. journalctl -u myapp -n 100 → מה הלוגים אומרים?

תרחיש ב': "השירות נפל"

1. systemctl status myapp  → מה המצב? מתי נפל?
2. journalctl -u myapp -n 50 → מה השגיאה שהפילה?
3. tail -f /var/log/myapp.log → עקוב בזמן אמת
4. systemctl restart myapp  → הפעל מחדש (אחרי שהבנת למה!)

תרחיש ג': "האפליקציה רצה אבל לא נגישה מבחוץ"

1. curl localhost:3000  → עובד מקומית? (אם כן — בעיית רשת/firewall)
2. ss -tlnp | grep 3000 → מאזין על 0.0.0.0 או רק 127.0.0.1?
3. sudo ufw status    → ה-port פתוח ב-firewall?
4. (מבחוץ) curl http://server-ip:3000 → נגיש?

העיקרון של דיבוג production: אל תנחש ואל תריץ restart באופן עיוור — אסוף מידע קודם. הסדר: מה המצב (status) → מה הלוגים (journalctl/var/log) → מה המשאבים (top/free/df) → מה הרשת (ss/curl). רק אחרי שהבנת למה, תתקן. restart עיוור "פותר" את הסימפטום ומסתיר את הבעיה שתחזור. זה אותו עיקרון של EXPLAIN ANALYZE (SQL) ו-profiling (Node) — מדוד, אל תנחש. ותמיד: הלוגים ב-/var/log ו-journalctl הם המקום הראשון להסתכל.

19. Best Practices, Cheat Sheet ומשאבים

Best Practices

  1. אף פעם לא לעבוד כ-root — sudo לפעולות ספציפיות. least privilege.
  2. זהירות עם rm -rf — בדוק את הנתיב פעמיים. זה ה-DROP TABLE של Linux.
  3. Tab-completion ו-Ctrl+R — מהירות ופחות טעויות הקלדה.
  4. הלוגים תמיד ראשונים — /var/log ו-journalctl כשמשהו נשבר.
  5. SSH keys, לא סיסמאות — עם chmod 600 על ה-private key.
  6. set -eu בכל סקריפט bash — עצירה בשגיאות ובמשתנים חסרים.
  7. נתיבים מלאים ב-cron — הסביבה מינימלית.
  8. אסוף מידע לפני restart — אל תדבג עיוור.
  9. secrets ב-env / vault, לא בקוד (חוזר מ-DevOps/Git/Auth).
  10. man/--help חברים שלך — אל תשנן, תדע איפה לחפש.

Cheat Sheet — הפקודות היומיומיות

# --- ניווט וקבצים ---
ls -la / cd / pwd / cp / mv / rm / mkdir / find
cat / less / head / tail -f      # צפייה (tail -f ללוגים!)

# --- טקסט וחיפוש ---
grep -i "text" file              # חיפוש
grep -rn "text" ./dir            # רקורסיבי + מספרי שורות
command | grep / sort / uniq -c / wc -l   # pipes

# --- הרשאות ---
chmod 755 file / chmod 600 key   # הרשאות
chown user:group file            # בעלות
sudo command                     # כ-root

# --- תהליכים ---
ps aux | grep name / htop        # מה רץ
kill -15 PID / kill -9 PID       # עצירה (העדף -15)
lsof -i :3000                    # מי על ה-port

# --- שירותים ---
systemctl status/start/restart svc
journalctl -u svc -f             # לוגים בזמן אמת

# --- משאבים ---

top / uptime                     # CPU / load

# --- רשת ---

curl localhost:3000 / ping / dig

סיכום — מה הלאה

שני דברים מעל הכל: ה-shell נלמד בשטף, לא בשינון — Tab-completion, man, ו-Ctrl+R חשובים יותר מלזכור דגלים; וכשמשהו נשבר, אסוף מידע לפני שאתה מתקן — status → logs → resources → network, ורק אז restart. ה-playbook בפרק 18 הוא הלב המעשי של המדריך.

שים לב כמה Linux מחבר את כל הסדרה: processes ו-permissions הם ה-OS ממדריך systems בפעולה; ports ו-firewall הם Networking; systemd ו-secrets הם DevOps; ה-shell הוא איפה ש-Docker, git, ו-deploy באמת קורים. Linux הוא הרצפה שכל התשתית שלך עומדת עליה — וה-shell הוא איך אתה נוגע בה.

הדרך היחידה ללמוד: לחיות ב-shell. הקם VM זול בענן (DigitalOcean/AWS free tier), התחבר ב-SSH, ותשחק — התקן nginx, כתוב systemd service, פרוס את פרויקט ה-RAG שלך עליו. שרת אמיתי אחד שהקמת ותחזקת ילמד אותך יותר מכל מדריך.
