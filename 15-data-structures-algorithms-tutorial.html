חלק א' — יסודות

1. מבוא: למה DS&A

Data Structure = דרך לארגן נתונים בזיכרון. Algorithm = רצף צעדים לפתרון בעיה. הבחירה בהם קובעת אם התוכנית שלך רצה במילישניות או בדקות על אותם נתונים.

למה זה חשוב — במיוחד בעידן ה-AI

AI כותב את הקוד של אלגוריתם. אבל ההחלטה איזה מבנה נתונים ואיזה אלגוריתם מתאימים לבעיה — היא שיקול דעת הנדסי, בדיוק כמו system design. "להשתמש ב-hash map כאן במקום array" זה ההבדל בין קוד שרץ ב-O(n) לקוד שרץ ב-O(n²) — ועל מיליון פריטים זה ההבדל בין שנייה לשבועיים. AI ייתן לך פתרון; להבין למה הוא נכון, ומתי הוא לא, זה מה שהופך אותך למהנדס. וזה נשאל בכמעט כל ראיון טכני.

החיבור ל-systems

זוכר ממדריך ה-systems ש-array מנצח linked list למרות אותו Big-O, בגלל cache locality? זה בדיוק החיבור בין שני העמודים: Big-O אומר לך את הכיוון, אבל ה-systems (cache, memory) קובע את המהירות בפועל. מהנדס טוב מחזיק את שניהם בראש. נחזור לזה לאורך המדריך.

2. Big-O — ניתוח סיבוכיות

לפני כל מבנה ואלגוריתם, צריך שפה למדוד יעילות. Big-O מתאר איך זמן הריצה (או הזיכרון) גדל ככל שהקלט גדל. זו השפה המשותפת של כל הדיון על ביצועים.

הרעיון: קצב גדילה, לא זמן מדויק

Big-O לא מודד שניות — הוא מודד איך המספר גדל ביחס לגודל הקלט (n). מתעלמים מקבועים ומגורמים זניחים, ומסתכלים על המגמה כש-n גדול. O(2n + 5) נהיה פשוט O(n) — כי כש-n ענק, הקבועים לא משנים.

מחלקות הסיבוכיות — מהטוב לרע

הקפיצה שחייבים להפנים: ההבדל בין O(n) ל-O(n²) על מיליון פריטים הוא בין מיליון ל-טריליון פעולות — שנייה מול שבועות. זו הסיבה ש"רק הוספתי לולאה קטנה" יכול להרוס ביצועים. וההבדל בין O(n²) ל-O(n log n) (למשל, sort טוב מול גרוע) הוא לרוב ההבדל בין "עובד" ל"לא שמיש". זיהוי לולאות מקוננות (O(n²)) והפיכתן ל-O(n) עם hash map — זו אחת המיומנויות הכי מעשיות ב-DS&A.

איך לנתח — כללים מהירים

  • לולאה אחת על n → O(n).
  • לולאה בתוך לולאה → O(n²).
  • חצייה בכל צעד (binary search) → O(log n).
  • פעולות רצופות → מחברים, לוקחים את הגדול (O(n) + O(n²) = O(n²)).
  • מתעלמים מקבועים (O(3n) = O(n)).

Time מול Space, ו-Best/Average/Worst

Big-O מתאר גם זמן וגם זיכרון (space complexity) — לפעמים יש tradeoff ("לשלם זיכרון כדי לחסוך זמן", למשל caching/memoization). וחשוב להבחין בין worst case (הכי גרוע — בד"כ מה שמדווחים), average, ו-best. למשל hash table הוא O(1) average אבל O(n) worst (בהתנגשויות). ראיונות בד"כ שואלים על worst.

Amortized — עלות ממוצעת לאורך הרבה פעולות. דוגמה: הוספה ל-dynamic array היא O(1) amortized — רוב ההוספות זולות, ומדי פעם יש resize יקר (O(n)), אבל בממוצע זה O(1). נסביר בפרק הבא.

חלק ב' — Data Structures

3. Arrays ו-Dynamic Arrays

המבנה הבסיסי והחשוב ביותר. array הוא רצף רציף של אלמנטים בזיכרון (זוכר ממדריך systems? contiguous memory), עם גישה לפי אינדקס.

למה גישה היא O(1)

כי הזיכרון רציף: הכתובת של arr[i] = כתובת ההתחלה + i × גודל_אלמנט. חישוב אחד, גישה ישירה. אין צורך "לחפש". זה מה שהופך array למהיר כל כך לקריאה.

סיבוכיות הפעולות

פעולהBig-Oהערה
גישה arr[i]O(1)חישוב כתובת ישיר
חיפוש ערךO(n)צריך לעבור (אלא אם ממוין)
הוספה/מחיקה בסוףO(1)*amortized
הוספה/מחיקה בהתחלה/אמצעO(n)צריך להזיז את כל השאר

Dynamic Array — איך array "גדל"

array פיזי הוא בגודל קבוע. אז איך [].push() ב-JS עובד? Dynamic array: מקצים array בגודל מסוים, וכשמתמלא — מקצים חדש כפול בגודל, מעתיקים הכל, ומשחררים את הישן. ההעתקה היא O(n), אבל היא קורית לעתים רחוקות (כל הכפלה), אז ה-amortized הוא O(1) להוספה. זו הדוגמה הקלאסית ל-amortized analysis. (זוכר heap ו-memory allocation ממדריך systems? זה מה שקורה מתחת ל-push).

מתי array

ברירת המחדל לרוב המקרים: גישה מהירה לפי אינדקס, iteration, ו-cache-friendly (רציף בזיכרון — הכי מהיר בפועל, זוכר ממדריך systems?). החולשה: הוספה/מחיקה באמצע יקרה (O(n)).

4. Linked Lists

ההפך מ-array מבחינת tradeoffs. במקום רצף רציף, כל אלמנט (node) מחזיק את הערך ו-pointer לאלמנט הבא. הם מפוזרים בזיכרון.

[1|•]──→[2|•]──→[3|•]──→[4|null]
 node    node    node    node
כל node מצביע לבא (singly linked). doubly = גם לקודם.

סיבוכיות — הראי של array

פעולהLinked ListArray
גישה לאינדקס iO(n) — צריך ללכת מההתחלהO(1)
הוספה/מחיקה בהתחלהO(1) — רק לשנות pointerO(n)
הוספה/מחיקה (עם pointer ל-node)O(1)O(n)

ה-tradeoff, וה-gotcha החשוב

linked list מבריק להוספה/מחיקה בקצוות (O(1) — רק מזיזים pointers, בלי להעתיק כלום). אבל גרוע לגישה אקראית (O(n)) וגרוע ל-iteration בפועל. וכאן החיבור הקריטי ל-systems: למרות שגם array וגם linked list הם O(n) ל-iteration, array מהיר פי כמה בגלל cache locality. ה-nodes של linked list מפוזרים בזיכרון — כל גישה היא cache miss שיורד ל-RAM (זוכר פרק 6 ב-systems?). זו הסיבה שבפועל, מפתחים מנוסים מעדיפים arrays כמעט תמיד, ו-linked lists נדירים בקוד אמיתי. זו דוגמה מושלמת לאיך Big-O לבדו מטעה — צריך גם את ה-systems.

איפה linked lists כן חשובים: מבנים אחרים בנויים עליהם (queues, hash table chaining), והם מלמדים pointers ו-recursion. אבל כברירת מחדל לרשימה — array.

5. Stacks ו-Queues

שני מבנים פשוטים אבל יסודיים, שנבדלים בסדר הגישה.

Stack — LIFO (Last In, First Out)

כמו ערימת צלחות: מוסיפים ומוציאים מלמעלה. push (הוסף למעלה), pop (הוצא מלמעלה) — שניהם O(1).

const stack = [];
stack.push(1); stack.push(2);   // [1, 2]
stack.pop();                     // מחזיר 2 (האחרון שנכנס)

שימושים: ה-call stack עצמו (זוכר ממדריך systems? כל קריאת פונקציה = push frame)! גם: undo/redo, בדיקת סוגריים מאוזנים, המרת ביטויים, ו-DFS (פרק 14).

Queue — FIFO (First In, First Out)

כמו תור בסופר: הראשון שנכנס — ראשון יוצא. enqueue (הוסף בסוף), dequeue (הוצא מההתחלה).

const queue = [];
queue.push(1); queue.push(2);    // [1, 2]
queue.shift();                    // מחזיר 1 (הראשון שנכנס)
// הערה: shift ב-JS הוא O(n)! ל-queue יעיל השתמש ב-deque או linked list

שימושים: BFS (פרק 14), task queues ו-message queues (זוכר ממדריך System Design?), scheduling (זוכר scheduler ממדריך systems?), buffering. ה-queue הוא מבנה שחוזר בכל מקום שיש "לטפל לפי סדר הגעה".

נקודה מעשית: ב-JS, array.shift() (הוצאה מההתחלה) הוא O(n) כי צריך להזיז את כל האלמנטים. ל-queue בעל ביצועים, השתמש ב-deque (double-ended queue) או linked list, שם dequeue הוא O(1). זו טעות נפוצה — לבנות queue על array עם shift ולתהות למה זה איטי.

6. Hash Tables — סוס העבודה

אם יש מבנה נתונים אחד ששווה לשלוט בו לעומק — זה זה. Hash Table (נקרא גם hash map, dictionary, associative array) נותן גישה, הוספה ומחיקה ב-O(1) בממוצע. הוא ה-Map/Object של JS, ה-dict של Python — ומאחורי אינספור פתרונות.

הרעיון: hash function

הקסם: במקום לחפש ערך (O(n)), מחשבים את מיקומו. hash function לוקחת מפתח (string, number) ומחזירה מספר — אינדקס במערך הפנימי. אז "איפה שמור user_42?" נענה בחישוב אחד: hash("user_42") % size → אינדקס → גישה ישירה O(1). זה בדיוק כמו array indexing, אבל עם מפתחות שרירותיים במקום מספרים.

key "name" ──hash──→ 3 → bucket[3] = "Eliya"
key "age" ──hash──→ 7 → bucket[7] = 30
גישה = חישוב hash + index. O(1).

Collisions — הבעיה, וכיצד פותרים

מה קורה כששני מפתחות שונים נותנים אותו hash (אותו אינדקס)? זו collision, ובלתי נמנעת (יותר מפתחות אפשריים מ-buckets). שתי שיטות פתרון:

  • Chaining — כל bucket הוא linked list; מפתחות מתנגשים נשמרים באותה רשימה. בחיפוש, עוברים על הרשימה הקצרה.
  • Open Addressing — אם ה-bucket תפוס, מחפשים את הבא הפנוי (linear/quadratic probing).

Load Factor ו-Resizing

ה-load factor = מספר פריטים / מספר buckets. כשהוא גבוה מדי (הרבה collisions), הביצועים יורדים מ-O(1) לכיוון O(n). הפתרון: כשה-load factor עובר סף (~0.75), ה-hash table מכפיל את גודלו ו-rehash את הכל — בדיוק כמו dynamic array. זה שומר על O(1) amortized.

למה O(1) average אבל O(n) worst

במקרה הרע — כל המפתחות מתנגשים לאותו bucket (hash function גרועה או קלט זדוני) — ה-hash table מתדרדר ל-linked list, ו-lookup הוא O(n). זו הסיבה ש-hash function טובה קריטית, ולמה קיימות מתקפות "hash collision DoS". בפועל עם hash function סבירה — O(1). ראיונות ישאלו: "מה ה-worst case של hash map?" — התשובה O(n).

מתי hash table — הכלי הראשון שלך

כמעט תמיד כשצריך lookup מהיר לפי מפתח, ספירה/קיבוץ, או בדיקת קיום/ייחודיות. הדפוס הכי נפוץ בפתרון בעיות: "יש לי לולאה מקוננת O(n²)? כנראה hash map הופך אותה ל-O(n)." למשל, "מצא זוג שמסתכם ל-X" — במקום לבדוק כל זוג (O(n²)), שומרים מה שראינו ב-hash set ובודקים משלים ב-O(1) → O(n). זה הטריק הכי שימושי ב-DS&A.

7. Trees ו-Binary Search Trees

Tree הוא מבנה היררכי — nodes עם קשרי הורה-ילד, בלי מעגלים. השורש למעלה, העלים למטה. משמש להיררכיות, לחיפוש מהיר, ולהמון אלגוריתמים.

מושגים

  • Root — הצומת העליון. Leaf — צומת בלי ילדים. Height — עומק העץ.
  • Binary Tree — כל צומת עד 2 ילדים (left, right).

Binary Search Tree (BST) — עץ עם סדר

BST הוא binary tree עם כלל: לכל צומת, כל מה שמשמאל קטן ממנו, כל מה שמימין גדול. הכלל הזה נותן חיפוש ב-O(log n): בכל צומת, אתה יודע לאיזה צד ללכת (כמו binary search!), וחוצה את העץ בכל צעד:

     8
   /  \
  3   10
 / \   \
1  6   14
חיפוש 6: 8→שמאל→3→ימין→6. שלושה צעדים במקום מעבר על הכל.

הבעיה: עצים לא מאוזנים

אם מכניסים ל-BST ערכים ממוינים (1,2,3,4...), הוא הופך ל"שרשרת" — בעצם linked list, וחיפוש נהיה O(n)! זו הסיבה שקיימים Self-Balancing Trees: AVL ו-Red-Black Trees מאזנים את עצמם אוטומטית בכל הוספה, ומבטיחים O(log n) תמיד. (Red-Black עומד מאחורי TreeMap ב-Java ומבני std רבים).

Traversals — מעבר על עץ

// In-order (שמאל → צומת → ימין): נותן BST ממוין!
function inOrder(node) {
  if (!node) return;
  inOrder(node.left);
  visit(node.value);
  inOrder(node.right);
}
// Pre-order (צומת → שמאל → ימין): לשכפול עץ
// Post-order (שמאל → ימין → צומת): למחיקת עץ
// BFS / Level-order: שכבה-שכבה (עם queue!)

החיבור ל-Databases: זוכר ש-DB indexes בנויים על B-trees (ממדריך SQL)? B-tree הוא הכללה של BST מאוזן, מותאם לדיסק (כל צומת מחזיק הרבה מפתחות = פחות גישות דיסק). זו הסיבה ש-index נותן חיפוש O(log n) במקום O(n) full scan. עכשיו אתה מבין את המבנה מתחת ל-indexes — זה אותו רעיון של BST, בקנה מידה של דיסק.

8. Heaps ו-Priority Queues

Heap הוא binary tree מיוחד שנותן גישה מהירה למינימום או מקסימום — בלי למיין את הכל. הוא המימוש של priority queue.

הכלל

Min-heap: כל הורה קטן או שווה לילדיו — אז השורש הוא תמיד המינימום. (Max-heap להפך). לא ממוין לגמרי, רק הכלל ההורה-ילד. זה מספיק כדי לשלוף את הקטן ביותר ב-O(1) ולהוציא/להכניס ב-O(log n).

פעולהBig-O
peek (המינימום)O(1)
insertO(log n)
extract-minO(log n)
build-heap (מ-array)O(n)

שימושים

Priority Queue — "טפל בבעל העדיפות הגבוהה" (זוכר scheduling ממדריך systems? OS scheduler משתמש בזה). Dijkstra (מסלול קצר, פרק 14). Top-K — "K הפריטים הגדולים" בלי למיין הכל (heap בגודל K → O(n log k)). Heap sort (פרק 11). Merge של K רשימות ממוינות.

מתי heap: כשאתה צריך שוב ושוב את המינימום/מקסימום מקבוצה שמשתנה, בלי למיין הכל. אם היית ממיין בכל פעם — O(n log n) לכל שאילתה; heap נותן O(log n). זה הכלי ל"תמיד תן לי את הבא בתור לפי עדיפות".

9. Tries (Prefix Trees)

Trie הוא עץ מיוחד לאחסון strings לפי prefix. כל צומת הוא תו, ומסלול מהשורש מרכיב מילה. מבריק ל-autocomplete וחיפוש לפי תחילית.

 / \
t  r   → "cat", "car", "to"

היתרון: חיפוש/הוספה של מילה הוא O(אורך המילה) — לא תלוי בכמות המילים! וכל המילים עם prefix מסוים נמצאות בתת-עץ אחד → autocomplete מיידי. שימושים: autocomplete, בדיקת איות, IP routing. פחות נפוץ, אבל כשצריך "כל המילים שמתחילות ב-" — אין תחליף.

10. Graphs

Graph הוא המבנה הכללי ביותר: צמתים (vertices) ו-קשתות (edges) ביניהם. הכל הוא graph — רשתות חברתיות, מפות, תלויות, האינטרנט עצמו (זוכר routing ממדריך Networking?).

סוגים

  • Directed / Undirected — קשתות עם כיוון (follow בטוויטר) או בלי (חברות בפייסבוק).
  • Weighted / Unweighted — לקשתות יש משקל (מרחק, עלות) או לא.
  • Cyclic / Acyclic — יש מעגלים או לא. DAG (Directed Acyclic Graph) חשוב מאוד — תלויות, scheduling, git commits!

שתי דרכי ייצוג

Adjacency List — לכל צומת, רשימת שכניו. חסכוני בזיכרון ל-graphs דלילים (מעט קשתות). זו הבחירה הנפוצה.

const graph = {
  A: ["B", "C"],
  B: ["A", "D"],
  C: ["A"],
  D: ["B"]
};

Adjacency Matrix — טבלה n×n, matrix[i][j]=1 אם יש קשת. בדיקת קשר ב-O(1), אבל O(n²) זיכרון — טוב רק ל-graphs צפופים. הבחירה תלויה בצפיפות (density) של ה-graph.

ה-graph עצמו הוא רק המבנה — הכוח שלו הוא באלגוריתמים שרצים עליו (BFS, DFS, מסלול קצר), שנכסה בפרק 14. כמעט כל בעיה "מורכבת" בראיונות היא graph בתחפושת.

11. Sorting

מיון הוא בעיה קלאסית שמלמדת המון על אלגוריתמים. בפועל תשתמש ב-sort() המובנה, אבל הבנת האלגוריתמים חיונית — לראיונות, ולהבין tradeoffs.

המיונים ה"פשוטים" — O(n²)

  • Bubble Sort — מחליף שכנים שוב ושוב. הכי פשוט, הכי איטי. חינוכי בלבד.
  • Selection Sort — מוצא את המינימום ומעביר להתחלה, חוזר.
  • Insertion Sort — בונה מערך ממוין אחד-אחד. מהיר על נתונים כמעט-ממוינים או קטנים (O(n) best case) — לכן משמש בתוך מיונים היברידיים.

המיונים היעילים — O(n log n)

Merge Sort — divide-and-conquer: מחלק את המערך לחצי, ממיין כל חצי (רקורסיבית), וממזג. יציב (שומר סדר של שווים) ו-O(n log n) מובטח (גם worst case). החיסרון: צריך O(n) זיכרון נוסף למיזוג.

function mergeSort(arr) {
  if (arr.length <= 1) return arr;
  const mid = Math.floor(arr.length / 2);
  const left = mergeSort(arr.slice(0, mid));    // חלק ומיין
  const right = mergeSort(arr.slice(mid));
  return merge(left, right);                     // מזג שני ממוינים
}

Quicksort — בוחר pivot, מחלק לקטנים/גדולים ממנו, ממיין רקורסיבית. מהיר מאוד בפועל ו-in-place (בלי זיכרון נוסף), אבל worst case O(n²) (pivot גרוע). הבחירה הנפוצה בפועל (עם pivot חכם). Heap Sort — משתמש ב-heap, O(n log n) מובטח ו-in-place, אבל לא יציב ולרוב איטי יותר מ-quicksort בפועל (cache).

מעבר ל-O(n log n) — מיונים "מיוחדים"

יש חסם תחתון: מיון מבוסס-השוואות לא יכול להיות מהיר מ-O(n log n). אבל אם לא משווים אלא מנצלים מבנה, אפשר מהר יותר: Counting Sort ו-Radix Sort ממיינים מספרים שלמים בטווח מוגבל ב-O(n) — בלי השוואות. שימושי כשהנתונים מספרים בטווח ידוע.

הטבלה שמסכמת

מיוןAverageWorstSpaceיציב?
Bubble/InsertionO(n²)O(n²)O(1)כן
Merge SortO(n log n)O(n log n)O(n)כן
QuicksortO(n log n)O(n²)O(log n)לא
Heap SortO(n log n)O(n log n)O(1)לא

מעשי: ה-sort() המובנה של רוב השפות הוא מיון היברידי (למשל Timsort ב-Python/Java, שמשלב merge + insertion). אתה כמעט לעולם לא תכתוב מיון בעצמך. אבל הבנת ה-tradeoffs — יציבות (חשוב כשממיינים לפי כמה מפתחות), זיכרון, worst case — היא מה שנשאל ומה שמאפשר לך לבחור נכון. וזהירות: ב-JS, [3,1,2].sort() ממיין כ-strings כברירת מחדל! צריך sort((a,b) => a-b) למספרים (זוכר את ה-gotcha ממדריך JavaScript?).

12. Searching ו-Binary Search

Linear Search — O(n)

עוברים אחד-אחד עד שמוצאים. הכרחי כשהנתונים לא ממוינים. פשוט, ולפעמים אין ברירה.

Binary Search — O(log n), אבל דורש נתונים ממוינים

אחד האלגוריתמים היפים והשימושיים ביותר. על מערך ממוין: בודקים את האמצע, ולפי אם הערך גדול/קטן — זורקים חצי מהמערך וחוזרים. כל צעד חוצה את מרחב החיפוש → O(log n):

function binarySearch(arr, target) {
  let low = 0, high = arr.length - 1;
  while (low <= high) {
    const mid = Math.floor((low + high) / 2);
    if (arr[mid] === target) return mid;
    if (arr[mid] < target) low = mid + 1;    // זרוק את החצי השמאלי
    else high = mid - 1;                       // זרוק את החצי הימני
  }
  return -1;
}

על מיליון פריטים: linear = עד מיליון בדיקות, binary = ~20 בדיקות. זה הכוח של O(log n).

כמה כבר פגשת את זה בסדרה: binary search הוא לא רק תרגיל — הוא בכל מקום. DB indexes (B-tree = binary search על דיסק, מדריך SQL). git bisect (מציאת commit ששבר, מדריך Git). BST (פרק 7). כל פעם ש"חוצים את מרחב החיפוש" — זה binary search. זיהוי ההזדמנות להשתמש בו (יש נתונים ממוינים? אפשר O(log n) במקום O(n)) הוא מיומנות מפתח.

13. Recursion ו-Divide-and-Conquer

Recursion = פונקציה שקוראת לעצמה. זה כלי חשיבה יסודי, ובסיס להרבה אלגוריתמים (עצים, מיונים, DP, graphs).

שני החלקים של כל רקורסיה

function factorial(n) {
  if (n <= 1) return 1;          // 1. Base case — תנאי עצירה (חובה!)
  return n * factorial(n - 1);   // 2. Recursive case — קורא לעצמו על בעיה קטנה יותר
}

בלי base case → רקורסיה אינסופית → stack overflow (זוכר ממדריך systems? כל קריאה דוחפת frame ל-stack עד שנגמר). זה החיבור הישיר: recursion "חי" על ה-call stack.

Divide-and-Conquer

דפוס עוצמתי: מחלקים בעיה לתת-בעיות קטנות יותר, פותרים כל אחת (רקורסיבית), ומשלבים. merge sort ו-binary search הם בדיוק זה. הרעיון: בעיה שקשה לפתור ישירות נהיית קלה כשמפרקים אותה.

הסכנה: רקורסיה נאיבית = O(2ⁿ)

הדוגמה הקלאסית — Fibonacci רקורסיבי:

function fib(n) {
  if (n <= 1) return n;
  return fib(n - 1) + fib(n - 2);   // מחשב את אותם ערכים שוב ושוב!
}
// fib(50) → מיליארדי קריאות. O(2ⁿ). בלתי אפשרי.

הבעיה: overlapping subproblems — fib(3) מחושב אינספור פעמים. וזה בדיוק מה ש-Dynamic Programming (הפרק הבא) פותר — לזכור תוצאות במקום לחשב מחדש. הבנת למה הרקורסיה הנאיבית איטית היא הדלת ל-DP.

14. Graph Algorithms — BFS, DFS, Dijkstra

ה-graph (פרק 10) מקבל חיים דרך האלגוריתמים שרצים עליו. שני המסעות הבסיסיים — BFS ו-DFS — הם הבסיס לכמעט כל בעיית graph.

BFS — Breadth-First Search (לרוחב)

חוקר את הגרף שכבה-שכבה: קודם כל השכנים הישירים, אז שכניהם, וכן הלאה. משתמש ב-queue (זוכר פרק 5? FIFO). התכונה החשובה: BFS מוצא את המסלול הקצר ביותר (במספר קשתות) בגרף לא-משוקלל.

function bfs(graph, start) {
  const visited = new Set([start]);
  const queue = [start];
  while (queue.length) {
    const node = queue.shift();          // FIFO
    for (const neighbor of graph[node]) {
      if (!visited.has(neighbor)) {
        visited.add(neighbor);
        queue.push(neighbor);
      }
    }
  }
}

שימושים: מסלול קצר (רשתות חברתיות — "כמה דרגות הפרדה"), web crawling שכבה-שכבה, "הכי קרוב".

DFS — Depth-First Search (לעומק)

צולל עמוק ככל האפשר לפני שחוזר. משתמש ב-stack (או רקורסיה, שמשתמשת ב-call stack). שימושים: זיהוי מעגלים, topological sort, מציאת רכיבים קשירים, פתרון מבוכים, backtracking.

function dfs(graph, node, visited = new Set()) {
  visited.add(node);
  for (const neighbor of graph[node]) {
    if (!visited.has(neighbor)) dfs(graph, neighbor, visited);   // צלול עמוק
  }
}

ההבדל מ-BFS: BFS = queue = לרוחב = מסלול קצר; DFS = stack = לעומק = חקירה מלאה. שניהם O(V+E) — צמתים + קשתות. הבחירה תלויה במה שאתה מחפש.

Dijkstra — מסלול קצר בגרף משוקלל

כשלקשתות יש משקלים (מרחקים, עלויות), BFS לא מספיק. Dijkstra מוצא את המסלול הזול ביותר, בעזרת priority queue (heap! פרק 8) — תמיד מרחיב את הצומת הכי-קרוב-עד-כה. זה מה שמאחורי Waze/Google Maps ומאחורי routing ברשת (זוכר ממדריך Networking?). O((V+E) log V).

Topological Sort — סידור DAG

ב-DAG (גרף מכוון בלי מעגלים), topological sort נותן סדר שבו כל צומת בא לפני התלויים בו. שימושים: build systems (מה לקמפל קודם), task scheduling עם תלויות, resolution של dependencies (npm!). אם יש מעגל — אין סדר תקין (dependency cycle — זוכר ממדריך NestJS?).

15. Dynamic Programming

DP הוא הנושא ש"מפחיד" הכי הרבה בראיונות, אבל הרעיון פשוט: לזכור תוצאות של תת-בעיות כדי לא לחשב אותן שוב. זה בדיוק הפתרון ל-overlapping subproblems מפרק 13.

מתי DP מתאים

DP עובד כשלבעיה יש: (1) overlapping subproblems — אותן תת-בעיות חוזרות, ו-(2) optimal substructure — הפתרון האופטימלי בנוי מפתרונות אופטימליים של תת-בעיות. אם שני אלה מתקיימים — DP הופך O(2ⁿ) ל-O(n).

שתי גישות

Memoization (top-down) — רקורסיה רגילה, אבל שומרים תוצאות ב-cache ובודקים לפני שמחשבים:

function fib(n, memo = {}) {
  if (n <= 1) return n;
  if (n in memo) return memo[n];              // כבר חישבנו? החזר
  memo[n] = fib(n-1, memo) + fib(n-2, memo);  // חשב פעם אחת, שמור
  return memo[n];
}
// עכשיו O(n) במקום O(2ⁿ)! כל fib(k) מחושב פעם אחת.

Tabulation (bottom-up) — בונים טבלה מהקטן לגדול, בלי רקורסיה:

function fib(n) {
  const dp = [0, 1];
  for (let i = 2; i <= n; i++) dp[i] = dp[i-1] + dp[i-2];
  return dp[n];
}

שתיהן O(n). memoization אינטואיטיבי יותר (רק מוסיפים cache לרקורסיה); tabulation נמנע מ-stack overflow ולפעמים מהיר יותר.

הבעיות הקלאסיות

שווה להכיר את הדפוסים: Knapsack (מקסום ערך במשקל מוגבל), Longest Common Subsequence (בסיס ל-git diff!), Edit Distance (spell check), Coin Change, מסלולים ברשת. ברגע שאתה מזהה "אני מחשב את אותו דבר שוב ושוב" — זה סימן ל-DP.

איך לגשת ל-DP: אל תנסה לכתוב DP ישר. (1) כתוב פתרון רקורסיבי נאיבי, (2) זהה שיש overlapping subproblems, (3) הוסף memoization. זהו — כבר יש לך DP. רוב האנשים נבהלים כי מנסים לקפוץ ישר ל-tabulation. הדרך דרך הרקורסיה הנאיבית + cache היא הרבה יותר טבעית.

16. Greedy Algorithms

Greedy הוא הפוך מ-DP: במקום לשקול את כל האפשרויות, בכל צעד בוחרים את הבחירה הכי טובה מקומית ומקווים שזה יוביל לאופטימום גלובלי.

// עודף במטבעות — greedy: תמיד קח את המטבע הגדול ביותר שאפשר:
function coinChange(amount, coins) {
  coins.sort((a, b) => b - a);
  const result = [];
  for (const coin of coins) {
    while (amount >= coin) { result.push(coin); amount -= coin; }
  }
  return result;
}

המלכודת: greedy לא תמיד נותן את הפתרון האופטימלי! הוא עובד רק לבעיות עם "greedy choice property". למשל, עודף במטבעות רגילים — greedy עובד. אבל עם מטבעות מוזרים (1, 3, 4) לסכום 6 — greedy נותן 4+1+1 (3 מטבעות), אבל האופטימום הוא 3+3 (2 מטבעות)! זו הסיבה שחייבים להוכיח ש-greedy נכון לבעיה, או להשתמש ב-DP. ההבחנה מתי greedy מספיק ומתי צריך DP היא בדיוק שיקול הדעת ש-DS&A מלמד. שימושים שבהם greedy מוכח: Dijkstra, Huffman coding (דחיסה), interval scheduling, MST.

17. Interview Patterns — Two Pointers, Sliding Window

מעבר לאלגוריתמים הקלאסיים, יש דפוסים שחוזרים בבעיות ראיונות. זיהוי הדפוס = חצי מהפתרון. אלה החשובים:

Two Pointers

שני מצביעים שרצים על מערך (מהקצוות פנימה, או בקצב שונה). הופך הרבה בעיות O(n²) ל-O(n):

// האם יש זוג ממוין שמסתכם ל-target? (מערך ממוין)
function twoSum(arr, target) {
  let left = 0, right = arr.length - 1;
  while (left < right) {
    const sum = arr[left] + arr[right];
    if (sum === target) return [left, right];
    if (sum < target) left++;      // צריך גדול יותר
    else right--;                   // צריך קטן יותר
  }
}   // O(n) במקום O(n²)

Sliding Window

"חלון" שזז על מערך/string, לבעיות של "תת-רצף רציף". במקום לחשב מחדש כל חלון (O(n²)), מעדכנים את החלון תוך כדי (O(n)). למשל: "התת-מערך הרציף הכי ארוך עם סכום ≤ K", "אורך ה-substring הכי ארוך בלי תו חוזר".

עוד דפוסים שכדאי להכיר

  • Hash map ל-O(n) — הדפוס הכי נפוץ (זוכר מפרק 6?): לולאה מקוננת → hash map.
  • Fast & Slow pointers — זיהוי מעגל ב-linked list, מציאת אמצע.
  • Binary search על התשובה — כשמחפשים ערך אופטימלי מונוטוני.
  • Backtracking — בעיות "כל הצירופים/תמורות" (DFS עם חזרה אחורה).

הסוד של ראיונות אלגוריתמים: אין מאות בעיות — יש ~15 דפוסים, וכל בעיה היא וריאציה. במקום לשנן פתרונות, למד לזהות דפוסים: "בעיית תת-רצף רציף? → sliding window. מערך ממוין וזוגות? → two pointers. לולאה מקוננת? → נסה hash map. אופטימום עם תת-בעיות חוזרות? → DP." זיהוי הדפוס הוא המיומנות האמיתית — לא שינון.

20. מסגרת לפתרון בעיה בראיון

ראיון אלגוריתמים בודק איך אתה חושב, לא אם אתה זוכר את הפתרון. הנה מסגרת (נקראת לפעמים UMPIRE) שמכריחה אותך לגשת נכון:

  1. Understand — הבן את הבעיה. שאל שאלות: מה הקלט/פלט? edge cases (ריק, כפילויות, שליליים)? גודל הקלט? אף פעם אל תקפוץ לקוד.
  2. Match — לאיזה דפוס זה מתאים? (ממוין → binary search / two pointers; lookup → hash map; תת-רצף → sliding window; תלויות → graph).
  3. Plan — תאר את הגישה במילים/פסאודו לפני קוד. תסכים עם המראיין על הגישה.
  4. Implement — עכשיו כתוב קוד, נקי וברור.
  5. Review — עבור על הקוד עם דוגמה, בדוק edge cases.
  6. Evaluate — מה ה-Big-O (time + space)? אפשר לשפר?

הטעות מספר אחת בראיונות: לקפוץ ישר לקוד. מראיינים מחפשים תקשורת ותהליך חשיבה — דבר בקול, הצהר הנחות, התחל מפתרון brute-force ("הכי פשוט זה O(n²) עם לולאה מקוננת"), ואז שפר ("אבל עם hash map זה O(n)"). מועמד שמתחיל פשוט ומשפר בהיגיון מנצח את זה שמנסה לזרוק פתרון מבריק ונתקע. זה בדיוק כמו מסגרת ה-System Design (מדריך 10) — התהליך חשוב מהתשובה.

21. תרגילים ומשאבים

איך ללמוד DS&A נכון

DS&A נלמד ביד, לא בעין. אי אפשר "לקרוא" את זה — חייבים לממש ולפתור. התוכנית:

  1. ממש כל מבנה נתונים בעצמך — dynamic array, linked list, hash table, stack/queue, BST, heap, graph. פעם אחת מאפס. זה מה שהופך אותם ל"שלך" (וזה גם מחבר ל-systems — תרגיש את ה-pointers וה-memory).
  2. פתור בעיות — LeetCode / NeetCode. התחל מ-Easy, עבור ל-Medium. אל תסתכל בפתרון לפני 20-30 דקות מאבק אמיתי.
  3. למד דפוסים, לא פתרונות — אחרי כל בעיה, שאל "לאיזה דפוס זה שייך?" (פרק 17). NeetCode 150 מסודר לפי דפוסים — מצוין.
  4. חזור — בעיה שפתרת לפני שבוע ולא זוכר — תפתור שוב. ההטמעה מגיעה מחזרה.

תרגילים להתחלה (לפי מבנה)

1 — Hash Map: Two Sum (מצא זוג שמסתכם ל-target ב-O(n)). הבעיה הכי קלאסית — מבינים למה hash map הופך O(n²) ל-O(n).

2 — Stack: Valid Parentheses (בדוק אם סוגריים מאוזנים).

3 — Two Pointers: הפוך מערך in-place; מצא אם string הוא palindrome.

4 — Binary Search: מצא ערך במערך ממוין; מצא את נקודת ההיפוך במערך מסובב.

5 — Sliding Window: ה-substring הכי ארוך בלי תו חוזר.

6 — Tree: מעבר in-order על BST; עומק מקסימלי של עץ; בדוק אם עץ הוא BST תקין.

7 — Graph (BFS/DFS): ספור "איים" ב-grid; מצא אם יש מסלול בין שני צמתים.

8 — DP: Fibonacci עם memoization; Climbing Stairs; Coin Change.

9 — מימוש מבנים: ממש hash table עם chaining; ממש min-heap; ממש LRU cache (משלב hash map + doubly linked list — בעיה מצוינת שמחברת הכל).

סיכום — וסגירת יסודות ה-CS

שני דברים מעל הכל: Big-O הוא השפה — זיהוי סיבוכיות (במיוחד לולאה מקוננת O(n²) שאפשר להפוך ל-O(n) עם hash map) הוא המיומנות היומיומית; ובחירת המבנה הנכון היא שיקול הדעת שמבדיל מהנדס — לא שינון המבנים, אלא לדעת מתי כל אחד.

וזה סוגר את שני עמודי יסודות ה-CS: Systems (מדריך 12 — איך המחשב עובד) ו-DS&A (זה — איך לארגן נתונים ולפתור בעיות). שים לב כמה הם שזורים: cache locality (systems) מסביר למה array מנצח linked list למרות אותו Big-O; ה-call stack (systems) מסביר recursion ו-stack overflow; B-trees (DS&A) עומדים מאחורי DB indexes (SQL); ו-hash tables עומדים מאחורי כל lookup מהיר. אלה לא נושאים נפרדים — זו הרצפה האמיתית שמתחת לכל framework וכל שפה.
