איך פותרים תרגילים ובונים פרויקט — בלי שהקוד “יברח” לך

הפער שהמדריך פותר: לדעת syntax פירושו לדעת מה for עושה. לדעת לתכנת פירושו לזהות מתי צריך לולאה, מה עובר בה, איזה state שומרים, מתי להוציא פונקציה ואיך לבדוק שהפתרון נכון. זאת מיומנות נפרדת שנקראת problem decomposition, והיא נבנית באימון.

1. למה לדעת Syntax עדיין לא מרגיש כמו לדעת לתכנת?

כשנותנים לך הוראה נקודתית—“עבור על users”—אתה מזהה את הכלי וכותב loop. בפרויקט הדרישה מגיעה בשפה עסקית: “משתמש מנהל יכול להשבית חשבון, אבל לא את עצמו, והפעולה צריכה להירשם”. אין בה מילים כמו loop או function. אתה צריך לתרגם אותה למודל, כללים, שלבים ונתונים.

היכולת הזאת מורכבת מארבע מיומנויות:

  • הבהרת הדרישה: מהו input, מהו output ומהם מקרי הקצה.
  • פירוק: להפוך משימה גדולה לכמה פעולות שכל אחת קלה לכתיבה.
  • בחירת ייצוג: לבחור list, dictionary, object, function או class לפי הצורך.
  • חיבור ואימות: לחבר את החלקים ולבדוק scenarios, errors ו־state changes.

לכן התחושה שאתה מתאר נורמלית: יש לך “מילים” של השפה, אבל עדיין אין מספיק משפטים שלמים שכתבת בעצמך. הדרך קדימה אינה לשנן עוד methods אלא לפתור רצף משימות שעולות בגודל בהדרגה.

2. שיטת שבעת השלבים

שלב 1 — נסח את הבעיה במשפט אחד

אם אינך יכול להסביר מה הפונקציה עושה בלי לדבר על הקוד, הדרישה עדיין מעורפלת. לדוגמה: “לקבל משתמשים ולהחזיר את שמות המשתמשים הפעילים בלבד, ללא שינוי הרשימה המקורית”.

שלב 2 — כתוב Input ו־Output מוחשיים

Input:
[
  {"name": "Dana", "active": true},
  {"name": "Avi", "active": false},
  {"name": "Noa", "active": true}
]

Output:
["Dana", "Noa"]

דוגמה מוחשית מאלצת אותך להבין את צורת הנתונים ומונעת כתיבה באוויר.

שלב 3 — רשום Rules ו־Edge Cases

  • מה קורה אם הרשימה ריקה?
  • מה קורה אם חסר active?
  • האם מותר לשנות את input?
  • האם צריך לשמור סדר?
  • מה קורה אם name ריק?

לא כל תרגיל דורש טיפול בכל אפשרות. צריך להגדיר חוזה, לא לנחש.

שלב 4 — כתוב פתרון בעברית או Pseudocode

צור רשימת תוצאות ריקה
עבור על כל משתמש
    אם המשתמש פעיל
        הוסף את השם שלו לתוצאות
החזר את התוצאות

אם ה־pseudocode אינו ברור, קוד לא יפתור את הערפול. אם הוא ברור, התרגום ל־Python או JavaScript כמעט מכני.

שלב 5 — הפוך כל שורה לכלי שפה

כוונהכלי
“צור תוצאות”list/array ריקה
“עבור על כל משתמש”for / for...of
“אם פעיל”if
“הוסף שם”append / push
“החזר”return

שלב 6 — הרץ ידנית דוגמה קטנה

עקוב אחרי המשתנים בכל איטרציה. אחרי Dana התוצאה היא ["Dana"]; אחרי Avi היא לא משתנה; אחרי Noa היא מכילה שני שמות. Dry run כזה מגלה טעויות לפני debugger.

שלב 7 — כתוב Tests ורק אז שפר

בדוק case רגיל, ריק ומקרה גבול. רק אחרי שהפתרון נכון שקול filter/map, comprehension, performance או abstraction. פתרון פשוט ונכון עדיף על one-liner שאינך יכול להסביר.

3. דוגמה מלאה: מנתח משתמשים

הדרישה: “קבל רשימת משתמשים והחזר כמה פעילים יש, את שמותיהם ואת הממוצע של גיליהם. משתמש ללא גיל לא משתתף בממוצע”.

פירוק לפני קוד

  1. צריך לעבור פעם אחת על המשתמשים.
  2. צריך count של פעילים.
  3. צריך list של שמות פעילים.
  4. לממוצע צריך age total וגם age count.
  5. בסוף, אם age count הוא אפס, הממוצע יהיה None/null.
def analyze_users(users):
    active_names = []
    age_total = 0
    age_count = 0

    for user in users:
        if not user.get("active", False):
            continue

        active_names.append(user["name"])

        age = user.get("age")
        if age is not None:
            age_total += age
            age_count += 1

    average_age = age_total / age_count if age_count else None
    return {
        "active_count": len(active_names),
        "active_names": active_names,
        "average_age": average_age,
    }

שים לב: ה־loop אינו החלק הקשה. ההחלטה איזה state צריך לשמור היא הלב. ברגע שכתבת “לממוצע צריך סכום וכמות”, הקוד נובע מהמודל.

מתי מפצלים לפונקציות?

אם validation, חישוב average או normalization נעשים מורכבים או חוזרים במקומות אחרים, מוציאים אותם לפונקציה. לא מפצלים כל שתי שורות רק כדי שיהיו הרבה functions. פונקציה צריכה שם שמוסיף משמעות ו־contract שניתן לבדוק.

4. איך עוברים מפונקציה לפרויקט?

פרויקט אינו “פונקציה ענקית”. הוא אוסף קטן של flows, וכל flow הוא שרשרת פעולות. לדוגמה, Task Manager מתחיל לא מ־database ו־framework אלא מהפעולה Add Task.

Milestoneמה בוניםמה עדיין לא בונים
1Task model ו־validationCLI, DB, auth
2add/list/complete בזיכרוןקבצים ו־HTTP
3Repository interface ומימוש memoryPostgreSQL
4שמירה ל־JSONWeb API
5CLI שמפעיל servicesFrontend
6Tests, errors ו־loggingFeatures חדשים

בכל milestone יש flow קטן שעובד מקצה לקצה. אינך צריך להחזיק את כל הפרויקט בראש; אתה צריך לדעת מהו השלב הנוכחי, מה נכנס אליו ומה Definition of Done שלו.

תבנית לכל Feature

  1. כתוב user story.
  2. הגדר input/output ושגיאות.
  3. כתוב domain rule כפונקציה או method.
  4. כתוב test.
  5. חבר storage או API.
  6. הרץ flow ידני.
  7. רק אז refactor.

אל תדלג מ־micro exercise ישר לאפליקציה מלאה. אם Function-level עדיין קשה, פתרון עוד פרויקט בעזרת AI לא יתקן את הפער; צריך 15–30 פונקציות עצמאיות ואחר כך features קטנים.

6. שימוש ב־AI בלי לאבד יכולת

כלל העבודה: AI נכנס אחרי שיש לך artifact משלך—pseudocode, ניסיון קוד, test נכשל או הסבר מדויק של התקיעה.
  1. 20–30 דקות ניסיון עצמאי.
  2. אם נתקעת, בקש שאלה מכוונת או רמז אחד.
  3. כתוב אתה את השינוי.
  4. הרץ tests ופרש את השגיאה לפני שאתה שולח אותה.
  5. בסוף בקש Code Review שמסביר בעיות, לא rewrite.
  6. למחרת כתוב מחדש את החלק המרכזי בלי להסתכל.

מותר ל־AI לייצר boilerplate רק אם אתה כבר יודע להסביר אותו והתרגול אינו עליו. אם המטרה היא ללמוד routing, אל תיתן לו לכתוב router. אם המטרה היא business logic, אפשר לקבל scaffold בסיסי—but not the logic.

7. מה עושים כשנתקעים?

אל תגיד רק “אני לא יודע”. סווג את התקיעה:

  • לא הבנתי דרישה: כתוב שאלות ודוגמאות.
  • לא יודע לייצג נתונים: צייר object/list ודוגמת input.
  • לא יודע algorithm: פתר ידנית עבור שלושה פריטים ותעד את הצעדים.
  • לא זוכר syntax: חפש syntax נקודתי, לא פתרון מלא.
  • הקוד לא עובד: צמצם reproduction, קרא traceback והדפס state בגבולות.
  • הפרויקט גדול מדי: בחר flow אחד והסר זמנית DB, auth ו־UI.

תקיעה איכותית נשמעת כך: “אני יודע שצריך לעבור על users ולשמור sum ו־count, אבל לא יודע איך להבדיל בין age חסר לבין age=0”. זאת שאלה שניתן לפתור וללמוד ממנה.

8. תוכנית אימון של ארבעה שבועות

  • שבוע 1: ארבעה micro exercises ועוד שתי functions בכל אחת מהשפות שאתה מתרגל. דגש על loops, conditions ו־collections.
  • שבוע 2: functions עם validation, grouping, errors ו־tests.
  • שבוע 3: שני features: service + in-memory repository + tests.
  • שבוע 4: mini-project קטן עם persistence, CLI/API ו־README.

בכל session שמור יומן קצר: מה הייתה הדרישה, איך פירקת, איפה נתקעת ומה תפתור שוב מחר. המדד אינו “כמה מדריכים קראתי”, אלא כמה פעמים הפכת דרישה לפתרון בלי שמישהו כתב אותו עבורך.

מתי הקוד מתחיל “להחליק”? כאשר אתה מזהה patterns שחוזרים: filter, aggregate, lookup, validation, state transition, repository ו־request flow. זה קורה אחרי חזרות מכוונות. המטרה אינה שלא תיתקע לעולם; המטרה היא שתדע לפרק את התקיעה ולהתקדם בעצמך.
