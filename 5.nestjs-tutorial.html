NestJS — המדריך המלא למפתח Backend

המשך ישיר למדריך TypeScript. המדריך הזה מניח שאתה כבר שולט ב-TypeScript — decorators, generics, ו-dependency injection דרך parameter properties. אם משהו מזה מעורפל, חזור למדריך הקודם.

ההסברים בעברית, הקוד והמונחים הטכניים באנגלית. כל פרק בונה על הקודם. הדרך הנכונה לעבור על זה: לפתוח פרויקט NestJS אמיתי לצד המדריך ולכתוב כל דבר תוך כדי קריאה.

1. מה זה NestJS ולמה הוא קיים

NestJS הוא framework ל-Backend על גבי Node.js, כתוב ב-TypeScript, שנותן לך ארכיטקטורה מובנית ודעתנית (opinionated) לבניית אפליקציות server-side. אם Express הוא ערכת לגו בלי הוראות, NestJS הוא הלגו עם ספר הוראות, מסגרת, ותאימות בין החלקים.

הבעיה ש-NestJS פותר

Express מדהים ומינימלי — אבל המינימליזם הזה הוא גם החיסרון. בפרויקט Express גדול כל צוות ממציא מבנה משלו: איפה שמים לוגיקה, איך מזריקים dependencies, איך מטפלים בשגיאות. התוצאה היא chaos ברגע שהפרויקט גדל.

NestJS מביא מבנה אחיד: כל אפליקציה בנויה מ-modules, controllers ו-providers, עם dependency injection מובנה. שני מפתחים שמכירים NestJS יכולים לקפוץ לכל פרויקט NestJS ולהתמצא מיד. זה הערך המרכזי — לא ביצועים, אלא תחזוקתיות ועקביות בקנה מידה.

על מה NestJS בנוי

NestJS לא מחליף את Express — הוא עוטף אותו. כברירת מחדל הוא רץ על Express מתחת למכסה (ואפשר להחליף ל-Fastify לביצועים גבוהים יותר). כל מה שאתה יודע על HTTP, middleware ו-routing עדיין נכון — NestJS רק מארגן את זה.

שלושת עמודי התווך

  • TypeScript-first — נבנה סביב TypeScript ו-decorators. כל מה שלמדת במדריך הקודם עובד כאן במלוא הכוח.
  • Dependency Injection — מערכת DI מובנית בהשראת Angular ו-Spring. אתה מצהיר מה אתה צריך, NestJS מספק את זה.
  • מודולריות — הקוד מחולק ל-modules עצמאיים שאפשר להרכיב ולעשות בהם שימוש חוזר.

המודל המנטלי החשוב ביותר: NestJS הוא בעצם מערכת של decorators ש-metadata שלהם מורכב על ידי ה-framework בזמן העלייה (bootstrap). אתה מתייג מחלקות (@Controller, @Injectable, @Module), ו-NestJS קורא את התיוגים ובונה מהם את כל הגרף של האפליקציה — routing, DI, lifecycle. כשתבין את זה, NestJS יפסיק להיראות כמו קסם.

2. התקנה, ה-CLI ומבנה הפרויקט

התקנת ה-CLI ויצירת פרויקט

ה-CLI של Nest הוא כלי מרכזי — הוא מייצר קוד, מריץ, ובונה. מתקינים אותו גלובלית:

npm install -g @nestjs/cli
nest new my-app        # יוצר פרויקט חדש עם כל ההגדרות
cd my-app
npm run start:dev      # מריץ עם hot-reload

השרת עולה כברירת מחדל על http://localhost:3000.

מבנה פרויקט טיפוסי

src/
├── main.ts                 # נקודת הכניסה — bootstrap
├── app.module.ts           # ה-root module
├── app.controller.ts
├── app.service.ts
└── users/                  # feature module
    ├── users.module.ts
    ├── users.controller.ts
    ├── users.service.ts
    ├── dto/
    │   ├── create-user.dto.ts
    │   └── update-user.dto.ts
    └── entities/
        └── user.entity.ts

הדפוס: כל feature מקבל תיקייה משלו עם module, controller, service ו-DTOs. זה מה שה-CLI מייצר, וכדאי להיצמד אליו.

נקודת הכניסה — main.ts

import { NestFactory } from "@nestjs/core";
import { AppModule } from "./app.module";

async function bootstrap() {
  const app = await NestFactory.create(AppModule);
  await app.listen(3000);
}
bootstrap();

NestFactory.create(AppModule) לוקח את ה-root module, קורא את כל ה-metadata של ה-decorators, בונה את כל גרף ה-DI, ומחזיר אפליקציה מוכנה. זו נקודת ההרכבה של הכל.

ייצור קוד עם ה-CLI

במקום לכתוב boilerplate ידנית, ה-CLI מייצר feature שלם:

nest generate module users        # או: nest g module users
nest generate controller users    # nest g controller users
nest generate service users       # nest g service users

# או הכל ביחד — CRUD מלא עם DTOs:
nest generate resource users      # nest g resource users

nest g resource הוא הדרך המהירה — הוא מייצר module, controller, service, entity ו-DTOs, וגם מחווט אותם יחד. השתמש בו כנקודת פתיחה לכל feature.

3. Modules — לב הארכיטקטורה

Module הוא יחידת הארגון הבסיסית של NestJS. כל אפליקציה היא עץ של modules שמתחיל ב-root module יחיד. אם לא הבנת modules, לא הבנת NestJS.

מבנה של module

import { Module } from "@nestjs/common";
import { UsersController } from "./users.controller";
import { UsersService } from "./users.service";

@Module({
  controllers: [UsersController],   // מי מטפל ב-HTTP requests
  providers: [UsersService],        // מה זמין להזרקה בתוך ה-module
  exports: [UsersService],          // מה ה-module חושף ל-modules אחרים
  imports: [],                      // אילו modules אחרים ה-module הזה צריך
})
export class UsersModule {}

ארבעת המפתחות של @Module הם כל מה שצריך להבין:

  • controllers — ה-controllers ששייכים ל-module הזה (מטפלים ב-routes).
  • providers — ה-services וכל דבר שאפשר להזריק, זמינים בתוך ה-module.
  • imports — modules אחרים שה-module הזה צריך את ה-exports שלהם.
  • exports — אילו providers ה-module חושף החוצה, כדי ש-modules אחרים שמייבאים אותו יוכלו להשתמש בהם.

עקרון ה-encapsulation — הנקודה הקריטית

זו הנקודה שהכי מבלבלת מתחילים ב-NestJS. provider זמין להזרקה רק בתוך ה-module שמצהיר עליו — אלא אם הוא ב-exports.

אם UsersModule מגדיר UsersService ולא מייצא אותו, ואז OrdersModule מנסה להזריק UsersService — תקבל שגיאת DI. הפתרון: UsersModule חייב לעשות exports: [UsersService], ו-OrdersModule חייב לעשות imports: [UsersModule].

// orders.module.ts
@Module({
  imports: [UsersModule],           // מייבא כדי לקבל גישה ל-UsersService
  controllers: [OrdersController],
  providers: [OrdersService],
})
export class OrdersModule {}

חשוב על זה כמו על public/private: providers הם private ל-module, exports הופכים אותם ל-public. זה בדיוק אותו רעיון של encapsulation שהכרת ב-classes.

ה-root module

@Module({
  imports: [UsersModule, OrdersModule, AuthModule],
})
export class AppModule {}

ה-AppModule בדרך כלל רק מייבא את כל ה-feature modules ומחבר הכל ביחד.

Global modules

לפעמים module נחוץ בכל מקום (למשל config או logging). במקום לייבא אותו בכל module, מסמנים אותו @Global():

@Global()
@Module({
  providers: [ConfigService],
  exports: [ConfigService],
})
export class ConfigModule {}

המלצה: השתמש ב-@Global() במשורה. הוא נוח אבל שובר את השקיפות — קשה לדעת מאיפה provider מגיע. שמור אותו ל-cross-cutting concerns אמיתיים (config, database) ולא כדרך לעקוף ניהול imports נכון.

4. Controllers — טיפול ב-requests

Controller אחראי על קבלת HTTP requests והחזרת responses. הוא השכבה הדקה בין העולם החיצון ללוגיקה שלך. הכלל: controllers צריכים להיות דקים — הם רק מנתבים, מוציאים פרמטרים, ומעבירים ל-service. שום לוגיקה עסקית לא יושבת ב-controller.

Controller בסיסי

import { Controller, Get, Post, Body, Param } from "@nestjs/common";
import { UsersService } from "./users.service";
import { CreateUserDto } from "./dto/create-user.dto";

@Controller("users")               // הבסיס: כל ה-routes מתחילים ב-/users
export class UsersController {
  constructor(private readonly usersService: UsersService) {}

  @Get()                           // GET /users
  findAll() {
    return this.usersService.findAll();
  }

  @Get(":id")                      // GET /users/:id
  findOne(@Param("id") id: string) {
    return this.usersService.findOne(id);
  }

  @Post()                          // POST /users
  create(@Body() dto: CreateUserDto) {
    return this.usersService.create(dto);
  }
}

שים לב: ה-@Controller("users") קובע prefix לכל ה-routes, וכל method decorator (@Get, @Post) מגדיר את שאר הנתיב. אם method מחזיר object, NestJS ממיר אותו אוטומטית ל-JSON ומחזיר 200 (או 201 ל-POST).

Route parameter decorators

אלה ה-decorators שמוציאים חלקים מה-request:

@Get(":id")
example(
  @Param("id") id: string,          // מ-URL: /users/:id
  @Query("page") page: string,      // מ-query string: ?page=2
  @Body() body: CreateUserDto,      // מ-request body (JSON)
  @Headers("authorization") auth: string,  // מ-header
) {}

במקום לגשת ל-req.params.id כמו ב-Express, אתה מצהיר בדיוק מה אתה צריך והוא מוזרק לך. זה קריא יותר וגם ניתן לבדיקה בקלות.

שליטה ב-status code וב-response

import { HttpCode, HttpStatus } from "@nestjs/common";

@Post()
@HttpCode(HttpStatus.CREATED)      // 201 מפורש
create(@Body() dto: CreateUserDto) {
  return this.usersService.create(dto);
}

עצה חשובה: אל תיגע ב-@Res() (ה-response object הגולמי של Express) אלא אם אתה חייב. ברגע שתשתמש בו, אתה מוותר על כל היתרונות של NestJS (interceptors, serialization אוטומטי). תן ל-NestJS לטפל ב-response — פשוט return את הנתונים.

5. Providers ו-Services — הלוגיקה העסקית

Provider הוא כל דבר שאפשר להזריק (inject) דרך ה-DI. ה-provider הנפוץ ביותר הוא service — המחלקה שמחזיקה את הלוגיקה העסקית האמיתית. כאן קורה הכל: חישובים, גישה ל-DB, קריאות ל-APIs חיצוניים.

Service בסיסי

import { Injectable, NotFoundException } from "@nestjs/common";
import { CreateUserDto } from "./dto/create-user.dto";
import { User } from "./entities/user.entity";

@Injectable()                       // הופך את המחלקה ל-provider שאפשר להזריק
export class UsersService {
  private users: User[] = [];

  findAll(): User[] {
    return this.users;
  }

  findOne(id: string): User {
    const user = this.users.find((u) => u.id === id);
    if (!user) {
      throw new NotFoundException(`User ${id} not found`);
    }
    return user;
  }

  create(dto: CreateUserDto): User {
    const user: User = { id: crypto.randomUUID(), ...dto };
    this.users.push(user);
    return user;
  }
}

ה-@Injectable() הוא המפתח: הוא מסמן ל-NestJS "המחלקה הזו יכולה להיות מנוהלת על ידי ה-DI container". בלעדיו, NestJS לא ידע להזריק אותה.

למה בכלל להפריד service מ-controller?

הפרדת האחריות (separation of concerns) היא לא פורמליזם — היא מעשית:

  • Testability — אפשר לבדוק את הלוגיקה בלי HTTP בכלל.
  • שימוש חוזר — כמה controllers (או services אחרים) יכולים להשתמש באותו service.
  • החלפה — אפשר להחליף מימוש בלי לגעת ב-controller.

הכלל: controller יודע על HTTP, service לא יודע כלום על HTTP. אם אתה רואה @Body או status codes ב-service, משהו לא במקום.

6. Dependency Injection לעומק

DI הוא הלב הפועם של NestJS. הבנה עמוקה שלו תעשה את ההבדל בין "זה עובד ואני לא יודע למה" ל"אני שולט במערכת".

מה זה DI בכלל

במקום שמחלקה תיצור בעצמה את מה שהיא צריכה (new UserRepository()), היא מצהירה על מה שהיא צריכה ב-constructor, ומישהו חיצוני (ה-DI container של NestJS) מספק את זה:

// בלי DI — coupling הדוק, קשה לבדיקה:
class UsersService {
  private repo = new UserRepository();   // המחלקה יוצרת בעצמה
}

// עם DI — המחלקה רק מבקשת, NestJS מספק:
@Injectable()
export class UsersService {
  constructor(private readonly repo: UserRepository) {}
}

זוכר את ה-parameter properties מ-TypeScript? private readonly repo בפרמטר יוצר את השדה ומשים אליו אוטומטית. NestJS מסתכל על הטיפוס (UserRepository), מוצא את ה-provider המתאים, ומזריק instance.

איך NestJS יודע מה להזריק

כאן נכנס emitDecoratorMetadata מ-tsconfig (זוכר מהמדריך הקודם?). הוא גורם ל-TypeScript לפלוט את טיפוסי הפרמטרים ל-runtime דרך reflect-metadata. NestJS קורא את המידע הזה, רואה שהפרמטר הוא מטיפוס UserRepository, ומחפש provider שתואם. בלי הדגל הזה, DI לפי טיפוס פשוט לא יעבוד.

Scopes — משך החיים של provider

כברירת מחדל, כל provider ב-NestJS הוא singleton — instance אחד שנוצר פעם אחת ומשותף לכל האפליקציה. זה יעיל ונכון ל-99% מהמקרים:

@Injectable()                                    // ברירת מחדל: singleton
export class UsersService {}

@Injectable({ scope: Scope.REQUEST })            // instance חדש לכל request
export class RequestScopedService {}

אזהרה: Scope.REQUEST נראה מפתה אבל יש לו מחיר ביצועים אמיתי — NestJS חייב לבנות את שרשרת ה-DI מחדש לכל request. השתמש בו רק כשאתה באמת צריך state ספציפי ל-request. ברוב המקרים singleton עם העברת נתונים כפרמטרים עדיף.

Custom providers — שליטה מלאה

לפעמים אתה צריך להזריק משהו שהוא לא סתם מחלקה — ערך, factory, או מימוש שנבחר בזמן ריצה. יש ארבע צורות:

@Module({
  providers: [
    // 1. useClass — המימוש הרגיל (זה מה ש-[UsersService] הוא קיצור שלו)
    UsersService,

    // 2. useValue — להזריק ערך קבוע (נוח מאוד לבדיקות ולקונפיג)
    { provide: "API_KEY", useValue: "secret-123" },

    // 3. useClass דינמי — לבחור מימוש לפי תנאי
    {
      provide: PaymentService,
      useClass: process.env.NODE_ENV === "production"
        ? StripePaymentService
        : FakePaymentService,
    },

    // 4. useFactory — לבנות את ה-provider עם לוגיקה ו-dependencies
    {
      provide: "DB_CONNECTION",
      useFactory: (config: ConfigService) => createConnection(config.dbUrl),
      inject: [ConfigService],       // ה-dependencies של ה-factory
    },
  ],
})
export class AppModule {}

Injection tokens

כשמזריקים לפי מחלקה, המחלקה עצמה היא ה-token. אבל כשמזריקים ערך או interface (שנמחק ב-runtime!), צריך token מפורש — string או symbol — ומשתמשים ב-@Inject:

@Injectable()
export class SomeService {
  constructor(
    @Inject("API_KEY") private readonly apiKey: string,
    @Inject("DB_CONNECTION") private readonly db: Connection,
  ) {}
}

למה צריך את זה? כי interface נמחק בקומפילציה (type erasure — זוכר?). אין לו ייצוג ב-runtime, אז NestJS לא יכול להזריק "לפי interface". לכן ל-abstractions משתמשים ב-token מפורש. זו דוגמה מצוינת לאיך ידע ב-TypeScript מסביר התנהגות ב-NestJS.

7. DTOs ו-Validation

DTO (Data Transfer Object) מגדיר את צורת הנתונים שנכנסים ויוצאים דרך ה-API. וכאן מגיע השיעור הכי חשוב שחזר גם במדריך TypeScript: טיפוסים לבדם לא מספיקים — צריך validation אמיתי בזמן ריצה.

למה טיפוס לא מספיק

אם תגדיר @Body() dto: CreateUserDto ותסמוך על זה — אתה בבעיה. הטיפוס נמחק בקומפילציה. בזמן ריצה, מישהו יכול לשלוח JSON עם שדות חסרים, טיפוסים שגויים, או זבל מוחלט, ו-TypeScript לא יעצור אותו. חייבים validation שרץ בפועל.

class-validator ו-class-transformer

NestJS פותר את זה עם decorators על ה-DTO. שים לב: ה-DTO חייב להיות class, לא interface — כי interface נמחק ב-runtime, ו-class נשאר כדי לשאת את ה-metadata של ה-validation:

import { IsString, IsEmail, IsInt, Min, Max, IsOptional } from "class-validator";

export class CreateUserDto {
  @IsString()
  name: string;

  @IsEmail()
  email: string;

  @IsInt()
  @Min(18)
  @Max(120)
  age: number;

  @IsOptional()
  @IsString()
  bio?: string;
}

הפעלת ה-ValidationPipe גלובלית

ה-decorators לבדם לא עושים כלום — צריך להפעיל את ה-ValidationPipe שקורא אותם ואוכף אותם. מפעילים אותו פעם אחת גלובלית ב-main.ts:

import { ValidationPipe } from "@nestjs/common";

async function bootstrap() {
  const app = await NestFactory.create(AppModule);

  app.useGlobalPipes(
    new ValidationPipe({
      whitelist: true,             // מסיר שדות שלא מוגדרים ב-DTO
      forbidNonWhitelisted: true,  // זורק שגיאה אם נשלחו שדות לא מוכרים
      transform: true,             // ממיר אוטומטית לטיפוסים הנכונים
    }),
  );

  await app.listen(3000);
}
bootstrap();

עכשיו, אם מישהו ישלח POST /users עם age: 15 או בלי email, NestJS יחזיר אוטומטית 400 Bad Request עם הודעה מפורטת — עוד לפני שה-controller בכלל רץ.

שלוש האפשרויות שחייבים להכיר: whitelist (זורק שדות עודפים), forbidNonWhitelisted (מתלונן עליהם במקום לזרוק בשקט), ו-transform (הופך את ה-payload ל-instance אמיתי של ה-DTO וממיר טיפוסים, למשל string מ-URL ל-number). כמעט תמיד תרצה את שלושתן.

Mapped types ל-DTOs — פחות שכפול

NestJS מספק utility types (במקביל לאלה של TypeScript) שגוזרים DTO אחד מהשני, כולל ה-validation decorators:

import { PartialType, OmitType, PickType } from "@nestjs/mapped-types";

// כל השדות של CreateUserDto, אבל אופציונליים — מושלם ל-update:
export class UpdateUserDto extends PartialType(CreateUserDto) {}

// כל השדות חוץ מ-email:
export class InternalUserDto extends OmitType(CreateUserDto, ["email"] as const) {}

זה בדיוק ה-Partial/Omit שהכרת, אבל בגרסה שמשמרת גם את ה-validation decorators. UpdateUserDto מקבל אוטומטית את כל הכללים של CreateUserDto, רק אופציונליים.

8. Pipes

Pipe הוא רכיב שמעבד או מאמת את הנתונים הנכנסים לפני שהם מגיעים ל-controller. ה-ValidationPipe שראית הוא pipe — אבל יש עוד, ואפשר לכתוב משלך.

Built-in pipes

הנפוצים ביותר ממירים ומאמתים פרמטר בודד:

import { ParseIntPipe, ParseUUIDPipe } from "@nestjs/common";

@Get(":id")
findOne(@Param("id", ParseUUIDPipe) id: string) {
  // אם id אינו UUID תקין — 400 אוטומטי, לפני שה-method רץ
  return this.usersService.findOne(id);
}

@Get()
findPage(@Query("page", ParseIntPipe) page: number) {
  // ה-string מה-query הופך ל-number אמיתי (או 400 אם לא מספר)
  return this.usersService.findPage(page);
}

Custom pipe

Pipe הוא מחלקה עם method אחד — transform:

import { PipeTransform, Injectable, BadRequestException } from "@nestjs/common";

@Injectable()
export class TrimPipe implements PipeTransform {
  transform(value: string): string {
    if (typeof value !== "string") {
      throw new BadRequestException("Expected a string");
    }
    return value.trim();
  }
}

שים לב ל-implements PipeTransform — עוד דוגמה ל-"programming to interfaces" שראית ב-TypeScript. NestJS מבטיח שהמחלקה תספק transform, וקורא לו אוטומטית.

9. Exception Filters — טיפול בשגיאות

NestJS מטפל בשגיאות בצורה מובנית. במקום try/catch בכל controller, אתה זורק exception וה-framework ממיר אותו ל-HTTP response מתאים.

Built-in HTTP exceptions

NestJS מספק מחלקות exception לכל status code נפוץ. זורקים אותן מכל מקום — service או controller — וה-framework מתרגם:

import {
  NotFoundException,
  BadRequestException,
  UnauthorizedException,
  ForbiddenException,
  ConflictException,
} from "@nestjs/common";

findOne(id: string): User {
  const user = this.users.find((u) => u.id === id);
  if (!user) {
    throw new NotFoundException(`User ${id} not found`);  // → 404 אוטומטי
  }
  return user;
}

NotFoundException הופך ל-404 עם JSON מסודר, UnauthorizedException ל-401, וכן הלאה. אתה פשוט זורק — NestJS מעצב את ה-response.

Custom Exception Filter

כשאתה צריך שליטה מלאה על צורת ה-error response (למשל פורמט אחיד לכל ה-API, או logging), כותבים exception filter:

import {
  ExceptionFilter, Catch, ArgumentsHost, HttpException,
} from "@nestjs/common";
import { Response } from "express";

@Catch(HttpException)
export class HttpExceptionFilter implements ExceptionFilter {
  catch(exception: HttpException, host: ArgumentsHost) {
    const ctx = host.switchToHttp();
    const response = ctx.getResponse<Response>();
    const status = exception.getStatus();

    response.status(status).json({
      statusCode: status,
      timestamp: new Date().toISOString(),
      message: exception.message,
    });
  }
}

ה-@Catch(HttpException) אומר "התפוס הזה מטפל ב-HttpException". מפעילים אותו גלובלית עם app.useGlobalFilters(new HttpExceptionFilter()), או נקודתית עם @UseFilters() על controller ספציפי.

10. Guards — אימות והרשאות

Guard מחליט אם request מורשה להמשיך — כן או לא. זה המקום הנכון ל-authentication (מי אתה) ו-authorization (מה מותר לך). Guard מחזיר true (המשך) או false/exception (עצור).

Guard בסיסי

import {
  CanActivate, ExecutionContext, Injectable, UnauthorizedException,
} from "@nestjs/common";

@Injectable()
export class AuthGuard implements CanActivate {
  canActivate(context: ExecutionContext): boolean {
    const request = context.switchToHttp().getRequest();
    const token = request.headers["authorization"];

    if (!token) {
      throw new UnauthorizedException("Missing token");
    }
    // כאן היית מאמת את ה-token באמת (JWT וכו')
    return true;
  }
}

הפעלת Guard

import { UseGuards } from "@nestjs/common";

@Controller("users")
@UseGuards(AuthGuard)              // מגן על כל ה-controller
export class UsersController {

  @Get("public")
  publicRoute() {}                // עדיין מוגן — כי ה-guard על ה-controller

  @Get("me")
  @UseGuards(AuthGuard)           // אפשר גם על route בודד
  getProfile() {}
}

Role-based authorization עם metadata

הדפוס הקלאסי: decorator מותאם שמצמיד metadata (אילו roles מותרים), ו-guard שקורא אותו. זה בדיוק "decorator = metadata" מהמדריך הקודם, בפעולה:

import { SetMetadata } from "@nestjs/common";

// decorator מותאם שמצמיד את ה-roles הנדרשים כ-metadata
export const Roles = (...roles: string[]) => SetMetadata("roles", roles);

@Injectable()
export class RolesGuard implements CanActivate {
  constructor(private reflector: Reflector) {}   // Reflector קורא metadata

  canActivate(context: ExecutionContext): boolean {
    const required = this.reflector.get<string[]>("roles", context.getHandler());
    if (!required) return true;                  // אין דרישת role — מותר

    const { user } = context.switchToHttp().getRequest();
    return required.some((role) => user.roles?.includes(role));
  }
}
// שימוש בקוד:
@Post()
@Roles("admin")                   // רק admin יכול ליצור
@UseGuards(AuthGuard, RolesGuard)
create(@Body() dto: CreateUserDto) {}

ה-Reflector הוא הכלי של NestJS לקריאת metadata ש-decorators הצמידו. זה מסגר את הכל: אתה מתייג עם @Roles, וה-guard קורא את התיוג ומחליט.

11. Interceptors

Interceptor עוטף את הריצה של ה-handler — הוא יכול לרוץ קוד לפני ואחרי ה-method, ולשנות את ה-response. שימושי ל-logging, למדידת זמנים, ולעיצוב אחיד של תגובות.

מבנה של interceptor

import {
  NestInterceptor, ExecutionContext, CallHandler, Injectable,
} from "@nestjs/common";
import { Observable } from "rxjs";
import { map, tap } from "rxjs/operators";

@Injectable()
export class LoggingInterceptor implements NestInterceptor {
  intercept(context: ExecutionContext, next: CallHandler): Observable<any> {
    const now = Date.now();

    // קוד "לפני" ה-handler רץ כאן

    return next.handle().pipe(
      // קוד "אחרי" — כשה-handler סיים
      tap(() => console.log(`Request took ${Date.now() - now}ms`)),
    );
  }
}

next.handle() מריץ את ה-handler בפועל ומחזיר Observable (מ-RxJS). כל מה שאחרי .pipe() רץ אחרי שה-handler סיים.

עיצוב אחיד של response

שימוש נפוץ — לעטוף כל תגובה במעטפת אחידה:

@Injectable()
export class TransformInterceptor implements NestInterceptor {
  intercept(context: ExecutionContext, next: CallHandler): Observable<any> {
    return next.handle().pipe(
      map((data) => ({ success: true, data, timestamp: Date.now() })),
    );
  }
}
// עכשיו כל תגובה תיראה: { success: true, data: {...}, timestamp: ... }

הערה על RxJS: NestJS משתמש ב-Observables ב-interceptors. אם אתה לא מכיר RxJS, אל תיבהל — ל-interceptors בסיסיים מספיק לדעת ש-map משנה את ה-response ו-tap מריץ side-effect בלי לשנות. לא צריך RxJS מלא כדי להתחיל.

12. Middleware וסדר ה-Request Lifecycle

Middleware הוא הרובד הקרוב ביותר ל-Express — פונקציה שרצה לפני שה-request מגיע ל-router של NestJS. שימושי לדברים גלובליים כמו logging גולמי, CORS, או parsing.

import { Injectable, NestMiddleware } from "@nestjs/common";
import { Request, Response, NextFunction } from "express";

@Injectable()
export class LoggerMiddleware implements NestMiddleware {
  use(req: Request, res: Response, next: NextFunction) {
    console.log(`${req.method} ${req.url}`);
    next();                         // חובה לקרוא ל-next כדי להמשיך
  }
}
// מפעילים middleware ב-module:
export class AppModule implements NestModule {
  configure(consumer: MiddlewareConsumer) {
    consumer.apply(LoggerMiddleware).forRoutes("*");
  }
}

סדר הריצה — הטבלה שחייבים לדעת בעל-פה

זו אחת הנקודות שהכי מבלבלות. כשמגיע request, NestJS מריץ את הרכיבים בסדר מדויק וקבוע:

שלבהרכיבלמה משמש
1Middlewareעיבוד גולמי, logging, CORS
2Guardsאימות והרשאות (אם לא מורשה — עוצר כאן)
3Interceptors (לפני)קוד שרץ לפני ה-handler
4Pipesvalidation והמרה של הנתונים
5ה-Handler (controller method)הלוגיקה שלך
6Interceptors (אחרי)עיצוב ה-response
7Exception Filtersתופסים כל שגיאה שנזרקה בדרך

למה זה חשוב מעשית? כי זה מסביר החלטות עיצוב. למשל: guard רץ לפני pipe, אז ה-guard לא יכול לסמוך על נתונים מאומתים — ה-validation עדיין לא רץ. ו-exception filter תופס שגיאות מכל השלבים. הבנת הסדר הזה חוסכת שעות של דיבוג.

13. Configuration ו-Environment

לעולם אל תכתוב סודות (מפתחות, סיסמאות DB) בקוד. NestJS מספק package רשמי לניהול קונפיגורציה מ-environment variables.

npm install @nestjs/config
import { ConfigModule, ConfigService } from "@nestjs/config";

@Module({
  imports: [
    ConfigModule.forRoot({
      isGlobal: true,              // זמין בכל האפליקציה בלי לייבא שוב
      envFilePath: ".env",
    }),
  ],
})
export class AppModule {}

forRoot() הוא דפוס נפוץ ב-NestJS — module שמקבל הגדרות. אחרי זה מזריקים את ConfigService וקוראים ערכים:

@Injectable()
export class DatabaseService {
  constructor(private config: ConfigService) {}

  connect() {
    const url = this.config.get<string>("DATABASE_URL");
    const port = this.config.get<number>("PORT", 3000);   // עם ברירת מחדל
  }
}

Best practice: הוסף validation גם ל-env vars (ConfigModule תומך ב-schema עם Joi). אפליקציה שנופלת בעלייה כי חסר DATABASE_URL עדיפה בהרבה על אפליקציה שעולה ומתרסקת בבקשה הראשונה. זה אותו עיקרון של "fail fast" — תפוס את הבעיה מוקדם ככל האפשר.

14. Database — TypeORM ו-Prisma

NestJS לא מכתיב DB או ORM. שתי הבחירות הנפוצות ביותר הן TypeORM (משתלב הכי הדוק, decorator-based) ו-Prisma (type-safety מעולה, schema נפרד). נראה את TypeORM כי הוא ה"native" ל-NestJS.

Entity — טבלה כמחלקה

import { Entity, PrimaryGeneratedColumn, Column, CreateDateColumn } from "typeorm";

@Entity()                          // הופך את המחלקה לטבלה ב-DB
export class User {
  @PrimaryGeneratedColumn("uuid")
  id: string;

  @Column()
  name: string;

  @Column({ unique: true })
  email: string;

  @Column({ default: true })
  isActive: boolean;

  @CreateDateColumn()
  createdAt: Date;
}

שוב decorators שמצרפים metadata — הפעם TypeORM קורא אותם ובונה מהם את סכמת ה-DB. אותו רעיון בדיוק כמו NestJS עצמו.

חיבור ה-Repository ל-Service

// users.module.ts — רושמים את ה-entity
@Module({
  imports: [TypeOrmModule.forFeature([User])],
  providers: [UsersService],
})
export class UsersModule {}
// users.service.ts — מזריקים את ה-repository
@Injectable()
export class UsersService {
  constructor(
    @InjectRepository(User)
    private readonly userRepo: Repository<User>,
  ) {}

  findAll(): Promise<User[]> {
    return this.userRepo.find();
  }

  async findOne(id: string): Promise<User> {
    const user = await this.userRepo.findOneBy({ id });
    if (!user) throw new NotFoundException(`User ${id} not found`);
    return user;
  }

  create(dto: CreateUserDto): Promise<User> {
    const user = this.userRepo.create(dto);   // בונה instance
    return this.userRepo.save(user);          // שומר ל-DB
  }
}

Repository<User> הוא בדיוק ה-generic repository שראית במדריך TypeScript — עכשיו עם מימוש אמיתי מ-TypeORM. הכל מתחבר.

15. Lifecycle Hooks ו-Async Providers

לפעמים provider צריך לעשות setup (פתיחת חיבור) בעלייה, או cleanup (סגירה) בכיבוי. NestJS מספק lifecycle hooks:

import { Injectable, OnModuleInit, OnModuleDestroy } from "@nestjs/common";

@Injectable()
export class DatabaseService implements OnModuleInit, OnModuleDestroy {
  async onModuleInit() {
    // רץ פעם אחת כשה-module עולה — מקום טוב לפתוח חיבור
    await this.connect();
  }

  async onModuleDestroy() {
    // רץ בכיבוי — סוגרים חיבורים, משחררים משאבים
    await this.disconnect();
  }
}

ה-hooks הנפוצים: onModuleInit (setup), onModuleDestroy (cleanup), ו-onApplicationBootstrap (אחרי שכל ה-modules אותחלו). השתמש בהם במקום לעשות side-effects ב-constructor — constructor צריך להישאר "טהור".

למה לא ב-constructor? constructor רץ בזמן בניית ה-DI graph, כשלא בטוח שכל ה-dependencies מוכנים, והוא סינכרוני (לא יכול await). lifecycle hooks רצים בזמן הנכון ויכולים להיות async. זה כלל אצבע טוב: constructor רק להזרקה, לוגיקה ב-hooks.

16. Testing

אחד היתרונות הגדולים של DI הוא שהוא הופך בדיקות לקלות — אפשר להחליף כל dependency ב-mock. NestJS מגיע עם utilities לבנות "מודול בדיקה".

Unit test ל-service

import { Test, TestingModule } from "@nestjs/testing";
import { UsersService } from "./users.service";

describe("UsersService", () => {
  let service: UsersService;

  beforeEach(async () => {
    const module: TestingModule = await Test.createTestingModule({
      providers: [
        UsersService,
        // מחליפים את ה-repository האמיתי ב-mock:
        {
          provide: getRepositoryToken(User),
          useValue: {
            find: jest.fn().mockResolvedValue([]),
            findOneBy: jest.fn(),
          },
        },
      ],
    }).compile();

    service = module.get<UsersService>(UsersService);
  });

  it("should return all users", async () => {
    expect(await service.findAll()).toEqual([]);
  });
});

שים לב איך useValue (זוכר את custom providers?) מחליף את ה-repository האמיתי ב-mock. זה בדיוק היתרון של DI — ה-service לא יודע ולא אכפת לו מה מוזרק, כל עוד זה מקיים את החוזה.

E2E test

בדיקת end-to-end מריצה את כל האפליקציה ובודקת HTTP אמיתי:

import * as request from "supertest";

it("/users (GET)", () => {
  return request(app.getHttpServer())
    .get("/users")
    .expect(200)
    .expect([]);
});

ההבחנה: unit tests בודקים לוגיקה בבידוד (מהירים, הרבה), e2e tests בודקים שהכל מחובר נכון (איטיים, מעטים). שילוב נכון של שניהם הוא הבסיס לפרויקט אמין.

17. Best Practices וטעויות נפוצות

  1. Controllers דקים, services שמנים. שום לוגיקה עסקית ב-controller — הוא רק מנתב.
  2. DTO תמיד class, אף פעם interface. interface נמחק ב-runtime ולא יכול לשאת validation decorators.
  3. ValidationPipe גלובלי עם whitelist ו-transform. הגדר פעם אחת, תיהנה בכל האפליקציה.
  4. אל תיגע ב-@Res() הגולמי. תן ל-NestJS לנהל את ה-response, אחרת אתה מאבד interceptors ו-serialization.
  5. כבד את ה-encapsulation של modules. provider חייב exports כדי לשמש module אחר. אל תשבור את זה עם @Global() על הכל.
  6. זרוק exceptions, אל תחזיר error objects. throw new NotFoundException() ולא return { error: ... }.
  7. singleton scope כברירת מחדל. הימנע מ-Scope.REQUEST אלא אם באמת נחוץ — יש לו מחיר ביצועים.
  8. סודות ב-env, לא בקוד. @nestjs/config עם validation.
  9. side-effects ב-lifecycle hooks, לא ב-constructor. constructor רק להזרקה.
  10. נצל את ה-CLI. nest g resource חוסך boilerplate ושומר על עקביות.

טעויות נפוצות שכדאי לזהות מוקדם

  • "Nest can't resolve dependencies" — הטעות הכי נפוצה. כמעט תמיד: שכחת exports ב-module שמספק, או imports ב-module שצורך, או @Injectable() על המחלקה.
  • validation לא רץ — שכחת app.useGlobalPipes(new ValidationPipe()), או השתמשת ב-interface במקום class ל-DTO.
  • circular dependency בין modules — שני modules שמייבאים זה את זה. פתרון: forwardRef(), או עדיף — לחשוב מחדש על הגבולות.
  • לשים לוגיקה ב-controller — מקשה על בדיקות ושימוש חוזר.

18. תרגיל מסכם

הדרך היחידה ללמוד NestJS היא לבנות. הנה פרויקט שמכסה את כל מה שכאן — בנה אותו מאפס:

המשימה: API לניהול משימות (Tasks).

  1. Setup: nest new tasks-api, הפעל ValidationPipe גלובלי ב-main.ts.
  2. Module: צור TasksModule עם controller ו-service (נסה nest g resource tasks).
  3. Entity: Task עם id, title, description, status ("open" | "in-progress" | "done"), createdAt.
  4. DTOs: CreateTaskDto עם validation (@IsString, @IsEnum), ו-UpdateTaskDto עם PartialType.
  5. CRUD: ממש GET /tasks, GET /tasks/:id (עם ParseUUIDPipe ו-NotFoundException), POST, PATCH, DELETE.
  6. Guard: הוסף AuthGuard פשוט שבודק header, והגן על POST ו-DELETE.
  7. Interceptor: הוסף TransformInterceptor שעוטף כל תגובה ב-{ success, data }.
  8. Config: העבר את ה-PORT ל-.env דרך @nestjs/config.
  9. Bonus: חבר ל-DB אמיתי עם TypeORM, והוסף unit test אחד ל-service.

אם תבנה את זה ותבין כל שורה — אתה מפתח NestJS מתפקד.

סיכום — מה הלאה

עברנו את כל שלד ה-NestJS: מהמודל המנטלי (framework שמרכיב metadata של decorators), דרך modules, controllers, providers ו-DI, ועד ה-request lifecycle המלא, database, ו-testing.

שים לב כמה מעט היה כאן "חדש" ברמת השפה — הכל נשען על TypeScript שכבר ידעת: decorators שמצרפים metadata, generics ב-repositories, DI דרך parameter properties, ו-interfaces ל-contracts. NestJS הוא בעיקר ארגון ומוסכמות על גבי TypeScript מוצק.

הצעד הבא היחיד שחשוב: לבנות את התרגיל המסכם. קריאה נותנת מפה, בנייה נותנת שליטה. פתח טרמינל, nest new, וצא לדרך.
