1. Authentication מול Authorization — ההבחנה הבסיסית

לפני הכל, שני מושגים שאנשים מבלבלים כל הזמן. הם נשמעים דומה (שניהם "Auth") אבל עונים על שאלות שונות:

  • Authentication (אימות, "authn") — מי אתה? להוכיח זהות. login עם סיסמה, טביעת אצבע, קוד מה-SMS.
  • Authorization (הרשאה, "authz") — מה מותר לך? בהינתן שאתה מזוהה, אילו פעולות ומשאבים פתוחים בפניך. admin מול user רגיל.

הסדר תמיד קבוע: קודם authentication, אחר כך authorization. אי אפשר להחליט מה מותר למישהו לפני שיודעים מי הוא. ארבעת הנושאים במדריך הזה עוסקים בעיקר ב-authentication ובשמירת הזהות לאורך זמן — חוץ מ-OAuth, שהוא בעצם על authorization מבוזר (עוד נגיע לזה).

הבעיה הבסיסית: HTTP הוא stateless

הנה הליבה של כל הנושא. פרוטוקול HTTP חסר זיכרון — כל request הוא עצמאי לחלוטין. השרת לא זוכר שום דבר מה-request הקודם. כשאתה מתחבר עם סיסמה בבקשה אחת, ובבקשה הבאה מבקש את הפרופיל שלך — מבחינת HTTP אלה שני זרים מוחלטים.

אז נוצרת השאלה שכל מנגנוני ה-auth מנסים לפתור: אחרי שהמשתמש הוכיח את זהותו פעם אחת, איך השרת "זוכר" אותו בבקשות הבאות בלי לבקש סיסמה כל פעם?

כל מה שנלמד — cookies, sessions, JWT — הוא בסופו של דבר תשובה שונה לשאלה הזו: איך נושאים הוכחת זהות מבקשה לבקשה.

2. המפה: למה אלה לא ארבעה מתחרים

זו הנקודה הכי חשובה במדריך, אז נעצור עליה לפני כל פרט טכני. אנשים שואלים "JWT או Session או Cookie או OAuth?" כאילו צריך לבחור אחד. זו שאלה שגויה. הם חיים בשלוש שכבות שונות:

מושגאיזו שכבהעונה על השאלה
Cookieמנגנון תעבורהאיפה שומרים את הזהות בדפדפן ואיך שולחים אותה אוטומטית בכל בקשה?
Sessionאסטרטגיית זהות (stateful)השרת זוכר את המשתמש — מחזיק state בצד שלו
JWTאסטרטגיית זהות (stateless)המשתמש נושא איתו טוקן חתום — השרת לא זוכר כלום
OAuth 2.0Framework להרשאה מבוזרתאיך אפליקציה מקבלת גישה בשם המשתמש לשירות אחר (Google, GitHub)?

איך הם מתחברים בפועל

הנה הקסם — הם עובדים יחד, לא במקום זה את זה:

  • Session-based auth משתמש ב-cookie כדי לשלוח את ה-session ID. (Session + Cookie)
  • JWT אפשר לשלוח בתוך cookie, או ב-header. (JWT + Cookie, או JWT לבד)
  • OAuth 2.0 מנפיק לך בסוף טוקנים — שלרוב הם JWT. (OAuth + JWT)

אז צירוף אמיתי בפרויקט יכול להיות: "התחברות דרך Google (OAuth 2.0 + OIDC), שמנפיקה JWT, שנשמר ב-HttpOnly cookie". שלושה מהמושגים בפעולה בו-זמנית. ברגע שתפנים שאלה שכבות ולא מתחרים — כל הנושא מתבהר.

המשפט לזכור: Cookie זה איפה, Session ו-JWT זה איך זוכרים (בשרת או אצל הלקוח), ו-OAuth זה איך נותנים לאפליקציה שלישית גישה. שאלה נכונה היא לא "מי מנצח" אלא "איזה שילוב מתאים לי".

3. Cookies — מנגנון התעבורה

נתחיל מהתשתית, כי הכל בנוי עליה. Cookie הוא פיסת מידע קטנה שהשרת מבקש מהדפדפן לשמור, והדפדפן שולח אותה אוטומטית בכל בקשה עתידית לאותו domain. זהו — זה כל הרעיון. Cookie בעצמו לא "auth", הוא רק צינור.

איך זה עובד

1. Server response: Set-Cookie: sessionId=abc123; HttpOnly; Secure
2. Browser stores the cookie
3. Every next request: Cookie: sessionId=abc123 (אוטומטית, בלי קוד)

היתרון המרכזי: אוטומטי. אתה לא צריך לכתוב קוד שמצרף את ה-cookie — הדפדפן עושה את זה לבד לכל בקשה לאותו domain. זו בדיוק הסיבה שהוא מתאים כל כך ל-auth.

ה-attributes שחייבים להכיר

כאן נמצאת רוב האבטחה. cookie בלי ה-attributes הנכונים הוא חור אבטחה:

Set-Cookie: sessionId=abc123;
  HttpOnly;              // JavaScript לא יכול לקרוא את ה-cookie — הגנה מ-XSS
  Secure;                // נשלח רק על HTTPS, אף פעם לא על HTTP
  SameSite=Strict;       // לא נשלח בבקשות cross-site — הגנה מ-CSRF
  Max-Age=3600;          // תוקף בשניות (או Expires עם תאריך)
  Path=/;                // לאילו נתיבים ה-cookie שייך
  Domain=example.com     // לאיזה domain
  • HttpOnly — הכי חשוב לאבטחה. הופך את ה-cookie לבלתי-נגיש ל-JavaScript (document.cookie לא יראה אותו). זה מה שמגן על טוקן גם אם יש XSS בדף.
  • Secure — ה-cookie נשלח רק על חיבור מוצפן (HTTPS). חובה ב-production.
  • SameSite — שולט אם ה-cookie נשלח בבקשות מ-sites אחרים. Strict (הכי מחמיר), Lax (ברירת מחדל סבירה), None (מחייב Secure). זה קו ההגנה המרכזי מפני CSRF.

נקודה קריטית: השילוב HttpOnly + Secure + SameSite הוא מה שהופך cookie לדרך בטוחה לשמור טוקן. בלי HttpOnly, כל סקריפט זדוני בדף יכול לגנוב את הטוקן. נחזור לזה בפרק האבטחה — זה ההבדל המעשי הגדול בין אחסון ב-cookie לאחסון ב-localStorage.

4. Session-based Auth — הגישה ה-Stateful

זו הגישה הוותיקה והפשוטה מבחינה מושגית. הרעיון: השרת זוכר את המשתמש. כשמתחברים, השרת יוצר "session" — רשומה בצד שלו — ונותן ללקוח רק מזהה קטן (session ID) שמצביע עליה.

הזרימה המלאה

1. POST /login { email, password }
2. Server: מאמת סיסמה → יוצר session ב-store → session id = "abc123"
3. Server response: Set-Cookie: sessionId=abc123; HttpOnly; Secure
4. כל בקשה הבאה: Cookie: sessionId=abc123
5. Server: מחפש "abc123" ב-store → מוצא { userId: 42 } → יודע מי המשתמש

הנקודה המרכזית: ה-session ID לבדו הוא חסר משמעות — הוא סתם מחרוזת אקראית. כל המידע האמיתי (מי המשתמש, מתי התחבר, ההרשאות) יושב בשרת. ה-ID הוא רק מפתח שמצביע לרשומה.

איפה ה-session נשמר בשרת

ה-session store הוא מסד נתונים כלשהו שמחזיק את הרשומות:

  • בזיכרון (in-memory) — הכי פשוט, אבל נעלם ב-restart ולא עובד עם כמה שרתים. רק לפיתוח.
  • Redis — הבחירה הנפוצה ל-production. מהיר, משותף בין שרתים, תומך ב-expiry אוטומטי.
  • מסד נתונים (Postgres וכו') — עמיד, אבל איטי יותר לגישה בכל בקשה.

היתרון הגדול: revocation מיידי

זה המקום שבו sessions זורחים. רוצה לנתק משתמש עכשיו (לחצן "התנתק מכל המכשירים", חשבון שנפרץ)? פשוט מוחקים את הרשומה מה-store. הבקשה הבאה עם אותו session ID לא תמצא רשומה — והמשתמש מנותק מיידית. שליטה מלאה ומיידית על מי מחובר.

החיסרון: state שצריך לנהל ולסקיילר

כל בקשה מחייבת חיפוש ב-store (round-trip ל-Redis/DB). וברגע שיש לך כמה שרתים, כולם חייבים גישה לאותו store משותף. זה עובד מצוין, אבל זה תלות תשתיתית שצריך לתחזק — וזו בדיוק הנקודה ש-JWT מנסה לפתור.

5. JWT — הגישה ה-Stateless

JWT (JSON Web Token, מבטאים "jot") הופך את המודל על הראש. במקום שהשרת יזכור את המשתמש, המשתמש נושא איתו את כל המידע — בתוך טוקן חתום דיגיטלית. השרת לא שומר כלום; הוא רק מאמת את החתימה.

המבנה: שלושה חלקים מופרדים בנקודה

JWT הוא מחרוזת אחת בפורמט xxxxx.yyyyy.zzzzz — שלושה חלקים מקודדים ב-Base64URL:

eyJhbGciOiJIUzI1NiJ9.eyJzdWIiOiI0MiIsIm5hbWUiOiJFbGl5YSJ9.dBjftJeZ4CVP...
└──── Header ────┘ └──────── Payload ────────┘ └─── Signature ───┘

1. Header — איזה אלגוריתם חתימה:

{ "alg": "HS256", "typ": "JWT" }

2. Payload (claims) — המידע עצמו. כאן שמים את זהות המשתמש והמטא-דאטה:

{
  "sub": "42",          // subject — מזהה המשתמש
  "name": "Eliya",
  "role": "admin",
  "iat": 1735680000,    // issued at — מתי נוצר
  "exp": 1735683600     // expiration — מתי פג (חובה!)
}

3. Signature — חתימה קריפטוגרפית של ה-header וה-payload עם מפתח סודי שרק השרת מכיר:

HMACSHA256( base64(header) + "." + base64(payload), secret )

הנקודה הקריטית ביותר להבין ב-JWT

ה-payload מקודד, לא מוצפן. כל אחד יכול לפענח Base64 ולקרוא את התוכן — נסה להדביק JWT ב-jwt.io ותראה הכל. אז לעולם אל תשים ב-JWT מידע רגיש (סיסמאות, מספרי כרטיס). מה שמגן על ה-JWT זה לא סודיות התוכן אלא החתימה: אם מישהו ישנה ולו תו אחד ב-payload, החתימה לא תתאים והשרת ידחה את הטוקן. החתימה מבטיחה שלמות ואותנטיות, לא סודיות.

הזרימה

1. POST /login { email, password }
2. Server: מאמת → חותם JWT עם ה-secret → מחזיר את הטוקן
3. הלקוח שומר את הטוקן ושולח אותו בכל בקשה:
   Authorization: Bearer eyJhbGc...
4. Server: מאמת את החתימה בלבד → קורא את ה-payload → יודע מי המשתמש
   (שום גישה ל-DB או store!)

שים לב לשלב 4: השרת לא פונה לשום מקום. הוא מוודא את החתימה מתמטית עם ה-secret, וזהו. זה מה ש"stateless" אומר — כל המידע הדרוש נמצא בטוקן עצמו.

היתרון: סקיילינג בלי state משותף

כל שרת שמכיר את ה-secret יכול לאמת את הטוקן, לבד, בלי Redis ובלי DB. זה הופך את הסקיילינג לפשוט — הוסף שרתים כרצונך, אין store משותף לתחזק. זו הסיבה ש-JWT פופולרי ב-microservices וב-APIs.

החיסרון הגדול: אי אפשר לבטל טוקן בקלות

וכאן ה-tradeoff שהופך את היתרון לחיסרון. אם השרת לא זוכר כלום, איך מבטלים טוקן לפני שפג? משתמש נפרץ, לחצת "התנתק" — אבל הטוקן החתום עדיין תקף עד ה-exp שלו, וכל שרת יקבל אותו. אין "מחיקת רשומה" כמו ב-session, כי אין רשומה.

הפתרונות (כולם מוסיפים בחזרה קצת state, קצת אירוני):

  • תוקף קצר — לתת ל-access token לחיות דקות ספורות, כך שגם אם נגנב הוא כמעט חסר ערך. זה מוביל ישר לדפוס refresh token (פרק הבא).
  • Blocklist — לנהל רשימת טוקנים שבוטלו (ב-Redis). אבל זה מחזיר את ה-state שרצינו להימנע ממנו.

6. Session מול JWT — ההשוואה האמיתית

עכשיו כשמבינים את שניהם, הנה ההשוואה הישירה. זו לא שאלה של "מי טוב יותר" אלא של tradeoffs:

קריטריוןSession (stateful)JWT (stateless)
איפה ה-stateבשרת (store)אצל הלקוח (בטוקן)
אימות בקשהחיפוש ב-store (round-trip)אימות חתימה מקומי (מהיר)
ביטול מיידי✅ קל — מוחקים רשומה❌ קשה — הטוקן תקף עד exp
סקיילינגצריך store משותף (Redis)✅ פשוט — אין state משותף
גודל בכל בקשהקטן (רק ID)גדול יותר (כל ה-payload)
מתאים ל-אפליקציות web מונוליטיות, כשצריך שליטהAPIs, microservices, mobile

האמת הלא-פופולרית: הרבה מפתחים בוחרים JWT כברירת מחדל כי זה "מודרני", ואז נאבקים בבעיית ה-revocation ומוסיפים blocklist ב-Redis — ובכך בונים מחדש session, רק יותר מסובך. אם יש לך אפליקציית web קלאסית עם שרת אחד או כמה מאחורי load balancer, session עם Redis לרוב פשוט יותר ובטוח יותר. בחר JWT כשאתה באמת צריך stateless (APIs חוצי-שירותים, mobile, אין לך רצון לתחזק store). אל תבחר לפי אופנה.

7. Access Token ו-Refresh Token

הדפוס הזה פותר את הבעיה המרכזית של JWT (אי-ביטול) ומשלב את הטוב משני העולמות. הרעיון: שני טוקנים במקום אחד.

  • Access Token — JWT קצר-חיים (5–15 דקות). נשלח בכל בקשה. אם נגנב — פג כמעט מיד, נזק מוגבל.
  • Refresh Token — ארוך-חיים (ימים/שבועות). נשמר בבטחה (HttpOnly cookie), ומשמש רק כדי לקבל access token חדש כשהישן פג.

הזרימה

1. Login → מקבלים access token (15 דק') + refresh token (7 ימים)
2. עובדים עם access token רגיל בכל בקשה
3. אחרי 15 דק' ה-access token פג → בקשה מחזירה 401
4. הלקוח שולח את ה-refresh token ל-POST /refresh
5. Server מאמת → מנפיק access token חדש (בלי login מחדש)
6. חוזרים לשלב 2

למה זה חכם: ה-access token קצר כל כך שהבעיה של "אי אפשר לבטל" כמעט לא רלוונטית — גם אם נגנב, הוא מת תוך דקות. וה-refresh token, שחי הרבה זמן, כן נשמר בצד השרת (או לפחות ניתן לביטול), אז אפשר לנתק משתמש על ידי ביטולו. קיבלת סקיילינג של JWT לבקשות היומיומיות, עם יכולת revocation דרך ה-refresh.

Best practice: refresh token נשמר ב-HttpOnly Secure cookie (לא ב-localStorage), ורצוי עם rotation — כל שימוש ב-refresh מנפיק refresh חדש ומבטל את הישן, כך שאם נגנב אחד, מזהים שימוש כפול ומנתקים הכל.

8. OAuth 2.0 — Framework להרשאה מבוזרת

OAuth 2.0 שונה מכל השאר, ולכן הכי מבלבל. הוא לא דרך לזכור משתמש — הוא framework שמאפשר לאפליקציה לקבל גישה מוגבלת למשאבים של משתמש בשירות אחר, בלי שהמשתמש ייתן לה את הסיסמה שלו.

הבעיה ש-OAuth פותר

דמיין אפליקציה שרוצה לגשת לקבצי Google Drive שלך. הפתרון הנאיבי: תיתן לה את סיסמת ה-Google שלך. נורא — עכשיו יש לה גישה מלאה לכל חשבון Google שלך, לתמיד. OAuth נותן פתרון: המשתמש מאשר ל-Google לתת לאפליקציה טוקן עם הרשאה מוגבלת ("קריאת קבצים בלבד"), בלי לחשוף את הסיסמה, וניתן לביטול בכל רגע.

זו הסיבה שכפתור "Sign in with Google / GitHub" קיים — מאחוריו רץ OAuth.

ארבעת התפקידים (Roles)

  • Resource Owner — המשתמש (בעל הנתונים).
  • Client — האפליקציה שרוצה גישה (שלך).
  • Authorization Server — מי שמנפיק טוקנים (למשל השרת של Google).
  • Resource Server — ה-API שמחזיק את המשאבים (Google Drive API).

ה-Flow הנפוץ: Authorization Code + PKCE

מבין כמה "grant types", זה המומלץ כיום לרוב האפליקציות (web ו-mobile). PKCE (מבטאים "pixie") הוא תוסף אבטחה שמונע גניבת ה-code בדרך:

1. המשתמש לוחץ "Sign in with Google" באפליקציה שלך
2. הפניה ל-Google: "האפליקציה X מבקשת גישה ל-email ו-profile"
3. המשתמש מתחבר ל-Google ומאשר
4. Google מפנה חזרה לאפליקציה עם authorization code זמני
5. השרת שלך מחליף את ה-code (+ secret/PKCE) מול Google → access token
6. עכשיו האפליקציה משתמשת ב-access token מול ה-Google API

הנקודה החשובה: הסיסמה של המשתמש אף פעם לא עוברת דרך האפליקציה שלך. היא נשארת בין המשתמש ל-Google. האפליקציה מקבלת רק טוקן מוגבל. וה-scopes (למשל read:email) קובעים בדיוק מה מותר לטוקן — הרשאה מדויקת ולא הכל-או-כלום.

הבהרה שחוסכת בלבול נפוץ: OAuth 2.0 לבדו הוא על authorization, לא authentication. הוא אומר "לאפליקציה הזו מותר לגשת ל-X", לא "המשתמש הזה הוא באמת אליה". להוכחת זהות (login) בנו שכבה מעל OAuth שנקראת OpenID Connect — הפרק הבא. אנשים אומרים "התחברתי עם OAuth" אבל מתכוונים בעצם ל-OIDC.

9. OpenID Connect (OIDC) — Login דרך OAuth

OIDC הוא שכבה דקה מעל OAuth 2.0 שמוסיפה את החלק החסר: הוכחת זהות. אם OAuth נותן "access token" (מה מותר), OIDC מוסיף ID Token — שהוא JWT שאומר מי המשתמש (email, name, מזהה ייחודי).

זה מה שבאמת רץ מאחורי "Sign in with Google" כשהמטרה היא להתחבר (ולא לגשת לקבצים). הזרימה זהה ל-OAuth, אבל בסוף מקבלים גם ID Token שממנו האפליקציה יודעת בוודאות מי התחבר.

OAuth 2.0OIDC
מטרהAuthorization (גישה)Authentication (זהות)
מנפיקAccess TokenAccess Token + ID Token
עונה על"מה מותר לאפליקציה""מי המשתמש"

הכלל הפשוט: רוצה שמשתמש יתחבר דרך ספק חיצוני → OIDC. רוצה גישה ל-API של ספק חיצוני בשם המשתמש → OAuth. בפועל, ספריות "social login" מטפלות בשניהם יחד.

11. מימוש בפועל ב-NestJS

עכשיו נחבר לקוד. NestJS משתמש ב-Passport (ספריית auth הסטנדרטית של Node) דרך @nestjs/passport, יחד עם guards שכבר הכרת מהמדריך הקודם.

שלב 1: אף פעם לא לשמור סיסמה כטקסט — bcrypt

לפני הכל, כלל הזהב: סיסמאות נשמרות ב-DB רק אחרי hashing (לא הצפנה — hashing חד-כיווני). התקן bcrypt:

import * as bcrypt from "bcrypt";

// בהרשמה — שומרים hash, לא את הסיסמה:
const hash = await bcrypt.hash(password, 10);   // 10 = salt rounds

// בהתחברות — משווים:
const isValid = await bcrypt.compare(password, user.passwordHash);

bcrypt מוסיף salt אוטומטית ואיטי בכוונה (כדי להקשות על brute-force). לעולם אל תשתמש ב-MD5/SHA לסיסמאות — הם מהירים מדי ולכן לא בטוחים לכך.

שלב 2: הנפקת JWT ב-login

import { JwtService } from "@nestjs/jwt";

@Injectable()
export class AuthService {
  constructor(
    private usersService: UsersService,
    private jwtService: JwtService,
  ) {}

  async login(email: string, password: string) {
    const user = await this.usersService.findByEmail(email);
    if (!user || !(await bcrypt.compare(password, user.passwordHash))) {
      throw new UnauthorizedException("Invalid credentials");
    }
    // ה-payload של ה-JWT — מה שיהיה בטוקן
    const payload = { sub: user.id, email: user.email, role: user.role };
    return { accessToken: this.jwtService.sign(payload) };
  }
}

שלב 3: JWT Strategy — איך מאמתים את הטוקן בבקשות

import { PassportStrategy } from "@nestjs/passport";
import { ExtractJwt, Strategy } from "passport-jwt";

@Injectable()
export class JwtStrategy extends PassportStrategy(Strategy) {
  constructor(config: ConfigService) {
    super({
      jwtFromRequest: ExtractJwt.fromAuthHeaderAsBearerToken(),
      secretOrKey: config.get("JWT_SECRET"),   // ה-secret לאימות החתימה
    });
  }

  // מה שחוזר מכאן מוזרק ל-request.user
  async validate(payload: any) {
    return { userId: payload.sub, email: payload.email, role: payload.role };
  }
}

שלב 4: הגנה על routes עם Guard

זוכר guards מהמדריך של NestJS? זה בדיוק אותו רעיון:

@Controller("profile")
export class ProfileController {
  @Get()
  @UseGuards(AuthGuard("jwt"))       // רק בקשות עם JWT תקין יעברו
  getProfile(@Req() req) {
    return req.user;                 // המידע מ-validate() למעלה
  }
}

הכל מתחבר: ה-guard מפעיל את ה-strategy, שמאמתת את החתימה, ש-validate שלה מזריקה את המשתמש ל-request. אותו מודל של "decorator + guard" שכבר ראית.

12. אבטחה — XSS, CSRF ואיפה לשמור טוקנים

הפרק הכי חשוב מעשית. שתי מתקפות מגדירות את כל ההחלטות של איפה ואיך לשמור טוקן.

XSS (Cross-Site Scripting)

קוד JavaScript זדוני שרץ בדף שלך (למשל דרך input לא מסונן) ויכול לקרוא כל דבר שנגיש ל-JS — כולל localStorage. זו הסיבה המרכזית שאחסון טוקן ב-localStorage מסוכן: XSS אחד = הטוקן נגנב.

CSRF (Cross-Site Request Forgery)

אתר זדוני גורם לדפדפן שלך לשלוח בקשה לאתר שאתה מחובר אליו, מנצל את זה שהדפדפן שולח cookies אוטומטית. זו דווקא חולשה של cookies — ולכן קיים SameSite.

הטבלה שמכריעה: איפה לשמור את הטוקן

מקוםחשוף ל-XSS?חשוף ל-CSRF?שורה תחתונה
localStorage❌ כן (JS קורא)✅ לאנוח, אבל מסוכן ל-XSS. הימנע לטוקנים.
HttpOnly Cookie✅ לא (JS חסום)❌ כן — אבל SameSite מגןהמומלץ: HttpOnly + Secure + SameSite

ההמלצה הפרקטית: שמור טוקנים ב-HttpOnly Secure SameSite cookie, לא ב-localStorage. כך XSS לא יכול לגנוב את הטוקן (הוא לא נגיש ל-JS), ו-SameSite חוסם את רוב מתקפות ה-CSRF. זה השילוב שנותן הגנה כפולה.

עוד כללי ברזל

  • HTTPS תמיד ב-production. בלי זה כל טוקן נשלח בטקסט גלוי וניתן ליירוט.
  • תוקף קצר ל-access token — מגביל את חלון הנזק אם נגנב.
  • אל תשים מידע רגיש ב-JWT payload — הוא קריא לכולם.
  • secret חזק ל-JWT (ארוך, אקראי, ב-env), ולעולם לא בקוד.
  • rate limiting על login — מונע brute-force על סיסמאות.
  • אמת קלט תמיד (זוכר את class-validator?) — XSS מתחיל בקלט לא מסונן.

13. מדריך החלטה — מה לבחור מתי

אין תשובה אחת נכונה, אבל יש התאמות טובות. הנה איך אני הייתי בוחר:

התרחישהבחירה המומלצתלמה
אפליקציית web מונוליטית, שרת אחד/כמהSession + Cookie (Redis)פשוט, בטוח, ביטול מיידי

MicroservicesJWTכל שירות מאמת לבד בלי store משותף

העצה החשובה ביותר: אל תבנה auth מאפס ב-production אם אתה יכול להימנע. השתמש בספריות בדוקות (Passport, @nestjs/jwt) או בשירותים מנוהלים (Auth0, Clerk, Supabase Auth, AWS Cognito). auth הוא תחום שבו באג קטן = פריצה, וספרייה שעברה ביקורת אבטחה עדיפה כמעט תמיד על מימוש עצמי. תלמד איך זה עובד (כמו במדריך הזה) — אבל תישען על קוד בדוק.

סיכום

הדבר האחד לקחת מהמדריך הזה: אלה לא מתחרים אלא שכבות. Cookie זה איפה שומרים ואיך שולחים. Session ו-JWT הן שתי תשובות לאותה שאלה — "איך זוכרים משתמש" — אחת בשרת (stateful, ביטול קל) ואחת אצל הלקוח (stateless, סקיילינג קל). OAuth 2.0 (עם OIDC) הוא רובד אחר לגמרי: איך נותנים לאפליקציה גישה או login דרך ספק חיצוני.

בפרויקט אמיתי תשלב אותם: למשל login עם Google (OIDC), שמנפיק JWT, שנשמר ב-HttpOnly cookie, עם refresh token לביטול. עכשיו כשאתה מבין כל חלק בנפרד — הצירופים הגיוניים.

הצעד הבא: קח פרויקט NestJS מהמדריך הקודם, והוסף לו auth מלא — bcrypt, JWT strategy, guards, refresh tokens. זה מגבש את הכל.
