1. מבוא: מגדל ההפשטות

כשאתה כותב const x = 5, קורה מסע מדהים: השורה הזו הופכת לפקודות מכונה, שרצות על CPU שמזיז אלקטרונים, שקורא מזיכרון שמנוהל על ידי מערכת הפעלה. כל שכבה מסתירה את זו שמתחתיה — וזה בדיוק היופי והסכנה.

למה זה חשוב לך — במיוחד עכשיו

אתה יכול לכתוב קוד שנים בלי להבין את השכבות האלה — עד שמשהו נשבר. למה הלולאה שלך איטית פי 10 עם linked list במקום array? למה שני threads "דורסים" ערך? למה Node מטפל באלפי חיבורים על thread אחד? למה סקריפט "אוכל" את כל ה-RAM? כל התשובות נמצאות בשכבות מתחת לקוד. ההבנה הזו היא מה שהופך אותך ממי שמעתיק פתרונות למי שמבין למה הם עובדים — וזה בדיוק מה ש-AI לא נותן לך, כי הוא נותן את ה"מה", לא את ה"למה".

המדריך מטפס במגדל מלמטה למעלה. בסוף, תעקוב אחרי web request דרך כל השכבות — ותראה איך הכל מתחבר.

2. בינארי וייצוג נתונים

הכל במחשב הוא bits — 0 או 1 (נוכחות/היעדר מתח חשמלי). כל מספר, טקסט, תמונה, וידאו — הכל בסופו של דבר רצף של bits. נבין איך.

Bits ו-Bytes

  • bit — הספרה הבינארית הבסיסית (0/1).
  • byte — 8 bits. יכול לייצג 2⁸ = 256 ערכים (0–255).
  • ספירה בינארית: 101 = 1×4 + 0×2 + 1×1 = 5.

ייצוג מספרים שליליים: Two's Complement

איך מייצגים מספר שלילי ב-bits? השיטה האוניברסלית היא two's complement: הופכים את כל ה-bits ומוסיפים 1. היתרון הגאוני — חיבור וחיסור עובדים באותו מעגל חומרה, בלי טיפול מיוחד בסימן:

ב-8 bits:
 5  = 00000101
-5  = 11111011   (הפוך את כל הביטים של 5, הוסף 1)
 5 + (-5) = 100000000 → נחתך ל-00000000 = 0  ✅

זו הסיבה ש-int ב-8 bits נע מ-128- עד 127 (לא 0–255): ה-bit העליון מסמן סימן. וזה מסביר integer overflow — כשמספר גדל מעבר לטווח, הוא "עוטף" למספר שלילי.

ייצוג מספרים עשרוניים: IEEE 754 — וכאן נפתר תעלומה

זוכר 0.1 + 0.2 !== 0.3 ממדריך JavaScript? הנה למה. מספרים עשרוניים מיוצגים ב-floating point לפי תקן IEEE 754: sign + exponent + mantissa (בערך "notation מדעי בבינארי"). הבעיה: 0.1 לא ניתן לייצוג מדויק ב-binary — בדיוק כמו ש-1/3 לא ניתן לייצוג מדויק בעשרוני (0.333...). אז 0.1 מאוחסן כקירוב, והשגיאות הזעירות מצטברות. זו לא תקלה של JS — זה איך כל שפה מייצגת floats בחומרה. הלקח (חוזר מ-SQL ו-JS): לעולם אל תשתמש ב-float לכסף — עבוד ב-integers (cents) או decimal.

ייצוג טקסט: Encoding

אותיות הן מספרים. ASCII מיפה 128 תווים (A=65). אבל 128 לא מספיק לעברית, אמוג'י, ושפות העולם — אז Unicode מגדיר מספר (code point) לכל תו, ו-UTF-8 מקודד אותם ל-bytes (1–4 bytes לתו). זו הסיבה שטקסט עברי ב-encoding שגוי = ג'יבריש (זוכר Buffers ממדריך Node?), ולמה תו עברי "שוקל" יותר bytes מתו אנגלי.

Hexadecimal — קיצור נוח

Hex (בסיס 16: 0-9, A-F) הוא דרך קומפקטית לכתוב binary — כל ספרת hex = 4 bits. לכן צבעים (#FF5733), כתובות זיכרון (0x7FFF), ו-hashes נכתבים ב-hex. 0xFF = 255 = 11111111.

3. איך קוד רץ — Compilation, Interpretation, JIT

ה-CPU מבין רק machine code (פקודות בינאריות). אבל אתה כותב JavaScript/Python. איך הפער נסגר? יש שלוש גישות, וההבדל ביניהן מסביר הרבה על ביצועים.

Compiled — תרגום מראש

שפות כמו C, C++, Rust, Go מקומפלות: compiler מתרגם את כל הקוד ל-machine code לפני ההרצה, פעם אחת. התוצאה — קובץ בינארי שרץ ישירות על ה-CPU. מהיר מאוד (אין תרגום בזמן ריצה), אבל תלוי-פלטפורמה (בינארי ל-Windows ≠ Linux) וצריך build.

Interpreted — תרגום תוך כדי

שפות כמו Python (בגישה הקלאסית) מפורשות: interpreter קורא ומריץ את הקוד שורה-שורה בזמן ריצה. גמיש (אין build, cross-platform, dynamic) אבל איטי יותר — כי התרגום קורה שוב ושוב בכל הרצה.

Bytecode + Virtual Machine — הביניים

Java, C# (ו-Python מתחת) מקמפלות ל-bytecode — פורמט ביניים, לא machine code אבל לא source. ה-bytecode רץ על Virtual Machine (JVM, CLR) שמתרגמת אותו לפלטפורמה. זה נותן "compile once, run anywhere" — ה-VM היא שכבת ההפשטה מעל החומרה.

JIT — הקסם של JavaScript

איך JavaScript "מפורשת" אבל מהירה? JIT (Just-In-Time compilation). מנוע V8 (זוכר ממדריך Node?) מתחיל לפרש, אבל מזהה קוד "חם" (פונקציות שרצות הרבה) ומקמפל אותן ל-machine code בזמן ריצה — משלב את הגמישות של interpreted עם המהירות של compiled. הוא גם עושה אופטימיזציות מבוססות-נתונים (למשל, מניח שמשתנה תמיד number ומקמפל בהתאם, ומבטל אם ההנחה נשברת). זו הסיבה שקוד JS "יציב" (טיפוסים עקביים) רץ מהר יותר מקוד "כאוטי" — ה-JIT יכול לאופטמז אותו טוב יותר. הבנת זה מסבירה למה טיפוסים עקביים (וגם TypeScript) עוזרים לביצועים.

4. ה-CPU מבפנים — Registers, ALU, Instructions

ה-CPU (Central Processing Unit) הוא ה"מוח" — הוא מבצע את הפקודות. נפרק אותו לרכיבים ונבין את המחזור שהוא רץ מיליארדי פעמים בשנייה.

הרכיבים המרכזיים

  • Registers — תאי זיכרון זעירים בתוך ה-CPU עצמו. הכי מהירים שיש (גישה ב-cycle אחד), אבל מעטים מאוד (עשרות). כאן ה-CPU מחזיק את הנתונים שהוא עובד עליהם עכשיו.
  • ALU (Arithmetic Logic Unit) — היחידה שמבצעת חישובים (חיבור, חיסור) ופעולות לוגיות (AND, OR). זה ה"מחשבון" של ה-CPU.
  • Control Unit — מנצח: מפענח פקודות ומכוון את שאר הרכיבים.
  • Clock — "פעימת הלב". כל tick (cycle) ה-CPU מתקדם צעד. 3GHz = 3 מיליארד ticks בשנייה.
  • Program Counter (PC) — register מיוחד שמצביע לכתובת הפקודה הבאה.

מחזור ה-Fetch-Decode-Execute

זה מה שה-CPU עושה, שוב ושוב, מיליארדי פעמים בשנייה. כל תוכנית בעולם היא בסופו של דבר המחזור הזה:

┌─→ 1. FETCH — שלוף את הפקודה הבאה מהזיכרון (לפי ה-PC)
│   2. DECODE — ה-Control Unit מפענח: מה הפקודה אומרת?
│   3. EXECUTE — ה-ALU/רכיבים מבצעים; התוצאה ל-register
└────── PC מתקדם לפקודה הבאה, חוזר

Instructions ו-ISA

ה-CPU מבין קבוצה מוגדרת של פקודות פשוטות — ה-Instruction Set Architecture (ISA). אלה פקודות אטומיות כמו "טען ערך מזיכרון ל-register", "חבר שני registers", "קפוץ לכתובת". שתי משפחות עיקריות:

  • x86 (Intel/AMD) — CISC, פקודות מורכבות. שולט ב-desktops/servers.
  • ARM — RISC, פקודות פשוטות וחסכוניות בחשמל. שולט במובייל, ובעלייה בשרתים (Apple Silicon, AWS Graviton).

כל שורת קוד שלך הופכת בסוף לרצף של פקודות ISA. למשל x = a + b ≈ "טען a ל-register, טען b ל-register, ALU מחבר, שמור תוצאה". Assembly הוא ייצוג קריא-לאדם של פקודות ה-ISA.

למה אכפת לך: אתה לא תכתוב assembly, אבל ההבנה שכל פעולה מתפרקת לפקודות זעירות שרצות ב-cycles מסבירה ביצועים. פעולה שנראית "אחת" בקוד (למשל גישה ל-property של object) יכולה להיות עשרות פקודות. וזה בסיס להבנת ה-cache (פרק 6) וה-atomics (פרק 17) — "פעולה אטומית" זה בדיוק שאלה של כמה פקודות CPU היא לוקחת.

5. Pipeline ו-CPU מודרני

אם ה-CPU היה עושה fetch-decode-execute אחד בכל פעם עד הסוף, הוא היה מבזבז זמן — בזמן ש-ALU עובד, יחידת ה-fetch בטלה. CPUs מודרניים משתמשים בטריקים מתוחכמים כדי לנצל כל cycle.

Pipelining — קו ייצור

כמו קו ייצור במפעל: בזמן שפקודה אחת ב-execute, הבאה כבר ב-decode, והשלישית ב-fetch — במקביל. במקום שכל פקודה תחכה לסיום המלא של הקודמת, הן "זורמות" בקו:

בלי pipeline: [F][D][E] [F][D][E] (פקודה, ואז הבאה)
עם pipeline: [F][D][E]
           [F][D][E]     ← חופפות! פי כמה throughput
              [F][D][E]

Hazards — מה שמשבש את ה-pipeline

ה-pipeline נשבר כשפקודה תלויה בתוצאה של קודמתה שעוד לא הסתיימה, או כשיש branch (if/loop) — ה-CPU לא יודע איזו פקודה באה אחרי ה-if עד שהוא מחשב את התנאי. וזה מוביל לטריק המדהים הבא.

Branch Prediction ו-Speculative Execution

במקום לחכות לתוצאת ה-if, ה-CPU מנחש לאיזה כיוון ה-branch ילך (על סמך היסטוריה — "בפעמים הקודמות הלולאה המשיכה") וממשיך להריץ באופן ספקולטיבי. אם ניחש נכון — חסך זמן. אם טעה — זורק את העבודה ומתחיל מחדש (branch misprediction, יקר). מנבאי ה-branch המודרניים מדויקים ב-~95%+.

למה אכפת לך: זה מסביר תופעה מפתיעה — קוד שמעבד מערך ממוין מהיר יותר מקוד על מערך לא-ממוין, כי ה-branch prediction מצליח יותר כשהדפוס צפוי. וזה גם הבסיס לפרצות אבטחה מפורסמות (Spectre/Meltdown) שניצלו את ה-speculative execution.

Superscalar ו-Out-of-Order

CPUs מודרניים הם superscalar (כמה ALUs — מריצים כמה פקודות בו-זמנית ממש) ו-out-of-order (מריצים פקודות לא לפי הסדר בקוד, אלא לפי מה שמוכן, כל עוד התוצאה נכונה). זו הסיבה ש"מספר הפקודות" לא שווה ל"זמן" — CPU מודרני עושה הרבה במקביל. גם hyper-threading (core פיזי אחד שנראה כשניים) הוא ניצול של ה-idle בזמן שפקודה מחכה לזיכרון.

6. Memory Hierarchy ו-Cache

זה אולי הפרק הכי חשוב לביצועים בפועל. ה-CPU מהיר בצורה מסחררת, אבל ה-RAM איטי בהשוואה — וכל הפער הזה מנוהל על ידי היררכיית זיכרון חכמה.

הבעיה: פער המהירות

ה-CPU יכול לבצע פקודה ב-cycle (~0.3 ננו-שנייה). אבל גישה ל-RAM לוקחת ~100 ננו-שניות — פי מאות. אם ה-CPU היה מחכה ל-RAM בכל גישה, הוא היה בטל 99% מהזמן. הפתרון: caches — זיכרונות קטנים ומהירים קרוב ל-CPU.

ההיררכיה

רמהגודלמהירות (בערך)
Registers~KB (עשרות)1 cycle
L1 Cache~32-64 KB~4 cycles
L2 Cache~256KB-1MB~12 cycles

ככל שיורדים — גדול יותר וזול יותר, אבל איטי יותר בסדרי גודל. ה-CPU מחפש נתון קודם ב-L1, ואם אין (cache miss) יורד ל-L2, L3, ולבסוף RAM — כל רמה יקרה יותר.

Cache Lines ו-Locality — הרעיון המרכזי

ה-cache לא מביא byte בודד — הוא מביא cache line שלם (בד"כ 64 bytes) בכל פעם. הרעיון מבוסס על שני עקרונות של locality:

  • Temporal locality — אם ניגשת לנתון, כנראה תיגש אליו שוב בקרוב (לכן שומרים אותו ב-cache).
  • Spatial locality — אם ניגשת לכתובת, כנראה תיגש לשכנות בקרוב (לכן מביאים line שלם).

למה זה מסביר Array מול Linked List

שאלה קלאסית: למה מעבר על array מהיר בהרבה ממעבר על linked list, גם כשה-Big-O זהה (O(n))? Cache locality. array הוא רצף רציף בזיכרון — כשה-CPU מביא cache line, הוא מקבל את האיברים הבאים "בחינם" (spatial locality). linked list פזור בזיכרון — כל node במקום אחר, כל גישה היא cache miss שיורד ל-RAM. בפועל, array יכול להיות פי 10+ מהיר, למרות אותו Big-O. זה הלקח הכי חשוב: Big-O מתעלם מה-cache, אבל בעולם האמיתי ה-cache שולט. זו הסיבה שמבני נתונים "cache-friendly" (arrays, contiguous memory) מנצחים בפועל.

נגזרת מעשית: false sharing — שני threads שכותבים למשתנים שונים שנמצאים באותו cache line גורמים ל-cache line "לקפוץ" ביניהם ומאטים דרמטית, גם שאין ביניהם קשר לוגי. זה מלכוד concurrency שנחזור אליו.

חלק ג' — Memory Management

7. RAM ו-Addressing

RAM (Random Access Memory) הוא הזיכרון הראשי — כאן חיים התוכניות והנתונים בזמן ריצה. "Random Access" = אפשר לגשת לכל כתובת באותה מהירות (בניגוד לדיסק/טייפ סדרתי).

המודל: מערך ענק של bytes

חשוב על RAM כמערך ענק של תאים, כל אחד בגודל byte, כל אחד עם כתובת ייחודית (מספר, שמיוצג ב-hex — 0x7FFF...). ה-CPU קורא/כותב לפי כתובת: "תן לי את ה-byte בכתובת X". זהו — כל המורכבות של structs, objects, arrays בנויה מעל המודל הפשוט הזה.

כתובת: 0x00 0x01 0x02 0x03 0x04 ...

Word size — 32 מול 64 bit

"מחשב 64-bit" אומר שהכתובות הן 64 bits — מה שמאפשר לפנות ל-2⁶⁴ כתובות (הרבה יותר ממה שקיים). 32-bit הוגבל ל-2³² = ~4GB RAM בלבד, וזו הסיבה שעברנו ל-64-bit. גם ה-registers ורוחב הנתונים הבסיסי הם 64 bits.

8. Stack מול Heap

כשתוכנית רצה, הזיכרון שלה מחולק לאזורים. שניים מהם קריטיים להבין — Stack ו-Heap — כי הם מסבירים איך משתנים חיים, למה יש stack overflow, ואיך GC עובד.

ה-Stack — מהיר ומסודר

ה-stack מנהל את קריאות הפונקציות והמשתנים המקומיים. הוא עובד LIFO (Last In First Out) — כמו ערימת צלחות. כל קריאה לפונקציה דוחפת stack frame חדש (הפרמטרים, המשתנים המקומיים, כתובת החזרה), וכשהפונקציה מסתיימת — ה-frame נזרק (pop):

function a() { b(); }
function b() { c(); }

Stack (גדל למטה):
│ frame של a │ ← נדחף כש-a נקראת
│ frame של b │ ← נדחף כש-b נקראת
│ frame של c │ ← נדחף כש-c נקראת, נזרק כשהיא מסתיימת

מאפיינים: מהיר מאוד (רק מזיז מצביע), אוטומטי (מתנקה לבד כשפונקציה מסתיימת), אבל מוגבל בגודל וקבוע.

Stack Overflow — עכשיו זה הגיוני

זוכר את השם של האתר? stack overflow הוא כשה-stack מתמלא — בדרך כלל מ-רקורסיה אינסופית: כל קריאה דוחפת frame, ובלי תנאי עצירה ה-stack נגמר וקורס. עכשיו אתה מבין למה — לא סתם "יותר מדי רקורסיה", אלא מיצוי פיזי של אזור ה-stack.

ה-Heap — גמיש ומנוהל

ה-heap הוא לאחסון דינמי — objects, arrays, כל דבר שגודלו לא ידוע מראש או שצריך לחיות מעבר לפונקציה שיצרה אותו. הקצאה ב-heap גמישה (כל גודל, בכל זמן) אבל איטית יותר (צריך למצוא מקום פנוי) ודורשת ניהול — מי משחרר את הזיכרון כשלא צריך? (פרק 10).

ההבחנה שמסבירה value מול reference

זוכר value מול reference ממדריך JavaScript? הנה השורש. ב-JS (וברוב השפות), primitives קטנים חיים ב-stack (מהיר, מועתק by value), ו-objects חיים ב-heap — והמשתנה ב-stack מחזיק רק pointer (כתובת) ל-object ב-heap. לכן:

let a = 5;         // 5 ב-stack
let obj = {...};   // ה-object ב-heap, המשתנה obj מחזיק pointer אליו
let obj2 = obj;    // מעתיק את ה-pointer — שניהם מצביעים לאותו object ב-heap!

זו הסיבה ש"העתקת object" משתפת reference — העתקת ה-pointer, לא ה-object. עכשיו זה לא "כלל שרירותי של JS" אלא תוצאה ישירה של איך stack ו-heap עובדים.

9. Virtual Memory

אחד הרעיונות הכי חכמים במערכות הפעלה, ופותר כמה בעיות בבת אחת. הרעיון: כל תהליך חושב שיש לו את כל הזיכרון לעצמו, ברצף נקי מכתובת 0 — אבל זו אשליה שה-OS וה-CPU יוצרים.

הבעיה שהוא פותר

בלי virtual memory: תהליכים היו צריכים לחלוק את ה-RAM הפיזי ישירות, לדעת אילו כתובות פנויות, ולהיזהר לא לדרוס זה את זה. כאוס ואבטחה אפסית. Virtual memory נותן לכל תהליך address space וירטואלי משלו — מבודד ופרטי.

איך זה עובד: Pages ו-Page Table

הזיכרון הווירטואלי מחולק ל-pages (בד"כ 4KB), והפיזי ל-frames באותו גודל. ה-page table ממפה כל virtual page ל-physical frame. כשהתוכנית ניגשת לכתובת וירטואלית, ה-MMU (Memory Management Unit, בחומרה) מתרגם אותה לכתובת פיזית דרך ה-page table:

כתובת וירטואלית (מה שהתוכנית רואה)
  ↓ MMU + Page Table (תרגום)
כתובת פיזית (איפה זה באמת ב-RAM)

TLB — cache לתרגום

תרגום בכל גישה יקר, אז יש TLB (Translation Lookaside Buffer) — cache של תרגומים אחרונים בתוך ה-CPU. TLB hit = תרגום מיידי. זה עוד רובד cache, הפעם לכתובות.

Paging / Swapping — RAM וירטואלי גדול מהפיזי

הקסם: virtual memory מאפשר לתוכניות להשתמש ביותר זיכרון ממה שיש פיזית. pages שלא בשימוש כרגע "מפונים" ל-disk (swap), ומוחזרים ל-RAM כשצריך. כשתוכנית ניגשת ל-page שלא ב-RAM — page fault: ה-OS עוצר, מביא את ה-page מהדיסק, וממשיך. זה שקוף לתוכנית, אבל איטי מאוד (דיסק פי אלפים מ-RAM). "המחשב נתקע וה-disk עובד קשה" = יותר מדי swapping ("thrashing"). זו הסיבה שחוסר RAM מאט הכל דרמטית — לא סתם "נגמר זיכרון", אלא swapping מתמיד לדיסק.

למה זה חשוב לך

  • בידוד ואבטחה — תהליך לא יכול לגשת לזיכרון של תהליך אחר. הבסיס לאבטחת OS (וזוכר containers ממדריך DevOps? זה נשען על זה).
  • "out of memory" — עכשיו אתה מבין: זה גם RAM פיזי וגם ניהול ה-virtual memory.
  • ביצועים — page faults ו-TLB misses הם עלויות נסתרות בקוד memory-heavy.

10. Pointers, References ו-Garbage Collection

השאלה הגדולה של ה-heap: מי משחרר זיכרון שכבר לא צריך? יש שתי גישות עולמיות, וההבחנה ביניהן מגדירה שפות שלמות.

Pointers ו-References

Pointer הוא משתנה שמחזיק כתובת זיכרון של ערך אחר (ב-heap בד"כ). זה בדיוק מה שראינו — משתנה object ב-JS מחזיק pointer ל-heap. שפות כמו C נותנות גישה ישירה ל-pointers (חזק ומסוכן); שפות מנוהלות (JS, Python, Java) מסתירות אותם מאחורי "references" אבל המנגנון זהה.

הבעיה: Memory Leaks ו-Dangling Pointers

  • Memory leak — הקצאת זיכרון ב-heap ואי-שחרורו כשלא צריך. מצטבר עד קריסה (זוכר ממדריך Node?).
  • Dangling pointer — pointer שמצביע לזיכרון ששוחרר כבר. גישה אליו = באג חמור/קריסה/פרצה.

שתי גישות לשחרור זיכרון

1. ניהול ידני (Manual) — C, C++

המתכנת אחראי: malloc להקצות, free לשחרר. שליטה מלאה וביצועים מקסימליים, אבל מסוכן — שכחת free = leak, free כפול/מוקדם = קריסה. מקור עצום לבאגים ופרצות.

2. Garbage Collection (GC) — JS, Python, Java, Go

ה-runtime מנהל את הזיכרון אוטומטית — מזהה objects ש"אף אחד לא מצביע אליהם יותר" ומשחרר אותם. בטוח ונוח (אין leaks קלאסיים), אבל עולה בביצועים ובשליטה.

איך GC עובד — האלגוריתמים

Reference Counting — כל object סופר כמה מצביעים אליו; כשמגיע ל-0, משוחרר. פשוט, אבל נכשל ב-circular references (A מצביע ל-B, B ל-A — שניהם ב-count 1 לנצח).

Mark-and-Sweep (מה ש-JS/Java משתמשים בו) — מתחילים מ"שורשים" (globals, stack) ו"מסמנים" כל object שאפשר להגיע אליו. מה שלא סומן — זבל, נמחק. פותר circular references.

Generational GC — אופטימיזציה מבוססת-תצפית: "רוב ה-objects מתים צעירים". מחלקים ל-young/old generations, וסורקים את ה-young הרבה יותר תדיר (זול). זה מה ש-V8 (Node) עושה.

ה-tradeoff שחשוב לך: Stop-the-World

ה-GC לפעמים חייב לעצור את כל התוכנית ("stop-the-world pause") כדי לסרוק זיכרון — וזה גורם ל-latency spikes. באפליקציה עם GC (Node, Java), אתה עלול לראות "קפיצות" ב-p99 latency שהן GC pauses. זו הסיבה ש-GC tuning חשוב לשירותים רגישי-latency, ולמה שפות בלי GC (Rust, C++) נבחרות ל-systems programming קריטי. Rust מיוחדת — היא נותנת בטיחות זיכרון בלי GC, דרך מערכת "ownership" שנאכפת בקומפילציה. זה למה Rust פופולרית לתשתית ביצועים. עכשיו אתה מבין את ה-tradeoff שמאחורי בחירת שפה: ידני (מהיר, מסוכן) מול GC (בטוח, pauses) מול Rust (בטוח, מהיר, עקומת למידה).

חלק ד' — Operating Systems

11. Kernel, User Mode ו-System Calls

מערכת ההפעלה (OS) היא השכבה בין החומרה לתוכניות שלך. היא מנהלת את הכל — CPU, זיכרון, קבצים, רשת — ומאפשרת להרבה תוכניות לחלוק מחשב אחד בבטחה.

ה-Kernel — הליבה

ה-kernel הוא הלב של ה-OS — הקוד שרץ עם הרשאות מלאות ומנהל את החומרה: scheduling של תהליכים, ניהול זיכרון (virtual memory מפרק 9), גישה לקבצים ולרשת. הכל עובר דרכו.

User Mode מול Kernel Mode — ההפרדה הקריטית

ה-CPU רץ בשני מצבים (rings), וזו אחת ההגנות החשובות ביותר:

  • User Mode — הקוד שלך רץ כאן, עם הרשאות מוגבלות. לא יכול לגשת ישירות לחומרה, לזיכרון של תהליכים אחרים, או לפקודות מסוכנות. מבודד.
  • Kernel Mode — ה-kernel רץ כאן, עם הרשאות מלאות — גישה לכל החומרה והזיכרון.

למה זה קריטי: אם כל תוכנית יכלה לגשת ישירות לחומרה, באג אחד או תוכנה זדונית היו מפילים את כל המערכת. ההפרדה מבטיחה שתוכנית פוגעת יכולה לקרוס — בלי להפיל את ה-OS או תוכניות אחרות.

System Calls — הגשר

אבל התוכנית שלך צריכה לקרוא קבצים, לשלוח ברשת, להקצות זיכרון — כל אלה דורשים kernel mode. הפתרון: system call (syscall) — בקשה מבוקרת מהתוכנית ל-kernel לבצע פעולה מיוחסת בשמה:

הקוד שלך (User Mode)
  ↓ syscall (למשל read, write, open, socket)
מעבר ל-Kernel Mode (context switch מבוקר)
  ↓ ה-kernel מבצע את הפעולה על החומרה
חוזר עם התוצאה ל-User Mode

למה זה חשוב לך מעשית: כל fs.readFile, fetch, או פתיחת socket בקוד שלך מתורגם בסוף ל-syscall. ו-syscall הוא יקר — המעבר בין user ל-kernel mode עולה מאות cycles. זו הסיבה ש-batching (קריאה אחת גדולה במקום אלף קטנות) וש-buffering משפרים ביצועים דרמטית. וזו הבסיס להבנת מודלי ה-I/O (פרק 19) — כל השאלה של blocking מול async היא איך מבצעים את ה-syscalls של ה-I/O.

12. Processes מול Threads

ההבחנה הזו היא מהחשובות ב-systems, וחוזרת ישירות למדריכי Node ו-System Design. שניהם דרכים ל"הרצה במקביל", אבל שונים מהותית.

Process — תוכנית בריצה, מבודדת

Process הוא instance של תוכנית רצה, עם address space וירטואלי משלו (זוכר virtual memory?), משאבים משלו, ובידוד מלא מ-processes אחרים. שני processes לא יכולים לגשת לזיכרון זה של זה (בלי IPC מפורש — פרק 14).

Thread — "חוט ביצוע" בתוך process

Thread הוא רצף ביצוע בתוך process. process יכול להכיל כמה threads, וכולם חולקים את אותו address space — אותו heap, אותם משתנים גלובליים. לכל thread יש רק stack משלו ו-registers משלו.

ההשלכה הכי חשובה: threads חולקים זיכרון — וזה בדיוק גם היתרון (תקשורת מהירה) וגם המקור לכל בעיות ה-concurrency (חלק ה'). כששני threads כותבים לאותו משתנה בו-זמנית — race condition. processes לא סובלים מזה (בידוד), אבל תקשורת ביניהם יקרה. זה ה-tradeoff המרכזי.

חיבור למדריך Node: זוכר ש-Node הוא single-threaded? עכשיו מדויק — הקוד שלך רץ על thread אחד (אין race conditions בקוד שלך!), אבל worker threads וה-libuv thread pool כן קיימים מתחת. וזוכר cluster ו-multiple containers ממדריך System Design? זה בחירה ב-processes (מבודדים, בטוחים) על פני threads — למה Node מעדיף לסקיילר ב-processes.

13. Scheduler ו-Context Switch

יש לך 8 cores אבל מאות תהליכים ו-threads. איך כולם "רצים במקביל"? הם לא באמת — ה-scheduler מחליף ביניהם מהר כל כך שזה נראה בו-זמני.

Concurrency מול Parallelism — הבחנה חשובה

שני מושגים שמבלבלים: Concurrency = לנהל כמה משימות שמתקדמות "בו-זמנית" על ידי החלפה מהירה (גם על core אחד). Parallelism = כמה משימות רצות ממש בו-זמנית (על כמה cores). אנלוגיה: concurrency = ברמן אחד שמטפל בכמה הזמנות לסירוגין; parallelism = כמה ברמנים. ה-scheduler נותן concurrency; כמה cores נותנים parallelism.

ה-Scheduler — מחלק את ה-CPU

ה-scheduler של ה-kernel מחליט איזה thread רץ על איזה core, ולכמה זמן. הוא נותן לכל thread time slice (quantum, ~מילישניות), ואז מעביר לבא. זה preemptive — ה-OS יכול "לחטוף" את ה-CPU מ-thread באמצע (בניגוד ל-cooperative, שם thread צריך "לוותר" מרצונו — מסוכן, כי thread תקוע מקפיא הכל).

Context Switch — ההחלפה, והמחיר שלה

כשה-scheduler מחליף thread, הוא עושה context switch: שומר את המצב המלא של ה-thread הנוכחי (registers, PC, stack pointer) וטוען את המצב של הבא. וזה יקר: לא רק שמירת/טעינת registers, אלא גם ה-cache וה-TLB "מתקררים" — ה-thread החדש לא נמצא ב-cache, אז הרבה cache misses עד שהוא "מתחמם". context switch עולה ~מיקרו-שניות, אבל כשקורה אלפי פעמים בשנייה — מצטבר.

למה זה חשוב לך: זו הסיבה שיותר threads לא תמיד = יותר מהיר. יותר מדי threads = יותר context switches = יותר overhead ופחות תפוקה אמיתית ("thrashing"). וזו הסיבה העמוקה שמאחורי המודל של Node — thread אחד עם event loop נמנע מ-context switches ומ-overhead של threads, ולכן יעיל מאוד ל-I/O. עכשיו אתה מבין למה single-threaded + async מנצח thread-per-request לעומסי I/O.

14. IPC — תקשורת בין תהליכים

Processes מבודדים (זוכר? address space נפרד) — אבל לפעמים הם צריכים לתקשר. IPC (Inter-Process Communication) הוא מנגנוני התקשורת ביניהם. כל אחד עם tradeoffs.

ה-tradeoff המרכזי

Shared memory הכי מהיר (גישה ישירה לזיכרון, בלי kernel) — אבל דורש סנכרון ידני (locks — חלק ה'!) כי כמה processes נוגעים באותו זיכרון. Message passing איטי יותר (עובר דרך ה-kernel, מעתיק נתונים) — אבל בטוח יותר (אין זיכרון משותף = אין race conditions). זה tradeoff שחוזר לאורך כל ה-systems: shared state מהיר אבל מסוכן, message passing בטוח אבל איטי. (זוכר ממדריך System Design — message queues בין microservices? זה IPC בקנה מידה של רשת. אותו רעיון, שכבה גבוהה יותר).

הבחנה יפה: Sockets הם IPC שעובד גם בין processes על אותה מכונה וגם בין מכונות ברשת — זה מה שמאחד את המדריך הזה עם מדריך Networking. HTTP request הוא בסוף socket, שהוא syscall, שעובר ל-kernel. הכל מתחבר.

חלק ה' — Concurrency & Synchronization

15. הבעיה — Race Conditions ו-Critical Sections

הגענו לאחד הנושאים הקשים בכל התוכנה. concurrency — כמה threads שרצים בו-זמנית וחולקים זיכרון (זוכר פרק 12?) — יוצר בעיות שקשה מאוד לדבג, כי הן לא-דטרמיניסטיות (תלויות בתזמון).

הבעיה בבסיס: אין אטומיות

פעולה שנראית "אחת" בקוד היא בעצם כמה פקודות CPU (זוכר פרק 4?). count++ הוא לא אטומי — הוא שלוש פעולות: קרא את count, הוסף 1, כתוב בחזרה. וכאן הבעיה:

count = 5;
// Thread A ו-Thread B מריצים count++ בו-זמנית:
Thread A: קורא count (5)
Thread B: קורא count (5)      ← עדיין 5! A לא סיים לכתוב
Thread A: מחשב 6, כותב 6
Thread B: מחשב 6, כותב 6      ← דרס!
// התוצאה: 6, אבל היה צריך להיות 7! אבד עדכון.

זה Race Condition — התוצאה תלויה ב"מרוץ" בין ה-threads, בתזמון המדויק שמשתנה מריצה לריצה. לפעמים עובד, לפעמים לא — הסיוט של הדיבוג.

Critical Section

ה-critical section הוא קטע הקוד שניגש למשאב משותף (למשל count++) וחייב לרוץ בבלעדיות — רק thread אחד בכל פעם. כל הפתרונות (locks וכו') הם דרכים להבטיח את הבלעדיות הזו. המושג המרכזי: mutual exclusion — הדרה הדדית, רק אחד בפנים.

למה זה חשוב לך גם ב-Node: אמנם הקוד שלך ב-Node single-threaded (אין race conditions ברמת ה-CPU), אבל race conditions לוגיות קורות גם שם — למשל, שתי בקשות אסינכרוניות שקוראות-משנות-כותבות את אותה שורה ב-DB (זוכר transactions ו-SELECT FOR UPDATE ממדריך SQL?). ה-DB פותר את זה עם locks — בדיוק המנגנונים כאן, שכבה אחת למעלה. הבנת ה-concurrency ברמת ה-CPU מסבירה למה isolation levels קיימים.

16. Locks — Mutex, Semaphore, RW Lock, Condition Variables

הכלים לאכוף mutual exclusion ולסנכרן threads. כל אחד לתרחיש שונה.

Mutex — המנעול הבסיסי

Mutex (MUTual EXclusion) — מנעול שרק thread אחד יכול "להחזיק" בכל רגע. thread נועל לפני ה-critical section, ומשחרר אחרי. thread אחר שמנסה לנעול — חוסם וממתין עד השחרור:

mutex.lock();       // אם תפוס — ממתין
count++;            // critical section — בטוח, רק אני כאן
mutex.unlock();     // משחרר, thread ממתין יכול להיכנס

זה פותר את ה-race מפרק 15: רק thread אחד נכנס ל-count++ בכל פעם. המחיר: threads ממתינים (serialization) — פחות מקביליות.

Semaphore — מונה של הרשאות

Semaphore מכליל את ה-mutex: במקום "אחד בלבד", הוא מרשה עד N בו-זמנית. יש לו מונה — כל thread שנכנס מוריד 1, כל יציאה מעלה 1; ב-0 הבאים ממתינים. שימוש קלאסי: connection pool (זוכר ממדריך Databases?) — "עד 10 חיבורים בו-זמנית". mutex הוא בעצם semaphore עם N=1.

Read-Write Lock — אופטימיזציה חכמה

תובנה: קריאות מקבילות בטוחות — רק כתיבה מסוכנת. אז למה לנעול קוראים אחד את השני? RW Lock מרשה: כמה קוראים בו-זמנית, אבל כותב אחד בלעדי (חוסם את כולם). מושלם לנתונים שנקראים הרבה ונכתבים מעט (config, cache) — שיפור ביצועים ענק מול mutex רגיל שהיה מסרסר גם קריאות. (זוכר read replicas ממדריך System Design? אותו עיקרון — קריאות מקבילות, כתיבה מסונכרנת, שכבה גבוהה יותר).

Condition Variables — "המתן עד שתנאי מתקיים"

לפעמים thread צריך לחכות לתנאי, לא רק למנעול — למשל, consumer שממתין ש-queue לא יהיה ריק. Condition variable מאפשר thread "לישון" עד ש-thread אחר "מעיר" אותו (wait / signal/notify). זה הבסיס לדפוס producer-consumer: producer מוסיף ל-queue ו-signals, consumer ישן עד שיש עבודה. יעיל יותר מ-busy-waiting (בדיקה בלולאה שמבזבזת CPU).

Monitor

Monitor הוא הפשטה ברמה גבוהה שעוטפת mutex + condition variables (למשל synchronized ב-Java) — object שכל המתודות שלו מסונכרנות אוטומטית. נוח, פחות מועד לטעויות מ-locks ידניים.

17. Atomic Operations, CAS ו-Lock-Free

locks עובדים, אבל יש להם מחיר — threads ממתינים, ויש overhead. לפעמים אפשר להימנע מהם לגמרי עם atomic operations.

Atomic Operations — פעולות בלתי-ניתנות-לחלוקה

פעולה אטומית קורית "בבת אחת" מבחינת threads אחרים — אי אפשר לראות אותה באמצע. החומרה מספקת פקודות אטומיות (למשל atomic increment) שעושות read-modify-write כיחידה אחת. count++ אטומי פותר את ה-race מפרק 15 בלי lock — מהיר יותר, כי אין המתנה.

CAS — Compare-And-Swap, הבסיס לכל lock-free

Compare-And-Swap היא פקודת CPU אטומית שאומרת: "אם הערך בכתובת עדיין X, החלף אותו ל-Y; אחרת, אל תעשה כלום ותגיד לי שנכשלת". באטומיות אחת:

// פסאודו:  CAS(address, expected, newValue)
// דפוס lock-free: קרא, חשב, נסה להחליף — ואם מישהו שינה בינתיים, נסה שוב:
do {
  old = counter;
  new = old + 1;
} while (!CAS(&counter, old, new));   // חזור אם הערך השתנה תחתיך

זה הבסיס ל-lock-free algorithms: במקום לנעול, מנסים לעדכן אטומית, ואם מישהו הקדים — מנסים שוב (retry). היתרון: אין threads שנחסמים לגמרי — המערכת תמיד מתקדמת. זה גם הבסיס ל-optimistic locking ב-DBs (זוכר?) ול-AtomicInteger וכו'.

Memory Barriers — הבעיה הנסתרת

מלכודת עמוקה: זוכר ש-CPUs מודרניים מבצעים out-of-order (פרק 5) ויש caches נפרדים לכל core (פרק 6)? המשמעות המפחידה: thread אחד עלול לא לראות מיד כתיבה של thread אחר — כי הכתיבה תקועה ב-cache של ה-core השני, או שהפקודות סודרו מחדש. Memory barrier (fence) היא פקודה שמכריחה סדר ו-visibility — "וודא שכל הכתיבות שלי גלויות לפני שתמשיך". locks ו-atomics כוללים barriers אוטומטית, ולכן הם עובדים. זו הסיבה ש-concurrency "ידני" בלי הכלים הנכונים הוא כמעט בלתי אפשרי לעשות נכון — ולמה כמעט תמיד עדיף להשתמש בפרימיטיבים בדוקים, לא לגלגל בעצמך.

18. מפגעי Concurrency — Deadlock, Livelock, Starvation

locks פותרים races, אבל יוצרים בעיות חדשות משלהם. אלה המפגעים שכל מתכנת concurrency חייב להכיר.

Deadlock — התקיעה ההדדית

Deadlock — שני threads (או יותר) ממתינים זה לזה לנצח. A מחזיק lock 1 ורוצה את 2; B מחזיק lock 2 ורוצה את 1. אף אחד לא משחרר, שניהם תקועים לנצח:

Thread A: lock(1) ✓ ... רוצה lock(2) — ממתין ל-B
Thread B: lock(2) ✓ ... רוצה lock(1) — ממתין ל-A
// שניהם ממתינים זה לזה. תקיעה מוחלטת.

Deadlock דורש ארבעה תנאים בו-זמנית (תנאי Coffman): (1) mutual exclusion, (2) hold-and-wait (מחזיק ומחכה), (3) no preemption (אי אפשר לחטוף lock), (4) circular wait (מעגל המתנה). שבירת אחד מהם מונעת deadlock. הפתרון המעשי הנפוץ: שבור את ה-circular wait — תמיד נעל משאבים באותו סדר גלובלי (זוכר את העצה הזו ממדריך SQL על deadlocks? הנה השורש שלה).

Livelock — עסוקים אבל לא מתקדמים

Livelock — ה-threads לא תקועים (הם פעילים), אבל לא מתקדמים. כמו שני אנשים במסדרון שכל אחד זז לאותו צד שוב ושוב כדי לפנות דרך לשני — תנועה בלי התקדמות. קורה כשה-threads "מגיבים" זה לזה בלולאה. קשה יותר לזהות מ-deadlock (הם נראים עסוקים).

Starvation — ה-thread שאף פעם לא מקבל תור

Starvation — thread אחד לא מקבל גישה למשאב לעולם, כי אחרים תמיד "מקדימים" אותו (למשל, כותב שממתין לנצח כי כל הזמן מגיעים קוראים חדשים ב-RW lock). הפתרון: fairness — מנגנון שמבטיח שכל thread יקבל תור בסוף (למשל, תור FIFO ל-lock).

Lock Contention ו-Spinlocks

Lock Contention — כשהרבה threads נלחמים על אותו lock, רובם ממתינים והמקביליות נהרסת. זה ה-bottleneck הנפוץ במערכות concurrent. הפתרונות: locks עדינים יותר (lock קטן לכל פריט במקום lock אחד ענק), RW locks, או lock-free.

Spinlock — במקום ש-thread "יישן" כשה-lock תפוס (מה שדורש context switch יקר — פרק 13), הוא "מסתובב" בלולאה ובודק שוב ושוב עד שמתפנה. יעיל רק כשההמתנה קצרה מאוד (פחות מ-context switch), כי הוא שורף CPU. משתמשים בו בתוך kernels ובקוד ביצועים קריטי. זו דוגמה מושלמת ל-tradeoff: לישון (חוסך CPU, יקר להעיר) מול spin (מבזבז CPU, מיידי).

הלקח הגדול של כל חלק ה': concurrency הוא קשה מיסודו — לא כי אתה לא חכם, אלא כי אי-הדטרמיניזם, ה-caches הנפרדים, וה-out-of-order הופכים אותו למלכודת. הכלל המעשי: הימנע מ-shared mutable state כשאפשר (זו הסיבה ש-message passing, immutability, ו-single-threaded models כמו Node כל כך פופולריים), וכשאתה חייב state משותף — השתמש בפרימיטיבים בדוקים (locks, atomics), לא תגלגל בעצמך. "shared state בין threads" הוא המקום שבו באגים חיים.

חלק ו' — I/O והרכבה

19. מודלי I/O — Blocking, Non-Blocking, Multiplexing, Async

הפרק שמחבר את כל ה-systems ל-Backend שאתה כותב. כל השאלה של "איך Node מטפל באלפי חיבורים על thread אחד" נענית כאן — וזה בעצם על איך מבצעים syscalls של I/O (זוכר פרק 11?).

הבעיה: I/O איטי

קריאה מדיסק/רשת איטית בסדרי גודל מה-CPU (זוכר את מספרי ה-latency ממדריך System Design?). השאלה: מה ה-thread עושה בזמן שהוא מחכה ל-I/O? ארבע תשובות, בסדר תחכום עולה.

1. Blocking I/O — המודל הפשוט

ה-thread קורא ל-read() ונחסם — ישן עד שהנתונים מגיעים. פשוט, אבל bזבזני: thread לכל חיבור, וכל אחד ישן רוב הזמן. 10,000 חיבורים = 10,000 threads = הרבה זיכרון והרבה context switches (פרק 13). זה המודל הקלאסי (Apache הישן, thread-per-request).

2. Non-Blocking I/O — "תבדוק ותחזור"

read() מחזיר מיד — או עם נתונים, או "עוד אין, נסה שוב". ה-thread לא נחסם, אבל עכשיו הוא צריך לבדוק שוב ושוב (polling) — מבזבז CPU על בדיקות ריקות. שיפור חלקי.

3. I/O Multiplexing — הפתרון החכם (epoll/select)

כאן הקסם. במקום thread לכל חיבור, thread אחד מנטר אלפי חיבורים בבת אחת ושואל את ה-kernel: "מבין כל ה-1000 חיבורים האלה, אילו מוכנים עכשיו?". ה-syscalls: select (ישן), poll, ו-epoll (Linux, יעיל) / kqueue (BSD/Mac):

// thread אחד, לולאה אחת, אלפי חיבורים:
while (true) {
  ready = epoll_wait(all_connections);   // ה-kernel מחזיר רק את המוכנים
  for (conn of ready) {
    handle(conn);                        // טפל רק במה שמוכן
  }
}

ה-thread ישן ב-epoll_wait עד שמשהו מוכן — לא מבזבז CPU, לא thread לכל חיבור. זה בדיוק ה-event loop.

4. Asynchronous I/O — "תודיע לי כשסיימת"

המודל הכי מתקדם: מתחילים פעולת I/O, ממשיכים לעבוד, וה-kernel מודיע (callback) כשהיא הסתיימה — כולל העברת הנתונים. (io_uring ב-Linux מודרני).

איך Node באמת עובד — הכל מתחבר

עכשיו התמונה המלאה של המודל של Node (ממדריך Node, עם ההסבר העמוק): Node הוא single-threaded עם event loop שבנוי על I/O multiplexing (epoll/kqueue) דרך libuv. כשאתה עושה fs.readFile או קריאת רשת, Node לא חוסם — הוא רושם את הפעולה ל-kernel וממשיך. כש-ה-kernel מסמן "מוכן" (דרך epoll), ה-callback נכנס לתור ורץ. thread אחד, אלפי חיבורים, כי רובם רק ממתינים ל-I/O והמתנה "לא עולה thread". זו הסיבה ש-Node מבריק ל-I/O ורע ל-CPU — CPU כבד חוסם את ה-thread היחיד (זוכר "אל תחסום את ה-event loop"?), אבל I/O הוא בדיוק מה שהמודל בנוי לו. (עבודה שבאמת חוסמת, כמו קריאת קובץ, libuv מריצה ב-thread pool קטן מאחורי הקלעים). עכשיו אתה מבין את המודל מהיסוד — מ-epoll ועד ה-callback שלך.

20. Interrupts, DMA ואיך I/O באמת עובד

ירדנו עד ה-syscall — אבל איך החומרה באמת מודיעה שנתונים הגיעו? שני מנגנונים משלימים את התמונה.

Interrupts — "תעצור הכל, קרה משהו"

איך ה-CPU יודע שחבילת רשת הגיעה או שהדיסק סיים? הוא לא בודק בלולאה (בזבזני). במקום זה, ההתקן שולח interrupt — אות חומרה שגורם ל-CPU לעצור את מה שהוא עושה, לשמור מצב, ולרוץ ל-interrupt handler של ה-kernel שמטפל באירוע, ואז לחזור. זה מה שמאפשר ל-CPU לעבוד על דברים אחרים ולהיות "מופרע" רק כשצריך — הבסיס לכל I/O אסינכרוני. (ה-timer שמפעיל את ה-scheduler? גם הוא interrupt).

DMA — העברת נתונים בלי לבזבז את ה-CPU

בעיה: להעביר megabyte מהדיסק ל-RAM byte-byte דרך ה-CPU היה משתק אותו. הפתרון: DMA (Direct Memory Access) — controller ייעודי שמעביר נתונים ישירות בין ההתקן ל-RAM, בלי לערב את ה-CPU. ה-CPU רק אומר "העבר X ל-Y", וה-DMA עושה את העבודה, ושולח interrupt כשסיים. ה-CPU חופשי לעבוד בינתיים. זה מה שמאפשר I/O throughput גבוה בלי לחנוק את המעבד.

התמונה המלאה של קריאת קובץ

1. הקוד: fs.readFile → syscall → מעבר ל-Kernel Mode
2. ה-kernel מורה ל-disk controller לקרוא, ורושם DMA
3. ה-thread ממשיך (async) / ישן (blocking)
4. ה-DMA מעביר את הנתונים לדיסק → RAM, בלי CPU
5. סיום → ההתקן שולח Interrupt
6. ה-kernel מטפל, מסמן "מוכן" (epoll), מעיר את ה-callback
7. ה-callback שלך רץ עם הנתונים

כל שכבה שלמדת מופיעה כאן: syscall (OS), kernel/user mode, DMA ו-interrupts (חומרה), epoll (I/O model), event loop (runtime). זה המסע המלא של פעולת I/O אחת.

21. הרכבה: איך Web Request עובר דרך הכל

הגיע הרגע לחבר את כל 20 הפרקים. נעקוב אחרי request אחד — GET /users/42 — מהחוט ועד התשובה, דרך כל שכבה. זה מאחד גם את המדריך הזה עם מדריכי Networking, Node, ו-System Design.

1. חבילת רשת מגיעה לכרטיס הרשת (NIC)
2. ה-NIC שולח INTERRUPT ל-CPU (פרק 20)
3. ה-CPU עוצר, עובר ל-KERNEL MODE (פרק 11), מריץ interrupt handler
4. DMA כבר העביר את החבילה ל-RAM (פרק 20)
5. ה-kernel מפרק את שכבות הרשת — TCP/IP (מדריך Networking)
6. ה-socket של השרת שלך מסומן "מוכן" ל-EPOLL (פרק 19)
7. ה-EVENT LOOP של Node מתעורר, שולף את הבקשה (פרק 19 + מדריך Node)
8. הקוד שלך רץ ב-USER MODE — NestJS: guards → validation → handler
9. הקוד ניגש למשתנים ב-STACK/HEAP (פרק 8), ה-CPU קורא דרך CACHE (פרק 6)
   כתובות מתורגמות דרך VIRTUAL MEMORY + TLB (פרק 9)
10. צריך נתונים מה-DB → עוד SYSCALL, עוד socket, החוצה לרשת
   (ה-thread לא נחסם — ASYNC, ה-event loop מטפל בבקשות אחרות בינתיים)
11. ה-DB עונה → INTERRUPT → epoll → callback → הקוד ממשיך
12. בונים JSON (עוד עבודת CPU, עוד cache, עוד heap)
13. res.end() → SYSCALL write → kernel → TCP → NIC → DMA → החוצה
14. התשובה בדרך חזרה ללקוח

זו הנקודה של המדריך כולו: מה שנראה כמו @Get() findOne() { return this.service.find(id); } — שורה אחת תמימה — הוא בעצם ריקוד מתואם בין חומרה, kernel, virtual memory, caches, event loop, ורשת. אתה לא צריך לחשוב על כל זה כשאתה כותב קוד. אבל כשמשהו נשבר — latency מוזר, memory leak, CPU ב-100%, deadlock — ההבנה הזו היא ההבדל בין "אני לא יודע למה זה איטי" ל"אני יודע בדיוק איפה להסתכל". וזה, בעידן ה-AI, מה שהופך אותך למהנדס ולא למעתיק קוד.

  • "Designing Data-Intensive Applications" — מגשר בין systems ל-Backend בקנה מידה (משלים את מדריך System Design).

איך ללמוד את זה באמת — לא רק לקרוא

  1. כתוב קצת C — כלום לא מלמד stack/heap/pointers כמו לנהל זיכרון ידנית. אפילו פרויקט קטן.
  2. שחק עם threads — כתוב race condition בכוונה (ב-Go/Java/C), ראה אותו נשבר, ותקן עם mutex. לראות זה להבין.
  3. פרופיילינג — הרץ profiler על קוד אמיתי, ראה cache misses, context switches, GC pauses. החומר מהמדריך הופך למוחשי.
  4. קרא את libuv — הקוד שמפעיל את event loop של Node הוא C פתוח. לראות את ה-epoll האמיתי סוגר את המעגל.

הנקודה האחרונה, והכי חשובה: אמרת שאתה רוצה להבין איך מערכות עובדות ולא רק סינטקס — וזו בדיוק הגישה הנכונה לעידן הזה. סינטקס AI כותב; הבנת מערכות היא מה שמאפשר לך לתכנן, לדבג, ולהחליט — הדברים ש-AI לא עושה בשבילך. המדריך הזה נתן לך את המפה. אבל מפה היא לא שטח: ההבנה תיהפך לאמיתית רק כשתראה את הדברים האלה קורים בקוד אמיתי — race condition שנשבר, cache miss שמאט, GC pause ב-profiler. תסתכל מתחת למכסה בכל הזדמנות. זה מה שיבדיל אותך.
