1. מבוא: המודל הרלציוני ומה SQL באמת

SQL (Structured Query Language) היא השפה לעבודה עם מסדי נתונים רלציוניים — מסדים שמארגנים מידע בטבלאות. טבלה היא כמו גיליון: שורות (rows/records — כל שורה היא ישות אחת) ועמודות (columns — כל עמודה היא תכונה עם טיפוס קבוע).

הרעיון המרכזי: SQL היא declarative

זו הנקודה שהכי חשוב להפנים, במיוחד כמתכנת שרגיל לקוד imperative. ב-Python או TypeScript אתה כותב איך להשיג תוצאה — לולאות, תנאים, שלב אחרי שלב. ב-SQL אתה מתאר מה אתה רוצה, וה-DB מחליט איך להשיג את זה בצורה הכי יעילה:

-- אתה לא כותב "עבור על כל שורה, בדוק אם הגיל > 18, אסוף לרשימה".
-- אתה פשוט מתאר את התוצאה הרצויה:
SELECT name, email FROM users WHERE age > 18;

ה-query planner (פרק 13) הוא זה שממיר את התיאור שלך לתוכנית ביצוע. זו הסיבה שאותה שאילתה יכולה לרוץ מהר או לאט תלוי ב-indexes ובנתונים — אתה מתאר כוונה, ה-DB בוחר אסטרטגיה. הבנת החלוקה הזו היא ההבדל בין לכתוב SQL שעובד לכתוב SQL שמהיר.

יחסים בין טבלאות

הכוח של המודל הרלציוני הוא בקשרים בין טבלאות דרך מפתחות:

  • Primary Key (PK) — עמודה שמזהה כל שורה ייחודית (למשל id).
  • Foreign Key (FK) — עמודה שמצביעה ל-PK בטבלה אחרת, ובכך יוצרת קשר (למשל orders.user_id מצביע ל-users.id).

סוגי קשרים: one-to-many (משתמש → הזמנות רבות), many-to-many (סטודנטים ↔ קורסים, דרך טבלת קישור), one-to-one.

דיאלקטים

SQL הוא תקן, אבל לכל מסד יש דיאלקט משלו: PostgreSQL, MySQL, SQL Server, Oracle, SQLite. הבסיס זהה ב-90%, אבל יש הבדלים (טיפוסים, פונקציות, syntax ל-pagination). כאן נשתמש ב-Postgres ואציין הבדלים חשובים.

2. DDL — הגדרת סכמה, טיפוסים ו-Constraints

DDL (Data Definition Language) הן הפקודות שמגדירות את מבנה ה-DB: CREATE, ALTER, DROP.

יצירת טבלה

CREATE TABLE users (
  id          SERIAL PRIMARY KEY,          -- מזהה אוטומטי עולה
  email       VARCHAR(255) UNIQUE NOT NULL,
  name        VARCHAR(100) NOT NULL,
  age         INT CHECK (age >= 0),
  is_active   BOOLEAN DEFAULT true,
  created_at  TIMESTAMPTZ DEFAULT now()
);

הערת Postgres: ב-Postgres מודרני עדיף id BIGINT GENERATED ALWAYS AS IDENTITY על פני SERIAL (תקני יותר). ב-MySQL זה AUTO_INCREMENT. ל-timestamp השתמש ב-TIMESTAMPTZ (עם time zone) ולא TIMESTAMP — כמעט תמיד זה מה שאתה רוצה.

טיפוסי נתונים עיקריים

קטגוריהטיפוסים
מספרים שלמיםSMALLINT, INT, BIGINT
עשרוני מדויקNUMERIC(p,s) / DECIMAL — לכסף! (לא FLOAT)
עשרוני מקורבREAL, DOUBLE PRECISION
טקסטVARCHAR(n), TEXT
תאריך/זמןDATE, TIME, TIMESTAMPTZ, INTERVAL
בוליאניBOOLEAN
מזהה ייחודיUUID
מובנה (Postgres)JSONB, arrays, ENUM

כלל ברזל: לעולם אל תשמור כסף ב-FLOAT/DOUBLE — הם מקורבים ויגרמו לשגיאות עיגול (0.1 + 0.2 ≠ 0.3). השתמש ב-NUMERIC, שהוא מדויק.

Constraints — הגנות ברמת ה-DB

  • PRIMARY KEY — ייחודי ולא NULL, מזהה השורה.
  • FOREIGN KEY — אוכף קשר לטבלה אחרת.
  • UNIQUE — הערך לא יכול לחזור.
  • NOT NULL — חובה לתת ערך.
  • CHECK — תנאי מותאם (age >= 0).
  • DEFAULT — ערך ברירת מחדל.

ה-FK עם referential actions קובע מה קורה כשמוחקים שורת-אב:

CREATE TABLE orders (
  id       BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  user_id  INT NOT NULL REFERENCES users(id) ON DELETE CASCADE,
  total    NUMERIC(10,2) NOT NULL
);
-- ON DELETE CASCADE = מחיקת user תמחק גם את ההזמנות שלו.
-- אפשרויות: RESTRICT (חוסם), SET NULL, NO ACTION.

עצה חשובה: אכוף כללים ברמת ה-DB, לא רק באפליקציה. גם אם ה-NestJS שלך בודק ש-email ייחודי, שים גם UNIQUE ב-DB — כי race conditions ובאגים יעקפו את בדיקת האפליקציה, וה-DB הוא קו ההגנה האחרון והאמין.

שינוי ומחיקה

ALTER TABLE users ADD COLUMN phone VARCHAR(20);
ALTER TABLE users ALTER COLUMN name TYPE VARCHAR(200);
ALTER TABLE users DROP COLUMN phone;
DROP TABLE users;              -- מוחק את הטבלה כולה!
TRUNCATE TABLE users;          -- מרוקן שורות, שומר מבנה (מהיר)

3. CRUD — INSERT, SELECT, UPDATE, DELETE

ארבע הפעולות הבסיסיות (DML — Data Manipulation Language).

INSERT

-- שורה אחת
INSERT INTO users (email, name, age)
VALUES ('eliya@x.com', 'Eliya', 30);

-- כמה שורות בבת אחת (יעיל יותר מ-INSERT נפרדים)
INSERT INTO users (email, name, age) VALUES
  ('a@x.com', 'A', 25),
  ('b@x.com', 'B', 40);

-- להחזיר את מה שנוצר (תכונה נהדרת של Postgres)
INSERT INTO users (email, name) VALUES ('c@x.com', 'C')
RETURNING id, created_at;

SELECT

SELECT * FROM users;                    -- כל העמודות (הימנע ב-production!)
SELECT id, name, email FROM users;      -- עמודות ספציפיות (מומלץ)
SELECT name AS full_name FROM users;    -- alias לשם עמודה
SELECT DISTINCT age FROM users;         -- ערכים ייחודיים בלבד

UPDATE

UPDATE users
SET age = 31, is_active = false
WHERE id = 42;                          -- ⚠️ בלי WHERE — מעדכן את כל הטבלה!
RETURNING *;

DELETE

DELETE FROM users WHERE id = 42;        -- ⚠️ בלי WHERE — מוחק הכל!

אזהרה שתצילך יום אחד: UPDATE ו-DELETE בלי WHERE משפיעים על כל השורות בטבלה. הרגל טוב: כתוב קודם SELECT עם אותו WHERE כדי לראות מה יושפע, ורק אז החלף ל-UPDATE/DELETE. וב-production — עבוד בתוך transaction (פרק 14) כדי שתוכל לעשות ROLLBACK.

4. Filtering — WHERE ואיך מתמודדים עם NULL

אופרטורים בסיסיים

SELECT * FROM users WHERE age > 18;
SELECT * FROM users WHERE age BETWEEN 18 AND 65;
SELECT * FROM users WHERE age IN (18, 21, 30);
SELECT * FROM users WHERE name LIKE 'E%';      -- מתחיל ב-E
SELECT * FROM users WHERE name ILIKE '%li%';   -- מכיל, case-insensitive (Postgres)
SELECT * FROM users WHERE age > 18 AND is_active = true;
SELECT * FROM users WHERE age < 18 OR age > 65;

NULL — המלכודת הכי נפוצה ב-SQL

זה חייב פרק משלו כי כמעט כל מתחיל נכשל בזה. NULL אינו ערך — הוא "לא ידוע". ולכן כל השוואה רגילה איתו מחזירה לא true ולא false אלא UNKNOWN:

SELECT * FROM users WHERE age = NULL;      -- ❌ תמיד ריק! לא עובד
SELECT * FROM users WHERE age IS NULL;     -- ✅ הדרך הנכונה
SELECT * FROM users WHERE age IS NOT NULL; -- ✅

הסיבה: "האם הגיל הלא-ידוע שווה ל-NULL?" — התשובה היא "לא ידוע", ושורות עם WHERE שאינו true לא מוחזרות. זו לוגיקה תלת-ערכית (three-valued logic): true / false / unknown.

עוד מלכודת NULL — ב-NOT IN עם NULL בפנים:

-- אם לרשימה יש NULL, זה עלול להחזיר תוצאות ריקות באופן מפתיע:
SELECT * FROM users WHERE id NOT IN (SELECT manager_id FROM teams);
-- אם manager_id יכול להיות NULL — השתמש ב-NOT EXISTS במקום (פרק 8).

לטיפול ב-NULL: COALESCE(value, fallback) מחזיר את הערך הראשון שאינו NULL:

SELECT name, COALESCE(phone, 'no phone') AS phone FROM users;

5. Sorting ו-Pagination

SELECT * FROM users ORDER BY age DESC;              -- מהגדול לקטן
SELECT * FROM users ORDER BY age DESC, name ASC;    -- מיון משני
SELECT * FROM users ORDER BY created_at DESC NULLS LAST;  -- NULLs בסוף

-- Pagination קלאסי (OFFSET/LIMIT):
SELECT * FROM users ORDER BY id LIMIT 20 OFFSET 40;  -- עמוד 3, 20 בעמוד

מלכודת ביצועים חשובה: OFFSET גדול איטי — כדי לדלג על 100,000 שורות, ה-DB חייב לקרוא ולזרוק את כולן. בטבלאות גדולות השתמש ב-keyset pagination (cursor-based): במקום OFFSET, סנן לפי הערך האחרון שראית:

-- מהיר גם במיליוני שורות — משתמש ב-index:
SELECT * FROM users WHERE id > 12345 ORDER BY id LIMIT 20;

הבדל דיאלקט: LIMIT/OFFSET ב-Postgres/MySQL, אבל ב-SQL Server זה OFFSET ... FETCH NEXT.

6. Aggregations — GROUP BY ו-HAVING

Aggregation = לקחת הרבה שורות ולסכם אותן לערך אחד. זה הבסיס לכל דוח וניתוח נתונים.

Aggregate functions

SELECT COUNT(*) FROM users;              -- כמה שורות
SELECT COUNT(phone) FROM users;         -- כמה שורות עם phone לא-NULL
SELECT AVG(age), MIN(age), MAX(age), SUM(age) FROM users;

שים לב: COUNT(*) סופר שורות, COUNT(column) סופר רק ערכים שאינם NULL — הבדל חשוב.

GROUP BY — סיכום לפי קבוצות

מחלק את השורות לקבוצות ומחשב aggregate לכל קבוצה:

-- כמה הזמנות וסכום כולל לכל משתמש:
SELECT user_id, COUNT(*) AS order_count, SUM(total) AS total_spent
FROM orders
GROUP BY user_id;

הכלל הברזל של GROUP BY: כל עמודה ב-SELECT חייבת להיות או ב-GROUP BY או בתוך aggregate function. אחרת ה-DB לא יודע איזה ערך להחזיר לקבוצה. זו שגיאה שכל מתחיל עושה.

HAVING מול WHERE — ההבחנה הקריטית

שאלה שנשאלת בכל ראיון עבודה. WHERE מסנן שורות לפני הקיבוץ; HAVING מסנן קבוצות אחרי הקיבוץ:

SELECT user_id, SUM(total) AS total_spent
FROM orders
WHERE total > 0                    -- מסנן שורות בודדות (לפני GROUP BY)
GROUP BY user_id
HAVING SUM(total) > 1000;          -- מסנן קבוצות (אחרי GROUP BY)

לא ניתן להשתמש ב-aggregate ב-WHERE (WHERE SUM(...) > 1000 ❌) כי ה-aggregate עדיין לא חושב בשלב הזה. זה מתחבר ישירות לפרק 18 (סדר הביצוע הלוגי) — WHERE רץ לפני GROUP BY, HAVING אחריו.

7. JOINs — כל הסוגים

JOIN מחבר שורות משתי טבלאות (או יותר) לפי תנאי. זה הלב של המודל הרלציוני — כאן הקשרים בין הטבלאות באים לידי ביטוי.

נתוני דוגמה

users:  id | name          orders: id | user_id | total
        1  | Alice                 1  | 1       | 100
        2  | Bob                   2  | 1       | 200
        3  | Carol                 3  | 2       | 50
                                   (ל-Carol אין הזמנות)

INNER JOIN — רק התאמות משני הצדדים

SELECT u.name, o.total
FROM users u
INNER JOIN orders o ON u.id = o.user_id;
-- תוצאה: Alice/100, Alice/200, Bob/50
-- Carol לא מופיעה — אין לה הזמנות

LEFT JOIN — כל השמאל + התאמות מהימין

SELECT u.name, o.total
FROM users u
LEFT JOIN orders o ON u.id = o.user_id;
-- תוצאה: Alice/100, Alice/200, Bob/50, Carol/NULL
-- Carol מופיעה עם NULL — כי אין התאמה מימין

זה ה-JOIN הכי שימושי בפועל. דוגמה קלאסית: "כל המשתמשים כולל אלה בלי הזמנות". השילוב עם IS NULL מוצא את חסרי-ההתאמה:

-- משתמשים שאין להם אף הזמנה:
SELECT u.name FROM users u
LEFT JOIN orders o ON u.id = o.user_id
WHERE o.id IS NULL;

שאר הסוגים

JOINמחזיר
INNERרק שורות עם התאמה בשני הצדדים
LEFTכל השמאל + התאמות (או NULL)
RIGHTכל הימין + התאמות (או NULL) — נדיר, הופכים ל-LEFT
FULL OUTERהכל משני הצדדים, NULL איפה שאין התאמה
CROSSמכפלה קרטזית — כל שילוב אפשרי

SELF JOIN — טבלה מצטרפת לעצמה

שימושי להיררכיות (עובד ↔ מנהל שגם הוא עובד):

SELECT e.name AS employee, m.name AS manager
FROM employees e
LEFT JOIN employees m ON e.manager_id = m.id;

מודל מנטלי: חשוב על INNER JOIN כחיתוך (intersection) של שתי הקבוצות, ו-LEFT JOIN כ"כל השמאל, עם תוספת מהימין אם יש". רוב באגי ה-JOIN הם בלבול בין השניים — או שכפול שורות כי תנאי ה-ON אינו ייחודי (JOIN על עמודה שאינה unique משכפל שורות — היזהר).

8. Subqueries ו-EXISTS

Subquery היא שאילתה בתוך שאילתה. שלושה סוגים עיקריים:

Scalar subquery — מחזירה ערך יחיד

SELECT name, age,
  (SELECT AVG(age) FROM users) AS avg_age    -- ערך יחיד לכל שורה
FROM users;

Subquery ב-WHERE עם IN

-- משתמשים שיש להם הזמנה מעל 1000:
SELECT name FROM users
WHERE id IN (SELECT user_id FROM orders WHERE total > 1000);

Correlated subquery — תלויה בשורה החיצונית

ה-subquery רצה מחדש לכל שורה של השאילתה החיצונית, ומתייחסת אליה:

SELECT u.name FROM users u
WHERE (SELECT COUNT(*) FROM orders o WHERE o.user_id = u.id) > 5;

EXISTS — הגרסה היעילה

לרוב EXISTS עדיף על IN עם subquery — הוא עוצר ברגע שמצא התאמה אחת, ומטפל נכון ב-NULL (זוכר את המלכודת מפרק 4?):

-- משתמשים שיש להם לפחות הזמנה אחת:
SELECT u.name FROM users u
WHERE EXISTS (SELECT 1 FROM orders o WHERE o.user_id = u.id);

-- משתמשים בלי אף הזמנה (בטוח יותר מ-NOT IN):
SELECT u.name FROM users u
WHERE NOT EXISTS (SELECT 1 FROM orders o WHERE o.user_id = u.id);

עצה: הרבה subqueries ניתנות לכתיבה גם כ-JOIN, ולרוב ה-planner ממילא ממיר ביניהן. בחר לפי קריאוּת. אבל NOT EXISTS עדיף כמעט תמיד על NOT IN כשיכולים להיות NULLs — זה מונע את הבאג השקט מפרק 4.

9. Set Operations

מחברות תוצאות של שתי שאילתות (שחייבות אותו מבנה עמודות):

-- UNION — מאחד ומסיר כפילויות
SELECT name FROM customers UNION SELECT name FROM suppliers;

-- UNION ALL — מאחד ושומר כפילויות (מהיר יותר — בלי בדיקת ייחודיות)
SELECT name FROM customers UNION ALL SELECT name FROM suppliers;

-- INTERSECT — רק מה שמופיע בשתיהן
SELECT name FROM customers INTERSECT SELECT name FROM suppliers;

-- EXCEPT — מה שבראשונה ולא בשנייה (MINUS ב-Oracle)
SELECT name FROM customers EXCEPT SELECT name FROM suppliers;

טיפ ביצועים: אם אתה יודע שאין כפילויות, השתמש ב-UNION ALL — הוא חוסך את שלב הסרת-הכפילויות היקר.

10. CTEs ו-Recursive Queries

CTE (Common Table Expression) עם WITH נותן שם לתת-שאילתה, מה שהופך שאילתות מורכבות לקריאות — כמו משתנה זמני בקוד.

CTE רגיל

WITH high_spenders AS (
  SELECT user_id, SUM(total) AS spent
  FROM orders
  GROUP BY user_id
  HAVING SUM(total) > 1000
)
SELECT u.name, hs.spent
FROM users u
JOIN high_spenders hs ON u.id = hs.user_id
ORDER BY hs.spent DESC;

אפשר לשרשר כמה CTEs, וכל אחד יכול להתייחס לקודמים — זה הופך שאילתה של 50 שורות מקוננות למספר שלבים ברורים. לקריאוּת ותחזוקה זה שדרוג ענק.

Recursive CTE — הנושא המתקדם

זה הכלי לשאילתות היררכיות/גרפיות: עץ ארגוני, קטגוריות מקוננות, "כל הצאצאים". ה-CTE קורא לעצמו עד שאין עוד שורות:

-- כל הכפופים (ישירים ועקיפים) למנהל 1:
WITH RECURSIVE subordinates AS (
  -- Anchor: נקודת ההתחלה
  SELECT id, name, manager_id
  FROM employees
  WHERE id = 1

  UNION ALL

  -- Recursive: מצרף את הכפופים של מי שכבר נמצא
  SELECT e.id, e.name, e.manager_id
  FROM employees e
  JOIN subordinates s ON e.manager_id = s.id
)
SELECT * FROM subordinates;

המבנה תמיד זהה: חלק anchor (ההתחלה), UNION ALL, וחלק recursive שמצטרף לתוצאות עד שהוא לא מוסיף שורות חדשות. זה הפתרון הנקי לנתונים היררכיים — במקום לולאה באפליקציה שמבצעת שאילתה לכל רמה.

11. Window Functions — הכלי המתקדם החשוב

אם יש נושא אחד שמפריד בין "יודע SQL" ל"חזק ב-SQL" — זה window functions. הן פותרות בעיות שאחרת דורשות subqueries מסובכות או קוד באפליקציה, והן נשאלות בכל ראיון בכיר.

מה הן עושות

ההבדל מ-GROUP BY: aggregation רגיל מכווץ שורות לקבוצה אחת. window function מחשבת ערך מצטבר בלי לאבד את השורות הבודדות — כל שורה נשארת, ומקבלת בנוסף חישוב על "חלון" של שורות סביבה.

SELECT
  name,
  department,
  salary,
  AVG(salary) OVER (PARTITION BY department) AS dept_avg
FROM employees;
-- כל עובד נשאר שורה, אבל מקבל גם את ממוצע המחלקה שלו לצידו.
-- עם GROUP BY היינו מאבדים את השורות הבודדות.

המבנה: OVER, PARTITION BY, ORDER BY

  • OVER (...) — מגדיר את ה"חלון". זה מה שהופך פונקציה ל-window function.
  • PARTITION BY — מחלק לקבוצות (כמו GROUP BY, אבל בלי לכווץ).
  • ORDER BY (בתוך OVER) — קובע סדר בתוך החלון, נחוץ ל-ranking ולסכומים רצים.

Ranking functions

SELECT name, department, salary,
  ROW_NUMBER() OVER (PARTITION BY department ORDER BY salary DESC) AS row_num,
  RANK()       OVER (PARTITION BY department ORDER BY salary DESC) AS rank,
  DENSE_RANK() OVER (PARTITION BY department ORDER BY salary DESC) AS dense_rank
FROM employees;

ההבדל ביניהן (חשוב!):

  • ROW_NUMBER — מספר רץ ייחודי (1,2,3,4), גם אם יש שוויון.
  • RANK — שוויון מקבל אותו rank, ואז מדלג (1,1,3).
  • DENSE_RANK — שוויון מקבל אותו rank, בלי דילוג (1,1,2).

דוגמה קלאסית: Top-N לכל קבוצה

"שני העובדים עם השכר הגבוה בכל מחלקה" — בעיה שקשה בלי window functions:

SELECT * FROM (
  SELECT name, department, salary,
    ROW_NUMBER() OVER (PARTITION BY department ORDER BY salary DESC) AS rn
  FROM employees
) ranked
WHERE rn <= 2;

Running totals ו-LAG/LEAD

-- סכום רץ (cumulative) לאורך זמן:
SELECT order_date, total,
  SUM(total) OVER (ORDER BY order_date) AS running_total
FROM orders;

-- השוואה לשורה הקודמת/הבאה — נהדר לחישוב שינויים:
SELECT order_date, total,
  LAG(total)  OVER (ORDER BY order_date) AS prev_total,
  LEAD(total) OVER (ORDER BY order_date) AS next_total,
  total - LAG(total) OVER (ORDER BY order_date) AS change
FROM orders;

LAG/LEAD מאפשרות לגשת לשורה קודמת/הבאה בלי self-join — מושלם לחישוב "כמה גדל לעומת אתמול", growth rates, וכו'. זה הופך ניתוחים שהיו דורשים קוד למספר שורות SQL.

למה זה כל כך חזק: כל מה שכאן — ranking, top-N per group, running totals, period-over-period — היו בלי window functions דורשים subqueries מקוננות או משיכת הכל לאפליקציה ולולאה. window functions מעבירות את החישוב ל-DB, קרוב לנתונים, ובצורה קריאה. שווה להשקיע ולשלוט בהן.

12. Indexes — איך מאיצים שאילתות

Index הוא מבנה נתונים נוסף שה-DB מתחזק כדי למצוא שורות מהר, בלי לסרוק את כל הטבלה. זה ההבדל בין שאילתה של אלפיות שנייה לשאילתה של דקות. זה גם הנושא שהכי משפיע על ביצועים בפועל.

המודל המנטלי

חשוב על אינדקס בספר: כדי למצוא נושא, אתה לא קורא את כל הספר — אתה הולך לאינדקס בסוף, מוצא את מספר העמוד, וקופץ ישר. בלי אינדקס, ה-DB עושה full table scan — קורא כל שורה. עם אינדקס, הוא קופץ ישר לשורות הרלוונטיות.

CREATE INDEX idx_users_email ON users(email);
-- עכשיו WHERE email = '...' מהיר גם במיליוני שורות.

B-tree — ברירת המחדל

רוב האינדקסים הם B-tree — עץ מאוזן שמאפשר חיפוש, טווחים ומיון ב-O(log n). מצוין ל-=, <, >, BETWEEN, ORDER BY, ו-LIKE 'prefix%' (prefix בלבד — לא %infix%).

Composite index — כמה עמודות

אינדקס על כמה עמודות. הסדר קריטי — חל כלל ה"leftmost prefix":

CREATE INDEX idx_orders_user_date ON orders(user_id, created_at);

-- משתמש באינדקס:
WHERE user_id = 5                          -- ✅ (עמודה ראשונה)
WHERE user_id = 5 AND created_at > '2024'  -- ✅ (שתיהן, בסדר)
-- לא משתמש באינדקס ביעילות:
WHERE created_at > '2024'                  -- ❌ (דילג על העמודה הראשונה)

כלל: שים את העמודה שהכי מסננת (או שתמיד ב-WHERE) ראשונה. אינדקס (a, b) עוזר ל-WHERE a ול-WHERE a AND b, אבל לא ל-WHERE b לבד.

סוגי אינדקסים מיוחדים (Postgres)

  • Partial index — רק על חלק מהשורות, קטן ומהיר יותר: CREATE INDEX ... WHERE is_active = true.
  • Unique index — אוכף ייחודיות וגם מאיץ.
  • GIN — ל-JSONB, arrays ו-full-text search (פרק 16).
  • Covering index (INCLUDE) — כולל עמודות נוספות כדי שהשאילתה תיענה מהאינדקס בלבד בלי לגעת בטבלה ("index-only scan").
  • Expression index — על תוצאת ביטוי: CREATE INDEX ON users(LOWER(email)) — מאיץ WHERE LOWER(email) = ....

המחיר — למה לא לאנדקס הכל

אינדקסים לא בחינם, וזו טעות נפוצה לפזר אותם בכל מקום:

  • מאטים כתיבה — כל INSERT/UPDATE/DELETE חייב לעדכן גם את כל האינדקסים.
  • תופסים מקום בדיסק ובזיכרון.
  • אינדקס לא בשימוש הוא רק עלות בלי תועלת.

הכלל: אנדקס עמודות שמופיעות הרבה ב-WHERE, ב-JOIN (במיוחד FKs!), וב-ORDER BY. אל תאנדקס עמודות שכמעט לא מסננות (כמו boolean עם התפלגות 50/50). מדוד עם EXPLAIN (הפרק הבא) לפני ואחרי.

13. Query Planner ו-EXPLAIN

זוכר שאמרתי ש-SQL הוא declarative — אתה מתאר מה, ה-DB בוחר איך? ה-query planner הוא מי שבוחר, ו-EXPLAIN הוא איך אתה רואה את הבחירה שלו. זה הכלי מספר אחת לדיבוג ביצועים.

EXPLAIN ו-EXPLAIN ANALYZE

EXPLAIN SELECT * FROM users WHERE email = 'a@x.com';
-- מראה את התוכנית המשוערת בלי להריץ

EXPLAIN ANALYZE SELECT * FROM users WHERE email = 'a@x.com';
-- מריץ באמת ומראה זמנים אמיתיים — זה מה שתשתמש בו לדיבוג

מה לחפש בפלט

מה שרואיםמשמעות
Seq Scanסריקת כל הטבלה — לרוב סימן שחסר אינדקס (בטבלה גדולה)
Index Scanשימוש באינדקס — טוב
Index Only Scanנענה מהאינדקס בלבד — הכי טוב (covering)
Nested Loop / Hash Join / Merge Joinאסטרטגיות JOIN שונות שה-planner בחר
cost=...הערכת עלות יחסית (לא שניות)

הדגל הכי חשוב לחפש

פער גדול בין rows משוער ל-actual rows אומר שהסטטיסטיקות של ה-DB לא מעודכנות — ה-planner מקבל החלטות גרועות על בסיס מידע שגוי. הפתרון: ANALYZE table_name; (מרענן סטטיסטיקות). וכש-Seq Scan על טבלה גדולה עם WHERE סלקטיבי — כנראה חסר אינדקס.

הרגל של מפתח טוב: כששאילתה איטית, אל תנחש — הרץ EXPLAIN ANALYZE. הוא מראה לך בדיוק איפה הזמן הולך ואם האינדקסים בשימוש. זה ההבדל בין "הוספתי אינדקס ואני מקווה שעזר" ל"ראיתי Seq Scan, הוספתי אינדקס, ועכשיו זה Index Scan ופי 100 מהר יותר".

14. Transactions, ACID ו-Isolation Levels

Transaction היא קבוצת פעולות שמתבצעות כיחידה אחת בלתי-נפרדת — או שהכל מצליח, או ששום דבר לא קורה. זה הבסיס לשלמות נתונים, וזה נושא מתקדם שכל מפתח Backend חייב לשלוט בו.

הדוגמה הקלאסית: העברה בנקאית

BEGIN;                                                    -- פותח transaction
  UPDATE accounts SET balance = balance - 100 WHERE id = 1;
  UPDATE accounts SET balance = balance + 100 WHERE id = 2;
COMMIT;                                                   -- מאשר הכל ביחד

למה זה קריטי: אם השרת קורס בין שתי הפקודות בלי transaction — כסף ירד מחשבון אחד ולא נכנס לשני. עם transaction, או ששתיהן קורות או אף אחת. אם משהו משתבש: ROLLBACK; מבטל הכל.

ACID — ארבע ההבטחות

  • Atomicity (אטומיות) — הכל או כלום. אין מצב ביניים.
  • Consistency (עקביות) — ה-DB עובר ממצב תקין למצב תקין; constraints נשמרים.
  • Isolation (בידוד) — transactions מקבילות לא דורסות זו את זו (ראה למטה).
  • Durability (עמידות) — אחרי COMMIT, המידע שמור גם אם יש קריסה/הפסקת חשמל.

Isolation Levels — הנושא המתקדם והמעניין

כשכמה transactions רצות בו-זמנית, נוצרות אנומליות. רמות הבידוד קובעות מאילו אנומליות מוגנים — יותר בידוד = יותר בטיחות אבל פחות concurrency. שלוש האנומליות:

  • Dirty read — קריאת נתונים שעדיין לא עברו COMMIT (ועלולים להתבטל).
  • Non-repeatable read — קריאת אותה שורה פעמיים נותנת ערכים שונים (מישהו עדכן בינתיים).
  • Phantom read — אותה שאילתה מחזירה שורות חדשות בהרצה שנייה (מישהו הוסיף שורות).
Isolation LevelDirtyNon-repeatablePhantom
READ UNCOMMITTEDאפשריאפשריאפשרי
READ COMMITTED❌ נמנעאפשריאפשרי
REPEATABLE READ❌❌ נמנעאפשרי*
SERIALIZABLE❌❌❌ נמנע

ברירת המחדל ב-Postgres היא READ COMMITTED. (הערה: ב-Postgres, REPEATABLE READ מונע גם phantoms בפועל, בזכות מימוש MVCC). ככל שעולים ברמה — יותר בטוח אבל יותר locks והתנגשויות. בוחרים לפי הצורך: לרוב READ COMMITTED מספיק; SERIALIZABLE לפעולות פיננסיות קריטיות.

BEGIN ISOLATION LEVEL SERIALIZABLE;
  -- ...
COMMIT;

Locking ו-Deadlocks

כדי לאכוף בידוד, ה-DB נועל שורות. SELECT ... FOR UPDATE נועל שורות שאתה עומד לעדכן, כדי שאף אחד אחר לא ייגע בהן עד ה-COMMIT:

BEGIN;
  SELECT balance FROM accounts WHERE id = 1 FOR UPDATE;  -- נעל את השורה
  UPDATE accounts SET balance = balance - 100 WHERE id = 1;
COMMIT;

Deadlock קורה כששתי transactions מחכות זו לזו: A נעל שורה 1 ורוצה את 2, B נעל 2 ורוצה את 1 — תקיעה הדדית. ה-DB מזהה את זה ומבטל אחת מהן אוטומטית (מחזיר שגיאה). ההגנה: תמיד נעל משאבים באותו סדר בכל הקוד (למשל תמיד לפי id עולה), וזה מונע את מעגל ההמתנה.

קשר ל-NestJS: TypeORM/Prisma עוטפים transactions ב-API נוח (dataSource.transaction(...)). אבל ההבנה של isolation levels ו-deadlocks היא שלך — ה-ORM לא יבחר בשבילך את רמת הבידוד הנכונה או ימנע deadlock מעיצוב גרוע. באגי concurrency הם מהקשים ביותר לדבג, אז שווה להבין אותם מראש.

15. Views ו-Materialized Views

View — שאילתה שמורה בשם

View הוא "טבלה וירטואלית" — שאילתה שמורה שאפשר להריץ עליה SELECT כאילו הייתה טבלה. היא לא מאחסנת נתונים; היא רצה מחדש בכל גישה:

CREATE VIEW active_high_spenders AS
SELECT u.id, u.name, SUM(o.total) AS spent
FROM users u
JOIN orders o ON o.user_id = u.id
WHERE u.is_active = true
GROUP BY u.id, u.name
HAVING SUM(o.total) > 1000;

-- עכשיו פשוט:
SELECT * FROM active_high_spenders;

יתרונות: מפשט שאילתות מורכבות שחוזרות, ומספק שכבת הפשטה (אפשר לשנות את ה-view בלי לשנות את הקוד שמשתמש בו).

Materialized View — תוצאה מאוחסנת

בניגוד ל-view רגיל, materialized view שומר את התוצאה פיזית. מהיר לקריאה (לא מחשב מחדש), אבל צריך רענון ידני/מתוזמן — הנתונים "תקועים" עד הרענון:

CREATE MATERIALIZED VIEW daily_sales AS
SELECT DATE(created_at) AS day, SUM(total) AS revenue
FROM orders GROUP BY DATE(created_at);

REFRESH MATERIALIZED VIEW daily_sales;   -- מרענן את הנתונים

מתי להשתמש: דוחות/דשבורדים כבדים שמורצים הרבה אבל לא צריכים נתונים בזמן-אמת. מחשבים פעם בשעה/לילה, וקוראים מהיר. ה-tradeoff: מהירות מול טריות הנתונים.

16. טיפוסים מתקדמים — JSONB, Arrays, Full-Text

כאן Postgres זורח מעל דיאלקטים אחרים. תכונות שמטשטשות את הגבול בין SQL ל-NoSQL.

JSONB — JSON בתוך ה-DB

JSONB שומר JSON בפורמט בינארי יעיל, עם אינדוקס ושאילתות. שימושי לשדות דינמיים/semi-structured בלי סכמה קשיחה:

CREATE TABLE products (
  id    BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  name  TEXT,
  attrs JSONB
);

INSERT INTO products (name, attrs)
VALUES ('Laptop', '{"brand": "Dell", "ram": 16, "tags": ["work"]}');

-- שאילתות על JSON:
SELECT name FROM products WHERE attrs->>'brand' = 'Dell';   -- ->> מחזיר text
SELECT attrs->'ram' FROM products;                          -- -> מחזיר JSON
SELECT * FROM products WHERE attrs @> '{"ram": 16}';        -- contains

-- אינדקס GIN ל-JSONB מהיר:
CREATE INDEX idx_products_attrs ON products USING GIN (attrs);

עצה: JSONB נהדר לגמישות, אבל אל תשתמש בו כדי לברוח מעיצוב סכמה. אם שדה מופיע בכל שורה ומחפשים לפיו הרבה — הוא צריך להיות עמודה אמיתית עם אינדקס, לא מפתח ב-JSONB. השתמש ב-JSONB ל-metadata משתנה באמת (הגדרות, attributes דינמיים).

Arrays

CREATE TABLE posts (id INT, tags TEXT[]);
INSERT INTO posts VALUES (1, ARRAY['sql', 'backend']);
SELECT * FROM posts WHERE 'sql' = ANY(tags);      -- מכיל ערך
SELECT * FROM posts WHERE tags @> ARRAY['sql'];   -- contains

Full-Text Search

חיפוש טקסט חכם (לא רק LIKE) — עם stemming, דירוג רלוונטיות:

SELECT title FROM articles
WHERE to_tsvector('english', body) @@ to_tsquery('english', 'database & index');
-- מוצא מסמכים עם שתי המילים, כולל צורות מוטות

עם אינדקס GIN על ה-tsvector, זה מהיר מאוד — מספיק לרוב האפליקציות בלי צורך ב-Elasticsearch נפרד.

17. Functions, Procedures ו-Triggers

Functions

לוגיקה שמורה ב-DB שאפשר לקרוא לה משאילתות:

CREATE FUNCTION get_user_order_count(uid INT)
RETURNS BIGINT AS $$
  SELECT COUNT(*) FROM orders WHERE user_id = uid;
$$ LANGUAGE sql;

SELECT name, get_user_order_count(id) FROM users;

ל-לוגיקה מורכבת יש PL/pgSQL — שפה פרוצדורלית מלאה עם משתנים, לולאות ותנאים בתוך ה-DB.

Triggers

קוד שרץ אוטומטית באירוע (INSERT/UPDATE/DELETE). שימוש קלאסי — עדכון updated_at:

CREATE FUNCTION set_updated_at() RETURNS TRIGGER AS $$
BEGIN
  NEW.updated_at = now();
  RETURN NEW;
END;
$$ LANGUAGE plpgsql;

CREATE TRIGGER trg_updated_at
BEFORE UPDATE ON users
FOR EACH ROW EXECUTE FUNCTION set_updated_at();
-- מעכשיו כל UPDATE מעדכן את updated_at לבד.

דעה שכדאי לשמוע: triggers ו-stored procedures חזקים, אבל מסתירים לוגיקה — קשה לדבג, לא נראים ב-code review של האפליקציה, וקשים ל-version control. הכלל שאני ממליץ עליו: השתמש בהם ללוגיקת שלמות נתונים (audit logs, updated_at, אכיפת constraints מורכבים) — אבל שמור לוגיקה עסקית באפליקציה (NestJS), איפה שהיא גלויה, נבדקת ומנוהלת ב-git. trigger שמחשב מחירים או שולח מיילים = כאב ראש עתידי.

18. סדר הביצוע הלוגי של שאילתה

זה אולי הדבר הכי חשוב במדריך כולו, ומעטים מלמדים אותו. הסדר שבו אתה כותב SQL אינו הסדר שבו הוא רץ. הבנת הסדר הלוגי מסבירה מיד עשרות "למה זה לא עובד".

הסדר שכותבים

SELECT ... FROM ... JOIN ... WHERE ... GROUP BY ... HAVING ... ORDER BY ... LIMIT

הסדר שבאמת רץ (לוגית)

#שלבמה קורה
1FROM / JOINקובעים ומחברים את הטבלאות
2WHEREמסננים שורות בודדות
3GROUP BYמקבצים לקבוצות
4HAVINGמסננים קבוצות
5SELECTבוחרים עמודות, מחשבים aliases
6DISTINCTמסירים כפילויות

למה זה פותר בלבולים אמיתיים

שים לב ש-SELECT (שלב 5) רץ אחרי WHERE (2) ו-GROUP BY (3). זה מסביר שתי שגיאות נפוצות:

-- ❌ שגיאה: alias שהוגדר ב-SELECT לא זמין ב-WHERE
SELECT price * quantity AS total FROM orders WHERE total > 100;
--                                                  ^^^^^ SELECT עדיין לא רץ!

-- ✅ נכון: חוזרים על הביטוי, או משתמשים ב-subquery/CTE
SELECT price * quantity AS total FROM orders WHERE price * quantity > 100;

וזה גם מסביר למה לא אפשר aggregate ב-WHERE (הקיבוץ בשלב 3, WHERE בשלב 2), אבל כן ב-HAVING (שלב 4) — בדיוק ההבחנה מפרק 6. ולמה ORDER BY כן יכול להשתמש ב-alias מ-SELECT (שלב 7 אחרי שלב 5). ברגע שאתה מחזיק את הטבלה הזו בראש — הרבה "מוזרויות" של SQL הופכות להגיוניות לגמרי.

19. Best Practices וטעויות נפוצות

  1. אל תשתמש ב-SELECT * ב-production. בחר עמודות מפורשות — פחות תעבורה, פחות שבירות כשהסכמה משתנה, ומאפשר index-only scans.
  2. אנדקס FKs ועמודות WHERE/JOIN. הרבה שאילתות איטיות הן FK לא מאונדקס.
  3. היזהר מ-N+1 queries. הטעות הכי נפוצה עם ORMs: לולאה שמריצה שאילתה לכל פריט (1 + N שאילתות) במקום JOIN אחד. זהה עם logging של השאילתות.
  4. השתמש ב-parameterized queries תמיד. לעולם אל תשרשר קלט משתמש ל-SQL — זה SQL injection. ORMs עושים את זה נכון; אם כותבים raw, השתמש ב-placeholders ($1).
  5. NUMERIC לכסף, לא FLOAT. (מפרק 2 — שווה לחזור).
  6. עבוד בתוך transactions לפעולות מרובות-שלבים, במיוחד כתיבות קשורות.
  7. מדוד עם EXPLAIN ANALYZE לפני שמאופטמים — אל תנחש איפה הצוואר.
  8. הימנע מפונקציות על עמודה ב-WHERE — WHERE LOWER(email) = ... מבטל אינדקס רגיל (צריך expression index).
  9. שמור לוגיקה עסקית באפליקציה, שלמות נתונים ב-DB (constraints/triggers).
  10. גבה, ותרגל שחזור. גיבוי שלא בדקת שחזור ממנו — הוא לא באמת גיבוי.

מלכודת ה-N+1 — דוגמה

-- ❌ N+1: קוד שרץ כך (פסאודו):
users = SELECT * FROM users;              -- שאילתה 1
for each user:
  orders = SELECT * FROM orders WHERE user_id = user.id;   -- N שאילתות!

-- ✅ שאילתה אחת עם JOIN:
SELECT u.*, o.* FROM users u LEFT JOIN orders o ON o.user_id = u.id;

20. תרגילים

סכמה לתרגול: users(id, name, country, created_at), orders(id, user_id, total, created_at).

1 — Aggregation. מצא את סך ההכנסות (SUM(total)) לכל מדינה, רק למדינות עם יותר מ-10 הזמנות, ממויין מהגבוה לנמוך.

2 — JOIN + NULL. מצא את כל המשתמשים שנרשמו אך מעולם לא ביצעו הזמנה (רמז: LEFT JOIN + IS NULL).

3 — Window function. לכל הזמנה, הצג את סכומה ואת ה-rank שלה בתוך המדינה של המשתמש (ההזמנה הגדולה ביותר במדינה = 1).

4 — Top-N per group. מצא את שלוש ההזמנות הגדולות ביותר בכל מדינה (רמז: ROW_NUMBER ב-subquery/CTE).

5 — Running total. הצג הכנסה מצטברת (cumulative) לפי יום עבור כל ההזמנות.

6 — Recursive CTE. בהינתן categories(id, name, parent_id), החזר את כל תת-הקטגוריות (בכל העומק) של קטגוריה נתונה.

7 — ניתוח ביצועים. נתונה שאילתה איטית עם WHERE email = ?. הרץ עליה EXPLAIN ANALYZE, זהה אם יש Seq Scan, הוסף אינדקס מתאים, והשווה.

8 — Transaction. כתוב transaction שמעביר סכום בין שני חשבונות עם SELECT ... FOR UPDATE, כולל טיפול במקרה של יתרה לא מספקת (ROLLBACK).

סיכום — מה הלאה

כיסינו את כל הטווח: מ-DDL ו-CRUD, דרך joins, aggregations ו-CTEs, ועד לנושאים שמפרידים מפתחים חזקים — window functions, indexes, execution plans, ו-isolation levels.

שני דברים לזכור מעל הכל: SQL הוא declarative (אתה מתאר, ה-planner מבצע — ולכן indexes ו-EXPLAIN הם הכלים שלך לשליטה בביצועים), והסדר הלוגי של הביצוע (פרק 18) מסביר את רוב ה"מוזרויות" של השפה.

הצעד הבא: קח מסד נתונים אמיתי (ה-Postgres של פרויקט NestJS שלך), טען אליו נתונים, והרץ את התרגילים. הרץ EXPLAIN ANALYZE על כל שאילתה כדי לראות מה קורה מתחת. SQL נלמד באצבעות, לא בעיניים.
