שלב 1 — API, Validation ו־State

#1 Node.js
Foundations

Safe Task API

מטרה: לבנות API קטן שמכריח אותך לחשוב על validation, parsing ו־HTTP semantics במקום רק לגרום ל־route לעבוד.

בנה: POST /tasks, ‏GET /tasks ו־GET /tasks?priority=3. ‏title חייב להיות string לא ריק ו־priority מספר שלם 1–5. החזר 201 ביצירה ו־400 לקלט לא תקין.

Starter guidance

שמור את הנתונים ב־array בזיכרון. הפרד validation מה־route. לפני שאתה נוגע ב־query parameter, בדוק איזה type Express באמת נותן לך.

Debugging scenario

ה־task שומר priority: 3, אבל req.query.priority מגיע כ־string ולכן השוואה strict מחזירה false. אל תפתור עם coercion עיוור; בצע parsing ו־validation.

Interview challenge

למה let nextId = 1 מפסיק להיות strategy תקין כשיש כמה processes מאחורי Load Balancer?

Bonus

הוסף pagination פשוט ונסה להחליט איך אתה מחזיר שגיאה ל־?priority=hello.

Review: validation מפורש, parsing תקין, status codes נכונים, והסבר ברור למה state ו־IDs בזיכרון אינם גלובליים.
#2 Python
Foundations

URL Shortener

מטרה: לתרגל API state, redirects, uniqueness וחשיבה על race conditions.

בנה: עם FastAPI או Flask: ‏POST /shorten שמקבל URL, יוצר code קצר, ו־GET /{code} שעושה redirect. URL ריק/לא תקין נדחה ו־code לא קיים מחזיר 404.

Starter guidance

התחל עם dict. החלט מראש מה הכיוון של המיפוי: code → URL. הפרד code generation, validation ו־route.

Debugging scenario

אם שמרת urls[url] = code אבל ב־redirect אתה עושה urls.get(code), עקוב אחרי state בפועל והסבר למה תמיד תקבל not found.

Interview challenge

שני requests מייצרים במקרה אותו code ושניהם מבצעים check לפני insert. למה check-then-write אינו atomic?

Bonus

הוסף GET /stats/{code} ומספר redirects.

Review: redirect עובד, collision לא דורס state קיים, ואתה מסוגל להסביר למה DB uniqueness חזק יותר מבדיקת if.

שלב 2 — Transactions ו־Concurrency

#4 Python + DB
Intermediate

Money Transfer Transaction

מטרה: להבין Atomicity ו־business invariants בעזרת העברת כסף בין accounts.

בנה: POST /transfer עם source, destination ו־amount. דחה amount ≤ 0, אותו account, account חסר או insufficient funds. Debit ו־credit חייבים להצליח או להיכשל יחד.

Starter guidance

הפרד route מלוגיקת transfer. פתח transaction אחת סביב read/validate/update/commit. בדוק rollback אמיתי על exception.

Debugging scenario

אם committed את הורדת הכסף ואז קרסה הפעולה לפני הזיכוי, איזה state נשאר? למה try/except בלי transaction לא מספיק?

Interview challenge

שתי העברות של 80 קוראות balance=100 בו־זמנית. למה transaction לבדה לא בהכרח מונעת overspending? חקור row locking או atomic update.

Bonus

שמור transfer history באותה transaction.

Review: אין partial state, אין negative balance, ואתה יודע להסביר Atomicity, isolation ו־row locking.
#7 Node.js + PostgreSQL
Advanced

Prevent Lost Updates

מטרה: להגן על inventory תחת concurrent purchases.

בנה: POST /products/:id/purchase. quantity תקין מפחית stock; insufficient stock מחזיר 409; אסור stock שלילי.

Starter guidance

נסה קודם read-check-write נאיבי ואז בנה בדיקת concurrency שמפעילה שני requests כמעט יחד.

Debugging scenario

stock=5 ושתי רכישות של 3 קוראות 5 וכותבות 2. הנתון הסופי נראה חוקי אבל העסק מכר 6 מתוך 5.

Interview challenge

פתור עם SELECT ... FOR UPDATE או atomic conditional UPDATE ... WHERE stock >= ... RETURNING. הסבר trade-off.

Bonus

מדוד מה request שני עושה בזמן שהראשון מחזיק lock.

Review: אין oversell, אתה יכול לשחזר Lost Update ולהסביר pessimistic מול atomic SQL.
#13 Node.js + PostgreSQL
Advanced

Optimistic Concurrency Control

מטרה: למנוע silent overwrite באמצעות version column.

בנה: PUT /users/:id מקבל version. update על version 7 מצליח ומעלה ל־8; update נוסף עם version 7 מקבל 409.

Starter guidance

אל תעשה SELECT ואז compare ואז UPDATE. תן ל־version להשתתף ב־WHERE של ה־UPDATE עצמו.

Debugging scenario

שני requests קוראים version=7 ושניהם עוברים application-side check לפני update.

Interview challenge

מתי optimistic locking עדיף על FOR UPDATE, ומתי contention גבוה גורם לו להיות פחות מתאים?

Bonus

החזר structured VERSION_CONFLICT והחלט כיצד client מתאושש.

Review: stale updates נכשלים atomically, ואתה יודע להסביר optimistic מול pessimistic locking.

שלב 3 — Reliability, Idempotency ו־Distributed Systems

#5 Node.js
Intermediate

Idempotency Key Fundamentals

מטרה: להבין למה retries ברשת יכולים ליצור duplicate operations.

בנה: POST /orders עם header ‏Idempotency-Key. retry עם אותו key מחזיר את אותה תוצאה ולא יוצר order חדש. בגרסה הזאת מותר Map.

Starter guidance

שמור key → result. שמור גם fingerprint של payload כדי לזהות שימוש באותו key לבקשה שונה.

Debugging scenario

שני requests מגיעים יחד: שניהם עושים has(key) → false, שניהם יוצרים order ורק אחר כך set. הסבר את race.

Interview challenge

מה קורה כשה־retry מגיע ל־instance אחר? השווה PostgreSQL UNIQUE, Redis ו־transaction.

Bonus

דחה same key + different payload.

Review: אתה מבין retry ambiguity, duplicate creation, ומדוע local memory אינו production guarantee.

#9 Node.js + PostgreSQL
Advanced

Refresh Token Rotation

מטרה: לתרגל token rotation, reuse detection ו־concurrent refresh.

בנה: POST /auth/refresh. שמור hash בלבד; token ישן הופך used/revoked; נוצר refresh token חדש ו־access token חדש באותה פעולה לוגית.

Starter guidance

מפה את הזרימה לפני הקוד: lookup → validate session/expiry → lock/claim token → create replacement → commit.

Debugging scenario

שני requests משתמשים באותו RT1 ושניהם רואים שהוא עדיין usable לפני שאחד מהם מסמן אותו. מתקבלים RT2 ו־RT3.

Interview challenge

Bonus

נהל token family או replacement chain.

Review: raw token לא נשמר, concurrent refresh בטוח, ואתה מבין reuse detection.
