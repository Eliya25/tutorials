1. מה זה TypeScript ולמה הוא קיים

TypeScript הוא superset של JavaScript. כלומר: כל קוד JavaScript תקין הוא גם קוד TypeScript תקין. מה ש-TypeScript מוסיף זה מערכת טיפוסים סטטית (static type system) — היכולת לתאר מראש איזה סוג ערך יש בכל משתנה, פרמטר, ומה מחזירה כל פונקציה.

הרעיון המרכזי: בדיקה בזמן קומפילציה, לא בזמן ריצה

ב-JavaScript הטעות מתגלה רק כשהקוד רץ:

// JavaScript
function getUserName(user) {
  return user.name.toUpperCase();
}

getUserName(undefined); // 💥 TypeError קורס רק בזמן ריצה

ב-TypeScript הטעות מתגלה כבר בזמן הכתיבה, לפני שהקוד בכלל רץ:

// TypeScript
function getUserName(user: { name: string }): string {
  return user.name.toUpperCase();
}

getUserName(undefined);
// ❌ Argument of type 'undefined' is not assignable to parameter of type '{ name: string }'.

זה ההבדל המהותי: TypeScript מזיז את גילוי הבאגים שמאלה על ציר הזמן — מ-runtime ל-compile time. בשביל Backend זה קריטי, כי runtime error ב-production זה request שנכשל או תהליך שקורס.

עובדה שחייבים להבין: Type Erasure

זו הנקודה שהכי מבלבלת מתחילים, אז נעצור עליה. הטיפוסים של TypeScript נמחקים לגמרי בזמן הקומפילציה. הם לא קיימים ב-runtime.

הקוד הזה:

let age: number = 30;
interface User { name: string; }

מתקמפל ל-JavaScript הזה:

let age = 30;
// ה-interface נעלם לחלוטין — אין לו שום ייצוג ב-runtime

המשמעויות המעשיות:

  • אי אפשר לבדוק טיפוס של TypeScript ב-runtime. אין if (x instanceof User) על interface.
  • הטיפוסים לא מגנים עליך מפני data שמגיע מבחוץ (מ-HTTP request, מ-DB, מ-JSON). TypeScript מאמין למה שאתה מצהיר. לכן ב-Backend צריך validation אמיתי בזמן ריצה (כמו class-validator ב-NestJS או zod) בנוסף לטיפוסים.

תזכור את המשפט הזה: טיפוסים הם הבטחה למקמפל, לא בדיקה ב-runtime.

קוד .ts  ──►  tsc (TypeScript compiler)  ──►  קוד .js  ──►  Node מריץ
              │
              └─► תוך כדי: type checking. אם יש שגיאת טיפוס — מדווח.

2. התקנה, הרצה ו-tsconfig ראשוני

התקנה

TypeScript עצמו הוא חבילת npm. בפרויקט אמיתי מתקינים אותו כ-dev dependency:

npm init -y
npm install --save-dev typescript
npx tsc --version

tsc הוא ה-compiler. npx מריץ אותו מתוך node_modules המקומי (עדיף על התקנה גלובלית, כי כל פרויקט נעול לגרסה משלו).

הקובץ tsconfig.json

זה קובץ ההגדרות של הקומפיילר. יוצרים אותו כך:

npx tsc --init

הנה גרסה מינימלית ושפויה להתחלה (נצלול לכל דגל בפרק 14):

{
  "compilerOptions": {
    "target": "ES2022",
    "module": "NodeNext",
    "moduleResolution": "NodeNext",
    "outDir": "./dist",
    "rootDir": "./src",
    "strict": true,
    "esModuleInterop": true,
    "skipLibCheck": true,
    "forceConsistentCasingInFileNames": true
  },
  "include": ["src/**/*"]
}

הדגל הכי חשוב כאן הוא "strict": true. תמיד תעבוד עם strict מופעל. הוא מפעיל חבילה של בדיקות שהופכות את TypeScript מ"הצללה נחמדה" ל"רשת ביטחון אמיתית".

להריץ קוד TypeScript

גישה 1 — קומפילציה ואז הרצה (מה שקורה ב-production):

npx tsc          # מייצר קבצי .js בתיקיית dist
node dist/index.js

גישה 2 — הרצה ישירה בפיתוח (נוח יותר):

npm install --save-dev tsx
npx tsx src/index.ts    # מקמפל ומריץ בזיכרון, בלי לייצר קבצים

הערה חשובה: tsx/ts-node בדרך כלל לא בודקים טיפוסים — הם רק ממירים ומריצים מהר. לכן צריך להריץ tsc --noEmit בנפרד (למשל ב-CI) כדי לקבל את בדיקות הטיפוסים בפועל. --noEmit אומר "רק תבדוק, אל תייצר קבצים".

3. טיפוסים בסיסיים

הצהרת טיפוס — הסינטקס

let username: string = "eliya";
let age: number = 30;
let isActive: boolean = true;

Type Inference — למה לרוב לא צריך לכתוב את הטיפוס

TypeScript חכם מספיק להסיק את הטיפוס לבד מהערך. זה נקרא type inference:

let username = "eliya";  // TypeScript מסיק: string
username = 42;           // ❌ Type 'number' is not assignable to type 'string'

הכלל המעשי: אל תכתוב טיפוס כשהוא ברור מההשמה. כתוב טיפוס מפורש כשהוא לא ברור — בעיקר בפרמטרים של פונקציות, בערכי החזרה חשובים, ובמשתנים שמאותחלים ל-null.

// מיותר — ה-inference עושה את העבודה:
let count: number = 0;

// טוב — כאן צריך, כי בלי זה TypeScript לא יודע מה יהיה בפנים:
let user: User | null = null;

הטיפוסים הפרימיטיביים

let s: string = "hello";
let n: number = 3.14;        // אין int/float נפרדים — הכל number
let big: bigint = 100n;      // למספרים ענקיים
let b: boolean = false;
let sym: symbol = Symbol();
let u: undefined = undefined;
let nl: null = null;

any — הבריחה ממערכת הטיפוסים (ולמה להימנע)

any אומר ל-TypeScript "כבה את הבדיקות למשתנה הזה". כל פעולה מותרת עליו, וזה מדביק:

let data: any = "hello";
data.foo.bar.baz();   // ✅ TypeScript לא מתלונן — וזה בדיוק הבעיה
data = 42;            // ✅ מותר
data.toUpperCase();   // ✅ מותר — יקרוס ב-runtime

הכלל: תתייחס לכל any בקוד שלך כאל באג פוטנציאלי.

unknown — הגרסה הבטוחה של any

unknown אומר "לא יודע מה זה עדיין". בניגוד ל-any, TypeScript מכריח אותך לבדוק לפני שאתה משתמש בו:

let value: unknown = fetchSomething();

value.toUpperCase();
// ❌ 'value' is of type 'unknown'. חייבים לצמצם קודם.

if (typeof value === "string") {
  value.toUpperCase(); // ✅ בתוך ה-if, TypeScript יודע שזה string
}

זה הטיפוס הנכון לכל data שמגיע מבחוץ: תגובת API, JSON.parse, קלט משתמש.

void ו-never

// void — הפונקציה לא מחזירה ערך שימושי
function logMessage(msg: string): void {
  console.log(msg);
}

// never — הפונקציה לעולם לא מסיימת נורמלית (זורקת שגיאה או לולאה אינסופית)
function throwError(msg: string): never {
  throw new Error(msg);
}

null, undefined ו-strictNullChecks

עם strict מופעל, אתה לא יכול לשים null או undefined במקום שמצפה לערך רגיל:

let name: string = null;   // ❌ Type 'null' is not assignable to type 'string'

אם ערך יכול להיות ריק, חייבים לומר את זה במפורש עם union:

let name: string | null = null;  // ✅ עכשיו מותר

זו אחת התכונות שמונעות הכי הרבה באגים — ה"billion dollar mistake" של null pointer מטופל כאן בזמן קומפילציה.

4. מערכים, Tuples ו-Enums

מערכים

שתי צורות כתיבה, זהות במשמעות:

let scores: number[] = [90, 85, 100];
let names: Array<string> = ["a", "b"];   // צורה גנרית — נבין אותה בפרק Generics

מערך שיכול להכיל כמה טיפוסים — union בתוך המערך:

let mixed: (string | number)[] = ["a", 1, "b", 2];

readonly arrays

const config: readonly string[] = ["a", "b"];
config.push("c");   // ❌ Property 'push' does not exist on type 'readonly string[]'
config[0] = "x";    // ❌ Index signature is readonly

Tuples — מערך באורך ובטיפוסים קבועים

Tuple הוא מערך שבו כל מיקום מוגדר מראש — גם האורך וגם הטיפוס של כל תא:

let point: [number, number] = [10, 20];
let entry: [string, number] = ["age", 30];

entry[0].toUpperCase();  // ✅ TypeScript יודע שזה string
entry[1].toFixed(2);     // ✅ יודע שזה number

let bad: [string, number] = [30, "age"]; // ❌ הסדר לא נכון

ב-Backend זה שימושי לפונקציות שמחזירות זוג ערכים, למשל [error, result]. אפשר גם tuple עם שמות:

let coord: [x: number, y: number] = [1, 2];

Enums — קבוצת קבועים בעלי שם

enum UserRole {
  Admin,   // 0
  Editor,  // 1
  Viewer,  // 2
}

let role: UserRole = UserRole.Admin;

כברירת מחדל הערכים הם מספרים שרצים מ-0. ולרוב עדיף string enum, כי אז הערך קריא גם ב-logs וב-DB:

enum UserRole {
  Admin = "ADMIN",
  Editor = "EDITOR",
  Viewer = "VIEWER",
}

console.log(UserRole.Admin); // "ADMIN"

אזהרה חשובה: enum הוא אחד המקרים הבודדים שבהם TypeScript מייצר קוד JavaScript אמיתי ב-runtime (הוא לא נמחק כמו שאר הטיפוסים). הרבה קבוצות מעדיפות היום union of string literals במקום enum:

type UserRole = "ADMIN" | "EDITOR" | "VIEWER";

let role: UserRole = "ADMIN";
let bad: UserRole = "SUPERUSER"; // ❌ לא חלק מה-union

זה נמחק לגמרי ב-runtime, פשוט יותר, ולרוב מספיק. ב-NestJS ספציפית עדיין תראה enum הרבה, אז חשוב להכיר את שניהם.

5. Objects, Interfaces ו-Type Aliases

הצהרת object type inline

function printUser(user: { name: string; age: number }): void {
  console.log(user.name, user.age);
}

Interface

interface User {
  name: string;
  age: number;
  email: string;
}

function printUser(user: User): void {
  console.log(user.name);
}

Type Alias

type User = {
  name: string;
  age: number;
  email: string;
};

מתי interface ומתי type?

  • interface — מיועד לתיאור צורת object, תומך ב-declaration merging וב-extends נקי. זו הבחירה המקובלת ל-object shapes וב-OOP, ולכן זה מה שתראה הכי הרבה ב-NestJS.
  • type — כללי יותר. יכול לתאר גם union, tuple, primitive, mapped type — כל דבר, לא רק object.

הכלל הפרקטי: השתמש ב-interface לצורות של objects/entities, וב-type לכל השאר (unions, tuples, טיפוסים מחושבים).

Optional properties ו-readonly

interface User {
  name: string;
  age?: number;          // אופציונלי — יכול להיות undefined או לא להופיע בכלל
  readonly id: string;   // אפשר לקרוא, אסור לשנות אחרי היצירה
}

const u: User = { name: "eliya", id: "123" };
u.id = "456";  // ❌ Cannot assign to 'id' because it is a read-only property

age? פירושו שהטיפוס בפועל הוא number | undefined. חייבים לבדוק לפני שימוש:

function greet(user: User) {
  // user.age.toFixed();  ❌ 'user.age' is possibly 'undefined'
  if (user.age !== undefined) {
    user.age.toFixed();   // ✅
  }
}

Extends — הרחבת interface

interface Entity {
  id: string;
  createdAt: Date;
}

interface User extends Entity {
  name: string;
  email: string;
}
// User עכשיו כולל id, createdAt, name, email

Index signatures — object עם מפתחות דינמיים

interface StringMap {
  [key: string]: string;
}

const headers: StringMap = {
  "content-type": "application/json",
  "authorization": "Bearer xyz",
};

השתמש בזה בזהירות — לרוב Record<string, string> קריא יותר לאותה מטרה.

6. Union, Intersection, Literal Types ו-Narrowing

זה אחד הפרקים הכי חשובים. מערכת הטיפוסים של TypeScript בנויה סביב היכולת לומר "זה או זה", ואז לצמצם בבטחה.

Union Types — "או"

type Id = string | number;

let userId: Id = "abc";
userId = 123;      // ✅
userId = true;     // ❌ boolean לא חלק מה-union

Literal Types — ערך ספציפי כטיפוס

type Direction = "up" | "down" | "left" | "right";

let move: Direction = "up";   // ✅
let bad: Direction = "north"; // ❌

משתמשים בזה כל הזמן ל-HTTP methods, ל-statuses, ל-roles.

Intersection Types — "וגם"

interface Timestamped { createdAt: Date; }
interface Identifiable { id: string; }

type Entity = Timestamped & Identifiable;

const e: Entity = {
  createdAt: new Date(),
  id: "123",
};  // חייב את שני השדות

Union זה "אחד מ-", Intersection זה "הכל ביחד".

Narrowing — הלב של העבודה עם unions

כשיש לך union, אתה לא יכול להשתמש בו עד שתצמצם אותו לטיפוס ספציפי. TypeScript עוקב אחרי הבדיקות שלך ומצמצם אוטומטית.

צמצום עם typeof:

function formatId(id: string | number): string {
  if (typeof id === "string") {
    return id.toUpperCase();   // ✅ כאן id הוא string
  }
  return id.toFixed(0);        // ✅ כאן id הוא number
}

צמצום עם in (בדיקת קיום property):

interface Dog { bark(): void; }
interface Cat { meow(): void; }

function makeSound(animal: Dog | Cat) {
  if ("bark" in animal) {
    animal.bark();  // ✅ TypeScript יודע שזה Dog
  } else {
    animal.meow();  // ✅ זה Cat
  }
}

צמצום עם instanceof (למחלקות אמיתיות):

function handle(err: Error | string) {
  if (err instanceof Error) {
    console.log(err.message);  // ✅ Error
  } else {
    console.log(err);          // ✅ string
  }
}

Discriminated Unions — הדפוס החשוב ביותר

לכל חבר ב-union יש שדה משותף עם literal type שמזהה אותו (ה-"discriminant"):

type ApiResponse =
  | { status: "success"; data: string }
  | { status: "error"; message: string }
  | { status: "loading" };

function handleResponse(res: ApiResponse) {
  switch (res.status) {
    case "success":
      console.log(res.data);     // ✅ TypeScript יודע שיש כאן data
      break;
    case "error":
      console.log(res.message);  // ✅ יש כאן message
      break;
    case "loading":
      console.log("...");
      break;
  }
}

Exhaustiveness Checking עם never

function handleResponse(res: ApiResponse): string {
  switch (res.status) {
    case "success": return res.data;
    case "error":   return res.message;
    case "loading": return "loading";
    default:
      // אם כל המקרים טופלו, res כאן הוא never.
      const _exhaustive: never = res;
      throw new Error(`Unhandled status: ${JSON.stringify(res)}`);
  }
}

אם מישהו יוסיף מחר { status: "timeout" } וישכח לטפל בו, השורה const _exhaustive: never = res תיכשל בקומפילציה. זו טכניקה שמונעת באגים שלמים.

7. Functions

הצהרת טיפוסים לפרמטרים וערך החזרה

function add(a: number, b: number): number {
  return a + b;
}

הפרמטרים כמעט תמיד צריכים טיפוס מפורש. ערך ההחזרה בדרך כלל מוסק אוטומטית, אבל מומלץ לכתוב אותו מפורשות בפונקציות ציבוריות/חשובות.

Optional, Default ו-Rest parameters

// optional — עם ?
function greet(name: string, greeting?: string): string {
  return `${greeting ?? "Hello"}, ${name}`;
}

// default value
function greet2(name: string, greeting: string = "Hello"): string {
  return `${greeting}, ${name}`;
}

// rest — מספר לא ידוע של ארגומנטים
function sum(...nums: number[]): number {
  return nums.reduce((acc, n) => acc + n, 0);
}
sum(1, 2, 3, 4); // 10

פרמטר optional (greeting?) הופך אוטומטית ל-string | undefined. ?? (nullish coalescing) הוא הדרך הנקייה לתת ברירת מחדל.

Function types — פונקציה כערך

// טיפוס: פונקציה שמקבלת number ומחזירה number
type Transformer = (input: number) => number;

const double: Transformer = (x) => x * 2;

function applyTwice(fn: Transformer, value: number): number {
  return fn(fn(value));
}
applyTwice(double, 5); // 20

בתוך double לא צריך לכתוב (x: number) — הטיפוס מוסק מ-Transformer. זה נקרא contextual typing.

Function Overloads

function parseInput(input: string): string[];
function parseInput(input: number): number[];
function parseInput(input: string | number): string[] | number[] {
  if (typeof input === "string") {
    return input.split("");
  }
  return [input];
}

const a = parseInput("abc"); // הטיפוס: string[]
const b = parseInput(42);    // הטיפוס: number[]

השורות הראשונות הן ה-overload signatures, והאחרונה היא ה-implementation. ב-Backend זה פחות שכיח — לרוב generics פותרים את זה יותר יפה.

8. Generics

זה השער בין "כותב TypeScript" ל"מבין TypeScript". Generics הם היכולת לכתוב קוד שעובד על טיפוס שיוחלט בעתיד, בלי לוותר על בטיחות טיפוסים.

הבעיה ש-generics פותרים

// גרסה 1 — עובדת רק על number:
function firstNumber(arr: number[]): number { return arr[0]; }

// גרסה 2 — עובדת על הכל, אבל מאבדת את הטיפוס:
function firstAny(arr: any[]): any { return arr[0]; }
const x = firstAny(["a", "b"]); // x הוא any — איבדנו הכל

Generics נותנים את הטוב משני העולמות:

function first<T>(arr: T[]): T {
  return arr[0];
}

const a = first([1, 2, 3]);        // a: number
const b = first(["x", "y"]);       // b: string
const c = first([true, false]);    // c: boolean

מה זה <T>?

T הוא type parameter — משתנה, אבל לטיפוסים במקום לערכים. כשאתה קורא לפונקציה, TypeScript "ממלא" את T לפי הארגומנט. אתה כמעט אף פעם לא צריך לציין את T ידנית — TypeScript מסיק אותו.

Generic Constraints — הגבלת T

// T חייב להיות משהו שיש לו .length
function longest<T extends { length: number }>(a: T, b: T): T {
  return a.length >= b.length ? a : b;
}

longest("hello", "hi");        // ✅ ל-string יש length
longest([1, 2, 3], [4]);       // ✅ למערך יש length
longest(10, 20);               // ❌ ל-number אין length

דוגמה מעשית: keyof עם generic constraint

function getProperty<T, K extends keyof T>(obj: T, key: K): T[K] {
  return obj[key];
}

const user = { name: "eliya", age: 30 };

const name = getProperty(user, "name"); // name: string
const age = getProperty(user, "age");   // age: number
getProperty(user, "email");             // ❌ "email" אינו מפתח של user

Generic Interfaces ו-Type Aliases

interface ApiResult<T> {
  data: T;
  statusCode: number;
  timestamp: Date;
}

const userResult: ApiResult<User> = {
  data: { name: "eliya", age: 30, email: "e@x.com" },
  statusCode: 200,
  timestamp: new Date(),
};

const listResult: ApiResult<User[]> = { /* ... */ };

Generic Classes

class Repository<T extends { id: string }> {
  private items: T[] = [];

  add(item: T): void {
    this.items.push(item);
  }

  findById(id: string): T | undefined {
    return this.items.find((item) => item.id === id);
  }
}

9. Advanced Types — הכוח האמיתי של TypeScript

כאן TypeScript הופך משפה שמתארת טיפוסים לשפה שמחשבת טיפוסים. זה מה שמאפשר לספריות כמו NestJS, Prisma ו-TypeORM לתת לך autocomplete מדויק.

keyof — כל המפתחות של טיפוס כ-union

interface User {
  name: string;
  age: number;
  email: string;
}

type UserKeys = keyof User; // "name" | "age" | "email"

typeof — לקחת טיפוס מתוך ערך קיים

const defaultConfig = {
  port: 3000,
  host: "localhost",
  debug: false,
};

type Config = typeof defaultConfig;
// { port: number; host: string; debug: boolean }

מגדירים object קונפיגורציה פעם אחת, ומקבלים ממנו את הטיפוס בחינם.

Indexed Access Types — לשלוף טיפוס של property

interface User {
  name: string;
  address: { city: string; zip: string };
}

type UserName = User["name"];        // string
type City = User["address"]["city"]; // string

Mapped Types — לייצר טיפוס מטיפוס אחר

הכלי שמייצר טיפוס חדש על ידי מעבר על כל המפתחות של טיפוס קיים — כמו "for loop על מפתחות":

type Optional<T> = {
  [K in keyof T]?: T[K];
};

interface User { name: string; age: number; }

type PartialUser = Optional<User>;
// { name?: string; age?: number }

אפשר גם להוסיף/להסיר readonly ו-?:

type Mutable<T> = {
  -readonly [K in keyof T]: T[K];  // מסיר readonly
};

type Required<T> = {
  [K in keyof T]-?: T[K];  // מסיר את האופציונליות
};

Conditional Types — טיפוס שתלוי בתנאי

type IsString<T> = T extends string ? "yes" : "no";

type A = IsString<string>;  // "yes"
type B = IsString<number>;  // "no"

עם infer אפשר "לחלץ" טיפוס מתוך טיפוס אחר:

type Unwrap<T> = T extends Promise<infer U> ? U : T;

type A = Unwrap<Promise<string>>; // string
type B = Unwrap<number>;          // number

Template Literal Types

type Method = "GET" | "POST";
type Endpoint = "/users" | "/posts";

type Route = `${Method} ${Endpoint}`;
// "GET /users" | "GET /posts" | "POST /users" | "POST /posts"

Utility Types — הכלים המובנים שתשתמש בהם כל יום

interface User {
  id: string;
  name: string;
  email: string;
  age: number;
}

// Partial<T> — כל השדות אופציונליים. מושלם ל-update DTOs.
type UserUpdate = Partial<User>;

// Required<T> — כל השדות חובה (ההפך).
type FullUser = Required<User>;

// Pick<T, K> — לבחור רק חלק מהשדות.
type UserPreview = Pick<User, "id" | "name">;

// Omit<T, K> — להסיר שדות.
type UserWithoutId = Omit<User, "id">;

// Readonly<T> — כל השדות for-read-only.
type ImmutableUser = Readonly<User>;

// Record<K, V> — object עם מפתחות מטיפוס K וערכים מטיפוס V.
type RolePermissions = Record<"admin" | "user", string[]>;

// Exclude<T, U> — להסיר מ-union.
type T1 = Exclude<"a" | "b" | "c", "a">; // "b" | "c"

// Extract<T, U> — לשמור מ-union רק מה שתואם.
type T2 = Extract<"a" | "b" | "c", "a" | "b">; // "a" | "b"

// NonNullable<T> — להסיר null ו-undefined.
type T3 = NonNullable<string | null | undefined>; // string

// ReturnType<T> — הטיפוס שפונקציה מחזירה.
function createUser() { return { id: "1", name: "x" }; }
type CreatedUser = ReturnType<typeof createUser>;

// Parameters<T> — tuple של טיפוסי הפרמטרים.
type CreateParams = Parameters<typeof createUser>;

// Awaited<T> — הטיפוס שבתוך Promise.
type Data = Awaited<Promise<string>>; // string

Partial, Pick, Omit, Record ו-ReturnType — אלה החמישה שתשתמש בהם הכי הרבה ב-Backend.

10. Classes

TypeScript מוסיף למחלקות של JavaScript שכבת טיפוסים ו-access modifiers. זה חשוב במיוחד כי NestJS בנוי כולו על מחלקות.

מחלקה בסיסית

class User {
  name: string;
  age: number;

  constructor(name: string, age: number) {
    this.name = name;
    this.age = age;
  }

  greet(): string {
    return `Hi, I'm ${this.name}`;
  }
}

const u = new User("eliya", 30);

Access Modifiers — public, private, protected

class BankAccount {
  public owner: string;      // נגיש מכל מקום (ברירת מחדל)
  private balance: number;   // רק בתוך המחלקה
  protected id: string;      // בתוך המחלקה ומחלקות שיורשות ממנה

  constructor(owner: string, balance: number) {
    this.owner = owner;
    this.balance = balance;
    this.id = crypto.randomUUID();
  }

  deposit(amount: number): void {
    this.balance += amount;
  }
}

const acc = new BankAccount("eliya", 100);
acc.owner;    // ✅ public
acc.balance;  // ❌ Property 'balance' is private

חשוב לזכור: private של TypeScript נאכף רק בזמן קומפילציה. אם צריך פרטיות אמיתית ב-runtime, יש #field של JavaScript:

class Secret {
  #token = "xyz";   // פרטי אמיתי גם ב-runtime
}

Parameter Properties — קיצור שתראה הרבה ב-NestJS

// במקום זה:
class UserService {
  private repo: UserRepository;
  constructor(repo: UserRepository) {
    this.repo = repo;
  }
}

// כותבים כך — זהה לגמרי:
class UserService {
  constructor(private repo: UserRepository) {}
}

ה-private repo בפרמטר יוצר אוטומטית שדה this.repo ומשים אליו. זה בדיוק הדפוס של dependency injection ב-NestJS — וזו תכונה של TypeScript עצמו, לא קסם של NestJS.

Abstract Classes

abstract class BaseRepository<T> {
  abstract findById(id: string): T | undefined;   // חייבים לממש

  exists(id: string): boolean {
    return this.findById(id) !== undefined;
  }
}

class UserRepository extends BaseRepository<User> {
  findById(id: string): User | undefined {
    return undefined; // מימוש אמיתי כאן
  }
}

new BaseRepository(); // ❌ Cannot create an instance of an abstract class

Implements — מחלקה שמקיימת interface

interface Logger {
  log(message: string): void;
}

class ConsoleLogger implements Logger {
  log(message: string): void {
    console.log(message);
  }
}

implements אומר "המחלקה חייבת לספק את כל מה שה-interface דורש". זה הבסיס ל-programming to interfaces — דפוס מרכזי ב-Backend נקי.

11. Decorators — הבסיס של NestJS

Decorators הם אולי הנושא הכי חשוב עבורך ספציפית, כי כל NestJS בנוי עליהם. @Controller, @Injectable, @Get, @Body — כולם decorators.

מה זה decorator

Decorator הוא פונקציה שמצמידים לפני class, method, property או parameter, והיא "עוטפת" או "מתייגת" אותם:

@Controller("users")
class UsersController {
  @Get()
  findAll() {
    return [];
  }
}

איך זה עובד מתחת למכסה

function LogClass(constructor: Function) {
  console.log(`Class defined: ${constructor.name}`);
}

@LogClass
class MyService {}
// בזמן טעינת הקובץ יודפס: "Class defined: MyService"

NestJS משתמש ב-decorators כדי לצרף metadata למחלקות — למשל "זה controller שמטפל בנתיב /users". ה-framework קורא את ה-metadata ובונה ממנו את ה-routing וה-DI.

הפעלת decorators ב-tsconfig

{
  "compilerOptions": {
    "experimentalDecorators": true,
    "emitDecoratorMetadata": true
  }
}
  • experimentalDecorators — מפעיל את התחביר.
  • emitDecoratorMetadata — גורם ל-TypeScript לפלוט מידע על טיפוסים ל-runtime (דרך reflect-metadata). זה מה שמאפשר ל-NestJS לדעת אילו dependencies להזריק לפי הטיפוסים בלבד.

הבהרה שחוסכת בלבול: יש שתי גרסאות של decorators — ה-"legacy" (מה ש-NestJS משתמש בו, מופעל עם experimentalDecorators), וה-standard החדש של ECMAScript. לעבודה עם NestJS אתה רוצה את ה-legacy עם שני הדגלים למעלה. אל תערבב ביניהם.

בפועל כמעט אף פעם לא תכתוב decorators בעצמך — תשתמש באלה של NestJS. אבל להבין שdecorator הוא פונקציה שמצרפת metadata יעזור לך להפסיק לראות ב-NestJS "קסם".

12. Modules ו-ארגון קוד

import / export

// user.ts
export interface User {
  id: string;
  name: string;
}

export function createUser(name: string): User {
  return { id: crypto.randomUUID(), name };
}

// default export — אחד לכל קובץ
export default class UserService {}
// main.ts
import UserService, { User, createUser } from "./user";

ההמלצה הרווחת ב-Backend: העדף named exports — הם עקביים, ידידותיים ל-refactoring ול-autocomplete. NestJS משתמש כמעט אך ורק ב-named exports.

import type — יבוא של טיפוסים בלבד

import type { User } from "./user";
import { createUser } from "./user";

זה מבהיר שהיבוא נמחק בקומפילציה, מונע בעיות circular dependencies וחשוב לביצועי build.

CommonJS מול ES Modules — הבלבול הגדול של Node

  • CommonJS (CJS) — הישן: require() ו-module.exports. עדיין ברירת המחדל בהרבה פרויקטי Node ו-NestJS.
  • ES Modules (ESM) — הסטנדרט המודרני: import/export.

אם אתה מתחיל עם NestJS, לרוב תעבוד ב-CommonJS (זו ברירת המחדל של nest new). פשוט תדע שזה קיים כשתיתקל בשגיאת Cannot use import statement outside a module.

Path aliases — לוותר על ../../../

{
  "compilerOptions": {
    "baseUrl": ".",
    "paths": {
      "@app/*": ["src/*"]
    }
  }
}
import { User } from "@app/users/user";  // במקום ../../users/user

מלכודת: path aliases הם תכונה של TypeScript בלבד. Node ב-runtime לא מכיר אותם. צריך כלי שיתרגם אותם ב-build (tsc-alias, tsconfig-paths, או ה-bundler). NestJS מטפל בזה דרך ה-CLI שלו.

13. Async, Promises ו-Error Handling

Promise types

async function fetchUser(id: string): Promise<User> {
  const res = await fetch(`/api/users/${id}`);
  return res.json() as Promise<User>;
}

const user = await fetchUser("123"); // user: User (ה-Promise "נפרם" ע"י await)

async function תמיד מחזירה Promise. await הוא זה ש"פורם" את ה-Promise חזרה לערך.

מלכודת נפוצה: JSON מגיע כ-any/unknown

const data = await res.json();       // data: any — מסוכן
const user = data as User;           // TypeScript מאמין לך — אבל אין בדיקה אמיתית

הפתרון הנכון ב-Backend: validation בזמן ריצה. מחוץ ל-NestJS פופולרי מאוד zod:

import { z } from "zod";

const UserSchema = z.object({
  id: z.string(),
  name: z.string(),
  age: z.number(),
});

const data: unknown = await res.json();
const user = UserSchema.parse(data);  // זורק אם ה-data לא תואם — בדיקה אמיתית ב-runtime!

הלקח הכי חשוב למפתח Backend: טיפוסים סטטיים לא מחליפים validation. הם משלימים אותו.

Error handling — הטיפוס של catch הוא unknown

try {
  await riskyOperation();
} catch (err) {
  // err: unknown
  if (err instanceof Error) {
    console.error(err.message);   // ✅ עכשיו זה Error
  } else {
    console.error("Unknown error:", err);
  }
}

Promise.all עם טיפוסים

const [user, posts] = await Promise.all([
  fetchUser("1"),      // Promise<User>
  fetchPosts("1"),     // Promise<Post[]>
]);
// user: User, posts: Post[]  ✅ הטיפוסים נשמרים לפי הסדר

tsconfig.json הוא ה-control panel של הפרויקט. הבנת הדגלים החשובים תחסוך לך שעות של תסכול.

דגלי היעד והמודולים

  • strictNullChecks — הכי חשוב. null/undefined לא מתקבלים אוטומטית. מונע את רוב ה-null pointer errors.

  • strictPropertyInitialization — מכריח לאתחל properties של מחלקה.
  • useUnknownInCatchVariables — משתנה ה-catch הוא unknown.

15. TypeScript ב-Backend אמיתי (Node / NestJS)

Typings לספריות — @types

npm install express
npm install --save-dev @types/express   # הטיפוסים ל-express

ספריות מודרניות (כולל NestJS, Prisma, zod) מגיעות עם טיפוסים מובנים. אם אתה מקבל "Could not find a declaration file for module 'x'" — כנראה חסר לך @types/x.

DTOs — Data Transfer Objects

interface User {
  id: string;
  name: string;
  email: string;
  passwordHash: string;   // לעולם לא נחזיר את זה ב-API
  createdAt: Date;
}

// מה שהלקוח שולח כדי ליצור user:
type CreateUserDto = Pick<User, "name" | "email"> & { password: string };

// מה שמחזירים ללקוח — בלי ה-hash:
type UserResponseDto = Omit<User, "passwordHash">;

// update — הכל אופציונלי:
type UpdateUserDto = Partial<CreateUserDto>;

משנים את ה-entity, וכל ה-DTOs מתעדכנים אוטומטית.

דוגמה: repository גנרי טיפוסי

interface Entity {
  id: string;
}

interface Repository<T extends Entity> {
  findById(id: string): Promise<T | null>;
  findAll(): Promise<T[]>;
  create(data: Omit<T, "id">): Promise<T>;
  delete(id: string): Promise<void>;
}

class InMemoryRepository<T extends Entity> implements Repository<T> {
  private store = new Map<string, T>();

  async findById(id: string): Promise<T | null> {
    return this.store.get(id) ?? null;
  }

  async findAll(): Promise<T[]> {
    return [...this.store.values()];
  }

  async create(data: Omit<T, "id">): Promise<T> {
    const entity = { ...data, id: crypto.randomUUID() } as T;
    this.store.set(entity.id, entity);
    return entity;
  }

  async delete(id: string): Promise<void> {
    this.store.delete(id);
  }
}

שילוב של כמעט כל מה שלמדנו: interface גנרי, constraint, implements, Omit, Promise, ו-Map גנרי.

איך זה נראה ב-NestJS

@Injectable()
export class UsersService {
  // parameter property = dependency injection
  constructor(private readonly repo: UserRepository) {}

  async findOne(id: string): Promise<UserResponseDto> {
    const user = await this.repo.findById(id);
    if (!user) throw new NotFoundException();
    return user;
  }
}

@Controller("users")
export class UsersController {
  constructor(private readonly usersService: UsersService) {}

  @Get(":id")
  findOne(@Param("id") id: string): Promise<UserResponseDto> {
    return this.usersService.findOne(id);
  }

  @Post()
  create(@Body() dto: CreateUserDto) {
    // ה-ValidationPipe של NestJS מבצע validation אמיתי ב-runtime על dto
    return this.usersService.create(dto);
  }
}

הכל כאן זה TypeScript שכבר מכיר: decorators שמצרפים metadata, parameter properties ל-DI, ו-Promise<T>. NestJS לא ממציא שפה חדשה — הוא רק מרכיב את התכונות של TypeScript לתוך framework.

16. Best Practices וטעויות נפוצות

  1. strict: true תמיד, any אף פעם. אם אתה חייב טיפוס לא ידוע, unknown ואז narrowing.
  2. תן ל-inference לעבוד, אבל תכתוב טיפוסים מפורשים בגבולות. משתנים מקומיים — inference. פרמטרים, ערכי החזרה ציבוריים, API boundaries — מפורש.
  3. טיפוסים ≠ validation. כל data מבחוץ (HTTP, DB, קבצים, env vars) חייב validation ב-runtime.
  4. אל תשתמש ב-as כדי "לשתוק" שגיאות. const user = {} as User; הוא שקר שיקרוס ב-runtime.
  5. העדף טיפוסים נגזרים על פני שכפול. Pick/Omit/Partial במקום לכתוב טיפוסים פעמיים.
  6. Discriminated unions לכל state עם וריאנטים, עם exhaustiveness check עם never.
  7. הימנע מ-enum, העדף union של string literals — אלא אם אתה באמת צריך את ההתנהגות של enum.
  8. import type לטיפוסים.
  9. אל תילחם ב-compiler. אם הוא מתלונן, לרוב הוא צודק. הוא ה-code reviewer הכי זול שיש לך.
  10. שגיאות טיפוס — קרא מלמטה למעלה. השורה האחרונה בדרך כלל הכי קונקרטית.

טעויות נפוצות שכדאי לזהות מוקדם

  • לצפות ש-private יגן ב-runtime — הוא compile-time בלבד. השתמש ב-#field.
  • לשכוח שפרמטר ? הוא T | undefined — חייבים לבדוק לפני שימוש.
  • לחשוב ש-enum "חינמי" — הוא מייצר קוד runtime.
  • להסתמך על טיפוסים ל-data חיצוני — הטעות הכי מסוכנת ב-Backend. תמיד validate.

17. תרגילים

תרגיל 1 — Narrowing. כתוב פונקציה formatValue(value: string | number | boolean): string שמחזירה: string ב-uppercase, number עם שתי ספרות אחרי הנקודה, ו-boolean כ-"yes"/"no".

תרגיל 2 — Generics. כתוב פונקציה גנרית groupBy<T, K extends keyof T>(items: T[], key: K): Map<T[K], T[]> שמקבצת מערך של objects לפי ערך של property מסוים.

תרגיל 3 — Discriminated Union. דגם טיפוס PaymentResult עם שלושה מצבים: approved (עם transactionId), declined (עם reason), ו-pending (עם retryAfter). כתוב פונקציה שמטפלת בכל המקרים עם switch ו-exhaustiveness check עם never.

תרגיל 4 — Utility Types. נתון interface Product { id: string; name: string; price: number; internalCost: number; createdAt: Date; }. הגדר: CreateProductDto (בלי id, createdAt, internalCost), PublicProduct (בלי internalCost), ו-UpdateProductDto (כל השדות של Create אבל אופציונליים). השתמש רק ב-utility types.

תרגיל 5 — Advanced. כתוב mapped type בשם Nullable<T> שהופך את כל השדות של T ל-T[K] | null.

תרגיל 6 — שילוב מלא. בנה מחלקה גנרית Cache<T> עם: set(key: string, value: T, ttlMs: number): void, get(key: string): T | null (מחזיר null אם פג התוקף), ו-has(key: string): boolean.

סיכום — מה הלאה

כיסינו את כל הבסיס ומעבר: מהמודל המנטלי (type erasure, compile-time מול runtime), דרך הטיפוסים, generics, ה-advanced types, ועד לדפוסי Backend אמיתיים ו-NestJS.

הצעד הכי חשוב עכשיו הוא לכתוב קוד. פתח פרויקט עם strict: true, כבה לעצמך את היכולת להשתמש ב-any, ותתאמן. הכאב הראשוני של להילחם ב-compiler הוא בדיוק תהליך הלמידה.

כשתרגיש בנוח עם כל הפרקים כאן, אתה מוכן לצלול ל-NestJS לעומק — וכפי שראית בפרק 15, לא תפגוש שם כמעט שום דבר חדש מבחינת TypeScript. זה אותם כלים, מורכבים לתוך framework.
